## 二、场景 A · 40 进程并发签发

- **期望**：40 个子进程指到**同一个** gate 目录（`AGENTCTL_AUTHDIR`→临时目录），各调一次
  `authstate.grant_task(scopes=["A"])`；成功签发数 = 40、无异常。
- **实测**：两轮均 40/40 成功、0 异常；最终 `authstate.json` 是合法 JSON、task 存在、
  scopes 含 A、未过期；账本目录无 `.tmp` 残留。子进程结果由各自独立 JSON 回执统计
  （异常带 traceback 落在回执里，两轮均空）。
- **结论**：`grant_task` 的读-改-写全程走 `_Txn → authstate._exclusive → gate_lock.exclusive`
  （msvcrt.locking 同目录 `gate.lock`），40 进程串行化成立，无超发、无锁超时（锁上限 10s，
  实际总耗时 <1.2s）。**承诺钉住**。

## 三、场景 B · 8 线程并发 acquire_lease

- **B1 同一 actor**：先签一次让 holder=自己，再 8 线程并发重入。实测 8/8 成功（每次换新
  lease_id）——`acquire_lease` 对 `holder == actor` 直接放行是**设计行为**（防同一 agent
  自身的并发调用互踩），不是漏洞。0 线程异常。
- **B2 互异 actor**：先释放现行租约，再 8 线程各用各的 actor 抢。实测**恰 1 个成功**、
  其余 7 个 `GateDenied(code=CODE_LEASE_HELD=10)`，两轮一致，错误码无一偏离。
  这是 `_exclusive` 线性化的直接推论：第一个拿到锁的线程看到无活租约 → 成功；
  后续线程重新读 `lease.json` → holder ≠ actor → 拒。**单写者承诺钉住**。
- **B3**：`lease.json` 全程合法 JSON。
- 备注（平台语义，非缺陷）：msvcrt.locking 的字节区间锁按**句柄**归属，同进程不同句柄
  同样互斥——所以纯线程压测也能验证跨进程语义；非 Windows 走 flock（按 ofd），语义等价。

## 四、场景 C · 8 线程并发写 eid 旁表

- **期望**：8 线程各以唯一 capture_id 调 `core._eid_sessions_put`（每条 2 个 eid 明细）；
  8/8 返回 True，读回 8 条全在、文件合法 JSON。
- **实测**：8/8 True、8 条全在（每条 eids=2、未过期）、`eid_sessions.json` 合法、
  无 `.tmp` 残留（0.08s / 0.09s）。
- **结论**：旁表写路径（`gate.exclusive_lock()` 锁内 读→清理过期→合并→原子替换）并发无损。
- **观察项（非缺陷，记录在案）**：`core._eid_save` 的临时名是**固定**的 `path + ".tmp"`
  （不像 brake 带 pid、不像 gate_lock.save_json 用 mkstemp）。当前它**永远在 `_exclusive`
  锁内被调**，所以两轮压测零冲突——但这个安全性和「每个调用点都记得先拿锁」这条纪律
  绑死。D16 事故（3000 次写 1198 次异常）正是固定临时名脱离锁的后果。建议下一单顺手把
  `_eid_save` 换成 `gate_lock.save_json` 同款（mkstemp + 有界重试），消除对纪律的依赖。

## 五、场景 D · 8 线程并发 brake set/release —— **发现一个未修竞态**

- **期望（派单门槛）**：1600 次操作后，最终旗子状态 == 最后一次**真实改变状态**的操作；
  无 `.tmp` 残留。
- **实测**：门槛两条三轮全绿（判据对 no-op 的 clear 做了跳过处理——`clear_brake` 的
  「急停本来就未拉下」分支不改变状态，见判据文件头口径说明）。**但**三轮都压出了
  操作级失败：
  - 第 1 轮：`set` 失败 5 / 800（`clear` 0/800），样例：
    `拉急停失败（重试 5 次仍不成功）：[WinError 32] 另一个程序正在使用此文件… '_急停.flag.tmp.34060' -> '_急停.flag'`
    及同型 `[WinError 5] 拒绝访问。`；
  - 第 2 轮：`set` 失败 4 / 800 + `clear` 失败 1 / 800；
  - 第 3 轮：`set` 失败 4 / 800 + `clear` 失败 1 / 800，clear 侧样例（TOCTOU 实锤）：
    `解除失败：[WinError 2] 系统找不到指定的文件。: '…\_急停.flag'`
    （`exists` 检查时旗子还在，`os.remove` 执行前已被并发对手拿走）。
  合计 15/4800 次操作失败 ≈ **0.31%**（set 侧 13/2400 ≈ 0.54%；clear 侧 2/2400 ≈ 0.08%）。

### 复现步骤

1. 临时目录 `D`，设 `AGENTCTL_BRAKE_FLAG=D\_急停.flag`（`AGENTCTL_APP_DIR` 同指 `D`，保持同源）；
2. `from agentctl import gate`；起 8 线程，每线程循环 100 次：`gate.set_brake("压测")` → `gate.clear_brake()`；
3. 统计返回值 `ok=False` 的次数——本机三轮均 5/1600（WinError 2/5/32，重试 5 次递增退避耗尽）；
4. 门槛项（最终状态一致、无 tmp 残留）始终绿 ⇒ 缺陷只表现在**单次操作的返回值**，不破坏最终一致性。

### 机理（读代码得出，与实测吻合）

- `set_brake` 的临时名带 pid（W5 修复）⇒ 临时文件互踩已消除；但它 `os.replace(tmp, BRAKE_FLAG)`
  的**目标文件**仍会与并发对手撞：另一线程的 `clear_brake()` 正在 `os.remove(BRAKE_FLAG)`，
  或另一 `set_brake` 正在替换同一目标 —— Windows 给瞬时 WinError 5/32，重试 5 次（最长约
  0.3s）耗尽 ⇒ 返回 `(False, "拉急停失败…")`。
- `clear_brake` 更脆：`exists → remove` 两步之间没有重试也没有锁，另一线程的 replace/remove
  插进来就是 WinError 2/5/32 ⇒ `(False, "解除失败…")`。
- **归类：产品缺陷**（flag 写路径的竞态窗口未闭合），不是测试环境限制 —— Windows 的
  瞬时冲突语义只是让窗口**可见**，锁住目标文件是产品自己的责任（同类账本路径早已用
  `_exclusive`/`gate_lock` 闭合了同样的窗口）。
- **影响面（诚实评估）**：低概率 + 低严重度。真实急停写路径的并发源极少（面板按钮、
  热键守护、agent 三方）；失败时**返回值与全局状态可能背离**——例如本线程 set 报失败，
  但另一线程的 set 已把旗子置上（调用方以为没拉下，实际拉下了）；反之 clear 报失败时
  旗子多半还在（被并发 set 置上）。最终一致性未破坏（门槛全绿）。
- **候选修法（下一单拍板，本单未动）**：① flag 写路径进互斥（同目录 `brake.lock` 走
  `_exclusive`，或并入 `gate.lock`），set/clear 都锁内执行，窗口闭合——推荐；②
  `clear_brake` 幂等化：`FileNotFoundError` 当成功，并给 remove 补同款有界重试；③ 失败
  返回值附带当前旗子状态，消掉「返回值 vs 实际状态」的背离。①+② 最小。
