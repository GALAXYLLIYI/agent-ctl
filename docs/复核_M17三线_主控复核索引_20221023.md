## 二、★ 主控自己挖的一条（B 线报告里没有的）——S1（置前 0.9s）不是常态

C2 的 S1 列「置前后固定等 0.9s」（act.py:1684 FOREGROUND_SWITCH_TIMEOUT = 0.9 / act.py:1710 time.sleep(...)），单笔 900ms 很吓人。
主控读源码发现它**有早退**：ensure_foreground（act.py:1717-1719）先判「目标已在前台 ⇒ 直接 return 0」，只有**不在前台**才进 _try_foreground 睡那 0.9s。

⇒ 再查 **live act.log（当日 4912 条带时间戳日志 / 3108 条动作行）**：

| 事件 | 次数 | 占动作行 |
|---|---|---|
| 「↑ 动作前自动置前成功」 | 31 | 1.0% |
| 置前失败（rc=5「现前台仍是…」） | 53 | 1.7% |
| **合计走到置前路径** | **84** | **2.7%** |

⇒ **那 0.9 秒只在 2.7% 的动作里触发**（其中约一半是失败即被拒）⇒ **它不是那 886ms 的来源**。
⇒ 但它**仍是体感最差的尖峰**（一旦触发就是白等 0.9 秒）⇒ 属「改等多久」类 ⇒ **需用户拍板**（已进 docs\待拍板_下一刀_20221023.md 候选③）。

## 三、★ 主控自己翻的一次案（方法论第四条的由来）

**原裁决写的**：「①不是 450ms 等生效预算（**实测只花 10ms**）」

**问题**：那个「10ms」在 A 线报告里其实是 **enum 模块的 import 耗时 8.51ms（占 10.2%）**（docs\实测_M17A_导入归因_20221022.md:122）——**主控把一个模块 import 数字当成了「等生效预算的实测消耗」**。

**C1 实测**：④→⑤ 等生效（_wait_effect）**p50 = 467.9ms / p95 = 490.9ms**（占端到端 **31.5%**，占 act 内部 44.9%）＝ 886.6ms 里最大的一块；其中 cpu 仅 140.6ms，**余下 ≈327ms 是轮询等待**。

⇒ 「等生效不是瓶颈」这个判断**作废**。正确表述：**「等生效在『画面不变』路径上吃满 450ms 预算（≈327ms 纯等待），在『画面立刻变化』路径上早退」**。

⇒ ★ **方法论第四条（已写进手册）**：**引用任何一个数字前，必须回原报告核它到底是哪一项**。
⇒ 这是本轮**第三次**翻案（M17 两次 + 本次），三次根因都是同一个：**拿一个窄数字当结论**。
