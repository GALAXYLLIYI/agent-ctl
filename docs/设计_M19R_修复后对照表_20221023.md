## 1. 为什么必须用假时钟

真实时钟下一轮 = 抓帧 24.0ms + diff 12.2ms + 间隔 50ms = **86.2ms**，
但单轮成本会随机器负载抖动（MiniMax Code 桌宠任务约 150~200% CPU）。
450ms 预算下，「第 6 轮能不能被采到」会变成抽奖 —— 同一格 n=20 可能得 18/20，
也可能 <15/20。**比例型阈值测的是运气，不是产品行为。**

假时钟把每轮成本固定为 86.2ms：

| 轮次 | 轮开始时刻 | 采样前预算检查 | 抓帧后 | diff 后（检查②） | 结果 |
|---|---|---|---|---|---|
| 1 | 0.0 | 0 < 450 ✔ | 24.0 | 36.2 < 450 ✔ | sleep → 86.2 |
| 2 | 86.2 | ✔ | 110.2 | 122.4 | sleep → 172.4 |
| 3 | 172.4 | ✔ | 196.4 | 208.6 | sleep → 258.6 |
| 4 | 258.6 | ✔ | 282.6 | 294.8 | sleep → 344.8 |
| 5 | 344.8 | ✔ | 368.8 | 381.0 | sleep → 431.0 |
| 6 | 431.0 | 431 < 450 ✔ | **455.0** | **467.2 ≥ 450 ⇒ 退出** | 第 6 轮被采样 |
| 7 | 517.2 | 517.2 ≥ 450 ⇒ 退出 | — | — | **第 7 轮采样前退出** |

★ 第 6 轮的抓帧完成时（455.0）已经超过 450，这是**产品原有检查顺序**造成的：
`_wait_effect` 的预算检查在**采样之前**（act.py:1352-1353 / 1377-1378），
所以「开始采样时还没超预算」就允许这一轮跑完。假时钟**照实复刻这个顺序**，
不把第 6 轮砍掉，也不让第 7 轮进来。

## 2. 假时钟怎么装（关键实现）

### 2.1 为什么不能改 `act.time`

`_wait_effect` 里是**函数内 import**：

```python
def _wait_effect(...):
    import time as _t          # act.py:1338
    t0 = _t.perf_counter()
    ...
    _t.sleep(POLL_INTERVAL_MS / 1000.0)
```

函数内 `import time as _t` 每次调用都从 `sys.modules["time"]` 取模块，
所以改 `act.time` 这个**全局名根本不生效**（函数内 import 会覆盖它）。

### 2.2 实际装法

调用 `_wait_effect` 期间，把 `sys.modules["time"]` 换成一个**代理对象**：

```python
class _FakeTimeModule:
    def perf_counter(self): return clock.perf_counter()   # 只读，每次 +0
    def sleep(self, sec):   clock.sleep(sec)             # 按 ms 推进
    def __getattr__(self, name): return getattr(real_time, name)  # 其余转发真模块
```

- 只拦 `perf_counter` / `sleep`；`time.time`、`time.monotonic` 等原样转发，
  避免 PIL / framecache 在本轮里 import time 时被二次打伤。
- `try/finally` 里**无条件还原** `sys.modules["time"]`；异常路径也一样。
- `FakeClock` 内部用 ms 存，`perf_counter()` 返回**秒**（产品是秒口径），
  `sleep(0.05)` 推进 50ms，`advance_ms(24.0)` 推进 24ms。

### 2.3 单轮成本怎么落进去

| 成本 | 值 | 由谁推进 | 依据 |
|---|---|---|---|
| capture | 24.0ms | 夹具 capture 回调（每次抓帧 `advance_ms(24.0)`） | 判据脚本 `tests\_P3_M19_语义修复_判据.py` 与 framecache 头注的实测值 |
| diff | 12.2ms | `act._img_diff` 的**只在调用期间生效**的包装器 | 同上；M18-d 实测 |
| interval | `act.POLL_INTERVAL_MS` = 50ms | 产品自己调 `_t.sleep()`，假时钟推进 | **只读**产品常量，不改 |

**diff 包装器只对每轮第一次 diff 收 12.2ms**，用 `charge_diff` 标志控制：

```python
def diff(a, b):
    if st["charge_diff"]:          # 抓帧刚发生过，这一轮还没收 diff 成本
        st["charge_diff"] = False
        clock.advance_ms(12.2)
    return real_diff(a, b)
```

为什么要这个标志：M19′ 的预算耗尽出口可能在返回前再调一次
`_img_diff(base, last)` 做判定（`_budget_verdict`）。那是**出口判定**，不是轮次成本；
若也推进假时钟，`耗时ms` 会虚增，口径就不干净（T/N/F 不受影响，但证据要可复核）。

> 说明：包装器只改**内存里的 `act._img_diff` 引用**，调用结束还原；
> 磁盘上的 `act.py` 一个字节都没动。

### 2.4 确定性自检（脚本内置，破裂即异常）

每次调用后脚本核对：

1. 采样轮数 ≤ 6（第 7 轮绝不许被采样）；
2. 非 `True` 的退出必须正好在第 6 轮（预算耗尽只能发生在检查②）。

任一不满足 ⇒ 抛 `RuntimeError` ⇒ 该格记异常 ⇒ 进程 `exit=1`。
这与「假时钟口径与产品检查顺序不一致」是同一件事，必须响亮失败，不能出假表。

## 3. 场景矩阵（17 格 × n=20）

夹具：`BASE` = 1632×1191 全白；`CHG` = 白底 + 100..107 的 8×8 黑块（64px²，
超过 framecache 的 `DIFF_MIN_AREA=24`，`changed=True`）。与主控判据脚本同一组夹具尺寸。

| 场景 | k | 第 n 次抓帧返回 |
|---|---|---|
| `never` | 0（不适用） | 永远 `BASE` |
| `flicker` | 1..8 | 只有第 k 帧 `CHG`，其余 `BASE`（变一帧又变回） |
| `change` | 1..8 | 第 k 帧起都是 `CHG` |

每格 **n=20**。假时钟下同一格 20 次应**完全同结论**；脚本仍按 20 次统计，
并把 `verdicts / rounds / captures` 原样写进 JSON，供核对确定性。

为什么 n=20 而不是 1：派单硬要求；同时它能暴露「假时钟没钉死」——
若某格出现 0<T<n，说明还有真实时间漏进了轮次，数据不可用。

## 4. 双态怎么切

### 4.1 产品态（product）

直接：

```python
act._wait_effect(0, base, budget_ms=450, capture=fake_capture)
```

不传 `need`，用产品默认 `POLL_HYSTERESIS=2`；不碰 `POLL_INTERVAL_MS`。
返回 `生效` 三态：`True` / `None` / `False`，分别记 `T / N / F`。

### 4.2 注入态（inject）——只在内存 monkeypatch

目标：把「预算耗尽出口」临时改回 M19′ 之前的 `False`。分两层，**两层都不写磁盘**：

**首选：patch 辅助函数**

若产品里有 M19′ 派单推荐的 `act._budget_verdict`，调用期间替换为：

```python
act._budget_verdict = lambda *_a, **_k: False
```

`finally` 还原原函数。这等价于「两个预算耗尽出口都走旧分支」。

**兜底：出口包装**

若产品把判定内联、没有 `_budget_verdict`（或名字不同），则在**调用出口**把
「预算耗尽的 `None`」改回 `False`：

```python
if inject and result["生效"] is None and not st["capture_none"] \
        and clock.now_ms >= budget_ms:
    result["生效"] = False
```

守卫条件缺一不可：

- `not st["capture_none"]`：抓帧失败导致的 `None` 是**真的没测出来**，不许改成 False；
- `clock.now_ms >= budget_ms`：证明确实是预算耗尽退出，不是产品在预算内主动返回 `None`。

脚本在 JSON 里记录 `has_budget_verdict`、每格 `helper_patched_calls` /
`wrapper_applied_calls`，让主控能看出这次注入走的是哪条路。

> 为什么需要兜底：M19′ 的实现细节由 MiniMax 施工，脚本不能在写的时候绑定一个
> 尚未存在的符号名。兜底只改「一个出口的结论」，**不重实现轮次逻辑**，
> 也不复制判据脚本里的 `m19p_wait_effect`。

**施工时点观察（2026-10-23 10:03，只读）**：`legacy_tools\_src\act.py` 已出现
MiniMax 的 `_budget_verdict(base_img, last)`（两个预算耗尽出口改为调用它），
但产物 `legacy_tools\act.py` **尚未重新生成**（dry-run 时 sha256
`1aaa10d8…`，无该符号）。⇒ 正式跑必须等 MiniMax 交卷、产物同步后再跑；
届时注入态会走「首选：patch `_budget_verdict`」，JSON 里
`helper_patched_calls=n`、`wrapper_applied_calls=0`。

## 7. 判读口径（写死、可机械核对）

`J1..J8` 与脚本 `checks` 一一对应。**全部为 PASS 才算「修好了」。**

### 7.1 算「修好了」的充分必要条件

| 编号 | 判据 | 机械表达式 |
|---|---|---|
| J1 | product / never：语义不许丢 | `T=0 且 N=0 且 F=n` |
| J2 | 双态 / flicker k=1..8：抗假阳性红线 | 所有格 `T=0` |
| J3a | product / change k=6：本刀的收益 | `N >= 18/20`（n=20）且 `T=0` |
| J3b | inject / change k=6：注入有牙 | `N=0 且 F=n` |
| J4 | 双态 / change k=1..5：正常路径不许坏 | 所有格 `T=n` |
| J5 | 双态 / change k=7..8：边界不许扩大 | 所有格 `T=0 且 N=0` |
| J6 | 双态差异格恰为 k=6 两格 | 差异集合 `== {(flicker,6),(change,6)}` |
| J7 | 假时钟确定性 | 每格 `T,N,F ∈ {0,n}` |
| J8 | 完整性 | 17×2 格全在，且 `errors=[]` |

★ J3a 写 `>=18/20` 是派单给的底线；假时钟若完全钉死，实际应得 **20/20**。
若只得 18~19，先按「可疑」处理：查 J7，若 J7 也 FAIL ⇒ 假时钟没钉死，数据不作数。

### 7.2 任一条命中即「修坏了 / 数据不作数」

| 编号 | 现象 | 结论 |
|---|---|---|
| B1 | product / change k=6 的 `N < 18`（尤其 `N=0, F=20`） | M19′ 未生效：边界轮仍被判「确认没变」⇒ agent 不重试 |
| B2 | 任一 flicker 格 `T > 0` | **红线破**：闪烁被判成功（M20「看见即认」的老毛病回来了） |
| B3 | change k=1..5 任一格 `T < n` | 正常成功路径被修坏（假阴性） |
| B4 | change k=7..8 任一格 `N > 0` | 边界被扩大：预算/采样轮次被暗改，或 `last` 判定越界 |
| B5 | never 格 `N > 0` 或 `F < n` | 「确认没变」语义丢失（core 会把真没变判成可重试） |
| B6 | J6 差异集合为空，或含 k=6 以外的格 | 修复未生效 / 注入未生效 / 修复碰了别的分支 ⇒ **双态对照失去证据力** |
| B7 | 任一格计数不在 `{0,n}` | 假时钟没钉死（有真实时间漏进轮次）⇒ **整张表不作数** |
| B8 | 任一格异常（脚本 exit=1） | 数据不完整，先修脚本/环境再重跑 |

### 7.3 三种典型结论

1. **产品态 == 注入态（J6 FAIL，B6）**：
   `has_budget_verdict` 可能是 false 且产品仍是旧代码 ⇒ **未修**；
   也可能产品已修但注入兜底没触发 ⇒ 查 JSON 的 `wrapper_applied_calls`。
2. **change k=6 变 N，但 flicker k=6 也变 T（B2）**：
   把「最后一帧有变化」误当成「连续两帧变化」⇒ **修错方向**（等价 M20），必须退回。
3. **change k=6 变 N、flicker 全 T=0、k=1..5 全 T、k=7..8 全 F（J1..J8 全 PASS）**：
   **修好了**。此时才允许把本表作为「M19′ 已收口」的量化证据。

## 8. 边界与已知限制（如实写）

1. **假时钟不是实时测量**：它证明的是「在产品当前检查顺序下，450ms 预算的轮次语义」，
   不证明真实机器上 PrintWindow/diff 的绝对耗时。真实 GUI 验证需另发令牌。
2. **`_img_diff` 的真实耗时不计入假时钟**：我们只按实测值 12.2ms 记账；
   若将来 framecache 实现变化导致真实 diff 成本大幅漂移，假时钟口径要重标定
   （脚本会打印 `act.POLL_INTERVAL_MS`，但不会自动重测 diff）。
3. **注入兜底是「出口语义等价」，不是逐行复刻旧代码**：它只把预算耗尽的 `None`
   改回 `False`；不含旧代码的其它分支。对本矩阵（抓帧永不失败）与逐行复刻等价。
4. **不改产品常量**：`--budget-ms` 只是传给 `_wait_effect` 的实参；
   产品文件里的 450/500/350 等预算字面量一个都没动。
5. **脚本只读 act.py**：所有 patch 都在进程内存里，`finally` 还原；
   JSON 里记录 act.py 的 sha256，便于主控核对跑的是哪一份。
6. **不开记事本、不碰窗口**：capture 是纯内存夹具，不调用 `_poll_sample` /
   `perceive._print_window` / 任何 Win32 窗口 API。
