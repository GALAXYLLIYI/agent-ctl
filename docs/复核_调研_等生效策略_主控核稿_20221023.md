## 一、主张 ①「语义压扁」——成立，但成立方式与原文略有出入（**主控补正**）

### 1.1 MiniMax 原文主张

> act.py:1354/1381 预算用完返回 {"生效": False}（字面＝「预算内没看到变化」），
> 而 core.py:2896 把 ch is False 判成 code=8「确认没变」；
> 只有 ch is None 才走 code=5「没测出来」。这违反 core.py:2881 自己写的铁律。

### 1.2 主控核到的真实链路（**比原文更精确**）

| 环节 | 源码位置 | 事实 |
|---|---|---|
| ① act 预算用完 | act.py:1353-1357 | 预算耗尽 ⇒ 返回 {"生效": False} |
| ② act 轮询到底也没变 | act.py:1377-1381 | 轮询跑完、最后帧仍无变化 ⇒ 同样返回 {"生效": False} |
| ③ act 把结果交回 core | act.py:2810 / 2823 / 2835 | changed = _eff.get("生效") —— **但这只管「要不要再点一次」（重试），不进退出码** |
| ④ core 判词的 df | core.py:3305 → _act_diff_of(_before, _after, ...) | ★ **core 用自己的尺子**：before 帧 vs after 帧，**不是** act 的 _eff |
| ⑤ after 帧从哪来 | core.py:2962 _img = r.get("图") | 取 act 轮询里的帧；act 没给就 core.py:2960 自己抓一张 |
| ⑥ core 三态判定 | core.py:2893-2906 | ch is True ⇒ 原样成功；ch is False ⇒ **code=8「确认没变」**；ch is None ⇒ **code=5「没测出来」** |
| ⑦ core 自己写的铁律 | core.py:2881 | 「『没测出来』与『没变』必须**分开**（unknown 永不当成功，也不当『没变』）」 |

### 1.3 ★ 主控补正（MiniMax 没说准的一层）

**MiniMax 说的「act 返回 False ⇒ core 判 code=8」这个箭头其实不成立**：core 判词**不读** act 的 生效 字段（core.py:3305 用的是自己的 _act_diff_of）。

**但结论照样成立，链路是这样**：预算用完 ⇒ act 返回 False ⇒ act **不再继续轮询**、把**最后一帧**交回 ⇒ core 用 before vs 最后一帧求差 ⇒ 该帧与 before 无差异 ⇒ changed is False ⇒ **code=8「确认没变」**。

⇒ ★ **真正的语义压扁点在这里**：act 在 1353 预算耗尽时**没有区分**「画面确实没变」与「我等不起、没机会看到变化」，两者都返回 False；core 的尺子只看到「最后一帧和 before 一样」，于是给出**比事实更强的结论**——事实是「我没测出来」，判词是「确认没变」。

⇒ **这正好违反 core.py:2881 自己写的铁律**（虽然犯错的不是 core，是 act 的信息丢失）。

### 1.4 后果量化（★ 这一条 MiniMax 没算，是本稿最有价值的补充）

| 场景 | act 返回 | core 判词 | agent 的行为 | 真相 |
|---|---|---|---|---|
| 应用 300ms 才响应，预算 450ms | True（等到） | code=0 成功 | 继续 | ✅ 正确 |
| 应用 600ms 才响应，预算 450ms | **False（预算耗尽）** | **code=8「确认没变」** | **不重试** | ❌ **实为「没测出来」** |
| 应用压根没反应 | False（轮询到底） | code=8「确认没变」 | 不重试 | ✅ 正确 |

⇒ ★ **砍预算 ⇒ 慢应用从「code=0 成功」被推成「code=8 确认没变」** ⇒ agent 拿到 code=8 **不重试**（只有 code=5「没测出来」才重试）⇒ **误判失败 ⇒ 自动化流程停在那里**。
⇒ 这是「缩短预算的真实代价」的**准确表述**，比「可能被判失败」精确得多。

### 1.5 ★ 最小修复方案（**零契约改动**，主控建议）

act.py:1353-1357（预算耗尽分支）把 {"生效": False} 改成 {"生效": None}：

- False = **看见了，没变**（轮询到底、逐帧都比过）
- None = **没测出来**（图取不到 / 退化 / 预算耗尽没机会比）

⇒ core.py:2896 走 code=8、core.py:2902 走 code=5 ⇒ **慢应用重新拿到「可重试」语义**。
⇒ ★ 只动一个分支、不碰契约、不碰闸门、不碰预算值 ⇒ **可独立上线、可独立回滚**。

⚠ **要防的副作用**：act.py:2824 的重试判定是「if changed is True or attempts > retry: break」—— 改 None 后，重试路（changed is None）会**继续重试**（原来 False 也会继续重试，因为 False ≠ True）⇒ **重试语义无副作用**。
⚠ 另需核：act.py:2841-2849 的文案分支（changed is False ⇒「页面无变化」；changed is None ⇒「判不了」）⇒ 改 None 后文案会变，这属于**如实报告**，符合判据 36。

> 「**非 0 时本版不另造等待机制** —— 异步效果（2 秒后才弹窗）请挂既有 ctl_wait 语义轮询。」

## 四、主控采纳的拍板口径（写进决策单）

1. ★ **先做语义修复**（§1.5：act.py:1353 分支 False→None），**再做提速**。两步**分开上线、分开可回滚**。语义修复**不提速**，但让后面任何提速都不再拿「误判失败」换钱。
2. **提速优先调轮次/间隔**（MiniMax b2：间隔 50→16~30ms），**不砍总预算**。理由：轮次多降低漏检，总预算不变不影响覆盖范围。与 Selenium「慢元素加 timeout 不要改 poll 频率」方向相反但目标相同——我们要「同样预算下更高命中率」。
3. **分档预算**（候选 c）：expect_within_sec 元数据已在，**但要接线就得动契约 description + 升 schema_version**（契约 tools.json:5 冻结线）。分档权必须**收在服务端**——agent 只能声明意图，不能自选预算（否则等于给 agent 一枚「把等待调长」的旋钮）。
4. **动作前复核（b3）**：本仓 M7 已有一版就绪轮询可复用 ⇒ 风险等级从「新机制」下调为「已有思路换位置」；仍是四个候选里最值得投的（开销 <0.1s，比 450ms 小一个数量级）。
5. ⛔ **明确不做**：AGENTCTL_SETTLE_MS 全局压档（它会**同时**覆盖全部档位——fill 200/350/500、click 450/450/450、retry 350，位置 act.py:2537/2549/2556/2747/2805/2818/2830），把打字路 500ms 压成 200ms 有「打了一半字判没变」的风险；「全局加长等待」同理（MiniMax §五 结论一致）。
