## 0. 一句话结论

**① 帧复用成立并已接线**：`ctl_screen --since <上一版>` 在画面没变时**不重扫 UIA**
（实测 **144 ms → 31 ms，−78%**），动作侧**复用观测帧**（动作前抓帧 **1 → 0**）、
**PNG 落盘 3 → 1**；
**② GPU 抓帧本轮按补充指令只出结论**：vendored `windows_capture` 的 WGC **能**在真实窗口
（含遮挡）下取到与屏幕一致的像素，但**一次性抓帧比现役 PrintWindow 慢 12 倍**
（236 ms vs 19.5 ms）⇒ 只有做成**常驻会话**才有价值，而常驻进程被本单边界禁止 ⇒ **本轮不接**；
**③ 图标字体反查在「确实是图标字体渲染」的按钮上成立**（资源管理器的 ← / ⟳ 认对，码点
U+E72B / U+E72C 对得上公开码表），但**在真实界面的正文文字区实测误报率 5.0%**
⇒ **只能当「多一条证据」，不许单独作为动作依据**（与派单 §③ 的要求一致）。

### 2.4 为什么「变化判据」长这样（依据都是实测，不是设计偏好）

1. **不许用整屏 hash**：实测整屏 hash 变化率 **90.6%**（屏有动画）⇒ 等于「永远在变」。
2. **不许用「一像素不同就算变」**：实测区域 hash 全等判变化 **100%**（光标闪 5~7 px）。
3. **不许用整窗当「同一张图」**：实测同一窗口连抓 3 次，**整窗**（带标题栏）三次 sha256
   **各不相同**（标题栏 DWM 亚像素噪声 2634 px = 3.43%）；**客户区**三次**完全相同**。
   本机 12 次连抓实测：客户区相邻两帧**瓦片差全为 0.000** ⇒ 本单把动作前后帧统一到**客户区口径**。
4. **光标规则改成形状判据**：老口径 `min(w,h) > caret_px` ⇒ **8×8 的方块也被丢掉**；
   新口径「窄边 ≤8 **且** 长宽比 ≥2.0」⇒ 方块留下、光标条丢掉（与 `eye.py:diff_box_features`
   记的是同一件事：「ratio 分不开，但**形状**分得开」）。
5. **退化画面 fail open**：客户区灰度标准差 < 3.0 ⇒ 判「没画面」⇒ **不进帧仓库**
   （恒等的退化指纹会「永远判没变」）。

### 2.5 按三方裁决 B2 的修订（2026-10-22 01:00 裁决后重做）

> 裁决原文：主线走「**复用现成**」路线 —— `core.py` 的 `_act_diff_of`
> （阈值 2/255、caret <8px 窄边滤除、min_area 24px²、三值 `changed`），
> **不要另造 64×64 瓦片方案**（降为第二阶段增强）；但**必须加「连续 2 帧」滞回**。

| 项 | 本轮改成 |
|---|---|
| **主线判据** | `framecache.diff_images` = **原 `_act_diff_of` 的那套算法**（阈值 2/255 → 分块 → 窄边 caret 滤除 → min_area 24px² → 三值）。`core._act_diff_of` 改为**薄封装**（口径不变，只加客户区原点换算）⇒ **一条实现、一份常量** |
| **唯一差别** | caret 滤除从「窄边 ≤8 一律丢」改成「窄边 ≤8 **且** 长宽比 ≥2.0 才丢」——老口径连 **8×8 的方块**也丢了，而派单补充 §2 明写「8px 方块必须报变」。光标条长宽比 ≥2 ⇒ 照样丢掉 ✓ |
| **连续 2 帧滞回** | 复用判定改为「**连续 2 帧都判没变**」才复用（`framecache.wait_stable`）；变化判定同样要连续 2 帧（`ChangeTracker`）⇒ 动画区永远「没测出来」，**不会被当成「没变」** |
| **64×64 瓦片** | 降为**阶段二增强** `framecache.diff_images_tiled`（同口径、同常量、按需启用）；实测 1632×1191 端到端 7.6 ms vs 主线 9.1 ms ⇒ 收益 1.2×，**主线够用** |
| **常量单一真相源** | `DIFF_STEP=2 / DIFF_CARET_PX=8 / DIFF_MIN_AREA=24 / DIFF_CARET_ASPECT=2.0 / HYSTERESIS=2` 全部住在 **`src/agentctl/framecache.py`**；`core.ACT_DIFF_STEP` / `ACT_DIFF_IGNORE_DEFAULT` **反过来引用它** ⇒ 全仓一份定义（M7 的 act.py 就绪轮询也用这一份） |

**代价（如实写）**：连续 2 帧滞回让复用判定从 31 ms 变成 **78 ms**（多一次抓帧 + 一次判据 ≈ 47 ms）。
这是裁决要求的反动画安全闸 —— **宁可多花 47 ms，不许拿一帧的读数当「这一屏没动」**。

### 2.6 边界（必须说清）
- **复用只覆盖「同一进程、同一扇窗、15 秒内」**：换进程没有基线 ⇒ 重扫；凭据 TTL 15 s 到了也重扫。
- **「动作前」那一帧最多 5 秒龄**（`FRAME_REUSE_MAX_AGE_SEC`）：太老的帧会把「动作之前就发生的
  变化」算成「我这次动作造成的」⇒ 判词失真。**这只影响证据与判词的质量，不影响安全性**
  （安全性由闸门的凭据校验管：hwnd/矩形/前台/tree 指纹）。
- **口径变了**：动作前后的帧从「整窗 mss」变成「**客户区 PrintWindow**」⇒
  ① 标题栏的变化不再进 diff（但标题栏本来就有噪声）；② `after.diff.bbox` 的原点从窗口原点
  变成**客户区原点**（对外仍是屏幕绝对坐标）；③ 落盘的 PNG 从整窗变成客户区。
- **变化即停是「宽限 50 ms + 自适应轮询（≤300 ms）」**，⛔ **不是把固定 settle 砍成 0**：
  固定等待要么白等、要么不够；这里是「等到真的变了，最多等这么久」。
- **未验**：跨进程复用、远程桌面、多显示器负坐标、UWP/Electron 窗口（客户区 PrintWindow
  可能返回全黑 ⇒ 走退化分支，不复用）。

## 3. ② GPU 抓帧：可行性结论（本轮**不动 src**）

> 补充指令 §0-1：GPU 只能从 30 ms 里省 10~20 ms，而一条动作路径 400~600 ms；还要吃 DRM 黑屏与
> WinRT 绑定两个真风险 ⇒ **② 降级为只出可行性结论**。下面就是结论，**一行 src 都没动**。

### 3.1 能不能用？—— 能，但**用法和原单设想的不一样**

| 实测项 | 数字 | 说明 |
|---|---|---|
| vendored 包能否直接 import | **失败** | `vendor/windows_capture/__init__.py` 顶层 `import cv2`，**本机没装 cv2**（requirements.txt 里也没有）⇒ 要用必须先装 opencv（60+ MB）⇒ **与「不许引新依赖」直接冲突** |
| 绕开 cv2 直接加载 `.pyd` | **成功** | `NativeWindowsCapture / NativeDxgiDuplication / NativeDxgiDuplicationFrame / NativeMappedFrame` |
| WGC 取真实窗口（记事本） | **成功**，1636×1193 BGRA | 一扇窗**只能同时开一个 WGC 会话**（第二个会卡住）⇒ 必须常驻 |
| WGC **首帧**耗时 | **295 ms**（首轮实测 236 ms，含建会话） | vs 现役 PrintWindow 客户区 **19.7 ms/帧** ⇒ **一次性抓帧慢 12~15 倍** |
| 像素一致性 | 裁到客户区后：**差异 4.74%**、平均绝对差 **2.07**（首轮空窗口那次是 0.48% / 0.76） | **视觉上同一张画面**，但**不是逐字节相同** ⇒ 差异来自光标与抗锯齿边缘；WGC 的 1636×1193 比客户区 1632×1191 多 2~4 px 边框 |
| **被别的窗口盖住时** | **照样取到内容** | 这是 WGC 相对「屏幕实抓（mss/ImageGrab）」的**唯一硬优势** |
| DXGI 桌面复制 | `monitor_index=0` 报 "must be greater than zero" | 另一条 GPU 路径，**整屏**复制，不是单窗 |

### 3.2 结论

**GPU 抓帧不能替代本单的一次性抓帧路径。** 理由三条（都有数）：

1. **一次性用**：WGC 建会话 236 ms vs PrintWindow 19.5 ms ⇒ **慢 12 倍**，
   而动作路径里能省的上限只有 155.2 → 8.7 ms（**−146 ms**）⇒ GPU 一次性用**净亏 200+ ms**。
2. **常驻用才有价值**：WGC 的帧是合成器**推**过来的（静止窗口 3 s 内 0 新帧）⇒ 常驻会话的边际
   帧成本≈0，而且**被盖住也能看**。但本单边界明写「**不许起常驻进程**」⇒ 走不了这条路。
3. **依赖冲突**：`windows_capture` 的 Python 层要 cv2（本机没有）⇒ 要么装（违反边界）、
   要么只加载 `.pyd`（绕过封装，**不是 vendored 包的公开用法**，将来升级会碎）。

⇒ **建议**：把 ② 记为「**方向对、用法待定**」。若将来允许常驻会话，WGC 的价值在
「**看被盖住的窗口**」（治 D3），而不是「抓帧更快」。

### 3.3 风险点（DSH 说的两个，加本轮实测的两个）

| 风险 | 实测/判断 |
|---|---|
| DRM/受保护内容黑屏 | **本轮没测**（没碰受保护内容）⇒ 仍是风险 |
| WinRT 绑定 | 本轮**绕开了**（直接加载 `.pyd`，不走 Python 封装）⇒ 封装层的 cv2 依赖是真障碍 |
| 一窗一会话 | **实测**：第二个 WGC 会话会卡住 ⇒ 任何「多窗并行抓」的设想都要重新设计 |
| 会话泄漏 | WGC 会话不释放 ⇒ 抓帧失败时**必须**显式 `stop()`，否则进程挂住（本轮踩到，探针超时两次） |

## 4. ③ 图标字体模板匹配：结论

### 4.1 怎么做的（对着补充指令 §3 的硬要求）

| 要求 | 本轮做法 |
|---|---|
| **按目标窗口 DPI 渲染** | 模板按 `size × dpi_scale` 渲染（本机 150% ⇒ 16 px 的字形按 24 px 渲染）⇒ 笔画结构与屏幕一致。判据④ 断言「模板按目标窗口 DPI 渲染，且与 100% 版不是同一批」 |
| **关 ClearType** | **已关**：PIL/FreeType 默认 `FT_RENDER_MODE_NORMAL`（**灰度抗锯齿，无子像素**）⇒ 没有 ClearType 的 RGB 毛刺；且比对用**三通道最大差**做二值化，不依赖灰度边缘 |
| 不用模型、不用 GPU | 纯 numpy + PIL + 系统字体；**不引新依赖**（连通块用纯 Python 洪水填充，**不用 scipy**——scipy 不在 requirements.txt 里） |
| 码点公开 | `segmdl2.ttf` / `SegoeIcons.ttf` 的码点是**公开**的；本轮**逐个渲染核对**（`证据_图标/码点对照_mdl2.png` / `_fluent.png`）⇒ **删掉了 8 个错的**（5 个重复码点 + `rocket` E135 **在 Fluent 里不存在**，渲染出来是 .notdef 黑方块 + `gift` E8D7 不是礼物） |

| 后退 ← | `后退` | **后退**（U+E72B） | 0.848 | 0.267 | ✔ 认对 |
| 刷新 ⟳ | `刷新"<用户>"(F5)` | **刷新**（U+E72C） | 0.681 | 0.021 | ✔ 认对 |
| 上移 ↑ | `上移到"用户"(Alt+向上键)` | 帮助 | 0.353 | **0.011** | ✔ **被双闸拒了**（正确地「认不出」） |
| 复制（**非**图标字体） | `复制` | 详细信息视图 | 0.650 | 0.227 | ⚠ **自信地认错了** |
| 正文文字区（925 个 32×32 块） | — | — | — | — | ⚠ **高置信误报 46 块 = 5.0%**，最高分 0.985（"最大化"） |

### 4.3 结论

**图标字体反查「认得出」，但「还不敢单独用」。** 三条实测理由：

1. **误报率 5.0%**（真实界面正文区，925 块扫下来 46 块高置信）⇒ 纯图标按钮的密度本来就低，
   5% 的误报会把正确率拖垮。
2. **近邻字形分不开**：E711(close) 与 E8BB(close_window) 都是 X（margin 0.006 ⇒ 正确被拒）；
   E71E(zoom) 与 E721(search) 只差一个「+」（margin 0.170 ⇒ **漏过**了）。
3. **不是图标字体的界面元素**（功能区的剪切/复制/粘贴是自定义图形）**匹配器给的是别的字形的名字**
   ⇒ 那是「**认错了**」，不是「认不出」⇒ 更危险。

⇒ **边界（与派单 §③ 一致）**：本模块的输出**只当「多一条证据」**，
**不替代 UIA/OCR、不许单独作为动作依据**（认错一个图标 = 点错一个按钮）。
⇒ 上线前还差两件：① 候选框必须是**已知图标格**（本轮已是）；② 扩模板集 + 用**人工框出的真图标**
做留出集（原型 README §6 的建议仍然成立）。

### 4.4 补充指令 §3 的三条替代路线：评估结论

| 路线 | 本轮实测 | 结论 |
|---|---|---|
| ① 「视觉上无字」≠「可访问性上无名」：读 UIA 的 HelpText / AutomationId / ClassName | 资源管理器里 **Name 为空的 18 个纯图标控件**：**HelpText 有值的 0/18**；**AutomationId 有值的 6/18**，而且**有信息量**（`PART_BreadCrumbBarIcon` / `PART_RootChevronButton` / `PART_ChevronButton`）；**ClassName 18/18** 但只有 `Image`/`Button`，信息量低 | **HelpText 这条路在本机没用（0/18）**；**AutomationId 有用（6/18，且能说出按钮的角色）**。★ 关键：`src/agentctl/uia_tree.py` **已经采了 AutomationId**（`node["aid"]`）⇒ **零改动**就能用 ⇒ **这是最省的一刀**。建议：把 `aid` 提到 `ctl_screen` 的 objects 里（D1 的第一顺位） |

## 5. 附录：原单 §5 的三个答问

### 5.1 「变化度排第一」这个权重本机站不住 —— 那什么站得住？

**站得住的是「分块 + 噪声地板 + 时间滞回」的三值判据**（补充指令 §2 的方案，本轮已落地）：

| 层 | 做法 | 本机依据 |
|---|---|---|
| ① **按目标窗客户区切 64×64 瓦片**（整屏不参与） | 降采样 8×，`|Δ| ≥ 2` 的采样点占比 > 2% 记候选 | 整屏 hash **90.6% 恒变**（不可用）；区域全等 **100%**（更差） |
| ② **噪声地板自适应** | 静止 1 s 采 10 帧估每瓦片噪声，阈值取 `max(2%, 3×噪声)` | 动画区（视频/时钟）天然一直在动 ⇒ 固定阈值会把它判成「一直在变」 |
| ③ **时间滞回** | 候选瓦片**连续 2 帧**都超阈才上报 | 光标闪烁只闪一帧就过去 ⇒ 单帧判据必然误报 |
| ④ **形状闸**（本轮加的） | 窄边 ≤8 **且** 长宽比 ≥2.0 才算光标 | 老口径连 **8×8 的方块**都丢了 ⇒ 派单补充 §2 明写「8px 方块必须报变」 |
| ⑤ **三值** | `changed ∈ {True, False, None}`，`None` 永不当 `False` | 「我没看见」≠「我看见了没变」（项目老纪律） |

**可实现方案 = 本轮落地的 `framecache.diff_images`**：两级（瓦片召回 → 候选瓦片内全分辨率分块），
**实测 2560×1600 端到端 15.3 ms**，且 8×8 方块**能报出来**（老口径报不出来）。

### 5.2 若 ①③ 做完仍然慢，瓶颈落在哪一段？下一刀砍哪里？

按本轮**直接计时**的结果，从大到小：

| 排序 | 瓶颈 | 实测 | 下一刀 |
|---|---|---|---|
| **1** | **被 spawn 的 act.py：进程启动 + 固定 `_settle(450)`** | `ctl_click` 总 1 111 ms，其中 settle 450 ms（`legacy_tools/act.py` 有 15 处 `_settle(400~500)`） | 把固定 settle 换成「**轮询指纹，变了就停**」——**这正是本轮 `framecache.wait_change` 做的事，但它在 `core.py` 侧（动作之后），改不了 act.py 内部那 450 ms** ⇒ **要下一刀，就改 act.py 的 `_settle`（在仓外，属客户端）**；仓内能做的是把 `AGENTCTL_*` 旋钮接上 |
| **2** | **动作后的 UIA 重扫**（`core.py:3714 → _click_after_state → _screen_build`） | 191 ms / 85 节点（仓内基线） | **只重扫变化区**：动作后的画面已经知道「变了哪一块」（本轮两级判据给出的 bbox）⇒ 只对那块做 UIA 子树查询；或用帧复用：屏幕没变就**不重扫** |
| **3** | **每次 `ctl_screen` 的 UIA 全树遍历** | 191 ms；带 `since` 复用后降到 **31 ms**（本轮已做） | 事件驱动感知（补充指令提到的中期项）：UIA 事件 + WinEventHook ⇒ 只在「真的变了」时才重扫 |
| **4** | **CDP 探测 + OCR** | CDP 探一次 ≈ 几十 ms；OCR 整屏 **460 ms**、裁剪 **42~58 ms** | 只对**变化区**做 OCR（把 diff 的 bbox 喂给 OCR 的 `rect=` 参数）——**本轮判据已具备 bbox，尚未接 OCR** |
| **5** | 抓帧与求差 | 抓帧 155.2 → 8.7 ms（**已做**）；求差 19.3 → 15.3 ms（1.3×，**已做**，收益有限） | 求差已不值得再砍 |

⇒ **一句话**：**仓内下一刀 = `_click_after_state` 的「只重扫变化区」+ 「OCR 只裁变化区」**；
**仓外下一刀 = act.py 的固定 `_settle(450)` 换成「变化即停」**（本单不能动，如实标出）。

### 5.3 答问（原单 §5 的两问 + 补充指令 §1 的 settle 之问）

- **「不许把固定 settle 砍成 0」怎么落地？** ⇒ 本轮**没有砍**，而是**换成自适应**：
  `framecache.wait_change` = 宽限 50 ms + 每 25 ms 轮询指纹、**变了就停**、最多 300 ms；
  且**第一轮抓的那张图就是「动作后」那一帧** ⇒ 界面已经变了时，动作只多抓 **1** 次帧。
- **(a) 变化即停 vs (b) 动作前重验，选哪个？** ⇒ 本轮选 **(a)**，因为 (b) 要在动作前再核对一次目标位置
  （又是一次 UIA 读取 ≈ 191 ms），而 (a) 的边际成本只有几次指纹（≈5~9 ms/次）。
  ⇒ **(b) 写进设计文档作为下一步**（补充指令 §1 的要求）：`_click_after_state` 已经有
  `expect_uid` 复核（结构位置 + 矩形重叠），可以在变化区里再核一次。
