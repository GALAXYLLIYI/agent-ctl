## 2. 对下一轮提速的**可执行指向**（只写有出处的）

1. **别再等 300ms 去「看有没有变」——去「动作前再验一次」**（L1 的 PUSV）：它的开销 **<0.1 s**（≈60~100ms 级），
   比我们 core 侧 `wait_change` 的 300ms 预算**便宜 3~5 倍**，而且它**不依赖「等多久」** ⇒ **不碰 TOCTOU 铁律**。
   ⇒ 候选：把「动作后等变化」换成「动作前 PUSV 式三点核验（目标点 SSIM + 客户区 diff + 窗口快照）」。
2. **GUI grounding 是社区公认瓶颈**（L2）⇒ **继续 UIA 优先、视觉兜底**，别把预算挪去加强视觉。
3. **抓帧成本降不动就别降**（L3）：`PrintWindow` 的耗时在**目标应用渲染**里 ⇒ 想省时间只能
   **少抓**（复用帧 / 降采样 / 事件驱动），不是换拷贝 API。
4. **「等变化」可能应该变「等事件」**（L6，**[待核实]**）：Windows 有窗口事件钩子 ⇒ 若成立，
   就能把「每轮 47.68ms 抓帧」变成「等一个通知」⇒ **CPU 占比从 48.8% 降到接近 0**。
