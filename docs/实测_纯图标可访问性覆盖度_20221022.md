## 二、结论（三条，指向明确）

1. **「视觉无字」≠「可访问性无名」—— 本机实测成立。**
   在原生 Win32/XAML 界面（资源管理器、记事本）里，**「真无名」的可交互控件数 = 0**。
   ⇒ D1「纯图标只能估坐标」这个痛点，**在原生界面上基本不成立** ⇒
   **走 UIA 树就能拿到机器可读标识，不需要像素识别、不需要训练模型**。
   （DSH 与 ZCode 提的第一条路 —— 先问可访问性 —— 被本机数据证实是**该先走的那条**。）

2. **真正的盲区是 Chromium/Electron —— 但它有 CDP。**
   ChatGPT 窗口的 UIA 树只有 **3 个节点** ⇒ UIA 这条路在 Electron 上基本读不到
   （ZCode 提的 `--force-renderer-accessibility` 可以救，但**不必救**：CDP 的 DOM 通道能直接读 `aria-label`）。
   ⇒ **UIA + DOM 双瞎**的只剩下：**自绘界面**（Canvas / 游戏 / 视频 / 远程桌面画面 / 图表控件）。

3. **⇒ M10 降级为「不做」。**
   M10 派单原本要做的三条路（可访问性 / hover tooltip / 模板匹配）里，
   **第一条已被本机数据证明覆盖度 100%**（无名率 0.0%），第二条只是补充，
   第三条（图标模板匹配）**M6 ③ 已经做完并实测「正文文字区高置信误报率 5.0%」**
   ⇒ **再投入一轮模板匹配，收益极低、风险不小**（认错一个图标 = 点错一个按钮）。

## 三、M6 ③ 图标反查的最终定位（不变，但更明确了）

`src/agentctl/iconfont.py` 保留，但**只当「多一条证据」**：

- 成立：确实是图标字体渲染的按钮能认对码点（资源管理器 ← `U+E72B`、刷新 `U+E72C`）
- 不成立：正文文字区高置信误报 5.0%（扫 925 个 32×32 块，46 个高置信命中）
- ⇒ **不许单独作为动作依据**（认错一个图标 = 点错一个按钮）

## 四、留下的真问题（下一个单，不是本轮）

**「UIA + DOM 双瞎」的自绘界面**怎么定位元素？本轮**没有**答案。候选（按代价排）：

1. **模板匹配（局部 NCC）** —— 小时级、零标注、零模型（比 M6 ③ 的全屏 NCC 便宜）
2. **现成视觉 API**（截图 + VLM grounding）—— 有现成模型可调，但引入云依赖（涉密场景不合）
3. **自己训** —— **最贵**（2000 个 bbox ≈ 17–33 小时纯人工 + 本机无 GPU 训练环境）
   ⇒ **顺序永远是：模板匹配 → 现成视觉 API → 自己训**。
   **触发重新评估的条件**：① 点名到某个 UIA+DOM 双瞎的具体应用；② 开始做跨应用通用 agent；③ 任务必须像素级接地。
