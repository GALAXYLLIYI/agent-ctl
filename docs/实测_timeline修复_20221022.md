**改动清单（store.py）**

1. 新增 `CrossProcessLock`（Windows `msvcrt.locking` / POSIX `fcntl.flock`）——OS 级锁，进程死 ⇒ 锁自动释放。
   - **可重入**：模块级登记表 `_LOCK_REGISTRY` + 守卫锁 ⇒ 同进程嵌套调用直接放行（实测嵌套 0.4 ms）。
     ★ 为什么必须可重入：Windows 字节区间锁按**句柄**计，同进程第二个句柄锁同一区间必失败 ⇒ 不做重入就是死锁。
   - **有上限**：默认等锁 5.0 s，超时抛 `TimeoutError`（消息含「等锁超时」）⇒ **绝不无限等**（铁律：unknown 永不当成功）。
   - **锁文件只当载体**：只在**空文件**时补 1 字节（不再每次重试 append ⇒ 老写法能把锁文件撑到 80 KB；实测现在恒为 **1 B**）。
   - 锁文件名 `.timeline-write.xlock`（**故意不叫** `.timeline-write.lock`）：判据参考实现 `RefStore` 用的是后者，而它 `with FileLock(...)` 之后又调真源 `append()` ⇒ 同文件两把锁 ⇒ Windows 上死锁（实测 6 个 worker 全卡死、锁文件长到 80 KB）。两把锁锁**不同文件** ⇒ 不冲突。
2. `append()` / `append_frame()`：整段「读链尾 → 算 seq → 追加 jsonl → 写索引」进**跨进程临界区**（`append_frame` 同样进临界区，否则帧链与事件链还会分叉）。
3. `_read_tail()`：**按文件顺序**取链尾（取代 `max(seq)` 那一行）——设计稿 §5 第 3 点明写要求。
4. 索引 schema **v1 → v2**：`seq` 去主键，改 `UNIQUE(seq, hash)`，写入改 `INSERT OR IGNORE`；`_migrate_index()` 自动迁移（**只动索引，不碰 jsonl**）。
5. `_append_jsonl()`：单次 `os.write` 写完整行（不再 `open(path,"a")` 的「先 seek EOF 再写」）。
6. 纪元：`epoch` 字段 + `migrate_to_epoch1()` + `verify(scope="epoch"|"full")` + `write_anchor()` 带 epoch。

**本单顺手修掉的两个自测抓出的 bug（都在 store.py 内）**

- `_verify_epoch` 的 `cur_expect_seq` 只在首条设一次、**再没推进** ⇒ 分段验从第二条起必然误报「seq 不连续」（沙箱实测 `expected_hash` 与 `actual_hash` 完全相同，只有 seq 检查误伤）⇒ 已改为逐条推进。
- `migrate_to_epoch1()` 写段锚时用的是**构造时**的 `_head` 快照，不是锁内真链尾 ⇒ 段锚可能与新纪元起点对不上 ⇒ 已改为锁内 `_read_tail()` 重读。

## 2. 三条缺陷逐条给证据

### 缺陷 1｜互斥只在进程内、链尾只在构造时读 ⇒ seq 撞车 + 链分叉

| 项 | 内容 |
|---|---|
| 病状 | 老 `store.py` 只有 `threading.RLock`（进程内），且 `self._head = self._load_head()` 只在**构造时**读一次 ⇒ 多个进程各拿一份**过期链尾快照** ⇒ 分配到同一个 `seq`、挂到同一条 `prev_hash` 上 ⇒ 链分叉。 |
| 修法 | 跨进程排他锁 + **锁内重读链尾**（按文件顺序）。 |
| 判据证据 | A 组（参考实现 = 修法 A 原型）：① jsonl 行数 240 == 写入总数 240、② 断链 0、③ sqlite 240 == jsonl 240 ⇒ **三条契约全立**；④「三条同时成立」也立 ⇒ 证明规格可满足。B 组（真源）：⑤⑥⑦ 同样**三条全立**，「不成立的是 无」。 |
| 现场证据 | 全历史逐条判定（基准 = **文件顺序上的前一条**的 seq）：`接着链尾 ✔ 4133 / 撞号 ✘ 61 / 超前(有插队) 43 / 跨文件起点 15`；04:50 重启之后：新代码写的记录 **9/9「接着链尾」、0 撞号**（`M6帧复用判据` 9 条：ctl_lease×4 / ctl_screen×4 / ctl_click×1）；仍有的 3 条撞号全部来自**没重启的旧 `agentctl.mcp`**（见 §7）。 |
| 锁的自检 | 可重入：嵌套进入 0.4 ms 通过；等锁超时：占用 8 s 时，1.0 s 后**报错**（消息含「等锁超时」）而不是无限等；锁文件恒 1 B。 |

### 缺陷 2｜jsonl 追加不是原子的 ⇒ 真相源自己丢事件

| 项 | 内容 |
|---|---|
| 病状 | 老写法 `open(path, "a")`：Windows 上 `O_APPEND` 的实现是「**先 seek 到 EOF，再写**」，**不是**原子的 `FILE_APPEND_DATA` ⇒ 两个进程可 seek 到**同一个** EOF ⇒ 后写的**覆盖**先写的字节 ⇒ 记录被拼坏/撕坏 ⇒ 源文件自己少条。 |
| 修法 | 追加动作整体进跨进程临界区 **＋** 单次 `os.write` 写完整行（撕裂窗口最小）。 |
| 判据证据 | A/B 组的契约 ①：「jsonl 行数 == 写入总数（无撕裂行）」——真源 240 == 240，**撕裂行 = 0**。 |
| 现场证据 | 判据 C 组现场读数「**撕裂行 = 0**」（2026-10-22 05:16 与 05:26 两次都是 0）；现场 15 个 jsonl 文件里**不可解析行 = 0**。 |

### 缺陷 3｜`events.seq` 是 PRIMARY KEY + `INSERT OR REPLACE` ⇒ 索引覆盖丢条

| 项 | 内容 |
|---|---|
| 病状 | `seq INTEGER PRIMARY KEY` ⇒ SQLite **装不下**两条同 seq 的记录；`INSERT OR REPLACE` = DELETE + INSERT ⇒ **后写覆盖先写** ⇒ 索引**结构性**少条（jsonl 里还在，索引里没了）。 |
| 修法 | 索引 schema v1 → v2：`seq` 去主键 + `UNIQUE(seq, hash)` + 写入 `INSERT OR IGNORE` ⇒ 同 seq 不同 hash 的两条**都装得下**（并发化石是**证据**，不是垃圾）。 |
| 证据 1（逐条坐实） | 对现场「jsonl 有、索引没有」的 **242 条**逐条判别：**242/242** 满足「① 同 seq 在 db 里存在**另一条**（被顶掉）② db 里那条 `t_wall` **更晚**（后来者赢）③ 两者 `hash` **不同**（确是两条不同记录）」；每条丢失记录的 seq 在 jsonl 里恰好有 **2 条** ⇒ 正是主键的一对一顶替行为。 |
| 证据 2（修好之后） | 索引升到 v2 后，**迁移之后**写入的并发化石**不再被覆盖**：db 里「同 seq 多行」的 seq 刚迁完时是 **67 个**，随现场继续写入已涨到 **90 个**（多余行 154），**都保住了**。 |
| 证据 3（可回收） | 沙箱里把 live 的 jsonl **只读复制**过去，用新代码 `rebuild_index()` 重建：**db 行数 4,271 == jsonl 行数 4,271 ⇒ 差额 0**（那 242 条**能全部找回来**，因为真相源一直完好）。★ live 未执行（需主控批准，属写操作）。 |

## 4. ⑨ 等式破的真因（重点）

### 4.1 等式本身在索引升到 v2 后**不再成立**（口径问题，不是丢事件）

判据 ⑨ 断言的是 **v1 时代**的口径：

```
jsonl 行数 − sqlite events 行数 == 重复 seq 条数
```

在 v1（`seq` 是主键）下，每个 seq 在索引里**最多一行** ⇒ 索引行数恒等于**不同 seq 数** ⇒ 差额**恒等于**「重复 seq」。

升到 v2（`UNIQUE(seq, hash)`）后，索引**故意**把同 seq 的并发化石**都留下** ⇒ 索引行数 = 不同 seq 数 + 化石数 ⇒

```
jsonl 行数 − sqlite events 行数 = 被覆盖丢掉的那部分  ≠  重复 seq 全部
```

现场两个数正好对上（05:16 那一拍）：**重复 seq 383 = 已被 v1 覆盖丢掉的 242 + 迁移后被 v2 保住、写进索引的 141**。
再取交付前最后一拍（05:3x）：**重复 seq 396 = 丢掉 242 + 保住 154** ⇒ 等式精确成立。

⇒ **「sqlite 比不同 seq 多」不是丢事件，是化石被保住了（好消息）；真正丢的是那 242 条（v1 时代的旧账）。**

### 4.1.1 交付前一致性核算（五个等式全部重算过）

原始输出：`work/_M8_timeline真源修复_20221022/_out_交付前核算.txt`（脚本 `_probe_交付前核算.py`，全程只读）

| 等式 | 实测 | 判定 |
|---|---|---|
| E1 `jsonl − sqlite == 被覆盖丢掉的条数` | 4,292 − 4,050 = **242**；逐条核对丢失记录 **242** 条 | 一致 ✔ |
| E2 `重复 seq == 丢掉的那批 + 被 v2 保住写进索引的` | 396 == 242 + **154** | 一致 ✔ |
| E3 `db 行数 == 不同 seq + 多余行` | 4,050 == 3,896 + **154** | 一致 ✔ |
| E4 丢失记录逐条「同 seq 被更晚的记录顶掉」 | 242/242 同 seq 有别的记录；242/242 那条**更晚** | 全部坐实 ✔ |
| E5 索引是真相源的纯投影 | db 4,050 行，jsonl 文本里找不到的 = **0** | 是纯投影 ✔ |

⇒ **丢事件只有一种机制**（缺陷 3），且**已不再增长**（E1 恒为 242）。

### 4.2 那 242 条丢在哪：逐条归因

| 归因 | 条数 | 说明 |
|---|---|---|
| 跨**文件**轮转重号（同 seq 出现在两个日期文件里） | **18** | `timeline-20261021.jsonl` 的 seq 3072..3402 与 `timeline-20261022.jsonl` 的 seq 3337..3896 —— **区间相交 3337..3402（66 个 seq 值）**，但两个文件**同时含有**的只有 **18 个**（区间 3337..3354）。 |
| 同**文件**内并发重号 | **224** | 同一时刻多个写者各自拿陈旧链尾 ⇒ 同一个 seq 写了两条（不同 hash）⇒ v1 主键覆盖掉先写的那条。 |
| 合计 | **242** | 与「jsonl − sqlite = 242」**逐分不差**。 |

丢失记录的时间分布（全部落在**索引迁移之前**）：10-07 3/1 条、10-09 2 条、10-15 17 条、10-19 11 条、10-20 3 条、10-21 24 条、**10-22 01 点 171 条**（主控重启长驻进程前的那一小时并发写入）。

### 4.3 结论与可回收性

- **只有一种丢事件机制**：`PRIMARY KEY + INSERT OR REPLACE`（缺陷 3）。**没有第二种机制**。
- 判据 ⑨ 的等式**不成立 ≠ 还有别的丢失机制**；不成立是**口径**没跟上索引升级（该条应改写为「jsonl − sqlite == 被覆盖丢掉的条数」，且「重复 seq」里要注明混了轮转重号与已保住化石）。
- **那 242 条能全部找回来**：真相源（jsonl）一直完好 ⇒ 沙箱里 `rebuild_index()` 重建后 `db 行数 == jsonl 行数`，差额 0（§2 证据 3）。**live 上没做**（属写操作，等主控批准）。

## 6. 纪元迁移口径（epoch + 段锚）

### 6.1 口径

- **纪元不另存状态文件**：由 `anchors.jsonl` 里的「段锚」推导 ⇒ 有 `epoch=0` 的段锚 ⇒ 当前纪元 = 1；没有 ⇒ 当前纪元 = 0。
  （⇒ 全新 timeline / 沙箱**自动是 epoch 0**，不会被平白多一个纪元。）
- **迁移只做两件事**：① 在 `anchors.jsonl` 追加一条 **epoch=0 的段锚**（`head_seq` / `head_hash` / `chain_ok` **如实写** / 统计）；② 此后新记录带 `epoch=1`。
- **不许重算、不许重写历史**：**一个 jsonl 字节都不动**；旧链的断点（现场 108 处）**如实留在 epoch 0 里**。
- **链跨纪元连续**：新纪元第一条的 `prev_hash` 指向上一段的链尾 ⇒ **旧的独立验证器 `verify/agentctl_verify.py` 不用改也能验**；段与段之间由**段锚**对账（epoch 1 首条的 `prev_hash` 必须 == epoch 0 段锚的 `head_hash`）。

### 6.2 沙箱实测（`_probe_纪元沙箱.py`）

| 步骤 | 实测 |
|---|---|
| 写 5 条旧链 | head = (seq 5, hash 0a90052b18e5…) |
| `migrate_to_epoch1()` | 段锚 `epoch=0 head_seq=5 chain_ok=True`；**历史 jsonl 字节数迁移前后完全相同**（1,670 B ⇒ 1,670 B） |
| 新进程续写 3 条 | seq 6/7/8，`epoch=1`，`prev_hash` 首尾相接 |
| `verify(scope="epoch")` | **ok=True**；`per_epoch={0:5, 1:3}`；旧纪元断链 0 |
| `verify(scope="full")` | 老口径**如实**判链（旧链有断点就红），不粉饰 |
| 段锚对账 | 段锚 `head_hash` == epoch 1 首条 `prev_hash` ✔ |
| 独立验证器口径（从 GENESIS 顺链） | 断链 0；**epoch 1 首条的 `prev_hash` 落在旧链里** ⇒ 旧验证器不用改也能验 ✔ |

### 6.3 现场还没迁（**等主控决定停写窗口**）

- 现场 `work\timeline\anchors.jsonl` **不存在** ⇒ 当前纪元仍是 **0** ⇒ `verify(scope="epoch")` 此刻判的是「整个历史」⇒ 会如实报红（旧链断点）。
- 迁移命令（**在停写窗口执行**，一条一条来）：

```powershell
$env:PYTHONPATH = '<仓库根>\src'
python -X utf8 -c "from agentctl.store import Store; s=Store(r'<仓库根>\work\timeline'); print(s.migrate_to_epoch1('M8 迁移：旧链定为 epoch 0，不重算不重写'))"
```

- ★ **迁移之后必须重启所有写者**：老进程的 `self._epoch` 是**构造时的快照** ⇒ 它会继续写 `epoch=0` 的记录 ⇒ 把 epoch 1 的起点挤到后面 ⇒「段锚对不上」会误报红。
- 迁移是**幂等**的：已迁过再调会直接返回「已有 epoch=0 的段锚 ⇒ 不重复迁移」。

具体改了什么（现库实际 schema，已用 `PRAGMA table_info` / `sqlite_master` 核对）：

| 对象 | 改前（v1） | 改后（v2，现库实际） |
|---|---|---|
| `events` 表 | `seq INTEGER PRIMARY KEY`（seq 是主键） | `seq INTEGER NOT NULL`（**主键去掉**），新增表级 `UNIQUE(seq, hash)`（`sqlite_autoindex_events_1`）；**其余 11 列与顺序完全不变** |

- **能否回滚**：
  - **索引层**：可以，但要付代价——回到 v1 语义（`seq` 重新当主键 + `INSERT OR REPLACE`）会把**已经保住的 154 行并发化石再覆盖掉**，而且 v2 表里同 seq 多行时 `ALTER` 回去会**直接失败**（主键冲突）⇒ 必须先 `DELETE` 冲突行。

## 8. 已知缺陷（本单**不修**，登记在案）

1. **跨日轮转时 seq 起点没接上昨天**（主控 04:27 提出，本单不修）：
   `timeline-20261021.jsonl` 的 seq 到 3,402 结束，而 `timeline-20261022.jsonl` **从 3,337 重新起** ⇒ 区间相交 66 个 seq 值、**两文件同时含有 18 个**。
   修法方向：轮转时新文件的 seq 起点必须接**前一天的真实链尾**（而不是某份陈旧快照），且轮转与写入要在**同一把跨进程锁**内完成。⇒ **单独开单**。
2. **过渡态的 seq 重用**（§5 第 3 条）：旧写者存活期间，新写者从**文件顺序链尾**续号，而链尾可能低于历史最大 seq ⇒ 会重用已占用的 seq。
   这是设计稿 §5 第 3 点（「链尾按文件顺序取」）的**必然代价**，不是新缺陷；旧写者重启 + 链尾越过 3,896 后自然消失。
   ⇒ 若要立刻消除：`rebuild_index()`（不动 jsonl，只让索引与真相源对齐）**不能**解决 seq 重用，只能解决「索引少条」；seq 重用只能靠上面那条。
3. **live 上还没做纪元迁移**（§6.3）—— 需要停写窗口 + 迁移后重启写者。
