## 一、本机当前基线（**全部本机实测，来源：M12 阶段二 / M11 分段计时 / M6 三件套**）

端到端 ctl_click：**1,496 ~ 1,622 ms**（M12 阶段二「等两遍→等一遍」之后）。构成：

| 段 | 耗时 | 备注 |
|---|---|---|
| 授权/租约/闸门 | 量级 10~50ms | 本轮不查 |
| **整窗抓帧 ×5~7** | 每次 ~40.96ms | 一次点击拍 5~7 张整窗、写 6~7 张 PNG |
| **PNG 落盘 ×6~7** | 每次 **29.9ms** | 交接格式；raw **1.9ms** / BMP **5.3ms** |
| diff 判变 | 每轮 15.4~18.5ms | |
| is_blank 每轮 | 5.7ms/轮 | 退化只是打标 ⇒ 最后一帧打一次就够 |
| _poll_gray 每轮 | 6.3ms/轮 | 只为判「图够不够大」⇒ img.size 就够 |
| 轮询 sleep | 50ms/轮 | |
| 动作后等待 | 预算 int(_settle(450)*1000)（**450ms**） | POLL_BUDGET_MS=800 只是函数默认值，**不是生产预算** |
| core 侧 wait_change | **13.9 ~ 31.0ms** | M12 阶段二已压到位 |
| **UIA 控件树** | **191ms / 次** | 每次 ctl_tree / ctl_find 重走 |
| OCR 整屏 | 926~1,074ms | 只对**变化区** OCR 时 **42~58ms** |
| 指纹变化检测 | 6.45ms/次 | 1fps ≈ 0.66% 单核 |

**已实测否掉的路**（不许重提）：BitBlt 代替 PrintWindow **慢 3~4 倍**（16.2 vs 52.4ms）；
去掉多余 .convert("RGB") 省 **−0.42ms**（噪声内）；把 poll_ms 50→15 **总 CPU 反涨**
（大窗每轮 ≈112ms，省 35ms/轮但轮次上涨 ⇒ OpenCode 的算式）。

## 四、给审阅方的**五个问题**

**Q1｜K2（UIA 树缓存）值不值？** 本机 UIA 191ms/次，重复调用频次未知。
- 缓存**只用于「读」**（找元素、读文本），**点击前必须用 live 树复验 eid**（M15 已落地「窗口代际闸」code=12，可复用）——这样对不对？
- 失效条件该定成什么？（hwnd + 代际 + 焦点 + 屏幕区域被遮挡）
- 风险：缓存过期 ⇒ agent 读到**已经不在那儿的元素** ⇒ 点错。**这个风险你认不认？**

**Q2｜K7（一次观测多动作）与「逐动作授权」铁律冲突吗？**
- 形状设想：**一次观测 ⇒ 产出 N 个动作 ⇒ 逐个授权、逐个执行**（不是一次授权一批）；
- 社区说的省的是 **LLM 往返**，不是**闸门**——但**闸门才是我们的红线**；
- 请判断：这条在本机铁律下**能不能做**，还是**必须否决**。

**Q3｜K3（退避调度）到底留不留？** OpenCode 的算式：每轮 ≈112ms，poll 50→15 只省 35ms/轮但轮次上涨 ⇒ 总 CPU 涨。
你同意**降级/砍掉**吗？还是能从别的角度救？

**Q4｜验收口径**：本轮「加速成功」定成端到端 p50 从 **1,496~1,622ms** 降到多少？
候选：**≤1000ms**（保守）｜**≤800ms**（对齐文献「感知即时」档）｜**≤500ms**（激进）。请给一个数并说清理由。

**Q5｜还剩哪些 ≥50ms 的刀是清单外的？**（本机实测优先，不许凭印象）
