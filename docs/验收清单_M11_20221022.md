## 3. ★ 它纠正了主控的一个假设（如实记，这是最有价值的一条）

主控原假设 A：「每轮重抓整窗是头号瓶颈（41.6ms × 16 轮 ≈ 677ms 吃满 800ms 预算）」。

**它实测后裁决：假设 A 只在「窗口大」时成立，不是普适结论，而且它不是头号瓶颈。**

| 场景 | act 每轮抓整窗 | 轮询 CPU 占几成 | 结论 |
|---|---|---|---|
| 大窗（客户区 1712×1078） | **47.7ms** | 47.7/(47.7+50) ≈ **48.8%** | 确实吃掉 act 等待近一半 |
| 默认大小记事本（≈800×500） | **13.6ms** | 13.6/63.6 ≈ **21%** | 那 800ms 里 **~640ms 是纯等待**，不是 CPU |

⇒ **主控的 41.6ms 是大窗数字**，在生产默认尺寸下**不成立**。它把这个纠正明写进文档 §4，没有迎合。

## 4. ★ 假设 B 成立（已量化）

- core 侧 `framecache.wait_change` 实测 **321~343ms**（大窗 414ms）；
- act 侧 `_wait_effect` 实测 **828ms**（画面不变时 843.1ms）；
- ⇒ 两层等的是**同一个窗口的画面变化** ⇒ **同一件事等了两遍**，合计 ≈ **1,165ms**，占端到端 **~78%**；
- 合并**省 200~340ms/次**（画面不变时省 core 那一遍 321~343ms；画面会变时省 198ms），
  **且失败口径不松**：画面没变仍落 `code=8`、`unknown` 永不当成功。

★ 它同时标了合并的**前提**：合并后 core 侧仍必须拿到一张「动作后」帧（落盘 diff 要用），
而 act 侧现在只回传布尔结论 ⇒ **要把「最后一帧」带回来，这是下一单的活**（不是本单能悄悄带过的）。
