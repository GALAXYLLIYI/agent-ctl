## 一、能力边界总览

### 1.1 三档能力 + 契约声明

契约（`contract/tools.json`）把工具分四档：

| 档位 | 含义 | 工具 |
|---|---|---|
| **A** | 只读感知 | `ctl_windows` `ctl_shot` `ctl_tree` `ctl_screen` `ctl_find` `ctl_witness` `ctl_browser` `ctl_quiz` |
| **B** | 点击 / 滚动 | `ctl_focus` `ctl_click` `ctl_scroll` `ctl_task` `ctl_browser` `ctl_quiz` |
| **C** | 打字 / 快捷键 | `ctl_type` `ctl_fill` `ctl_keys` |
| **D** | 拖拽 | （契约已列，工具清单里未出现） |
| — | 免闸门的控制面 | `ctl_status` `ctl_preflight` `ctl_timeline` `ctl_verify` `ctl_memory` `ctl_lease` `ctl_authorize` `ctl_brake` `ctl_record` `ctl_replay` `ctl_wait` |

### 1.2 ★ 最重要的边界：**连 A 级感知也要通行证**

契约把 `ctl_shot` / `ctl_windows` / `ctl_tree` / `ctl_screen` / `ctl_find` / `ctl_witness`
标成 `gate: A`，**看起来** A 级是免授权的只读通道。

**实测不是这样**：无通行证时调它们全部返回 **code=9（未获授权）**。

根因在 `src/agentctl/core.py` 的 `_perceive()`：

```python
gate.require_any(gate.PERCEIVE, why or "ctl_perceive", count=False)
```

`gate.PERCEIVE` 就是 A 级 —— 但 A 级本身**也是一种需要签发的范围**，
不是「不需要授权」。**契约的 `gate: "A"` 读起来像「A 级闸门」，实际是「需要 A 级通行证」。**

⇒ **实际影响**：agent 拿到仓的第一件事不是 `ctl_windows`，
而是 `ctl_status` → `ctl_authorize` → `ctl_lease`。
契约这一处措辞会让人以为可以先探再授权，**是个会误导调用的坑**。

### 1.3 写动作三步（契约声明，实测确认）

```
status → authorize → lease → act
```

实测确认的三条：

| # | 事实 | 证据 |
|---|---|---|
| 1 | **`ctl_lease` 不需要通行证** —— 无证也能拿租约（code=0） | E1 轮：无证状态直接 acquire 成功 |
| 2 | **通行证优先于租约检查** —— 有证无租约时，拒的理由是 code=9（没证）而不是 code=10 | D2 轮：释放租约后调 `ctl_click` → code=9 |
| 3 | **`ctl_scroll` / `ctl_keys` 的闸门顺序不同** —— 它们先查前置条件（前台/参数），**再**查证 ⇒ 无证时返回 code=5 而非 code=9 | B1 轮：这两个返回 code=5，其余写动作返回 code=9 |

### 1.4 单写者租约（实测完全正确）

| 场景 | 实测 | 说明 |
|---|---|---|
| 持有中，另一 actor 抢 | **code=10** | 「租约被 sandbox 持有，剩余 599 秒」 |
| 同 holder 续期 | code=0 | 正常 |
| 释放后他人拿 | code=0 | 正常让位 |
| **旧租约已过期**后他人拿 | code=0 | `gate.py:985` 的条件是 `expires_at > now` ⇒ 过期即让位（**这是正确行为，不是漏洞**） |

## 三、每个动作的响应时间

### 3.1 口径（先说清楚，别混）

- **往返(ms)** = 客户端视角：HTTP 发出 → 完整响应回来。
  含协议栈 + 服务端处理 + **真实动作执行** + 响应序列化。
- **动作(ms)** = 服务端信封里的 `elapsed_ms`（真动作执行耗时）。
- 往返 ⊇ 动作，差值 = 协议与序列化开销。

本表给的是**往返**（客户端真正等待的时间）。

### 3.3·二 ★ 有证后的真实耗时（**这才是动作本身的耗时**）

⚠ **上一节的数字绝大多数是「被闸门拒」时的耗时** —— 测的是**闸门拒绝**有多快，
不是动作有多快。拿到证之后重测，差距很大：

| 工具 | 无证（被拒） | **有证（真跑）** | 差几倍 | 服务端自报 elapsed_ms |
|---|---|---|---|---|
| `ctl_shot`（整屏截图） | 29.9ms（code=9） | **154.8ms**（code=0） | **5.2×** | 138ms |
| `ctl_witness`（OCR 读时钟） | 33.8ms（code=9） | **109.7ms**（code=0） | **3.2×** | 86ms |
| `ctl_tree`（UIA 树） | 32.0ms（code=4） | **87.1ms**（code=0） | 2.7× | 63ms |
| `ctl_find`（找控件） | 28.9ms（code=4） | **92.3ms**（code=0） | 3.2× | 62ms |
| `ctl_windows` | 31.6ms（code=9） | 28.4ms（code=0） | ≈ | 7ms |
| `ctl_preflight` | 21.0ms（code=0） | 15.2ms（code=0） | ≈ | **0ms** |
| **`ctl_screen`（裁剪屏幕）** | 25.4ms（code=4） | **998.4ms**（code=0） | **39×** | 970ms |

⇒ ★ **`ctl_screen` 是感知通道里最重的一个**：998ms，
   其中 970ms 是服务端自己花的（采集 + 等 ready 证据：日志里「等待毫秒 800、重试 2、间隔 400」）
   ⇒ **它每次调用要等 0.8~1.2 秒**。
   ⇒ **热路径上不该用它** —— 要用它就得缓存。

⇒ **协议开销约 15~30ms**：对比「往返」与「服务端自报 elapsed_ms」——
   `ctl_preflight` 服务端只花 **0ms**，往返却要 15~40ms ⇒ **那 15~40ms 全是协议与序列化开销**。
   ⇒ 想知道「服务端到底干了多久」，**必须看 `elapsed_ms`，不能看往返时间**。

### 3.4 ⚠ 失败路径也会消耗预算

`ctl_windows` 在**无通行证**时返回 code=9，但响应里仍然带着**完整的窗口列表**
（`data.windows` 有内容）⇒ **被闸门拒了，枚举的活还是干了**。

⇒ 一个「先探后授权」的 agent 会白白付出每次 30~240ms 的窗口枚举成本，
而这些数据在没证时按契约本来就不该给。


### 3.6 ★ B 级真动作的实测耗时（记事本靶场 · 属主 Notepad.exe）

|---|---|---|---|---|---|
| `ctl_focus` | H | **1933ms** | 1907ms | 0 / 8 | 真置前成功（`现在前台=True`）；**这是真动作的真实代价** |
| `ctl_focus` | I | 1889ms | 1877ms | 5 | 置前**失败**（前台被别的窗占着）⇒ 同样是 ~1.9s |
| `ctl_click` | I | 28.1ms | 10.5ms | 12 | `foreground_blocked` —— **点击前目标必须在前台** |
| `ctl_scroll` | I | 20.0ms | 0ms | 5 | `amount=0`（参数口径问题，非性能） |

⇒ ★ **`ctl_focus` 要 ~1.9 秒** —— 因为它做完动作还要**逐像素比对前后画面**
  （`after.diff`：共 1 块变化、其中窄边≤8 且长宽比≥2.0 判为光标类、剩余面积 0px² ⇒ 判为没变）。
  ⇒ **置前不是「切一下」那么快，是「切 + 验」**。
⇒ ★ **`ctl_click` 只要 28ms**（服务端 10ms）—— 但**前提是目标已在前台**，
  否则 12ms 内就返回 `code=12 foreground_blocked`。
⇒ ⇒ **真实工作流的成本 = 置前 1.9s + 每次点击 28ms**。
  **置前是最大的一笔**（占单次交互的 98%）。

### 3.5 ★★ 本机能力边界：**键盘注入被拦，鼠标注入通**

这一轮探测中最有价值的发现 —— 而且它**不是 agentctl 的 bug**，是**本机环境**的边界。

| 通道 | 实测 | 怎么测的 |
|---|---|---|
| **鼠标注入** | ✅ **通** | `act.click_at(321, 234)` → 光标**精确落在 (321,234)**；点击能让前台窗口切换 |
| **键盘注入** | ❌ **不通** | 连**原生控件**（记事本的 Edit 子控件）都收不到字符 |

**关键：agentctl 自己的注入路径也不通。**
`act.send_unicode()` 发的 `INPUT` 里 `dwExtraInfo = INJECT_MAGIC (683543)`
（这是 agentctl 防「假注入」的设计），用它打字符**同样收不到**。

⇒ **不是 agentctl 写错了、也不是 tkinter 的问题**（用原生记事本做对照，
原生控件同样收不到）⇒ 是**这台机器的输入注入被拦**
（UIPI / 安全软件 / 远程会话限制三者之一；本机有 Defender，shell 是 Medium 完整性、
SessionId 1 的本机交互会话）。

**这个区分必须能被机器判出来**，否则 agent 会：
① 以为「我打字没成功 = 目标没响应」→ 去盲目重试 → **白烧动作额度**；
② 更糟：把「键盘没打进去」误判成 code=8「画面没变」→ 报一个**假的失败原因**。

⇒ 本轮新增 **`tools\probe_input_injection.py`**（输入注入可用性体检）：

```powershell
python -X utf8 tools\probe_input_injection.py
# 退出码：0=键鼠都通 ｜ 1=键盘不通（C 级不可用）｜ 2=鼠标也不通（B/C 级都不可用）
```

它开一个**记事本测试窗**（%TEMP% 临时文件，测完自己关掉删掉），
用 agentctl 自己的注入路径分别测键鼠 ⇒ 结论与 agentctl 完全同源，不会漂。

**对本机的影响**：
- **B 级（点击/滚动）可用** → §三 的 B 级耗时可以测出真值
- **C 级（打字/快捷键）不可用** → C 级耗时**测不出真值**（测到的只是「发出去了但没进去」，
  不是 agentctl 的性能问题）
- ⇒ **C 级耗时在本报告里标注为「本机不可测」，不拿失败的耗时冒充性能数据**

## 四、这一轮发现的真问题

### 4.1 ✅ 已修：`ctl_status` 序列化崩溃（真 bug）

**现象**：调 `ctl_status` 直接返回 JSON-RPC 内部错误：

```
{"code": -32603, "message": "Internal error: Object of type LockedDict is not JSON serializable"}
```

**根因**：`src/agentctl/core.py:654`

```python
_INTEGRITY_CACHE.update(out)
return _INTEGRITY_CACHE        # ← 返回的是 LockedDict 对象本身
```

`LockedDict`（`src/agentctl/sync.py:39`）继承自 `object`，**不是 dict**，
`json.dumps` 必然抛异常。而 `t_status()` 里
`st["service"]["integrity"] = _my_integrity()` 把它塞进了响应 ⇒ **整个 ctl_status 挂掉**。

**影响面**：`_my_integrity()` 的唯一调用点就是 `core.py:710`（`t_status`）⇒
**`ctl_status` 100% 不可用**。

> ★ 这与「任何 agent 开工第一件事就是 `ctl_status`」的设计直接冲突 ——
> **一个 agent 连自己的状态都看不到**。而 `ctl_status` 的 `integrity` 字段
> 恰恰是用来诊断「UIPI 拦点击」这类问题的 —— 它自己先挂了。

**修法**（缓存语义不变：仍然只真正探测一次）：

```python
_INTEGRITY_CACHE.update(out)
return dict(_INTEGRITY_CACHE.items())   # 交出去的是普通 dict 拷贝
```

（`:622` 的提前返回分支同样改成 `dict(_INTEGRITY_CACHE.items())`。）

**修复后实测**：`ctl_status` → code=0，正常返回完整状态。

### 4.2 ⚠ 已定位未修：`ctl_verify` 报「哈希链断」是**误报**

**现象**：`ctl_verify` 返回 code=4，第一个坏点 `timeline-20261007.jsonl` 第 43 行 / seq 78。

**诊断**（独立脚本重算全部 20 个时间线文件、17517 行）：

| 文件 | 行数 | seq 单调 | 链自洽 |
|---|---|---|---|
| timeline-20261002 / 0610 / 1012 / 1014 / 1016 / 1017 / 1018 | — | ✅ | ✅ |
| **timeline-20261007** | 154 | ❌ | ❌ |
| **timeline-20261009** | 97 | ❌ | ❌ |
| **timeline-20261015** | 251 | ❌ | ❌ |
| **timeline-20261019** | 770 | ❌ | ❌ |
| **timeline-20261020** | 423 | ❌ | ❌ |
| **timeline-20261021** | 337 | ❌ | ❌ |
| timeline-20261022 | 8249 | ❌ | ❌ |
| timeline-20261023 / 1024 / 1025 / 1026 / 1027 | — | ✅ | ✅ |

**规律很清楚**：**10-07 ~ 10-22 的文件有 seq 乱序，10-23 之后的文件全部正常。**

⇒ 乱序是**那个阶段的并发写 bug 的历史遗留**（`store.py:_append_jsonl` 的注释
   明确记了当时 `O_APPEND` 在 Windows 上不原子、两进程会写坏记录），
   写入路径后来修好了（一次 `os.write` + 跨进程锁）。
   ⇒ **现在写入是干净的，乱序只存在于旧文件里。**

**为什么 `ctl_verify` 还在报**：验证器扫**全部** jsonl 文件（`store.py:572` 的
`_jsonl_files()`），按**文件顺序**算 `prev_hash` ⇒ 遇到 seq 乱序的旧文件就报「链断」。

**结论**：**这是验证器对历史文件的误报，不是内容被篡改。**
但它有真实代价 —— `ctl_verify` 是「独立验证器」，它的**唯一价值就是「内容没被改过」**。
一个总是报红的历史验证器，会让人养成忽略它的习惯 ⇒ **这个红比没有验证器更坏**。

**建议修法**（本次未做，需你拍板）：
① 验证器先按 `seq` 排序再算链（乱序是写入顺序问题，不是内容问题）；
② 或给旧文件做一次性重排（但那会改历史证据，需你同意）。

### 4.3 ⚠ 契约措辞误导：A 级也要通行证

见 [§1.2](#12--最重要的边界连-a-级感知也要通行证)。

### 4.4 ⚠ code=4 歧义：缺 hwnd 也报「找不到控件」

## 五、沙箱怎么起的、怎么复现

### 5.1 隔离口径

用 `AGENTCTL_APP_DIR` 把**状态**挪走（授权账本 / 租约 / 急停标志 / 录制 / 面板状态），
用 `AGENTCTL_STATE` 把**令牌**挪走，用 `AGENTCTL_MCP_PORT` 换端口（8799，避开真实 8761）：

```
work/sandbox_20261027/
├── app/          ← AGENTCTL_APP_DIR：_auth/ lease.json brake_daemon.json ...
├── state/        ← AGENTCTL_STATE：token
├── mcp_http.log
└── sandbox.json  ← 端口 / 令牌 / pid 清单
```

**不隔离的**：真实屏幕操作本身 —— 所以必须配**靶场窗口**
（`tools/ab_target_winforms.ps1`，8 控件 WinForms 表单），不对你的真实窗口动手。

### 5.2 复现步骤

```powershell
# 1) 起沙箱（隔离状态目录 + 端口 + 靶场窗口）
python -X utf8 tools\launch_agentctl.py        # 或按本文 env 口径手工起

# 2) 首次：设沙箱密钥（弹窗里输两遍，明文不落盘）
$env:AGENTCTL_APP_DIR = "<仓>\work\sandbox_20261027\app"
python -X utf8 legacy_tools\auth_popup.py --set

# 3) 申请通行证（弹窗里输密钥 + 点授权；人必须在场）
python -X utf8 tools\加协作者.py --check        # 查权限
#   或经 MCP 调 ctl_authorize

# 4) 拿租约 → 动
ctl_lease --action acquire --scopes BC --actor sandbox
```

### 5.3 ★ 复现时踩到的五个坑

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | **token 文件没落沙箱** | 服务日志说令牌文件在沙箱路径，实际读到了 `work\state\token` 的旧值 | 起服务时**必须**传 `AGENTCTL_STATE`；漏传会静默复用真实令牌（不报错） |
| 2 | ★ **环境变量优先于文件** | 服务端 `ensure_token()` 里 **`AGENTCTL_MCP_TOKEN` 优先于 `state\token`** ⇒ 父进程带着这个变量时，沙箱会**静默复用真环境的令牌** | 起沙箱服务时**必须 `env.pop("AGENTCTL_MCP_TOKEN")`** |
| 3 | **授权弹窗 180 秒超时** | `ctl_authorize` 返回 code=9 / rc=124，日志显示「授权请求」已发出但 180 秒内零提交 | 授权**必须人当场在弹窗上操作**；且本机**键盘注入被拦**（见 §3.5）⇒ 弹窗这条路走不通 ⇒ 本轮改走 `issue_pass`（仓内判据同款路径） |
| 4 | **沙箱没密钥 ⇒ 弹窗报「还没有密钥，请先运行 --set」** | 看着像 bug | 沙箱是新目录 ⇒ 必须先 `--set` 设一把沙箱专用密钥 |
| 5 | ★ **靶场窗口被当敏感窗** | 用 pwsh 起的靶场 ⇒ 属主 `pwsh.exe` ⇒ 命中终端名单 ⇒ `ctl_click` code=3、`ctl_focus` code=7（等 20 秒）；换 python 起的 ⇒ 属主 `python.exe` ⇒ 命中硬拒名单 ⇒ 同样 code=3 | ⇒ **真动作测量必须用属主不在名单里的窗口**（记事本 `Notepad.exe`）；⇒ 这两条名单都是**故意的安全设计**，不是缺陷 |

### 5.4 ★ 「代理自己不能拆自己拉下的急停」

本轮实测：`ctl_focus` 成功后我**在同一坐标连点 8 次** ⇒ 触发 `action_guard` 的
`same_target_streak`（阈值 5）⇒ 第二次命中 ⇒ **自动拉下急停**（并连带吊销租约）。

⇒ 之后 `ctl_brake --action release` 返回 **code=9**，理由写明：
> ⛔ 解除急停是**人的动作**，agent 侧只允许 `ctl_brake` 的 `stop` / `status`。

⇒ 两条人路：① 面板「▶ 解除急停」按钮 ② 命令行 `AgentCtl.exe brake --action release --confirm-release`
（本轮用第二条解除，留痕 `brake_release` / actor=`cli`）。

⇒ ★ **这条设计的价值**：agent 连自己触发的急停都拆不掉 ⇒ 急停才是真的急停。

## 六、一句话总结

**能力边界**：26 个工具、四档闸门、免闸门的控制面 11 个。
**真正的边界不是「工具能做什么」，而是「拿到通行证之前什么都做不了」** ——
连 A 级只读感知都要证（契约没写清楚这点）。

**响应时间**：控制面与感知面 **17~38ms**（p50），
记忆库检索 **78ms** 是最慢的，窗口枚举有 **240ms** 长尾。
失败路径 fail-fast（25~42ms），但 `ctl_windows` 例外 —— 被拒也在干活。

**两个真问题**：`ctl_status` 序列化崩溃（**已修**，否则 agent 连状态都看不到）；
`ctl_verify` 对历史文件误报链断（**已定位未修**，需要你拍板是改验证器还是重排历史）。
