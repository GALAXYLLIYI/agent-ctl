## 一、这一轮做成的三件事

### 1.1 ★ 工具面瘦身（直击「agent 调用工具要迅速」）

**为什么改这里**：MCP 的 tools/list 载荷实测 55182 字节，其中 description 9906 +
input_schema 20102 = **30008 字符是纯文案**。★ **每一步 agent 调用都要重读这一整张表**
⇒ 文案越大，模型每步越慢越贵。这是「调用工具要迅速」里唯一能测、也最该测的量。

**剪的边界（不许越）**：
- 只剪**历史与机制细节**（某年某月补、实测多少节点、推导过程）；
  ★ **一条操作规则都不许丢**（禁令、口径、拒绝码、必填项全留）。
- 字段名 / type / required / enum / default / 码表**一个字不许动**（不许靠删字段换体积）。
- 搬走的正文落到 docs/AGENT接口.md **附录 A**（不许删了没处存）。

**结果**：

| 项 | 改前 | 改后 | 变化 |
|---|---|---|---|
| tools/list 线上载荷（实拉） | 55182 字节 | **48286 字节** | −12.5% |
| description | 9906 字符 | 8110 | −18.1% |
| input_schema | 20102 字符 | 18741 | −6.8% |
| 合计 | 30008 字符 | 26851 | −10.5% |
| 工具数 / 参数集合 / type / required / 码表 | — | **一字未改** | 冻结 |

★ 为什么只瘦了 10.5%（不是更多）：**结构（参数名 + type + required）本身就占约 10k 字符，一行不能动**；
能动的只有文案，而文案里几乎全是规则 ⇒ 真正可省的就是「历史与机制细节」这一块。
**本报告不把「我重写了描述」说成「体积问题解决了」。**

**判据**（tests/_P3_工具面瘦身_判据.py，7 绿）：体积上限（基线 90% 且 ≤27000）/ 工具集合 /
结构冻结 / **39 条必留句逐条点名** / 码表冻结 / 落点文档 / 线上载荷实测；
--inject（换回未瘦身基线）如期变红。

### 1.2 ★ 单例弹窗仲裁器（直击用户那句「为什么会有四个闸口弹窗访问我」）

**病根是实证的，不是猜的**：闸门日志（<上游项目仓>/tools/_auth/gate_agentctl.log）里
2026-10-21 **00:25:27 / 00:26:25 / 00:28:10 三笔授权请求重叠**，而第一笔直到 **00:29:10**
才被点掉 ⇒ 那一刻屏幕上最多同时有 **3 个弹窗**。
原因：并发 ctl_authorize **各自拉一个独立弹窗进程**。

**做法**（src/agentctl/popup_slot.py + core.t_authorize 接线）：
- 跨进程**单例槽**（槽文件在 AUTHDIR 下，原子创建取得），同一时刻只允许一个进程持有；
- 后到的请求**等**：拿到槽后先查证「现在这张证是否已覆盖我要的范围」
  ⇒ 覆盖就直接放行（**不再弹第二个**）；不覆盖才弹（此时前一个已关，屏幕上仍只有一个）；
- 等不到 ⇒ **fail-closed**（明确拒绝，绝不 fail-open）。
★ 语义没变：还是要人亲自在弹窗里输密钥，agent 拿不到明文。

**判据**（tests/_P0_单例弹窗_判据.py，6 绿；不弹真窗、不碰真通行证）：
并发 4 路 ⇒ 弹窗 **1 次**（注入「改前行为」⇒ 4 次 ⇒ 判据有判别力）／4 路都有结果（不饿死）／
单路语义不变／**跨进程** 2 路 ⇒ 1 次／拿不到槽 ⇒ 拒绝且弹窗 0 次／接线在 core 的授权路径上。

### 1.3 ★ 看门狗恢复提速（既开既用的另一半）

看门狗每 **20 秒**探一次端口 ⇒ 服务崩了最长 **20 秒不可用**。
改成 **3 秒**（本地 TCP connect 到没人听的端口是瞬时拒绝，探测代价可忽略）。

**实测**（A/B 各三轮，杀服务 → 端口回来）：

| | 第1轮 | 第2轮 | 第3轮 |
|---|---|---|---|
| 改前（20s 轮询） | 20.3s | 24.3s | 24.7s |
| 改后（3s 轮询） | **3.2s** | **6.9s** | **6.9s** |

★ **顺带查清一件被误判的事**：服务重启后 agent 的第一次调用要 ~430ms。
先怀疑是「服务进程冷启动」，于是给看门狗加了**服务级暖机**（起来后先自己调一次）——
**A/B 三轮实测无效**：暖机开 444/448/462ms（中位 448），暖机关 537/454/422ms（中位 454）
⇒ 差 5ms 没有意义。真相是：**热服务上新建会话的首调只要 19/26ms** ⇒ 那 430ms 不是服务冷启动，
另有原因（未查清，见 §四 backlog）。
⇒ **暖机代码已回退**，不拿一个没证据的「优化」冒充改进。
