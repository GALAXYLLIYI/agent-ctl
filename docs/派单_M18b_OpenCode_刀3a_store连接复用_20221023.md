## 〇、一句话

**`store.py` 每写一条事件就新建一个 sqlite 连接、并重设一次 `PRAGMA journal_mode=WAL`——改成连接复用 + PRAGMA 只设一次。**
只改 `store.py`，不碰 `core.py`（那是 ZCode 的）。预计这一刀是三刀里最可能拿大头的（core 侧事后段共 ~347ms）。

## 二、★ 风险（本刀唯一红线）

- **⛔ 不许砍 fsync / 审计完整性**：证据丢了就是事故。**「审计异步批量写」是明令禁项**——不许把落盘改成后台线程批量刷。
- **⛔ 不许改事件语义**：事件一条不少、字段不少、哈希链不断。
- 连接复用必须考虑：多线程并发写、进程重启后重连、连接失效（`database is locked`）时的重试、**跨进程**（多个进程各开一个连接 ⇒ WAL 下本来就能并发写，别引入新的锁竞争）。
- **不许引入「连接泄漏」**：长连接意味着文件句柄常驻 ⇒ 判据里要有「文件句柄数不增长」的断言（跑 1000 次事件后，句柄数回到基线 ±小量）。

### 9.2 根因（主控已逐行核对 `store.py`，行号以你动手时的盘上版本为准）

`store.py:446` 拿跨进程锁 → `store.py:447` 拿进程内锁 → `store.py:448` **每条事件都调一次** `_read_tail()`。

而 `_read_tail()`（`store.py:357-388`）做的是：`store.py:367` `sorted(self._jsonl_files())`（listdir 整个 timeline 目录）→ `store.py:371-380` **逐行读整个文件**且**每行都 `json.loads`** → 只为了取最后一条的 `seq` 和 `hash`。

⇒ **每写一条事件，就把当天整份 JSONL（今天已 6.02MB）逐行读一遍 + 每行 json.loads 一次。**
⇒ 事件数 N ⇒ 累计 O(N²)：写 100 条 ≈ 读 100 遍 6MB。**这才是「事后段 ≈347ms」的真正大头**（sqlite 那 0.8ms 几乎可以忽略）。

### 9.3 ★ 为什么不能简单删掉 `_read_tail`

`store.py:357-365` 的注释写得很清楚（M8 修复）：老口径取 `max(seq)` 那一行，**一旦链分过叉，`max(seq)` 未必是文件里的最后一行** ⇒ 真源会**从错误的位置续链**。
⇒ 「按**文件顺序**取最后一条有效记录」是 M8 的**正确性保证**，不是性能代码，**语义不许丢**。

### 9.4 改法方向（自己定，但必须满足下面全部约束）

1. **等价性第一**：读出来的 `(seq, hash)` 必须与现在的 `_read_tail()` **逐次完全相同**（含坏行/半行跳过、跨多个文件回退、`GENESIS` 兜底这些边界）。
2. **不许「只读最后一行」就完事**——文件末尾可能是**半行**（进程被杀 / 写入被打断）⇒ 必须做完整性检查。
3. 常见省法是**从文件尾部倒着读**（seek 到末尾分块回读），只解析最后若干行；**若没找到完整行再回退全量**。**回退路径必须保留**。
4. **不许用 sqlite 里的 `max(seq)` 代替**（那正是 M8 修掉的 bug）。
5. **不许改变锁语义**：读取仍在 `self._xlock` + `self._lock` 内（`store.py:446-448`）。
6. **不许砍 fsync / 审计完整性**；**「审计异步批量写」是明令禁项**。

### 9.5 判据追加（在 §三 的判据之外再加这四条）

1. **等价性**：造 5 个不同状态的 timeline 目录（空目录 / 只有空文件 / 末尾半行 / 中间有坏行 / 跨 3 个文件），**逐个比对新旧 `_read_tail()` 返回的 `(seq, hash)` 必须完全相同**。
2. **规模效应**：当天 JSONL 分别造 1MB / 6MB / 30MB 三档，量「每条事件写入的耗时」⇒ 新实现应**基本不随文件大小增长**（旧实现线性增长）。**三档数字列进报告**。
3. **坏行/半行不误判**：末尾半行 ⇒ 返回**上一条完整记录**（不是半行的内容，也不是 0）。
4. **先红后绿**：注入一个「读到半行当完整行」的缺陷 ⇒ 必须 **exit=1**。
