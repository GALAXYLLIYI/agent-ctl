## 2.5 ★★ 主控实测新情报（2026-10-22 01:05，你动手前**先读这一节**，别照 §2 的旧说法从零设计）

主控已把 `legacy_tools/act.py` 打开核对过，窗口A 的指认**属实**，而且**料比它说的还多**：

### 2.5.1 「变化即停」的原料**已经齐了**，不要重写采集层

- `act.py:2177 evidence(hwnd, tag)` → 调 `perceive.shot()` 抓帧并**落 PNG 到磁盘**
- `act.py:2188 _img_fp(path)` → 读回该 PNG 算 **md5**
- `act.py:2382-2410` 已经在做「before 指纹 → 动作 → sleep → after 指纹 → 比对」
- `act.py:2329-2331` 已有**反竞态**机制：「要求隔 0.25 秒两次读数完全一致才动手，否则宁可不点」
  ⇒ **这就是「变化即停」的雏形**，本单是把它系统化，不是从零发明。

### 2.5.2 ⚠ 但轮询**绝不能沿用 `_img_fp` 的整文件 md5**

- `_img_fp` 是**整个 PNG 的 md5** ⇒ 光标闪 5–7px 就变 ⇒ 这正是「整屏 hash 90.6% 恒变」的成因
- ⇒ 轮询必须换成**降采样/区域指纹**（仓内 `recorder.fingerprint` 实测 6.45ms/次；或降 1/4 灰度 + 阈值）
- 同时要叠 **`core.py:2507 _act_diff_of` 的窄边滤除（<8px）与 min_area 24px²**，
  否则 caret 会被当变化（本地 agent 与 窗口A 两边的口径都对：一边防 caret，一边防面积噪声）

### 2.5.3 ⚠ 轮询时**别把 PNG 落盘**（否则磁盘 IO 变成新瓶颈）

`evidence()` 每次都**写一张带时间戳的 PNG 到磁盘**，`_img_fp` 再**读回**算 md5。
若轮询每 30ms 走一次 `evidence()`，等于每 30ms 落一张全窗 PNG —— **会比省下来的 450ms 更亏**。
⇒ 轮询必须**内存内采样**（mss/bitmap 灰度降采样即可），**只把最终判变后的那一张落盘**
（与 M6 的「只在 changed 时落盘」同一口径，两单要共用同一套落盘策略，别各写一套）。

### 2.5.4 ★ `_settle` **已经是旋钮**（2026-10-19 改的）—— 零代码就能拿到第一组数据

```python
# act.py:1045
def _settle(default_ms):
    v = os.environ.get("AGENTCTL_SETTLE_MS")   # ← 旋钮
    if v is not None and str(v).strip() != "":
        return max(0.0, float(v) / 1000.0)
    return default_ms / 1000.0
```

⇒ **本单第 0 步可以先不改任何代码**：用 `AGENTCTL_SETTLE_MS` 扫 0/50/100/200/450，
在**同一组目标**上各跑 N 次，得到「延迟 vs 误判（点了没反应/重复点）」的曲线。
**这条曲线决定默认值该定多少**，比拍脑袋强。原始数据落盘。

### 2.5.5 ★ spawn 子进程的开销已实测（比 sleep 还硬）

| 项 | 实测 |
|---|---|
| python 冷启动 | **43ms** |
| `import perceive` | **123ms** |
| `import win32* + psutil` | **37ms** |
| **合计（每次动作的纯启动开销）** | **≈ 200ms+** |

`core.py:2731` 是 `_legacy("act.py", argv, timeout=...)` ⇒ **每次动作起一个新 python 进程**。
⇒ 这解释了 窗口A 说的「单动作 0.8–1.3s」：**200ms 启动 + 450ms sleep + 2 次全窗抓帧 + PNG 落盘/读盘**。

### 2.5.6 主控建议的**刀序**（按收益/风险排，你复核后可调）

| 刀 | 收益 | 风险 | 本单是否落地 |
|---|---|---|---|
| ① 固定 sleep → 「变化即停」轮询 | **300–400ms** | 中（TOCTOU ⇒ 配动作前重验） | ✅ 落地 |
| ② 证据比对走内存，轮询期不落盘 | 磁盘 IO + 几十 ms | 低 | ✅ 落地 |
| ③ 免 spawn / 常驻 worker 复用 | **200ms+** | 高（改架构，涉及常驻进程与三闸边界） | ❗**本单只出设计，不落地**（写清方案、代价、风险，交主控裁决） |

**为什么 ③ 不落地**：「不许起常驻进程」是本轮硬边界；把动作执行改成常驻 worker 还要重审三闸
（授权、租约、凭据在常驻进程里怎么管）。⇒ 本单给设计，主控决定是否另开单、是否请用户拍板。

## 4. 怎么做：不是「砍成 0」，是「换成就绪轮询」

### 4.1 铁律约束（不可协商）

- **不许把 sleep 直接改成 0。** 文献 TOCTOU（arXiv:2604.18860）实测「观测→动作」间隙平均 **6.51 秒**，
  这正是「点了但界面已变」的成因。砍掉等待会放大它。
- **unknown 永不当成功**：轮询超时 ⇒ 报「没测出来」，不报「没变」，必须给人看（铁律 11⑨）。
- 三闸不变：档位不由模型自省、逐任务授权、密钥即销毁。

### 4.2 判据（复用现成实现，别造轮子 —— 裁决 B2）

**直接复用 `core.py:2507` 的 `_act_diff_of`**：

- 阈值 2/255、caret <8px 窄边滤除、min_area 24px²、分块计数；
- 返回**三值** `changed`（True / False / **None=没测出来**）＋ 屏幕绝对坐标 bbox。

**区域划法（窗口A 口径，与 M6 补充 §2 一致）**：
目标窗客户区 ∩ 声明的 `expect_region`（有声明才细化），**永不整屏**。
脏区粗筛可加 16×16 下采样 dHash（MAD>6 或 hamming>6 才进精 diff）。

**两处要叠加才算完整**（本地 agent 口径）：
窄边滤除解决 caret ⇒ 还要**「连续 2 帧」滞回**解决动画区 ⇒ **两帧都判变才动手**。
可选增强（第二阶段，不必本单做）：64×64 瓦片 + 静止 1s 采 10 帧估**噪声地板**，
阈值取 `max(2%, 3×噪声)` 自适应。

### 4.3 轮询参数（给建议值，你实测后改）

- 首次采样间隔 **~16–30ms**（别 0），最多 2–3 次采样后给一个「初判」；
- 连续 2 帧判变 ⇒ 立即返回（≈ **32–60ms** 替换掉 250–500ms 的固定等待）；
- 总超时上限：按动作类型定（例如点击 800ms、填字 1500ms），超时 ⇒ 三值里的 **None**（没测出来），
  **不是 False**；
- 空闲时（无变化）才继续等；已稳定 ⇒ 立刻返回。

### 4.4 子进程复用

每动作 spawn 子进程的开销单独实测（`time.perf_counter` 直接计），
**能复用就复用，不能复用就把数字摆出来**（别为省事做缓存导致状态串味）。
