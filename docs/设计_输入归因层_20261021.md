## 0. 摘要

本层要回答一个问题：**本机每一笔输入动作，是 agent 做的、电脑前真人做的，还是远程/其他程序注入的？**

现在这个答案是**不存在的**。`timeline.db` 的 `events` 表里确实有 `actor` 字段，但那是 **agent 自报**的——
`codex`、`dsh`、`mcp-http`、`cli`、`判据26`……**全是 agent 自己写上去的**。电脑前真人敲的键、
远程程序注入的键，在事件流里**长一个样**：`kind='type'`、`actor='codex'`。
事后翻账本，没人能分清哪一笔是 agent 干的、哪一笔是人干的。

**本层不是再添一个 `actor` 字段，而是添一条**独立于 agent 自报**的证据链**：
从操作系统输入链路（低级钩子）直接观测事件，用**注入位**（`LLKHF_INJECTED` / `LLMHF_INJECTED`）
和 **timeline 对账**两条独立证据交叉判定。

**核心结论（本机实测，见 §7 与附录 C）：**

| 结论 | 证据 |
|---|---|
| 本机**可以**做输入归因 | 低级钩子装得上（`hMod=NULL`），回调链路通，注入位读得到 |
| 归因的**决定性证据**是注入位，不是 `actor` 字段 | 探针自注入事件 `flags=0x01`（`LLMHF_INJECTED`） |
| agent 自报的 `actor` 字段**不能**当证据 | 它是自证；本机时间线已有 38 条被覆盖、21 处断链 |
| **存在盲区**：DOM 级注入低级钩子看不见 | 本机 8 条真 agent 动作走 `insertText`/`dispatchEvent`，不经过 `SendInput` |
| 「捕捉图形变化 + 抓文字图像」**本机已经全有了** | UIA 191ms / CDP DOM / Windows OCR 926–1074ms / 指纹 6.45ms |
| **不建议训练识别器** | 覆盖率上现有通道已经够，训练只补 UIA/CDP 都瞎的长尾；详见附录 B |

## 1. 数据流

### 1.1 采集层（三条独立通道）

```
        ┌─ 通道 A：低级钩子（Win32 输入链路）──────────────────────┐
        │  WH_KEYBOARD_LL(13) / WH_MOUSE_LL(14)                  │
        │  SetWindowsHookExW(hMod=NULL)                          │
        │  事件字段：vkCode/scanCode/flags/time/dwExtraInfo/pt   │
        │  ⇒ 注入位 injected / lower_il                          │
        └─────────────────────────────────────────────────────────┘
                                    │
        ┌─ 通道 B：agent 自报（timeline）────────────────────────┐
        │  work/timeline/timeline-*.jsonl（真相源）              │
        │  seq/kind/actor/tool/t_wall/payload                   │
        │  ⇒ 谁自称做了什么、什么时候做的                        │
        └─────────────────────────────────────────────────────────┘
                                    │
        ┌─ 通道 C：环境上下文 ────────────────────────────────────┐
        │  完整性级别 / 会话 id / 是否远程会话(RDP) / 屏幕尺寸     │
        │  ⇒ 「电脑前的人」是否真在电脑前                         │
        └─────────────────────────────────────────────────────────┘
                                    ↓
                          ┌─────────────────────┐
                          │  归因判定（纯函数）  │
                          │  见 §2 判据表        │
                          └──────────┬──────────┘
                                     ↓
   ┌────────────────────┬──────────────────────────┬──────────────────────┐
   ↓                    ↓                          ↓                      ↓
 记账(哈希链)      实时流(只读订阅)          对账(与 timeline 交叉)   面板呈现
```

**为什么必须是三条而不是一条：**

- 只有 A：知道「是程序注入」，但**不知道是哪个程序**——注入位不携带发起方身份。
- 只有 B：那是 agent **自报**，自己说自己是自己，不是独立证据（而且本机已被证明会被覆盖）。
- A + B 才能闭合：「注入」+「时间窗内 timeline 有一条同类型的 agent 动作」⇒ agent。

### 1.2 记账层（账本）

**账本即 `timeline` 的事件流**，不另起一套存储——理由是本仓已有的铁律：
`store.py` 的 jsonl 是**唯一真相源**，SQLite 只是可重建索引，
且 `hash = sha256(prev_hash ‖ "\n" ‖ canonical(body))` 构成**哈希链**。

归因层要做的是**在同一条链上追加事件**，而不是在旁边另开一本账：

```python
st.append("input_attribution",
           actor="attr",                       # 记账者自己，不是被判定者
           tool="attr_probe",
           payload={
             "source": "agent",               # agent | human | remote_or_other | unknown
             "confidence": 0.80,
             "evidence": ["injected=True",
                          "timeline seq=3308 kind=click actor=codex tool=ctl_click"],
             "raw": {"device": "mouse", "flags": 1, "vkCode": None,
                     "x": 1510, "y": 280, "dwExtraInfo": 0,
                     "t_mono": 12345.6789, "t_wall": "2026-10-21T21:59:23.084+08:00"},
           })
```

**单写者纪律（必须）**：本机时间线已经因为**多进程并发写**吃过亏——
见 §7「顺手发现 ①」。归因层如果也用多进程 append，会**继承同一个缺陷**。
落地时必须做到：要么单写者，要么在 `store.append` 上加文件锁，要么**改用不依赖 seq 唯一性的事件 id**
（见 §3.4）。

### 1.3 对外暴露层

**本单只交付设计 + 探针 + 判据，不改 `contract/tools.json`**（派单明令禁改 contract）。
后续落地时建议新增一个只读工具 `ctl_attribution`：

```jsonc
// 建议的契约形状（**本单未落地**，只是设计）
{
  "name": "ctl_attribution",
  "description": "查询输入归因判定。只读，不产生任何输入。",
  "input_schema": {
    "type": "object",
    "properties": {
      "from":  {"type": "string"},   // 时间窗
      "to":    {"type": "string"},
      "source":{"type": "string", "enum": ["agent","human","remote_or_other","unknown"]},
      "min_confidence": {"type": "number", "default": 0.0},
      "limit": {"type": "integer", "default": 200}
    }
  }
}
```

**暴露时的硬规矩（沿用本仓「不许只给摘要，要给证据指针」的纪律）**：
每条判定都必须能回指到**原始行**——
`timeline seq` / 探针原始字段 / 钩子事件时间戳，**不许只给一个结论词**。

## 2. 归因判据表

### 2.1 证据字段（每条事件都记）

| 字段 | 来源 | 含义 |
|---|---|---|
| `device` | 钩子类型 | `keyboard` / `mouse` |
| `flags` | `KBDLLHOOKSTRUCT.flags` / `MSLLHOOKSTRUCT.flags` | **注入位所在字段** |
| `injected` | `flags & (LLKHF_INJECTED 0x10 \| LLMHF_INJECTED 0x01)` | 程序注入？ |
| `lower_il` | `flags & (LLKHF_LOWER_IL_INJECTED 0x02 \| LLMHF_LOWER_IL_INJECTED 0x02)` | 低层注入？ |
| `dwExtraInfo` | `ULONG_PTR` | 注入方自定义标记（**可选**，见 §5.2） |
| `vkCode` / `scanCode` | 键盘钩子 | 按键 |
| `x` / `y` / `mouseData` | 鼠标钩子 | 位置与滚轮/按键 |
| `t_mono` | `time.perf_counter()` | **单调钟**，不受系统时间改动影响 |
| `t_wall` | ISO8601 | 墙钟，与 timeline 对账用 |
| `fg_hwnd` / `hit_hwnd` | `GetForegroundWindow` / 落点归属 | 这次输入打到了哪个窗口 |
| `timeline_match` | jsonl 对账 | `{seq, kind, actor, tool}` |
| `agent_running` | jsonl 近窗 | 此刻有没有 agent 在动作 |
| `remote_session` | `GetSystemMetrics(SM_REMOTESESSION)` | 是不是远程会话 |

### 2.2 判据表（四档）

| 档 | 判定条件 | 置信度 | 误判情形（**必须知道**） |
|---|---|---|---|
| **agent** | `injected==True` **且** 对账窗口（±2.0s）内 timeline 有**输入类**动作（`ctl_click`/`ctl_type`/`ctl_keys`/`ctl_scroll`/`ctl_fill`）且 `tool` 类型与事件类型一致 | **0.80** | ① **别的程序**在同一 2 秒内也注入 ⇒ 被冤枉成 agent（远控工具 + agent 同时动作）。<br>② agent 的动作走了 **timeline 之外的口子**（如 DOM 注入，见 §5.1）⇒ 这条注入事件**对不上**，反被误判成「远程或他程序」。<br>③ 同一物理动作被 timeline 记成多条（click + focus）⇒ 取错行。 |
| **agent（弱）** | `injected==True` 且对上了 timeline，但那条是**感知类**动作（`ctl_focus`/`ctl_shot`/`ctl_screen`） | **0.60** | 只靠时间邻近，证据链只有一半。远控程序恰好在 agent 感知时注入 ⇒ 被误挂到 agent 头上。**这是最容易出错的一档**，所以置信度必须低于上一档。 |
| **真人** | `injected==False`（**无任何注入位**） | **0.90** | ① **远程会话（RDP）里的"人"**：`SM_REMOTESESSION` 为真时，键盘事件同样是物理的 ⇒ 置信降到 **0.55**，因为「电脑前的人」可能压根不在电脑前。<br>② **硬件级注入**（KVM、模拟器 USB 键盘）不置注入位 ⇒ 会被读成真人。**这是本层的固有上限。**<br>③ 屏幕外/被遮挡窗口的输入仍会经过钩子，但 `hit_hwnd` 可能为空 ⇒ 不能证明「打到了哪」。 |
| **远程或他程序** | `injected==True` 且**对不上** timeline 输入类动作 | **0.75**（agent 正在跑时降到 **0.55**） | ① **agent 的盲区**：agent 用 DOM 注入（`insertText`/`dispatchEvent`）或直接调 Win32 而没记账 ⇒ 真 agent 被误判成「远程或他程序」。**本机实测就有 8 条这种动作**（§5.1）。<br>② agent 记账了但**动作延后落地**（异步 UI 响应）⇒ 2 秒窗口不够。<br>③ 远控软件（RDP 剪贴板同步、输入法）产生的注入事件 ⇒ 归到这档是对的，但和「恶意程序」分不开。 |
| **未知** | `flags` 读不出来（钩子没装上 / 事件字段残缺 / 完整性级别不够） | **0.00** | **这一档不许被硬猜成任何其它档。**本仓纪律：`code=8` 时要区分「没点到」和「点了没生效」，同理这里要区分「没观察到」和「观察到是真人」。**没有判据就不猜。** |

### 2.3 判据的三条不变式

1. **注入事件永远不能读成「真人」**——`injected==True` 时，真人档**不可达**。
   （`tests/_P1_输入归因_判据.py` 的 `--inject` 注入的正是这个缺陷，判据必红。）
2. **证据越弱，置信越低**——不许「全都 0.9」。
3. **未知是一等公民**——`flags` 不可读 ⇒ 落「未知」，并**如实说"没观察到"**，不许拿邻近证据补。

## 3. 失败与降级语义

**总原则：宁可说"没观察到"，不许说"是真人"。**
理由：本层的产出是**指控**。把「没看见」写成「是真人」，等于替真正的注入背书。

### 3.1 钩子装不上

**本机实测的两个真实原因（都已定位并解决）：**

| 症状 | 真实原因 | 处理 |
|---|---|---|
| `SetWindowsHookEx` 返回 `NULL`，`GetLastError()=126` (`ERROR_MOD_NOT_FOUND`) | **`hMod` 传了 exe 的模块句柄**。文档规定：钩子过程在当前进程内时 `hMod` **可为 NULL**。传 exe 句柄 ⇒ 系统当成 DLL 去找 ⇒ 126 | **`hMod=NULL`**。本机实测：`hMod=NULL` ⇒ 装得上（`hhook` 非 0，`err=0`）；`hMod=exe` ⇒ 必失败 126 |
| 钩子装上了但收不到事件 | 装钩子的线程**没有消息泵**。低级钩子在**安装它的线程**上下文里被调用 | 主线程必须跑 `GetMessageW` 循环 |

**降级说法：**

- 两个钩子都失败 ⇒ **归因层整体不可用**，事件流里记一条
  `kind='input_attribution_unavailable'`，`payload={'reason':'SetWindowsHookEx failed, err=126', ...}`，
  对外暴露的 `ctl_attribution` 返回 **`{"available": false, "reason": ...}`**，
  **不许返回空列表冒充"这段时间没有注入事件"**——那是把「没观察到」说成「安全」。
- 只装上一个（键盘装了鼠标没装）⇒ **半可用**：`source` 仍给四档，
  但**每个事件必须带 `coverage` 字段**（`keyboard` / `mouse` / `both`），
  面板上必须显示"鼠标事件未覆盖"。
- 完整性级别不足（探针是 Medium `S-1-16-8192`，见 §7 顺手发现 ③）⇒
  **看不见比自己级别高的窗口的输入**。这不是 bug，是 Windows 的硬边界，
  但**必须写出来**，否则用户会以为"没看到注入 = 没有注入"。

### 3.2 事件丢失

低级钩子有两个已知丢事件的口子：

| 机制 | 表现 | 降级说法 |
|---|---|---|
| `LowLevelHooksTimeout`（默认 5s） | 回调超时 ⇒ Windows **静默摘掉钩子** | 探针每轮**必须重新 `GetModuleHandle` 校验钩子仍在**：句柄非 0 不代表还活着。**探针已经做到：回调里不做任何 I/O，只 append**（`tests/_attr_probe.py` 的 `EVENTS.append`），实测 6 秒窗口零阻塞 |
| 钩子被**系统或安全软件摘掉** | 回调不再触发 | 记账时记 `hook_alive=false`，归因降级为「未知」，**不许把"突然没有事件"读成"没人操作"** |
| 事件本身残缺（`flags` 读不出来） | 字段异常 | 落「未知」档（§2.2） |

### 3.3 时钟漂移

本仓 `clock.py` 已经有一套现成的时钟纪律，**归因层必须复用，不许自己另发明一套**：

- `t_mono = time.perf_counter()`：**单调钟**。系统时间被人改，**不影响**事件之间的先后。
- `t_wall = ISO8601`：墙钟。**只用于跟 timeline 对账**。
- `clock.Clock.drift_report()`：用锚点对拟合 `wall ≈ a + b·mono`，
  `|b-1| > 0.02` ⇒ 判定"时钟被改"；残差跳变 > 1500ms ⇒ "中途被改一次"。

**归因层的降级说法：**

1. 对账**一律用 `t_wall`**（timeline 只有墙钟），但**同时记 `t_mono`**。
2. 一旦 `drift_report()` 报"时钟被改"，**对账结论一律降置信**（统一 −0.15），
   并在 `evidence` 里附 `clock_drift`。
3. **时钟被改 ⇒ 对账结果只能当"候选"，不能当"结论"。**
   因为攻击者改系统时间正是为了让「注入事件」和「agent 动作」在墙钟上错开。
   ⇒ **单调钟对账是必须的第二通道**：如果 agent 侧也记 `t_mono`
   （`store.append` **本来就有 `t_mono` 字段**），就能做**不受时钟影响的**对账。
   **本单实测**：timeline 的 `t_mono` 字段确实存在且逐条有值（`store.py:161` 写 `time.perf_counter()`），
   ⇒ **单调钟对账这条路是通的**，落地时优先用它。

### 3.4 链断了怎么办

本机时间线**现在就有 21 处断链 + 38 条重复 seq**（§7 顺手发现 ①）。
归因层若把归因事件写进同一条链，**就会继承这个毛病**。

**降级语义：**

- 归因事件**自己**必须能被单独验：`Store.verify()` 断在归因事件上时，
  要能区分"是归因层写坏了"还是"是别处先坏了" ⇒ 归因事件的 `payload` 里**自带** `prev_hash` 上下文，
  便于二分定位。
- **重复 seq 绝不能静默覆盖**。本机 `store.py:173` 用的是
  `INSERT OR REPLACE` ⇒ 后写的**覆盖**先写的，**旧事件凭空消失**（实测少 38 条）。
  ⇒ 落地时归因层**要么**保证单写者，**要么**改用不依赖 `seq` 唯一性的 id
  （推荐：归因事件用 `payload.evidence.raw.t_mono + device + vkCode` 做内容寻址 id）。

## 4. 与现有 `timeline.db` 的对账

### 4.1 对账口径（硬规矩）

> **真相源是 `work/timeline/timeline-*.jsonl`，不是 `timeline.db` 的 `events` 表。**

**本机实测（`tests/fixtures/attr_probe_out.txt` §⑥ 与判据 ⑫）**：

| 量 | 实测值 | 出处 |
|---|---|---|
| jsonl 文件数 | 14 个 | `work/timeline/timeline-*.jsonl` |
| jsonl 事件行 | **3354** | 逐行数 |
| SQLite `events` 行 | **3316** | `select count(*) from events` |
| **差** | **38 条** | 重复 seq 被 `INSERT OR REPLACE` 覆盖 |
| 链断点 | **21 处** | 用 `store.compute_hash` 公式复算 |
| 首个断点 | `timeline-20261007.jsonl` seq=78 kind=`authorize_request` actor=`panel` | 复算定位 |

⇒ **SQLite 索引比真相源少 38 条。**拿 `events` 表做对账，会**漏掉 38 条真事件**，
且这些漏掉的事件**恰恰是最早写入的那几条**（被覆盖的是先写的）。

### 4.2 对账算法

```
对每条钩子事件 E：
    W = 对账时间窗（默认 ±2.0s）
    候选 = { R ∈ jsonl | |R.t_wall - E.t_wall| ≤ W 且 R.kind ∈ 输入类 }
    其中 输入类 = {click, type, keys, scroll, fill}          ← 只认输入类，不认 shot/screen/focus
    若 候选为空 ⇒ E 走「远程或他程序」分支
    否则：
        取 dt 最小者 M
        若 M.tool ∈ {ctl_click, ctl_type, ctl_keys, ctl_scroll, ctl_fill} ⇒
            source=agent, confidence=0.80
        否则 ⇒
            source=agent, confidence=0.60（弱证据：M 是感知类动作）
```

**两条必须写死的细节：**

1. **只认输入类 kind。**本机实测 `click=470 / type=87 / keys=51 / scroll=18 / fill=10`
   ＝ 输入类 **636** 条；而 `focus=149 / shot=512 / browser=188` 是感知类，
   **不能**拿来当"输入是 agent 做的"的证据——那是**拿感知冒充因果**。
   （本仓已有同款纪律：`core.py:2367` 「必须在**动作前**就拍：事后补拍无法归因」。）
2. **时间基准优先单调钟。**timeline 每条事件都带 `t_mono`（`store.py:161`），
   而探针也记 `t_mono`。两者**不同进程**，`perf_counter` 的零点不可比，
   ⇒ 需要一个**会话锚点**把两边的 `t_mono` 对齐（`clock.Clock.session_open()` 就是干这个的）。
   墙钟对账作为兜底，并受 §3.3 的漂移规则约束。

### 4.3 对账结果怎么对外说

- **对上了** ⇒ 给 `timeline seq`（**证据指针**），用户可自己去翻那一行。
- **对不上** ⇒ **必须说"对不上"**，并把该时间窗内的 timeline 行**列出来**
  （哪怕是空的），让人能自己判断"是真没有，还是我没找到"。
  **不许只回一个 `remote_or_other` 词。**

## 5. 盲区（本层看不见什么）

**这一节是本设计最重要的部分之一：把"看不见"写清楚，比把"能看见"吹漂亮重要。**

### 5.1 盲区①：DOM 级注入完全不可见 ★最要紧

本机实测：时间线里 `ctl_browser` 事件 **189** 条，其中带 `js` 的 **130** 条，
**8 条**用了 `insertText` / `dispatchEvent` / `execCommand`（例如 seq=3308 的
`document.execCommand('insertText', ...)`、seq=3309 的 `new MouseEvent(...)`）。

**这 8 条是货真价实的 agent 动作，但低级钩子一个也看不见**——因为它们**根本不经过
`SendInput`**，而是在渲染进程里直接改 DOM。

**后果**：这 8 条会在归因层落进「远程或他程序」档（因为注入 + 对不上 timeline）。
**这是误判，不是发现入侵。**

⇒ **落地要求**：归因层**必须**额外消费 timeline 里的 `ctl_browser` 事件，
把 DOM 注入**从 timeline 侧补回来**（`source=agent`，`evidence` 注明"DOM 注入，钩子不可见"）。
⇒ 统计口径要写明：**钩子覆盖率 ≈ 636 / (636 + 8) ≈ 98.8%**（按当前时间线的动作分布估）。

### 5.2 盲区②：`dwExtraInfo` 不带身份

`KBDLLHOOKSTRUCT.dwExtraInfo` 是注入方可以自定义的标记位。
**agentctl 现在的 `SendInput` 没有设置它**（探针实测自注入事件 `extra=0x0`）。
⇒ 就算将来对上了时间，也只能靠时间邻近，**拿不到"是哪个进程注入的"**。
⇒ **建议（不在本单范围）**：agentctl 的 `SendInput` 调用统一带上一个专属
`dwExtraInfo` 魔数（如 `0xA6E17C71`）。这样归因层能**一票确定**"这是 agent"，
不再依赖时间邻近——**这是投入产出比最高的一个改动**（改一处、收益直接砍掉一整类误判）。

### 5.3 盲区③：完整性级别

探针跑在 **Medium 完整性**（`S-1-16-8192`，实测）⇒ **看不见高完整性（管理员）窗口的输入**。
被提权的程序对归因层**完全隐形**。

### 5.4 盲区④：硬件级注入

KVM、模拟器 USB 键盘/鼠标产生的是**物理输入**，不置注入位 ⇒ 被读成「真人」。
**这是原理性上限，不是实现缺陷。**本层对这一类**无解**。

### 5.5 盲区⑤：远程会话里的"人"

RDP 会话中键盘事件同样是物理的。`SM_REMOTESESSION` 为真 ⇒ 真人档置信度必须降到 **0.55**，
并标注「"电脑前的人"可能不在电脑前」。本机当前 `remote_session=False`（会话 id=1）。

## 6. 安全不变量（本层自身的红线）

1. **不拦截、不吞噬、不改写输入。**
   钩子回调**永远返回 `CallNextHookEx` 的结果**；任何异常路径**兜底 `return 1`**。
   ★ 特别注意：`ctypes` 在回调里抛异常时会**忽略异常并返回 `None`**（`None → 0`），
   **那就等于吞事件**。⇒ 必须像 `tests/_attr_probe.py` 那样在最外层兜一层 `except: return 1`。
2. **永不调用 `BlockInput`。**
3. **本仓已有的禁令要遵守**：`src/agentctl/widget.py:409` 已经把
   `SendInput`/`keybd_event`/`mouse_event`/`BlockInput`/`SetCursorPos`/
   `SetWindowsHookEx`/`RegisterRawInputDevices` 全列为**只读挂件禁用 API**。
   ⇒ 归因层**必须是独立模块**（未来落 `src/agentctl/attribution.py`），
   **不得放进 `widget.py`**；`widget.py` 的自检红线保持不变。
4. **不读密钥**：归因层只碰 `timeline-*.jsonl` 的
   `seq/kind/actor/tool/t_wall` 五个字段，**不复制 `payload` 正文**
   （payload 里可能有用户输入的私密内容——本机时间线里就有整段的工作单原文）。
5. **探针必须可自证、必须能自己退出**：
   ① 自证——自注入一次**零位移**事件，证明「钩子装上了 + 回调确实被调用 + 注入位读得到」；
   ② 自退——`--seconds N` 到点 `PostThreadMessageW(WM_QUIT)`，**无常驻**。

## 7. 顺手发现（**未自行开工，仅回报**）

### ① 时间线有 38 条事件被 SQLite 静默覆盖 + 21 处断链 ★最严重

- **实测**：`work/timeline/timeline-*.jsonl` 共 3354 行；`timeline.db` 的 `events` 表只有 **3316** 行。
  差额 **38** = **重复 seq 的组数**。原因是 `store.py:173` 用
  `INSERT OR REPLACE ... (seq ... PRIMARY KEY)` ⇒ **后写的覆盖先写的**。
- **断链 21 处**，首个断点 `timeline-20261007.jsonl` seq=78 kind=`authorize_request` actor=`panel`。
- **根因**：多个进程**各自**持有 `Store` 实例，各自在启动时 `_load_head()` 读链尾，
  于是**并发 append 时 seq 撞车**、链分叉。`store.py:52` 的锁是**进程内** `threading.RLock`，**跨进程无效**。
- **为什么重要**：**这直接关系到本单**。归因层要往这条链上写事件 ⇒ 会**继承同一个缺陷**。
  ⇒ 落地前必须先解决单写者/文件锁，否则归因事件也会被静默吞掉。
- **建议**（不在本单范围）：`store.append` 加**跨进程文件锁**（`msvcrt.locking`），
  或把 `seq` 换成内容寻址 id。**这条建议优先级高于本单本身。**

### ② agent 的 DOM 注入对操作系统输入链路完全隐形

见 §5.1。8 条真 agent 动作低级钩子看不见。
⇒ 归因层必须**双通道**（钩子 + timeline），单靠钩子会误判。

### ③ `SetWindowsHookEx` 的 `hMod` 必须传 NULL（否则 126）

实测：传 exe 模块句柄 ⇒ `ERROR_MOD_NOT_FOUND (126)`；传 `NULL` ⇒ 装得上。
这条已固化进 `tests/_attr_probe.py` 的注释里。**任何后来人写钩子都会踩这个坑。**

### ④ DPI 感知不是可选项

实测：本机 150% 缩放下，DPI-unaware 进程的 `GetCursorPos` 给**逻辑坐标**（1510, 280），
而低级钩子给**物理像素**（2265, 420）——**差 1.5 倍**。
不设 `PER_MONITOR_AWARE_V2`，两套坐标永远对不上，任何按坐标的对账都会错位。
（探针已设，且自检实测位移 `[0, 0]`。）

### ⑤ `agentctl` 服务当前**未运行**

实测 `http://127.0.0.1:8760/v1/status` 连接被拒（`127.0.0.1:8760`）。
⇒ 归因层的"对外暴露"目前**没有服务端可挂**。本单的探针是**独立进程**，
不依赖服务，**因此判据仍能真跑**（判据 ⑧⑨⑩⑪ 全绿）。

## 附录 B：「要不要训练一个识别器」的结论与理由

> 用户原话：**「捕捉图形变化 + 抓文字图像」**，并问**值不值得训练一个识别器**。

### B.1 结论

> **不建议现在训练。**
> 本机已有的 **UIA（结构）→ CDP（DOM）→ Windows OCR（像素文字）** 三层通道，
> **加上**指纹变化检测，**已经覆盖了本机绝大多数真实操作**。
> 训练一个识别器的**边际收益远小于它的成本**，而且**解决的不是当前的瓶颈**。

### B.2 为什么（逐条对照「投入」与「产出」）

**投入（真实成本，不是拍脑袋）：**

| 项 | 成本 | 说明 |
|---|---|---|
| 标注 | **最大头** | 要教模型"这个像素块是个按钮"，就得标 bbox。哪怕只覆盖 20 个常用窗口，每个标 100 个元素 = **2000 个标注**。按每个 30–60 秒计 = **17–33 小时**纯人工。 |
| 训练算力 | 中 | 本机**没有 GPU 训练环境**（无 torch/tensorflow，装它们就违反"禁止装依赖"）。⇒ 只能走云端 ⇒ 引入数据出境与复现成本。 |
| 迭代 | 持续 | 换应用、换主题、换缩放比（**本机 150%**）、换深浅色 ⇒ 模型持续掉点，要**持续标注**。 |
| 基础设施 | 中 | 推理端要维护模型文件、版本、灰度、回滚。 |
| **真源冲突** | **高** | 本仓铁律：`.gitignore` 排除 `work/`，新 clone 机器**跑不红**。模型权重放哪、怎么保证「换台机器结论一致」——**没答案。** |

**产出（真实收益，且要扣掉已有的部分）：**

| 想要的能力 | 本机**已有**的等价物 | 训练能多拿到的 |
|---|---|---|
| 「画面变了吗」 | `recorder.fingerprint` + `fp_diff`（**6.45 ms / 0.10 ms**） | **0**。这一项**根本不需要识别器**，是指纹的事。 |
| 「文字是什么」 | **Windows.Media.Ocr**（926–1074 ms，中文） | **≈0**。OCR 不该自己训——通用中文 OCR 训不过官方引擎。 |
| 「这是个什么控件 / 点哪」 | **UIA 树**（191 ms，结构精确，含 uid/stable key） | 只在 **UIA 瞎了的自绘界面**上多拿一点。 |
| 「网页里点了哪」 | **CDP DOM**（毫秒级，元素级精确） | **0**。 |
| 「变的那个东西在哪」 | `eye.region_diff` + `diff_box_to_screen`（变化 bbox） | 部分。 |

**关键算式：**

```
现有通道覆盖 ≈ 636/644 ≈ 98.8% 的 agent 输入动作（§5.1 实测）
"必须靠训练才能做对"的剩余部分
    = UIA 瞎 + DOM 瞎 + 文字也不是 OCR 能读的那一小块
    ≲ 1%，且**主要是长尾应用**
⇒ 训练投入 ≈ 数天到数周 + 持续标注
   训练收益 ≈ 那 1% 里的一部分，且**置信度还不如 UIA 精确**
```

### B.3 什么情况下**才**值得训练（先记下来，别现在做）

**触发条件（满足任一才重新评估）：**

1. **点名到具体应用**：明确说出"我就要在这个软件里自动化"，且该软件 **UIA 与 CDP 双瞎**（先验证，别假设）。
2. **覆盖面成为瓶颈**：开始做**跨应用的通用 agent**（不限这几个窗口），此时长尾才累积成规模。
3. **需要像素级接地**：任务要求"找到那个图标/那张图/那个色块"，而 UIA 给不出语义。

**真要训练时的最小可行路线（不训练大模型）：**

| 方案 | 成本 | 覆盖 |
|---|---|---|
| **模板匹配 / 特征点**（OpenCV `matchTemplate` / `ORB`） | **小时级**，零标注 | 固定位置的图标/按钮 —— 解决 80% 的"自绘界面"问题 |
| **多模态大模型现成 API 视觉** | 按量付费 | 通用，但慢、贵、坐标不稳 |
| **真训一个检测器** | 天～周 | 只在模板匹配打不住的**动态布局**上 |

⇒ **顺序永远是：模板匹配 → 现成视觉 API → 自己训。**
**先训模型是最贵的路，不是最快的路。**

### B.4 与本单主线的区别（别混了）

- **附录 B 回答的**是「要不要自己训一个识别器」。
- **本单主线**是「谁在操作这台机器」——**归因层**。
- 两者**共用**同一批感知通道，但**不是同一件事**：
  归因层要的是**输入事件的来源**，靠的是**钩子的注入位**，**不是**图像识别。
  ⇒ **归因层的落地**完全不依赖"训练识别器"。两件事**不要捆在一起做**。
