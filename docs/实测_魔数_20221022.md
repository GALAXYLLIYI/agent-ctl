### 1.1 定在哪、为什么

| 项 | 决定 |
|---|---|
| 定义位置 | **`legacy_tools/_src/inject_magic.py` 的 `INJECT_MAGIC`**（新增文件，29 行） |
| 值 | **`0xA6E17`**（十进制 682519） |
| 谁引它 | ① 真源 `act.py`（注入方）；② 判据 `tests/_P2_魔数_判据.py`（判定方）；③ 将来的 `src/agentctl/attribution.py`（M5）—— **同一个定义，不是各写一个数** |
| 为什么不是写在 act.py 里 | 注入方与判定方**必须用同一个数**；各写一个 ⇒ 今天 0xA6E17、明天 0xA6E18 ⇒ 归因**静默失效**（而「归因说不是 agent、其实是 agent」是最坏的一类错） |
| 为什么这个值 | 非 0 ⇒ 与「没带标记」的注入（`dwExtraInfo = NULL = 0`）**天然可区分**；不是任何常见 Win32 tag；`ULONG_PTR` 装得下（x64 8 字节 / x86 4 字节） |
| **主控前提的一处更正** | 主控说「SendInput 路径在 `legacy_tools/act.py` 与 `src/agentctl/core.py` **两边都有**」——**实测不是**：`src/agentctl/core.py` **没有**任何 SendInput 注入（它走子进程调 legacy `act.py`，`core.py` 里只有注释提到 SendInput）。⇒ 实际注入点**只有 4 个，全在 `legacy_tools/_src/act.py`**（`send_scan` / `send_mouse` / `send_unicode` / `send_vk`）。「单一真源」的要求因此**成立且已满足**。 |

| 注入点 | 改前 | 改后 |
|---|---|---|
| `send_scan`（扫描码） | `KEYBDINPUT(0, scancode, flags, 0, None)` | `KEYBDINPUT(0, scancode, flags, 0, inject_magic.INJECT_MAGIC)` |
| `send_mouse`（鼠标） | `MOUSEINPUT(x, y, data, flags, 0, None)` | `MOUSEINPUT(x, y, data, flags, 0, inject_magic.INJECT_MAGIC)` |
| `send_unicode`（中文/emoji） | `KEYBDINPUT(0, _u, flags, 0, None)` | `KEYBDINPUT(0, _u, flags, 0, inject_magic.INJECT_MAGIC)` |
| `send_vk`（虚拟键/快捷键） | `KEYBDINPUT(vk, 0, flags, 0, None)` | `KEYBDINPUT(vk, 0, flags, 0, inject_magic.INJECT_MAGIC)` |

**唯一一处「顺手必须改」**：`dwExtraInfo` 的字段类型由 `ctypes.POINTER(ctypes.c_ulong)` 改成 `ctypes.c_size_t`。
理由只有一个：**要能把魔数填进去**。
Win32 的定义是 `ULONG_PTR dwExtraInfo`（指针宽度的无符号整数），老代码把它声明成「指针」——
宽度**恰好相同**（x64 8 字节 / x86 4 字节）⇒ **结构体布局一个字节都不变**，`sizeof(INPUT)` 改前改后都是 40；
但语义是「指针」⇒ 填不进值。改成 `c_size_t` 后宽度不变、语义正确 ⇒ 老代码的 `None`（= NULL = 0）仍然合法。

**没有顺手动的任何别的东西**：闸门、租约、坐标换算、DPI、扫描码逻辑、白名单 —— 一律未碰。

### 2.1.0 ★ 证据类型必须分清（不许让读者误以为有系统级证据）

| 证据 | 是什么 | 能证明什么 | **不能**证明什么 | 本轮状态 |
|---|---|---|---|---|
| **B 组 ④⑤⑥** | **API 边界的实参截获**：在驱动进程里包装 `SendInput`，读出它真正传进去的 `dwExtraInfo` | 「产品确实把魔数 `0xA6E17` 塞进了 API 实参」「非 agent 注入的实参是 `0x0`，可区分」 | ❌ **不等于**「在系统里观测到该事件」——它没经过系统的事件分发与钩子链 | ✔ 绿（实参实测 `0xa6e17` / `0x0`） |
| **C 组 ⑦** | **系统级观察**：判据进程自己的低级钩子，观测事件**到达钩子回调**时携带的 `dwExtraInfo` | 「这个事件真的带着魔数到了系统里」 | —— | ⚠ **验不了**（本机此刻钩子链对我们不可达：SendInput 返回 1、窗口站/桌面一致，但回调一次都没被调用；M2 探针 10-21 收得到、今夜收不到 ⇒ 环境差异） |

⇒ **本单没有系统级证据**，只有 **API 边界的实参截获**（B 组）。判据输出与本文档都按这个口径措辞（**铁律：unknown 永不当成功**）。
（`docs\AGENT接口.md` §5.5 末尾同样标了 C 组钩子在本机此刻「验不了」。）

**安全不变量**：从不调 BlockInput；钩子回调永不返回 0；注入用 **VK_F24（0x87，极少被绑定）**；鼠标用「绝对移动到光标当前像素」⇒ **实测位移 [0,0]**（判据每次都打印，不自夸）。
**★ 失效保护**：取不到当前光标像素就**放弃那次注入** —— ABSOLUTE 模式下 `(0,0)` 的含义是「屏幕左上角」⇒ 会把用户的鼠标甩到角上（**用户玩网络游戏时绝不允许**）。
（真零位移只有两种安全写法：① 绝对移动到**当前光标像素**（本判据与真源 `act.send_mouse` 同法）；② 相对移动 `(0,0)` 且不带 `MOUSEEVENTF_ABSOLUTE` —— 但 Windows 会把「相对 (0,0)」**优化掉** ⇒ 不产生事件，故不能用作观测手段。）

### 2.1.1 ★ C 组（钩子·系统级观察）的泵怎么写的（主控指出的坑，已修）

低级钩子的回调是**靠消息投递**给「装钩子的那个线程」的 ⇒ 那个线程不泵消息，回调就永远不执行、`EVENTS` 一直是空的。判据现在：

1. **自己声明 `PeekMessageW` 的 argtypes**（`POINTER(MSG), c_void_p, UINT, UINT, UINT`）——
   ★ 探针只声明了 `GetMessageW`；不声明 argtypes 时 ctypes **按 int 传指针** ⇒ 调用直接失败 ⇒ 泵根本没生效。
2. **主泵用 `GetMessageW` 阻塞 + 定时 `PostThreadMessageW(WM_QUIT)`**（与 M2 探针 `_attr_probe.py:546-547` 同法），`PeekMessageW` 作兜底清残留。
3. **泵覆盖「注入之后 → 读之前」整段**：子进程跑着的时候一直泵（每 0.6 s 一轮），子进程结束后**再补泵 2 s** 再读 `EVENTS`；不是「注入完 sleep 完再一次性补泵」。
4. 注入由**独立子进程**发起（被测物只在子进程里 import），判据进程**只装自己的钩子、只读自己的 `EVENTS`**。
