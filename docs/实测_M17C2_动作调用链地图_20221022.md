## 三、§1.3 与 A 线交叉核对（886.6ms 里哪些是「A 线那种一次性」）

### 3.1 先把「一次性」拆成三种，否则会得出错误结论

A 线的「一次性」是**进程级**的：一个进程只付一次。但动作链里**每个动作都是一个新 act 进程**（`core.py:3239` → `subprocess.run`），所以：

| 类型 | 例子 | 在 886.6ms 里的地位 |
|---|---|---|
| **真·一次性**（core 进程内只付一次） | `framecache` 的 `import numpy`（`framecache.py:442`）、`uia_tree` 模块、`gate` 模块、`store()` 构造时的 `_load_head`（`store.py:219`） | 只有**第一次动作**付；后续动作免费。**不属于** 886.6ms 的稳定成分 |
| **伪·一次性**（act 进程内只付一次，但每动作一个新进程） | act 的 83.5ms import、自检 `find_spec`（`129`）、`whitelist.json`（`617`）、`post_compat.json`（`1015`）、`uiautomation`（`1830`）、`PIL`（`1146`/`perceive:46`）、`win32ui`（`perceive:45`）、`numpy`（`framecache:442`） | **每个动作都重付**。这就是 A 线「import 只占 8.3%」与「真实 click 一定 ≥83.5ms」的差别所在 |
| **每步重做**（同一次动作内重复） | 两张证据 PNG、基线 BMP 解 2 次、`gate` 读 2 次、`gate.log` 2 次、`PrintWindow` 轮询 N 轮 | 不随进程复用而减少；只能改机制 |

**一句话回答派单的提问**：886.6ms 里**没有**「A 线那种真正只付一次」的成本——因为 act 是短命进程。凡是「进程内只付一次」的（import、自检、UIA 初始化、两个 JSON），**每一个动作都重付**；真正能摊薄的只有 core 进程里的那几项（numpy、UIA 模块），而它们本来就不在这 886.6ms 的 act 侧。

### 3.2 算术：0.9s 装不进 886.6ms

```
A 线三个数：31.7（进程创建） + 83.5（import） + 886.6（其余） = 1001.8ms   （A:11-13）
若 S1 的 900ms 完整发生在这一次：
    886.6 − 900 = −13.4ms   ⇒ 剩下所有事（截图/UIA/闸门/JSON/注入）要在负数里完成
```

⇒ **结论**：A 线那个 1001.8ms 样本，**大概率没有吃满 0.9s**（目标当时就在前台，`act.py:1729-1731` 直接返回）。0.9s 仍然是**其他样本**的头号候选，但它**不能解释这一次的 886.6ms**。
⇒ 这是一个**排他性结论**，不是猜测：只要三个数同源，900 > 886.6 就是硬矛盾。

### 3.3 A 线的「190ms import 上限」漏了 numpy

A:203 的推断是：`83.5 + PIL 32 + UIA 77 ≈ 190ms`。但静态看，**真实 click 一定会走到 numpy**：

```
do_click → _wait_effect(2906) → _img_diff(1258) → framecache.diff_images(1274)
         → framecache.py:442  import numpy as np
```

A:155 也记了 `act.py:1280` 这条 numpy，但把它归到「函数内、本次 no-arg 入口没触发」。真实 click 会触发。按 A:196-201 的增量做**上界**相加：

| 口径 | 组成 | 静态上界 | 占 1001.8ms |
|---|---|---:|---:|
| core 驱动的 `--xy --coord` click | 83.5 + PIL 32.2 + win32ui 47.7 + numpy 98.4 | **≈261.8ms** | 26.1% |
| 直接 `act.py click --name` | 上面 + uiautomation 77.2 | **≈339.0ms** | 33.8% |

⚠ 这是**推断**：A 的增量是「首次用到时新增 cumulative」，模块间可能有共享依赖（例如 win32ui 是否已拉过 PIL 的一部分），直接相加会**高估**。但它足以说明一件事：**A 的 190ms 是下限侧的上界，不是上界侧的上界**。C1 的 P0→P1（见 §5）就是用来把这块钉死的。

### 3.4 886.6ms 的静态「可解释下限」

只算**必做且机制上不可能为 0** 的项（都用注释值/报告值，不当实测）：

| 项 | 量级 | 出处 |
|---|---:|---|
| `click_at` 固定等待 | 130ms | `act.py:2359/2361` |
| `import numpy`（P2-20） | ≈98.4ms | A:197 |
| 两张整窗证据 PNG + 编码 | ≈86~156ms | `act.py:2730`（43/78 各一张） |
| 基线 BMP 解 2 次 | **未核到** | `act.py:2759/1485` |
| 过闸（读 2 写 1 日志 2 + 锁） | ≥12.9ms（仅写回一项） | A:362 |
| `_wait_effect` 轮询（2 帧滞回 + 50ms 间隔） | ≈100~450ms（由注释值与 `1415/1461` 推算） | `act.py:1415/1461` |
| **合计（不含未核到项）** | **≈427~847ms** | — |

⇒ 886.6ms **不是「一个怪物」**，而是「130ms 注入等待 + ~100ms import + 100~450ms 轮询 + ~100ms 两张图 + 十几 ms 闸门」叠出来的。这也解释了为什么砍任何**单项**都端到端不可判（A:40-41）：最大单项（轮询 450ms）也只占 45%。

### 3.5 886.6ms 的边界仍然不清（必须由 C1 解决）

A 的 886.6 是差值，**不知道含不含 P3**。如果 `1001.8ms` 是 CLI 端到端，那么它至少还含：

- P3-11 `store.append`（全量 6.3MB 重读 + fsync）
- P3-6 `_act_diff_store`（1~3 张 PNG + `listdir`）
- P3-10 `evidence.json` 落盘
- P3-3 若 `first.bmp` 不可用，回落的 `wait_change` 300ms（`core.py:2957`）

⇒ **C1 的探针必须同时给「act 内部总和」和「core 端到端」，两者相减才知道 886.6 的归属**。只测 act 内部会把 P3 漏掉；只测端到端会把 P1/P3 算进「动作本身」。

> 目标：把 §1.1.2 的 20 步压成 6 个可测区间，且每个区间都能**归因到具体嫌疑**。

### 5.1 六个点

| 点 | 插在哪（行号 + 锚点） | 切出什么 | 对应嫌疑 |
|---|---|---|---|
| **① 进程入口** | `act.py:1` **任何 import 之前**（文件第 1 行前插） | 解释器启动 + 模块自检 + 顶层 import + 两个 JSON 的**总和** | P2-1~4；S3/S11；A 的 83.5ms 是否被低估 |

### 5.2 每个点必须记什么（否则归因会错）

```python
{
  "tag": "...",
  "mono_ns":  time.monotonic_ns(),        # 不受系统时钟调整影响，算区间用这个
  "pc_ns":    time.perf_counter_ns(),     # 与 A 线的 perf_counter 口径对齐
  "proc_ns":  time.process_time_ns(),     # CPU 时间；wall - cpu ≈ sleep/IO 等待
  "wall":     time.time(),                # 墙钟，给 core 侧对齐 t_spawn
  "pid":      os.getpid()
}
```

三条硬要求：

1. **`monotonic_ns` 与 `process_time_ns` 都要**：`⑤` 如果 wall 涨了 450ms 但 `proc` 只涨 30ms ⇒ 是在 `sleep` 等界面；如果 `proc` 涨了 200ms ⇒ 是 `PrintWindow`/numpy 在烧 CPU。**只看墙钟分不开这两件事**。
2. **必须 `atexit` 落盘**：act 有大量 `return` 分支（拒绝/异常），只在正常出口写会把被拒样本全丢掉。C1 现有的 `make_act_probe.py` 已经用 `atexit` + `_m17_dump`，这点是对的。
3. **别开 `AGENTCTL_PROFILE=1`**：`act.py:1072` 用了未导入的 `tempfile`（`act.py` 全文没有 `import tempfile`），一开就 `NameError`。用自己的探针文件，走 `AGENTCTL_M17_PROBE_FILE` 这类独立开关。

### 5.3 与 C1 现有探针的对齐情况（我读了 `work\_M17_解剖_20221022\C\make_act_probe.py`）

C1 的 `make_act_probe.py` 已经在这 6 个点上打了 tag，而且比本单建议**多切了几组**，这是好事：

**还缺的两块（建议 C1 补，但不必新增第 7 个「主点」，可在现有点里加子标记）**：
