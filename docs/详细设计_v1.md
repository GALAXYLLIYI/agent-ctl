## 0. 摘要（先看这一页）

**要解决的问题**：现在的控制系统是一堆各自为政的 Python 命令行脚本，只有"知道绝对路径 + 会拼参数"的 agent 才用得上；而且**动作日志和截图之间没有共同键**，事后对不上账。

**三步升级**：
1. **统一控制面**：一个常驻本地服务，同时暴露 **MCP（stdio + HTTP）**、**本地 HTTP+JSON**、**CLI** 三种入口，同源同行为 → 任何 agent 装一个连接就能用。
2. **可信时间线**：事件驱动采集 + 帧自带时间码 + 单调钟/墙钟双锚 + 会话起始见证 + 哈希链 → 能按时间回溯、能独立复算、能被实时查看与干预。
3. **可安装包**：PyInstaller 冻结 + 免管理员安装器 + 卸载 + 给 agent 读的接入文档。
> ⚠️ **2026-10-14 注（S11）**：上面目标第 3 条的「免管理员安装器 ＋ 卸载」属**当时的安装包路线**，
>   **已被 `install.ps1` 取代**（依据 `install.ps1:7`「不做安装包」／`README.md:71-79`「为什么不用安装包」）。
>   `tools\installer.py` 保留在盘上、不进仓、不删。**原文一字不删，保留为设计史。**

**对用户原始提案的裁定**（这是本轮最重要的技术结论）：

| 用户的想法 | 裁定 | 理由 |
|---|---|---|
| 开始控制要有一个**时间点** | ✅ **采纳，而且是关键** | 每次控制会话建立 `session`，记录单调钟/墙钟**锚点对**；会话开始时拍一张**含任务栏时钟的"起手见证帧"** |
| 截图看时间、和内部时间匹配 | ⚠️ **降级为见证通道，不能当主时间源** | 全屏/任务栏自动隐藏时读不到；OCR 有错；秒级精度。主时间源必须是**录制器自己烧进帧的时间码**（单调钟） |
| 录制视频 | ✅ 采纳，但**不是全程常录** | 改为「事件驱动 + 心跳」采集 + 环形留存 + 关键帧剪辑，省内存省磁盘（本机 F 盘只剩 10.0 GB，实测） |
| 通过时间线回溯 | ✅ 采纳 | 回放命令出片（自研 MJPEG-AVI，不依赖 ffmpeg）+ 索引查询 |
| 实时进行修改控制 | ✅ 采纳 | SSE 实时帧流 + 暂停/放行/急停三个干预动作 |

**行业校验**：这套路子与 2026-08 的 arXiv 论文 *Activity Frames* 高度同构——它用**零模型、确定性编译**把屏幕活动编成"活动帧"，带**证据指针**回指原始行，并**强制披露 blind_spots**，且提供 **MCP 六个工具**给任意 agent [arXiv:2608.05784]。我们直接采用它的 schema 纪律。

| `act.py` | `tools\` | 点击/打字/滚动/拖拽/原子填字段，白名单限制 | 已含模态拦截、前后图核验 |

| `guardian.py` + `guardian_policy.json` | `tools\` | 内存守护（阈值 65/80/90% 提交使用率；可用物理 3500/1500/600 MB） | 新服务必须与它联动 |
| `whitelist.json` | `tools\` | 可操作窗口白名单（8 条） | 改动需用户点头 |

### 1.2 九个缺口（每条都有实测依据）

1. **没有服务，只有命令行**。`agent_tools.json` 是给人看的清单，不是可挂载的接口——**agent 必须会拼命令行才能用**。
2. **每次调用起新进程**。截图/动作各自 `python tools/xxx.py`，重复 import + 重复设 DPI；没有常驻状态、没有会话对象。
3. **没有共同键**。截图按 `%Y%m%d_%H%M%S` 落盘（秒级、无单调序），动作日志在 `_auth\gate.log`/`act.log`，**两边无法机器对齐**。实测规模：`_监控\shots\` **1274 张 / 241.5 MB**（2026-09-17 ~ 10-01）。
4. **闸门非原子**。`gate.check()` 读 → 动作 → `require()` 写计数，三步之间可插入；多进程并发会**丢计数或超发**。通行证是明文 JSON，任何进程可写。
5. **没有单写者**。两个 agent 同时动鼠标无任何拦截——**这是当前最危险的缺口**。
6. **证据不可篡改检测**。图是散文件，可被覆盖/删除/替换而不留痕；"证据"只能证明**生成过**，不能证明**没被换过**。
7. **无实时通道**。用户要介入只能拉急停（全停）；没有"暂停某一步 / 放行 / 看现在的屏幕"。
8. **路径写死 `<盘符>:\`**。`perceive.py` 的 `SHOTDIR`、`brake.py` 的 `FLAG`、`guardian_policy.json` 的日志目录都是绝对路径——**换机/换盘即坏**，也是打包的死结。
9. **零打包**。没有安装器、没有卸载、没有版本号，无法交给别人（或另一个 agent）安装使用。

### 1.3 必须守住的不变量（设计红线）

- **远程命脉**：本机通过 ToDesk/GameViewer 远程使用；用户原话「别把远程关了就行」。**禁止**杀/停/禁 GameViewer 四件套与 `DeepSeek Harness.exe`、断网、改 IP/DNS/代理、关机/重启/睡眠、改分辨率/多屏、锁屏、跑全屏独占程序。自检口诀：**「这一步会不会让我看不见屏幕？」会 → 不做**。
- **铁律 11 三闸**：领头模型不变；每次控制前弹窗授权；密钥不落盘不回显；急停双通道；档位 A→B→C→D 只升不跳。
- **资源**：16 GB 内存、8 GB 显存；死法是**提交内存被榨干**；`F:` 盘**只剩 10.0 GB**（实测），`C:` 剩 133.9 GB。
- **兼容**：现有 `tools\*.py` 与 `agent_tools.json` 是别人现在能用的东西，**本轮只新增、不改老文件**。

## 2. 总体架构

```
┌─ L4 消费层 ─────────────────────────────────────────────┐
│  agent（DSH / Trae / ZCode / WorkBuddy / 本地模型）      │
│  人（回放查看器 / 时间线看板 / 实时干预页）              │
└───────────▲───────────────▲──────────────▲──────────────┘
            │ MCP stdio     │ MCP HTTP     │ CLI
┌───────────┴───────────────┴──────────────┴──────────────┐
│ L3 接口层   AgentCtl.exe / mcp_server.py / cli.py        │
│   统一信封 {ok,code,data,event_id,frame_before/after}    │
│   鉴权：本地 token + actor 标识 + 单写者租约             │
└───────────▲─────────────────────────────────────────────┘
┌───────────┴─────────────────────────────────────────────┐
│ L2 控制面   gate(原子闸门) / lease(单写者) / whitelist   │
│   perceive（感知）  act（动作）  brake（急停）           │
│   ★ 任何写动作无证即拒，无 --no-gate 开关                │
└───────────▲─────────────────────────────────────────────┘
┌───────────┴─────────────────────────────────────────────┐
│ L1 时间线内核                                            │
│   clock（单调钟+墙钟锚+见证）  store（SQLite+jsonl+哈希链）│
│   recorder（采集线程：事件驱动+心跳+时间码烧录+环形留存） │
└───────────▲─────────────────────────────────────────────┘
┌───────────┴─────────────────────────────────────────────┐
│ L0 采集源（可替换，靠"捕获表契约"解耦）                  │
│   mss 抓屏 / PrintWindow 取窗口自身 / UIA / 输入钩子     │
└─────────────────────────────────────────────────────────┘
```

**关键设计决策：L0 与 L1 之间用「捕获表契约」解耦**——任何采集器只要写出约定字段的表，编译器就能用。这是抄 *activity-frames* 的做法（它的 `$AFRAMES_DB` 可指向任意兼容库，编译器对缺表优雅降级）[SPEC.md §9]。好处：**将来换采集引擎不必改上层**。

**单进程原则**：L1/L2/L3 跑在**同一个常驻进程**里（采集是它的线程），不再"每次截图起一个 Python"。

## 3. 时间模型（★ 直接回应用户提案）

### 3.1 三层时间源，各司其职

| 层 | 取值 | 用途 | 为什么需要它 |
|---|---|---|---|
| **T1 单调钟** | `time.perf_counter()`（Windows 底层 QPC，微秒级、不随系统时钟调整） | 排序、间隔、烧进帧的时间码 | 系统时钟被 NTP 校时或被改时，单调钟**不受影响**——这是"顺序可信"的底座 |
| **T2 墙钟** | `datetime.now()` + 每次会话记录 `(mono, wall)` **锚点对** | 人能读的"几点几分" | 单调钟没有"日期"，必须锚到人类时间 |
| **T3 见证** | 抓**任务栏时钟区域** → OCR → 与 T2 比对 | **独立交叉校验**，检出"我们记的时间和屏幕显示的时间对不上" | 用户提案里真正有价值的那一半 |

**锚点对的作用**：会话开始记 `(m0, w0)`，每 30 分钟再记一对，会话结束记 `(m1, w1)`。用线性模型 `wall ≈ a + b·mono` 拟合：
- `|b − 1| > 阈值` → 系统时钟被**改过**（不是漂移）；
- 残差突然跳变 → 中途被校时；
- 两种情况都在时间线上写一条 `clock_anomaly` 事件，**并标记其后所有帧的墙钟为"受污染"**。

### 3.2 会话起始见证（用户说的"开始控制有一个时间点"，落地形态）

会话开始时的固定四步：
1. `sessions` 表插入一行：`session_id`、`t_mono0`、`t_wall0`、`actor`、`授权范围`、`通行证 nonce`；
2. 抓一张**全屏帧**，区域**必须包含任务栏时钟**（右下角工作区外）；
3. 对这张帧做 OCR，得到"屏幕上显示的时钟"→ 与 `t_wall0` 比对，写入 `witness` 表；
4. 若 `|差| > 2 秒` → **当场告警并按配置拒绝进入 B 级以上控制**（可配为仅告警）。

> 这样"开始时间"就有了**三份互相独立的记录**：单调钟、系统墙钟、屏幕上肉眼可见的时钟照片。事后谁想争"那次到底是几点开始的"，三份都得改才行。

### 3.3 巡更见证

会话进行中每 **60 秒**（可配 30–300 秒）重复 3.2 的第 2–3 步，写 `witness` 表。
判定：
- `|见证 − 系统墙钟| > 2s` → `witness_drift` 告警；
- OCR **置信度不足** → 写 `result="未识别"`，**绝不猜、绝不填数**（不猜不编，铁律 1）；
- 连续 3 次未识别 → 写 `witness_blind`，时间线的 `blind_spots` 里加一条。

#### 3.3.1 ★ 实测规格（2026-10-02，用**历史上已授权的**全屏图量的，没有新抓屏）

| 项 | 实测值 |
|---|---|
| 任务栏高度 | 约 **72 px**（物理像素；屏幕 2560×1600 @150%） |
| 时钟文字所在区域 | 屏幕**右下角 260×64** 之内 |
| **单字高度** | **13 px**（`2026` 四个数字各自独立量到；字宽约 **7 px**） |
| 图上时间 vs 文件名时间 | 文件名 `20260927_211821_full.png` ↔ 屏幕上显示 **21:18** → **对得上** |

**由此定下见证通道的实现规格**：
1. 裁剪右下角固定区域 → **LANCZOS 放大 4–6 倍** → **再**做模板匹配（PIL 渲染 Segoe UI 数字）或 OCR；
2. ⛔ **禁止在 1x 原图上直接 OCR** —— 13 px 字高对通用 OCR 偏小，硬上必然时好时坏；
3. 若某台机器上量到**单字高 < 10 px** → 见证通道**降级为"只存图不识别"**，并在 `blind_spots` 里如实写明；
4. 见证区域坐标**不许写死**（任务栏可能在顶部/自动隐藏、可能多屏）→ 运行时用 `SHAppBarMessage` / 工作区矩形推算，取不到就写"未识别"。

> ★ **用户提案的第一次真实检验**：拿 2026-09-27 那张已授权的全屏图，**屏幕上显示的 21:18 与文件名时间戳 21:18 对得上**——
> 说明"截图看时间"这条路**物理上走得通**；但它仍是**见证**，主时间源依旧是单调钟（理由见 §3.1）。

#### 3.3.2 ✅ **见证通道已跑通：Windows 自带 OCR，零依赖、零 API 成本**（2026-10-02 端到端实测）

**背景**：原先 §21.6 记着一条风险——官方文档说 `Windows.Media.Ocr` **只支持有 MSIX package identity 的桌面应用**，
而我们要交付的是 PyInstaller 冻结的普通 exe。**这条现在已经实测掉了**（读的是**盘上已有的图**，没有新抓屏）：

| 输入 | OCR 输出 | 结论 |
|---|---|---|
| 原尺寸整块 **260×64** | `2026 / 9 / 27` | 只读到日期，**漏了时间行** |
| **4 倍放大 1040×256** | **`21 ： 18 2026 / 9 / 27`** | ✅ **两行全对**，与图上显示一致 |
| 只裁时间行 **1x** 170×32 | （空） | 认不出 |
| 只裁时间行 **4x** 680×128 | `21 ： 18` | ✅ 正确 |

**同时测得的环境事实**：
- `[Windows.Media.Ocr.OcrEngine]::TryCreateFromUserProfileLanguages()` → **OK**（**普通进程，无 MSIX identity**）；
- `AvailableRecognizerLanguages` = **`zh-Hans-CN`**（中文识别包已在本机）；
- `MaxImageDimension` = **10000**（我们用的尺寸远在限内）；
- PSVersion = **5.1.26100.9444**。

**由此定下见证通道的最终实现规格**：
1. 裁任务栏时钟区 → **LANCZOS 放大 4 倍** → **Windows 自带 OCR**（`zh-Hans-CN`）；
2. ⛔ **不许在 1x 上直接 OCR**——实测 1x 会漏掉时间行，**4 倍放大是必需的，不是优化**；
3. ⚠️ **OCR 返回的是全角冒号 `：`**（`21：18`），**解析前必须归一化**（这是实测踩到的具体坑）；
4. 结果仍要与系统墙钟比对（§3.2），差 > 2 秒告警；认不出就写"未识别"，**绝不猜**。

**⚠️ 仍未核实的部分（不许当成已解决）**：
上面是在 **PowerShell 进程**里通过 WinRT 投影调通的。**"PyInstaller 冻结的 Python 进程"能不能同样调通，还没测**——
两条路可选：①用 `winrt-Windows.Media.Ocr`（pywinrt，纯 wheel、MIT）；②**服务直接 shell 调这个已验证可用的 PS 脚本**。
**哪条先落地，S2 时实测决定。**

### 3.4 帧的时间码（burn-in）规范

每一张**落盘的帧**在**左上角**画一条半透明黑底白字：
```
2026-10-01 19:20:51.234 | M 12 345.678 | #000123 | sess=7f3a
```
- 第 1 段：墙钟（毫秒）
- 第 2 段：**单调钟秒数**（M = mono）
- 第 3 段：本会话内帧序号
- 第 4 段：会话短 id

**为什么烧进画面**：帧一旦离开数据库（被截图、被转发、被贴进对话），它的时间身份仍然**跟着它走**。这不是为了好看，是为了**证据可携带**。

### 3.5 本设计**做不到**的（必须写进 blind_spots，不许粉饰）

- OCR 读任务栏时钟**会失败**（全屏、任务栏自动隐藏、自定义时钟、非 100% 缩放）→ 见证通道是**尽力而为**，主时间源仍是 T1/T2；
- 本机**没有** TPM/VBS Enclave 那套保护（Recall 用的是 VBS Enclave + Windows Hello ESS 才能做到"密钥只在安全环境里用"）[MS Recall 安全架构]。我们的时间线库就是**本机普通文件**：同一 Windows 账户下的任何进程都能读改。**所以本方案给的是"防误改、防事后抵赖的弱形式"，不是"防同用户恶意进程的密码学边界"**——这句诚实话必须原样写进给 agent 的接口文档；
- 单调钟**跨重启不连续**（QPC 每次开机重新计数）→ 跨会话排序靠墙钟 + `boot_id`（开机标识）拼接。

## 4. 可信性模型（防篡改：哪些是真增益，哪些只是形式感）

### 4.1 机制

1. **哈希链**：每条事件 / 每帧的 `hash = SHA256(prev_hash ‖ 规范化字段 ‖ 内容摘要)`。链头存在 `sessions` 行里。
2. **双写**：同一批记录写 `timeline.db`（便于查询）**和** `timeline-YYYYMMDD.jsonl`（追加式纯文本，便于**用任何工具独立复算**，且 SQLite 损坏时仍可核）。
3. **内容摘要**：帧写 `sha256(jpeg 字节)`；只存摘要不存原图的部分（如被留存策略清理掉的）**如实标注 `purged`**，不假装还在。
4. **锚点**：会话结束把当次链头写入 `anchors.jsonl`（一行：会话 id、链头哈希、事件数、帧数、起止时间）；可选把锚点文件**打印/抄写/邮件给自己**——这才叫真正的带外锚。
5. **验证命令**：`agentctl verify --from <会话> ` → 重算全部哈希；任何一处不符即报错并指出**第一个坏掉的 id**。

### 4.2 诚实的强度评估（不接受奉承）

| 机制 | 真增益 | 形式感 / 局限 |
|---|---|---|
| 哈希链 | 事后**改一条必须重算整条链**；误删单帧、误改一条记录**必然暴露** | 攻击者若能改全部文件，可整链重算 → **必须有链外锚点** |
| 双写 jsonl | **可用性收益**：SQLite 损坏时仍可从 jsonl 重建 | ❌ **不是防篡改**：同目录、同权限、同一账户，能改 SQLite 的就能改 jsonl。**我原稿写成"两者同时被改写难度更高"，这是自欺——调研当场驳掉，我认栽并改正** |
| 内容摘要 | 能证明"这张图不是我后来换的" | 图被删就只能证明"曾经存在" |
| 锚点（**签名 + RFC 3161 时间戳**，每日一次足够） | **唯一**能对抗"整链重算"的手段 | 锚点若留在 agent 能写的目录里＝整链可被重算，**不可抵赖性≈0**；本机无代码签名证书 → 先落地「人工抄录 + 只读介质」，证书待用户决定 |
| 写入者与 agent 权限分离 | 让被审计者不能直接改审计文件 | 单账户下做不到彻底；可试 **NTFS 只追加 ACL**（允许 `FILE_APPEND_DATA`、拒 `FILE_WRITE_DATA`/`DELETE`）——**待实测** |
| **独立 verifier** | 验证代码**不在写入进程内**，只读日志+锚点，报"从第 i 条起被改" | 若 verifier 和写入者在同一个 exe/进程里，等于没有验证 |
| 时间戳见证 | 独立于软件的**第三个时间来源** | OCR 可能失败；失败时必须如实写"未识别" |

> 结论（已按调研修正）：**哈希链 + 签名带外锚点 + 独立 verifier** 三件齐了才算"可回溯"。
> 「双写」只是抗损坏，「哈希链」只是抗局部改动；**没有离开本机的锚点，前三件加起来仍然可以被整链重算**。

### 4.3 链路细节（原稿缺失，按调研补齐）

1. **head 定义与轮转续链**：jsonl 按日轮转；当日文件**首条**的 `prev_hash` = 前一日**末条**的 hash；`head` = 最新一条的 hash。跨日不能断链（原稿没写这条，是真缺口）。
2. **独立 verifier 独立成件**：`agentctl-verify.py` —— **纯标准库、只读、可单独复制到别处运行**，不 import 主程序任何模块；输入 = jsonl + anchors，输出 = "OK / 第一条坏点在 #i（期望 hash X，实算 Y）"。
3. **字段命名借标准，不自己发明**：provenance 对齐 **W3C PROV-O**（Recommendation）；动作名对齐 **OpenTelemetry GenAI semconv** 的 `execute_tool` / `invoke_agent` / `plan`（⚠ 该规范状态为 **Development**，字段会变 → **只借语义，不锁死格式**）。
4. **性能取舍（别在没瓶颈的地方花力气）**：SHA-256 参考基准 **484 MiB/s**（BLAKE3 官方基准图，16 KiB 输入、单线程、Cascade Lake-SP，2019）vs 本需求 600 KB × 8 fps ≈ **4.8 MB/s ≈ 基准的 1%** → **哈希不是瓶颈**。真正的瓶颈是**耐久写**：SQLite `synchronous=FULL` 每次提交都 fsync WAL → 采用 `synchronous=NORMAL` + jsonl 追加 + 定期 fsync + 批量提交。（逐条 fsync 的绝对毫秒数**未能核实**，故选型以"批量"为准，不赌单条延迟。）
5. **威胁模型要写进文档原文**：本方案防**事后篡改与删除**；**不防**"有本机控制权且能同时改掉锚点介质"的攻击者。不许含糊成"安全"。
6. **够用即止**：不建 Merkle 树、不做透明日志、不逐条取 TSA、不碰区块链/分布式账本（NIST IR 8202 定义的分布式账本解决的是**多方互不信任**；单机没有多方，共识成本换不到任何本机防线）。
7. **Windows 事件日志不能当锚点**：`wevtutil` 明摆着支持 `cl`（清空）与改存储路径/权限；它内部是否有密码学链完整性**未能核实** → 只能当旁证，不进设计。
8. **反例要记住**：LangSmith 的 trace 可被 `delete_runs` 删掉，只有"删除动作"进 audit log——这就是**被审计者自己写审计日志**的典型失效形态。我们的对策就是第 4 行的权限分离 + 第 2 行的独立 verifier。

### 5.3 留存策略（★ 已按 2026-10-02 本机实测重写；原稿的"常态 1 fps"是**不可行的**）

**先看实测（用历史全屏图当样本，2560×1600，JPEG）**：

| 缩放 | 尺寸 | 质量 | 单帧体积 | 单帧编码耗时 |
|---|---|---|---|---|
| 1.0 | 2560×1600 | 70 | **226.7 KB** | ~7 ms |
| 1.0 | 2560×1600 | 85 | 289.1 KB | ~7 ms |
| **0.5** | 1280×800 | 70 | **65.1 KB** | 1.8 ms |
| 0.5 | 1280×800 | 85 | 89.1 KB | 1.9 ms |
| **0.25** | 640×400 | 70 | **20.4 KB** | 0.6 ms |

**按原稿默认（常态 1 fps × 全尺寸 q70）推算 = 18.68 GB/天** —— 8 GB 的环形**半天就爆**，完全不可行。
即便缩到 0.5 也仍是 **5.37 GB/天**。**所以原稿那行必须改**：

| 类别 | ★ 修正后的默认 | 依据（实测） |
|---|---|---|
| **常态帧** | **缩到 0.25（640×400）＋ q70 ＝ 20.4 KB/帧**；**且只在指纹变化超阈值时才落盘**，上限 1 fps | 全尺寸 226.7 KB/帧会把盘吃光；0.25 档单帧只 20.4 KB |
| **动作前后关键帧** | **缩到 0.5（1280×800）＋ q70 ＝ 65.1 KB/帧**，前后各 5 秒 @8 fps | 一次动作 ≈ 80 帧 ≈ **5.2 MB**；这是"回溯某次点击"的主证据，值得给清晰度 |
| **心跳帧** | 30 秒 1 张，**只存指纹与一行元数据，不落全图** | 屏没变时存全图纯浪费；抄 activity-frames 的心跳设计（其语料心跳行占 19%） |
| **见证帧** | 60 秒 1 张，**只存任务栏时钟条带**（实测 ≈ 260×64），不存全屏 | 一张条带 ≈ 几 KB |
| **环形上限** | **8 GB / 72 小时**，先到先删；`trigger ∈ {action, opening, witness}` **永久** | 按"每天 100 次动作＋约 1000 张常态帧"估算 ≈ **0.54 GB/天** → 72 小时 ≈ 1.6 GB，8 GB 绰绰有余 |
| **敏感窗口** | **代码级永不采**（见 §7.4） | 用户在弹窗里输密钥 |

**运行开销（实测，用于 §11 验收）**：

| 项 | 实测值 | 折算 |
|---|---|---|
| 指纹生成（灰度 1/8 → 200×320） | **6.45 ms** | —— |
| 指纹比较（平均绝对差） | **0.10 ms** | 一次"变没变"检查 ≈ **6.6 ms** |
| 变化检查 1 fps | —— | ≈ **0.66%** 单核 |
| 变化检查 8 fps | —— | ≈ **5.3%** 单核 |
| 烧时间码（PIL 画黑底白字） | **5.78 ms**（含一次全图 `copy()`，实际更低） | 只对**要落盘的帧**做，不做常态帧 |
| 一帧 2560×1600 RGB 常驻内存 | **11.7 MB** | ⛔ **绝不许"每帧留一份"** |
| 指纹常驻内存 | **0.12 MB** | 采集循环只需持有一帧 + 一份指纹 |
| PNG 解码 2560×1600 | 20.7 ms | 仅回放/复核时用 |

> ★ **这条改动的意义**：原稿的"1 fps 常态录"是**拍脑袋定的**，实测一出就废。
> 现在默认档是有数字撑着的：**常态薄、动作厚、心跳只留指纹**。
>
> ★★ **2026-10-02 再改一次（见 §22、§23）**：本节仍是"以像素为主"的方案；§22 把它升级为**证据分层**
> ——**控件树快照（实测每节点 gzip 36 字节）＋ 低频视觉锚点 ＋ 动作前后帧 ＋ 按需片段**。
> **三处口径已对齐**：§22 估 **65–145 MB/天**、§23 子代理独立估算 **≈100 MB/天** → **按 ≈100 MB/天 定预算**。
> 冲突时**以 §22/§23 为准**（本节是旧口径）。

> ⚠️ **未实测的一项（不许当结论）**：`mss` 在本机 2560×1600 下单次**抓屏**的耗时。本设计**刻意没有去新抓屏幕**（新抓屏属于"看屏幕"，铁律 11 要求用户弹窗授权）。可参考 dxcam 作者基准里 python-mss 在 1920×1080 的 75.87 fps（≈13 ms/帧），但**那是 1920×1080 且是别人机器**，直接外推到 2560×1600 属于推测 —— S2 拿到授权后第一件事就是实测这个数。

## 6. 接口契约（三态同源）

### 6.1 统一返回信封（所有入口一致）

```jsonc
{
  "ok": true,
  "code": 0,                       // 0 成功 3 白名单/敏感拒 4 找不到控件 5 坐标/前台拒
                                   // 8 动作发了但页面没变 9 未授权 10 租约被占 11 刹车 12 capture_id 过期
                                   // ⚠️ 上面全是【信封码】。ctl_timeline 的 data.events[].code 不是信封码 ——
                                   //    它是「信封码的镜像 ∪ 事件级内部码」，事件级内部码见契约 tools.json 的
                                   //    event_codes（当前 13 ＝ 录制自保护停录），两个命名空间靠 kind 区分。
  "data": { },                     // 工具各自的结构化结果
  "event_id": 10231,               // ★ 本次调用在时间线上的事件号
  "frame_before": 5521,            // ★ 动作前后帧号（只读工具为 null）
  "frame_after": 5522,
  "session_id": "7f3a…",
  "t_mono": 12345.678,
  "t_wall": "2026-10-01T19:20:51.234+08:00",
  "elapsed_ms": 213,
  "blind_spots": ["…"],            // 本次结论的盲区（不隐藏）
  "warning": null
}
```

> ★ **「码相同、情形不同」的机读标记（2026-10-13 补）**：`code` 相同**不等于**原因相同。服务会在
> `data` 里额外给**机读标记**，调用方**不要只看 `code` 下判断**：
>
> - **`data.blocked_by = "modal_dialog"`** —— `code=5`，但**原因不是坐标/前台不稳**，而是
>   **目标窗口上有模态对话框挡着**，动作**根本没有发出去**。处置是**先关掉那个对话框**
>   （模态框会吞掉一切点击/输入），关掉后**重新观测拿新的 `capture_id`** 再动手；
>   ⛔ 不是「重新观测坐标再点」（自修复动作与另一情形相反）。
> - **`data.unknown_rc = true`** —— `code=5`，但**不属于任何已知情形**：老脚本返回了
>   `act.py` **没约定**的返回码，原始码在 `data.rc`。⛔ **不许当成功**，也⛔ **不许当成
>   「找不到控件」**（那会把人送去重扫控件树，白绕一圈）。先看 `data.raw` 原文再判断。
>
> **两种情形都【不新增错误码】** —— 码表是 `src\agentctl\gate.py` 顶部那段 `CODE_*` 常量表（⚠️ **刻意不写死行号**：2026-10-13 的 S6 在它后面追加了 `13` 的常量与注释，原来的 `:427-430` 已盖不住全表），
> 本设计**不扩它**；也正因如此才需要这两个标记来区分同码不同因。

> **设计要点**：**每个写动作都自带 `frame_before/frame_after` 和 `event_id`**。这样 agent 说"我点了提交"时，交付物不是一个布尔值，而是**两个可查的帧号 + 一条可复算的事件**——正好对上本机的交付铁律 A（动作完成 ≠ 效果达成）。

## 7. 授权与安全

### 7.1 闸门原子化（补上缺口 4）

把通行证与租约状态从 `auth_pass.json` 搬进 **`state.db`**，用 SQLite 事务保证原子：
```sql
BEGIN IMMEDIATE;
  -- 校验：未消费、未过期、范围含本次、计数未超、刹车未拉
  UPDATE passes SET acts = acts + 1, last_act = ? WHERE ... AND acts < acts_limit;
  -- 受影响行数 = 0 → 拒绝
COMMIT;
```
**同时保留 JSON 镜像写穿**（老脚本 `gate.py` 继续读得到），保证兼容。

其余不变：范围字符串**完全匹配**（A/B/C/D 不通用）、默认 10 分钟、B/C 各 20 次、D 10 次、A 200 次。

### 7.2 单写者租约（补上缺口 5）

- 写动作前必须持有租约：`ctl_lease(acquire, actor, scopes, ttl≤10min)` → 返回 `lease_id`；
- 同一时刻**只允许一个租约**持有 B/C/D 权限；第二者申请 → `code=10`，附当前持有者与剩余时间；
- 只读感知（A）**不受租约限制**（多个 agent 同时看屏幕无害）；
- 租约**到期自动失效**，与通行证同时校验，二者缺一不可；
- `ctl_status` 永远显示当前持有者——**用户一眼能看出"现在是谁在动我的鼠标"**。

### 7.3 急停不变，但多一条自杀通道

- 原有：`Ctrl+Alt+Home`、`%LOCALAPPDATA%\AgentCtl\_急停.flag`（T10 起统一，桌面路径已作废）；
- 新增：`POST /v1/control/abort` 与看板上的红色按钮 → 走同一个 `brake.stop()`，同样留痕；
- 服务每 1 秒检查急停文件（与 guardian 同频），拉下即**拒绝一切写动作**（只读也建议停采集，可配）。

### 7.4 敏感窗口（录制器也必须守）

现有 `perceive.py` 已有：标题含「DSH电脑控制授权」的窗口，**代码级拒绝截图/读控件树**。
**录制器是新风险**：连续采集会把用户输密钥的全过程录进去。补三条：
1. 采集线程每次取帧前检查敏感窗口存在 → 存在则**跳过本次采集**并在时间线写一条 `sensitive_skip`；
2. 已有的帧若与敏感窗口时间区间重叠 → 不删（删了就是篡改），但 `frames.state='restricted'` 并在查询层**默认不返回**；
3. 弹窗进程自己**在创建窗口前**调用一次 `recorder.pause()`，窗口销毁后 `resume()`——双保险。

### 7.5 明确**不做**的事（写进文档，免得后人加回去）

- 不做 `--no-gate` 之类的绕过开关；
- 不用 **MCP elicitation 收集密钥/口令**：MCP 规范明文写着 *"Servers MUST NOT use elicitation to request sensitive information"* [MCP elicitation spec]。所以密钥弹窗**继续用独立 tkinter 进程**（铁律 11④ 的"最佳实现"），MCP 只承担**一般性确认**（如"用户，允许我点这个删除按钮吗？"）；
- 不监听外网、不装自签证书、不做 OAuth（本机单人场景用不到，徒增攻击面）；
- 不把时间线库放进 `<工作区>`（那是工作区，agent 可写；时间线库应放在服务自己的 home 下）。

## 8. 回放与实时介入（补上缺口 6/7）

### 8.1 回放

```
agentctl replay --from "2026-10-01 19:18:00" --to "19:22:00" --fps 8 --out clips\
```
产出三样：
1. `clip.avi` —— **自研 MJPEG-AVI 写入器**（RIFF 容器 + MJPG fourcc，纯标准库，**不依赖 ffmpeg**——本机实测无 ffmpeg）；
2. `contact_sheet.png` —— 联络表（N×M 缩略图 + 时间码），一眼看完整段；
3. `manifest.json` —— 帧号/时间码/哈希清单，**可拿去做独立核验**。

`agentctl replay --around-event 10231 --pad 5` → 直接出"某次动作前后 5 秒"的片子（对应用户说的"回溯"）。

### 8.2 实时

- `GET /v1/watch`（SSE）：1 fps 的 JPEG 帧 + 每帧的时间码/帧号；**背压策略是丢弃旧帧**，绝不堆积（防内存爆）；
- `GET /`：一页极简看板 —— 顶部实时画面、底部时间线拖动条（按小时/按事件跳）、三个按钮：**暂停 / 继续 / 急停**；
- 「实时修改控制」的落地形态（v1 只做这三个，不做花活）：
  - **暂停**：冻结写动作（只读继续），可用于"我看到它要点错了，先停住"；
  - **继续**：解除暂停；
  - **急停**：走刹车，全停且留痕。

## 13. 风险与止损

| 风险 | 触发信号 | 止损动作 |
|---|---|---|
| 常驻服务 + 录制把提交内存榨干 | `guardian` 报提交使用率 > 65% 或可用物理 < 3.5 GB | **自动停录**；写 `recorder_autostop` 事件；不重启、不锁屏（远程命脉） |

### 15.3 为什么"观测-动作绑定"值得采纳（论据来自本机自己的事故史，不靠 cua）

本机反复踩的**头号事故**就是"拿旧观测去点新画面"：

| 事故（本机实测） | 后果 |
|---|---|
| 窗口会被移动/缩放 → 坐标随时过期（`act.py` 的矩形检查被注释为"保命的，别绕过"） | 点空 |
| 2026-09-19：定位与点击之间**布局漂移 60px** | 4 次点击全打偏 |
| 同晚：肉眼从缩略图估坐标，实测偏差 **100~170px** | 同一个坑摔 4 次 |
| 2026-10-01：DPI 两套坐标系打架（1463×914 vs 2560×1600） | 怎么点都不中 |

**机制化对策（本设计采纳，并给它一个本机名字：`capture_id`）**：
1. `ctl_shot` / `ctl_tree` 返回值里带 `capture_id` = 哈希(`hwnd` + 窗口 rect + 前台状态 + 图像 SHA-256 + 单调时刻 + TTL)；
2. 凡走坐标的动作（`ctl_click --xy`、`ctl_drag`）**必须**带 `--from-capture <capture_id>`；
3. 服务端执行前校验：窗口 rect 未变、前台状态未变、图像哈希未变、TTL 未过 —— **任一变化即拒，返回 `code=12 stale_capture`**，要求重新观测。

> 这条比"提醒自己重跑 perceive"可靠得多：**能做成断言的就做成断言，别留给记性**（本机 `tools\README.md` 自己写下的原则）。

### 15.4 接口约定

- 命名：本机新工具统一 `ctl_*`（snake_case），与现有 `agent_tools.json` 的 `gate.status` / `browser.pages` 风格刻意区分——**老清单留给人看，新 `tools.json` 给机器读**；
- 返回：图像默认走**文件路径 + 帧号**，内联图像仅在 `inline=true` 且缩放后 < 上限时才给（避免撞客户端结果体积上限）；
- 诊断输出：**stdout 只走协议**，日志一律 stderr（且不打印参数原值，防止把密钥/隐私写进日志）；
- 失败**必须显式**：宁可报"缓冲不足/超出上限"，**绝不静默截断**。

## 16. 调研回填②：时间线 · 录制 · 回放选型

> 本节改由**主 agent 自写**，只用两样东西：①我自己 fetch 并读过的原文；②我在**本机跑出来的实测**。

### 16.1 采集节奏：直接采用 activity-frames 的"事件驱动 + 心跳"

我完整读过该论文 HTML 正文，其采集引擎与常数为（**原文事实**）：

- **事件驱动 + 心跳**：在**交互时**与**屏幕变化时**存一行快照；另外在**无输入约 30 秒**后存一行周期性快照；
- **语料实测**：心跳行占 **19%**；同一显示器流内**帧间隔中位数 6.1 秒**、**90 分位 30.7 秒**；
- **会话化常数**：单帧计入活跃时长 `min(Δt, 90s)`；间隔 **> 300 秒**关闭当前帧；**A→B→A 且 B ≤ 20 秒**折叠成一个 A 帧，但 B **不丢弃**——记在 `interruptions` 里带实测秒数，且**不计入 A 的活跃时长**（原文："nothing is hidden and nothing is double-counted"）；
- **缺口 ≥ 5 分钟**必须在文档里报出来；`blind_spots` 是文档的**必备字段**，不许为了让输出看起来完整而删条目。

→ **本设计直接沿用 90 / 300 / 20 / 5min 这四个常数**。理由：它们是**公开、确定性的规则，且有一份 128,756 帧 / 51 个活跃日的语料**在背后 [arXiv:2608.05784]；比我自己拍阈值可靠。

### 16.2 采集后端（本机实测 + 业界顺序）

| 项 | 本机实测 | 决定 |
|---|---|---|
| `mss` | **已装 10.2.0** | ✅ v1 用它起步（零安装） |
| `dxcam` | **未装**，但**可装**（见末行） | ⏸→✅ **升级为 v1.1 首选取图后端**：Windows-MCP 的取图顺序是 `auto(dxcam → mss → pillow)`；PyPI 上 dxcam 0.3.0（2026-03-12）给出**作者自测**（5900X + RTX 3090、屏幕持续渲染 240fps、只取新帧）：**DXcam 239.19 fps（std 1.25） vs python-mss 75.87（std 0.54） vs D3DShot 118.36**；定点帧率 60fps→61.71、30fps→30.08。有 **cp310–cp314 的 Windows 官方 wheel（cp312 仅 339.4 kB）**，本机 Python 3.12.7 **在支持范围内**；MIT；底层 **Desktop Duplication API**，且支持 **DXGI / Windows Graphics Capture 双后端** |
| **出网能力（推翻了一个错误前提）** | **实测可出网** | ✅ 2026-10-02 实测：Python 进程向 `pypi.org` 发 HTTPS **返回 200** → **"装包要联网所以不可行"这个前提是错的**；某子代理曾报"本机 shell 无出网权限"，**与本机实测不符，以实测为准**（它当时遇到的是沙箱对它的限制，不是机器没网）<br>⚠️ 但 `pip download` 实测**很慢**（120 秒未完成即转后台）→ v1 仍以 `mss`（已装、零等待）起步，dxcam 列为**需用户点头才装**的 v1.1 项 |

**两条通道不能混**（本机 `tools\README.md` 已知坑第 0 条，实测过）：
- **整屏** → `mss` / `ImageGrab`（拿的是屏幕上那块像素）；
- **单个窗口** → `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT=2)`，**窗口被遮挡也能拿到它自己的内容**（实测：Notepad 被 Edge 盖住、`是否前台 false` 时，读出的仍是记事本自己的标题、标签页、正文、状态栏）。
- ⛔ 若某窗口 PrintWindow 全黑且不在前台 → **拒绝给图，绝不悄悄退回整屏抓取**（否则"证据"里装的是别的窗口）。

#### 16.2.1 一个意外收获：帧可以自带**合成器时间戳**（⚠ 待核实，先不写进时间模型）

dxcam README 原文写明：`get_latest_frame(with_timestamp=True)` 返回 `(frame, ts)`，其中
`backend="dxgi"` 的 `ts` 来自 **`DXGI_OUTDUPL_FRAME_INFO.LastPresentTime`**，`backend="winrt"` 来自 WinRT **`SystemRelativeTime`**。

**为什么这条可能很重要**：我原设计的时间码是"**我抓到它的时刻**"；而这是"**画面被合成到屏幕上的时刻**"——在"回放某次点击"这种场景里，后者才是真正想对齐的时间轴。

**但必须挡住自己**：
- `LastPresentTime` 的**单位与时钟基准**（是否 QPC 100 ns、是否与 `perf_counter` 同基）**我没有核实**；
- **所以本节不把它写进 §3 的时间模型**——标为「S2 实测后再定」，实测项包括：①与 `perf_counter` 的差值分布；②跨显示器是否同基；③休眠/分辨率切换后是否仍单调。
- 这条正好是本机手册那句老话的又一次应用：**能实测的别用推断**。

### 16.3 时间码烧录

- 纯 PIL 自绘（左上角半透明黑底 + 白字）**零依赖可行**，本机 PIL 12.3.0 已装，字体用系统 `consola.ttf`（等宽，数字不跳）。

### 16.4 回放出片（本机没有 ffmpeg，这才是真约束）

- 本机 `ffmpeg` **无**；`imageio` / `PyAV` **未装**且都要联网装包。
- **v1 方案**：自写 **MJPEG-AVI 写入器**（RIFF `AVI ` 容器 + `MJPG` fourcc + `idx1` 索引，**纯标准库**）+ **联络表 PNG**（PIL）+ **`manifest.json`**（帧号 / 时间码 / 哈希，**可拿去独立核验**）。
- **补充格式**：短片段出 **APNG / GIF**（PIL `save_all=True`，零依赖）。
- ⚠️ **待实测（已进判据表）**：MJPEG-AVI 在实际播放器里的兼容性——**写完必须当场用系统播放器打开、核对时长 = 帧数 ÷ 帧率、随机抽帧与当时实拍帧逐像素一致**。说不出这个，就不许报"回放能用"。

### 16.5 实时看屏

- **v1 用 SSE（`text/event-stream`）+ 每帧一张 JPEG**：纯标准库可写，本地单人看一块屏幕足够；**背压策略是丢旧帧，绝不堆积**（防内存爆）。
- **v1.1 候选**：`multipart/x-mixed-replace` 的 MJPEG over HTTP——浏览器 `<img>` 直接显示，实现比 SSE 更简单。
- ❌ **v1 不引入** go2rtc / mediamtx / WebRTC：它们是**多路低延迟视频分发**方案，本场景（本地单人看自己的屏幕）**过度设计**。
  ⚠️ 仍未补上的：这三者的**开销对比我没有实测数据**（原调研未交付）。但**决策依据已经从"场景推理"换成硬数字**（见 16.8 的 Rerun 体积结论），不再只是拍脑袋。

### 16.6 隐私与"看得见"：抄 Recall 的四条原则（我读过其官方架构原文）

| Recall 的做法 | 本机落地 |
|---|---|
| **opt-in**：不主动选就不录 | ✅ 录制默认**关**，必须显式开 |
| **保留与配额可控**（可设保存时长、磁盘配额，可删一个时间区间/某应用全部） | ✅ §5.3 的环形留存 + `agentctl timeline purge --from --to` |
| **按应用/站点排除** + 敏感内容过滤 | ✅ 授权弹窗黑名单**录制器必须复用**（§7.4）；"密码/身份证/卡号过滤"列 v2 并**如实说明它不可能完美** |
| **用户始终知道正在记录**（托盘图标 + 随时暂停） | ✅ 托盘/悬浮指示 + 暂停入口。**另借 Windows-MCP 的一招**：采集后画一圈短暂提示边框（它是在**采集之后**画，所以不会进画面）——"刚被看过"要让人看得见 |

### 18.4 代码签名 / SmartScreen（诚实结论）

- **不签名与自签名表现完全相同**——都弹 "Windows protected your PC"；**自签名不等于缓解**（Microsoft Learn，2026-05-06 更新）；
- 无证书时**每个新版本哈希从零攒声誉**，无法继承；消费端**不存在**手动提交声誉的机制；EV 已不再自动免疫；
- **本机离线交付天然没有 Mark of the Web** → SmartScreen 大概率不介入；
- 唯一诚实的缓解：**离线交付 + 公示 SHA256**（Inno 官方自己就是发 `.issig` + sha256）。

### 18.5 防火墙与 `127.0.0.1`

官方口径：默认拦截所有未被请求的入站流量；应用首次监听会弹框；**非管理员用户无论点什么都只会生成 Block 规则，且生成后不再弹**。
→ **只绑 `127.0.0.1` 是正确选择**；且**首次启动必须由用户点一次**，否则可能被静默 Block。
⚠️ "仅绑 loopback 是否就不进防火墙规则/不弹框"——**未能核实，需实测**。

### 18.6 本机必须实测的三件（交付前）

1. 冻结后 `uiautomation` / `pywin32` / `comtypes` / `mss` 是否正常（这四个最容易在冻结后失效）；
2. 冻结产物在 **150% DPI** 下的坐标口径是否仍与 `coord.py` 一致；

## 20. ★ 范围变更（用户 2026-10-02 澄清）：单 agent 专用，不是多租户

用户原话：**「这个系统是固定给一个指定的 agent 用的」**。这一句改掉三处设计前提：

| 原设计（"任何 agent 都能接"） | 改后（单个指定 agent 专用） |
|---|---|
| 单写者租约是为了**防两个不同 agent 抢鼠标** | 租约**保留**，但理由变了：防止**同一个 agent 自己的并发调用/残留进程**互相踩（重试、子代理、多窗口并跑） |
| 接入文档要照顾"各种客户端" | 接入文档**只服务那一个 agent**；`tools.json` 仍保持通用形状（便于日后复用），但不为多租户做设计 |
| 需要 actor 仲裁、公平排队 | **不需要**公平性；只需要"同一时刻只有一路在动" |

**没有变**：铁律 11 三闸、时间线、打包形态、`capture_id` 绑定、错误码体系——全部照旧。
**好处**：省掉多租户的复杂度，可以把力气放在"这一个 agent 用起来爽"上（更短的调用链、更贴场景的默认值）。

| **② 区域聚焦视觉** | **全局→局部**分配视觉预算：先决定看哪块，再裁剪放大 | SeeClick、Ferret-UI、R-VLM、RegionFocus、ShowUI、DiMo-GUI、ScreenSpot-Pro、SimpAgent |
| **③ 观测增强（解析与混合）** | 把像素**解析成结构化元素**再给模型 | **Set-of-Mark**、ScreenAI、**OmniParser**、Tree-of-Lens、GUI-Actor、Agent-S、Ferret-UI 2、UGround、Aria-UI、Aguvis、UI-TARS |

论文自己总结的五条收敛思路（原话）：**selective reading instead of full-context ingestion、global-to-local visual allocation、recoverable memory rather than raw history replay、verification-aware control、hybrid runtimes that can switch between GUI and non-GUI execution。**

### 21.2 本机该走哪条（按"先便宜后贵"排）

| 档 | 手段 | 本机现状 | 判断 |
|---|---|---|---|
| **① 剪枝** | UIA 树**只留可交互/有名字/目标窗口内**的元素，其余折叠成计数 | `perceive.py --tree` 已有，但**是全量 400 节点直接输出**（等于白烧 token） | ✅ **立刻做**：剪枝是纯本地算法，零依赖 |
| **② 标注（Set-of-Mark 式）** | 把剪枝后的元素矩形**画到截图上并编号**，让模型**输出编号**而不是坐标 | 无（本机只有原图） | ✅ **最值得抄的一招**：纯 PIL 画框，**零新依赖**；而且它**绕开了本机已实测的坑**——手册记载「真正送进模型的是 1011×632，缩了 2.53 倍，按模型自报坐标点击会偏 2.5 倍」；改成"输出编号"这个坑**从根上不存在** |
| **③ 局部放大** | 先定位再裁剪放大重看 | `zoomgrid.py` 有放大标定经验（实测肉眼估坐标偏差 100~170px） | ✅ 做，作为 ② 的补充 |
| **④ 本地视觉兜底** | 本地 VLM 做定位/OCR/界面描述，**零 API 成本** | ★ **`qwen2.5vl:7b`（6.0 GB）已在本机** `<本地模型目录>`（今日实测 manifests 里在，共 11 个模型 / 20.0 GB blob；ollama 当前**未运行**）；8 GB 显存可用约 6.9 GB | ⏸ **要用户同意才启动**（占 6 GB 显存 + 起服务）。⚠️ 但它**已经躺在盘上**，这是本机做视觉最划算的一档 |
| **⑤ 浏览器场景** | 能用 DOM/CDP 就别看像素 | `cdp.py` 已能读 pages/text/find/eval | ✅ 已是主力，保持 |

**明确不做**：
- ⛔ 把 **2560×1600 原图直接丢给云端模型** —— 本机实测会被缩到 1011×632，坐标必错；
- ⛔ 装 **torch / onnxruntime** 去跑 OmniParser 一类解析器 —— 体积大、需用户同意，且收益被 ② 覆盖大半；
- ⛔ 为了"新方法"换掉 UIA：**无障碍树仍是第一优先**，视觉是兜底（下节列死穴）。

### 21.3 UIA 的死穴（什么时候必须退到视觉）

- **自绘控件**（游戏、部分 Qt/自绘 UI）：树里根本没有；
- **Electron / WebView 内嵌**：`RootWebArea` 可能不暴露（Windows-MCP README 提到 Firefox 得走 IAccessible2 兜底）；
- **最小化 / 后台窗口**：取不到内容（本机 `perceive.py` 已明确拒绝出图，防"碎片当证据"）；
- **画布型内容**（图片、图表、报错弹窗的视觉状态）：树里只有"有一个图"，看不出画了什么；
- **跨进程权限差**：更高权限的窗口读不到。

→ 所以正确姿势是 **① 剪枝 → 不行就 ② 标注 → 还不行 ③ 放大 → 都不行 ④ 本地 VLM**，而不是一上来就截图问模型。

### 21.4 ★ SoM 不是我的偏好，是**有实测支撑的**（这一条把我原来的"推理"升级成证据）

**GUI-Primitives（EMNLP 2026，[arXiv:2608.21832](https://arxiv.org/abs/2608.21832)）**测了 **19 个 VLM** 做界面元素定位，结论是：
- **严格命中最高只有 32%**；
- **60%–92% 的预测落在候选区之外**；
- **而"用 SoM 把候选区标出来"能提升 35–57 个百分点**。

→ 这直接说明：**问题不在模型不够强，而在"没给它候选区"**。本设计选 SoM 作为第②档，**依据在这里**，不是我拍脑袋。

**同源的另一条真话**：官方榜上的分数不等于可用性——ScreenSpot-Pro 榜首 92.7%（GPT-6 Astra）是**二手聚合**，而同一批模型在严格命中口径下只有 32%。
**规矩：不许拿榜单分数当选型理由。**

### 21.8 ★ 本机实测：剪枝到底能砍多少（**打了我自己一巴掌，也抓到现有系统一个真缺陷**）

2026-10-02，用盘上那份真实 UIA 树导出（`<上游项目仓>\_archive\tree_test.json`，34 个节点）实测。

#### ① ⛔ 先记一个**现有系统的真缺陷**（这就是用户问的"有什么可以加强"）

`tools\perceive.py` **第 248 行**：
```python
"可点击": bool(getattr(ctrl, "IsEnabled", False)),
```
**字段名叫"可点击"，取的值却是 `IsEnabled`（控件是否启用）** —— 而 UIA 里真正的"可点击"是**模式**
（`Invoke` / `Toggle` / `SelectionItem` / `Value` …），**根本不是属性**。

**后果（实测）**：这份树里 **34/34 个节点全部 `可点击=True`（100%）** —— 这个字段**作为信号价值为零**，
而且它**会骗人**：任何 agent（或剪枝算法）照它判断"哪些元素能点"，会**全盘误判**。
> ★ 我第一版剪枝就是照它写的，结果**只砍掉 3%**，当场发现字段是假的。
> **这是"加强项"清单里的第一条硬货。**

**修法（已进契约）**：`tools.json` 里 `ctl_tree` 的返回字段已经改成
`{ level, type, name, automation_id, class, rect, **enabled**, **focusable**, **patterns** }` ——
**废弃"可点击"这个名字，拆成 `enabled`（是否启用）＋ `patterns`（能不能点/能不能填）**。
实现时必须**按契约走，不要继承老字段名**。

#### ② 正确的剪枝判据与**诚实的**效果

判据（按优先级）：**有 `patterns` → 必留**；**可交互类型（Button/Edit/ComboBox/TabItem/ListItem/MenuItem…）且有名字或自动化 ID → 留**；
**有名字的非容器 → 留**；其余（无名 `Pane`/`Group`/`Custom`/`Image`、光秃秃的 `Tab`/`List` 容器）→ 砍。

| | 结果 |
|---|---|
| 保留节点 | **25 / 34 → 削减 26%** |
| 体积（未压缩） | 10,055 B → **5,220 B（52%）** |
| 体积（gzip） | 1,235 B → **905 B（73%）** |

⚠️ **必须诚实**：这跟社区报的「Prune4Web：500 多个候选 → 不足 20 个可操作」**完全不是一个量级**。
原因很清楚：**网页 DOM 冗余极大，而 UIA 的 control view 本身已经比较精炼**。
→ **不许把网页的数字搬到桌面场景上吹。桌面侧的本机标定就是：节点约削 1/4、字节约省一半。**

#### ③ 顺带发现的真实世界细节：**图标按钮没有名字**

保留下来的节点里出现了 `名称='\ue710'`、`'\ue921'` 这类 —— 那是 **Segoe MDL2 图标的私用区字形**，
**不是可读名字**。也就是说：**"有名字"这个判据对图标按钮是失效的**。
→ 这正是 **SoM 编号标注**（§21.2 第②档）不可替代的地方：**视觉上它是个"关闭"图标，树里它只是一串乱码**。

#### ④ 未能得出结论的一项

**"工具结果里能塞多大的图"（§14 第 1 条）本轮没查出来**：
`%USERPROFILE%\.dsh\settings.yaml` **不存在**；会话缓存里的 `imageLimits` 行是 `{"ver":1,"seq":...,"val":null}`（**无有效覆盖值**）。
→ 说明用的是**默认值**，但要拿到确切数字得去 DSH 本体里找（`app.asar` 是打包文件，grep 不进去）。
**保持"未核实"，`scale` 默认值先按 §16.2 的实测体积（0.5 → 65.1 KB）保守定，实现时实测再调。**

### 21.9 ★ 本机实测：网页场景识别到哪一步了、动作侧的缺口又在哪（2026-10-14 补记）

这一节记的是**实测**，不是设想。结论由三方独立得出（窗1 / 窗2 / WorkBuddy），DSH 另**亲自读码复核**过。

#### ① 识别侧已经到位 —— 这是这套系统最扎实的一块

2026-10-14 实机（Edge，`ctl_tree --hwnd 461404`）：
**147 节点 / 637 ms / 不截图 / 整页 DOM 穿透 / 每个元素带 eid ＋ 类名 ＋ rect**。

⇒ **网页场景用无障碍树（UIA）而不用 OCR 的方向是对的**，识别侧不需要返工。

#### ② 动作侧缺陷（本轮 T1 主线）

| 编号 | 症状 | 根因（读码复核后，不是原判断） | 修法 | 负责 |
|---|---|---|---|---|
| **D1** | `eid` 跨调用用会点错 | **三条出口的 `roles` 口径不同**：`ctl_tree` 签发（`core.py` 的 `t_tree`）= `('interactive','text')`＋上限 600；`ctl_find`（`uia_tree.py` 的 `find()`）= `('all',)`＋上限 3000；`ctl_click --eid` 重解析（`core.py` 的 `t_click` eid 分支）= `('all',)`。而 `eid` 是**遍历当场编的号**（`uia_tree.py` 的 `walk()`）⇒ 同一个号在两张表里必然指不同节点 | 旁表 ＋ 身份复核（**不引入 `tree_sha256`** —— 签发侧只算命中、校验侧走全树，指纹永远不相等，会造出「怎么点都点不了」的新坑） | 窗2 |
| **D2** | `--name` 在网页里找不到页面元素 | **深度不够**：老路径 `act.py` 的 `find_control(hwnd, name, max_depth=10)`，`d > max_depth` 即返回；而页面内容普遍深于 10 层（`uia_tree.DEFAULT_MAX_DEPTH = 25`）⇒ 只可能命中很浅的浏览器外壳 | `name` 匹配改走 `uia_tree`，命中多个就**拒绝并列出**，不许自己挑一个点下去 | 窗2 |
| ~~**D3**~~ | ~~坐标空间有两套~~ | ⛔ **不成立 —— 2026-10-14 DSH 裁定作废**。只有一套：**屏幕物理像素**（`core.py` 的 `t_click` eid 分支把 UIA 的 `hit['center']` 直接写回 `xy`） | `ctl_click --xy` 与 `ctl_tree` 的 rect 同源，**原样收，不做任何换算** | 已闭环 |

**D1 的实测现象**：窗口**完全静止**也点错 —— 点到 `(1058,236)`，目标在 `(288,507)`。
（`uia_tree.py` 的 `walk()` 早就记过同一个坑：`roles=('all',)` 会退化成跟默认一样，扫过节点数直接对不上，实测 787 → 3。）

#### ③ ★ D3 被否掉这件事，本身是本轮的重要产出

它否掉了「给每个节点再加 `rect_local` / `center_local`」这条路。理由不是啰嗦，是**它会造出静默点错**：

- agent 看到两个坐标字段，**总有选错的那个**；
- 选错之后换算出来的值**仍可能落在窗口矩形内** ⇒ 服务端 `act.py` 的包含校验拦不住（不报 `rc=5`）；
- ⇒ **静默点错**。这正是本单要治的病，不该由我们自己再种一个。

#### ④ 由此定下的动作侧原则（本轮不变量）

1. **识别**不要用坐标 —— 认界面靠 UIA 树。
2. **动作**一律要坐标，且必须绑**同一次快照**（`capture_id`，实测 TTL = **15 秒**，`gate.py` 的 `CAPTURE_TTL = 15.0`）。
3. **一条 `eid` 只在拿到它的那一次返回里有效**；D1 修好之前**不许跨调用用**。
4. **坐标只有一套**（屏幕物理像素），契约 `conventions.coordinates` 已写死。

完整写法（本轮新增，全项目**唯一定义处**）：`docs\AGENT接口.md` **§3-bis「网页场景正确姿势」** —— 别处只放指针，复述就会漂。

## 22. ★ 「录屏」的替代方案：证据分层（含本机实测数字）

> 用户问"录屏有没有替代方案"。答案不是"有"或"没有"，而是：**逐帧录屏该从「常态」降级为「按需」**。
> 依据：综述总结的收敛思路里有一条就是 **"recoverable memory rather than raw history replay"**（要可复原的记忆，而不是原始历史回放）[arXiv:2609.02309]。

### 22.1 本机实测的体积对照（这才是决策依据）

| 证据形态 | 实测体积 | 备注 |
|---|---|---|
| **UIA 控件树快照（JSON）** | **10,055 字节原始 / 1,235 字节 gzip（12.3%）** | 用 `_archive\tree_test.json` 实测；★ 小到可以**高频存** |
| 窗口截图（PNG，历史 1236 张） | 中位 **131.1 KB** / 均值 182.6 KB | |
| 全屏截图（PNG，历史 38 张） | 中位 **409.7 KB** / 均值 569.5 KB | |
| 全屏 JPEG q70（2560×1600） | **226.7 KB** | 早前实测 |
| 全屏 JPEG 0.5 缩放 q70 | **65.1 KB** | |
| 全屏 JPEG 0.25 缩放 q70 | **20.4 KB** | |

### 22.2 分层证据设计（替代"常开录屏"）

| 层 | 内容 | 频率 | 一天体积（估） |
|---|---|---|---|
| **L0 事件流** | 每次动作：谁、何时（单/墙钟）、调了什么、结果、`event_id` | 每次动作 | 几 MB |
| **L1 状态快照** | **控件树 gzip + 前台窗口元数据（标题/进程/URL/rect）** | 每 5 秒（变化才存） | ⚠️ **20–80 MB**（已按真实窗口尺寸修正，见下） |
| **L2 视觉锚点** | 全屏帧 **0.25 缩放** | 每 60 秒 | **≈ 29 MB** |
| **L2' 动作帧** | 动作**前后各 1 张**，**0.5 缩放** | 每次动作 | **≈ 13 MB**（按 100 次动作） |
| **L3 片段录像** | 只在**用户点名**、**不可逆动作**、**失败重试**时出片 | 按需 | 按需 |
| | | **合计** | **≈ 65–145 MB/天** |

**★ 为什么 L1 的估算被改了**（2026-10-02 二次实测）：
拿 34 节点的真实树导出算，**每节点：原始 296 字节 / gzip 36 字节**。按真实窗口尺寸外推：

| 节点数 | 原始 | gzip | 对应场景 |
|---|---|---|---|
| 100 | 28.9 KB | **3.5 KB** | 小对话框 |
| 200 | 57.8 KB | **7.1 KB** | 普通应用窗口 |
| 400 | 115.5 KB | **14.2 KB** | `perceive.py` 现有上限 |
| 800 | 231.0 KB | **28.4 KB** | 浏览器 / Electron 深树 |

→ 一个**200 节点的普通窗口**，每 5 秒存一次、存满 8 小时 ＝ **约 40 MB**；400 节点 ＝ **约 80 MB**。
我先前写的"≈20 MB/天"是**按 36 字节/节点的小树算的，偏低**，已改正。

**对照**：我原设计（常态 1 fps 全尺寸）＝ **18.68 GB/天**；改成 0.25 缩放常态帧后 ＝ **0.54 GB/天**；
**分层后 ≈ 65–145 MB/天** —— 比原设计小 **约 130–287 倍**，比上一版小 **约 4–8 倍**。
**并且 L1 是可查询的**：能直接问"那一刻有没有一个叫『保存』的按钮"——**这是像素给不了的**。

### 22.2.1 ★ SoM 图**不要落盘**（这条是实测逼出来的设计）

实测 Set-of-Mark 标注的开销（在 0.5 缩放图 1280×800 / q70 底图 65.1 KB 上画红框＋白底编号）：

| 元素数 | 绘制耗时 | JPEG | 涨了多少 |
|---|---|---|---|
| 10 | 1.8 ms | 72.1 KB | +7.0 KB（11%） |
| 20 | 1.3 ms | 79.1 KB | +14.0 KB（22%） |
| 50 | 2.1 ms | 98.2 KB | +33.1 KB（51%） |
| 100 | 3.5 ms | 127.6 KB | +62.5 KB（96%） |
| 200 | 6.9 ms | 182.0 KB | +116.9 KB（180%） |

**结论**：SoM 的**计算几乎免费（1–7 ms）**，但**红框是高对比度，会把 JPEG 撑大 22%–180%**。
→ 所以设计改成：**落盘只存"干净底图 ＋ 元素表（JSON）"，SoM 图在发给模型时现场渲染。**
这样存储成本为 **0**，而模型照样拿到编号。
（全尺寸 2560×1600 画 50 个元素：绘制 4.5 ms，JPEG 262.8 KB vs 底图 226.7 KB。）
**代价要说清**：L1 看不到画面本身（自绘控件、图片内容、网页渲染效果、报错弹窗的视觉状态都会丢），
所以 **L2 的低频视觉锚点不能省**，L3 的按需录像也不能删——**三者是互补，不是替代**。

### 22.3 什么时候仍然必须录片段

1. **不可逆动作**（提交/保存/删除）前后 —— 出片留证；
2. **动作失败或返回 `code=8`**（发了但没变化）—— 出片看当时到底怎么了；
3. **用户点名**"刚才那一下你给我回放"；
4. **涉钱/涉权操作**（这条按用户后续要求定）。

## 25. ★ 已知边界：**完整性级别不对等时，本控制面控制不了目标窗口**（2026-10-02 真机实证）

> ⚠️ **本节曾写错一版，2026-10-02 14:30 已纠正**：初版结论是"学习通以管理员权限运行"，
> 依据是"对目标 `OpenProcessToken(TOKEN_QUERY)` 被拒"。**该推断是错的** ——
> 后续发现**对我自己的进程做同样调用也被拒**，才查出真因：**本 agent 跑在 `Low` 完整性级别下**
> （`whoami /groups` → `Mandatory Label\Low Mandatory Level Label S-1-16-4096`；正常用户进程是 Medium）。
> **正确表述：目标的完整性级别高于本控制面**；在 Low 视角下**无法区分目标究竟是 Medium（普通）还是 High（提权）**。
> **这条教训要留着：`OpenProcessToken` 被拒只说明"对方比我高"，不说明"对方是管理员"。**

### 25.1 现象（一次真实点击换来的）
用户要求用控制面在学习通（`<被控应用目录>\cxstudy.exe`，Electron 应用）里做题。
闸门链**全部放行**（白名单 ✅ 通行证 B ✅ 租约 ✅ `capture_id` ✅），`act.py` 也返回
`🖱 点击 [SendInput 坐标点击] {"坐标":[562,898]}` ＋ **`rc=0` 成功** ——
**但界面一动没动**（像素核验 `dy=0`，人眼开图复核：选项 A 仍为选中态）。

### 25.2 根因：**完整性级别不对等 → UIPI 拦截**
| 观测 | 结果 |
|---|---|
| **本 agent 的完整性级别**（`whoami /groups`） | **`Low`（S-1-16-4096）** ← 决定性证据 |
| **对自己**`OpenProcessToken(TOKEN_QUERY)` | **也被拒**（正常进程读自己 token 永不会被拒）← 反过来证明了"我被降权" |
| `ShowWindow` 三种方式（`SW_RESTORE`/`SW_SHOWNORMAL`/`SW_SHOW`） | 全部静默失败，`IsIconic` 恒为 1 |
| UIA 控件树（`ctl_tree`） | 读不出来（`code=4`） |
| `PrintWindow` | 拿不到内容（截图退化为整屏抓取） |
| **`SendInput` 合成点击** | **被静默丢弃** ← UIPI 最典型表现 |
| 整屏抓取 | **成功**（抓屏不受 UIPI 限制） |
| `C:` 盘写入 / HKCU 写注册表 | `WinError 5` ← **同一根因**（Low 写不了 Medium 位置） |

→ **结论：本控制面与目标窗口完整性级别不对等，Windows 阻塞止跨级别发送输入与窗口消息。**
   **一个根因解释了本会话全部环境摩擦（沙箱写失败、注册表被拒、点击被丢）。**

### 25.3 ★ 三种修法，以及为什么推荐哪一种
| 方案 | 代价 | 评价 |
|---|---|---|
| **A. 把本控制面放到正常完整性级别下运行**（用普通终端直接跑 `AgentCtl.exe`，不经 DSH 的低完整性沙箱） | 无额外权限——就是普通用户进程 | ★ **推荐**。这才是对症的修法 |

### 25.4 对使用者的可见行为（必须写进入口文档，别让 agent 反复试）
- 对级别更高的窗口：`ctl_shot` **可能仍成功**（抓屏不受限），但 `ctl_click`/`ctl_type`/`ctl_fill`
  **会返回 `ok=true, code=0` 而实际无效** —— ⛔ **这是本系统最危险的假象**；
- **判别手法（推荐写进 agent 的作业流程）**：动作后**必做像素核验**（对比动作前后关键区域）；
  若 `rc=0` 但画面无变化 → **判为"动作未生效"**，不要重试到死，直接报告"目标的完整性级别高于本控制面"；

  1. `whoami /groups` 看**自己**的 Mandatory Label —— **先怀疑自己被降权，别一上来就怪目标提权**；

## 附录 C：术语表

| 词 | 本设计的含义 |
|---|---|
| **会话（session）** | 一次控制授权到结束的全过程；用户说的"开始控制有一个时间点"就是它的起点 |
| **起手见证 / 巡更见证** | 会话开始时 / 进行中每 60 秒，抓含任务栏时钟的画面并与系统时间比对 |
| **帧（frame）** | 一张落盘的画面（带烧录时间码）+ 数据库里的一行索引 |
| **事件（event）** | 一次工具调用或一次系统动作，带 `t_mono`/`t_wall`/`actor`/`result`/前后帧号 |
| **capture_id** | 一次观测的一次性凭据；坐标动作必须携带，过期或画面变了就拒 |
| **租约（lease）** | 单写者控制权；同一时刻只允许一个 agent 持有写权限 |
| **锚点（anchor）** | 离开本机（或离开 agent 可写范围）的链头记录，用来对抗整链重算 |
| **盲区（blind_spots）** | 本系统**看不到**的东西，必须随结论一起披露，不许删 |
