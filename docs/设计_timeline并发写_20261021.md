## 0. 一句话结论

> 真源的 timeline 写路径**只在进程内互斥**，而真源的应用形态恰恰是**多进程**——
> 于是 **seq 撞车 ⇒ 哈希链分叉 ⇒ SQLite 索引覆盖丢条**，并发再叠一层
> **jsonl 追加非原子 ⇒ 真相源自己被撕坏丢事件**。
> 修法首选**跨进程文件锁**（改动最小、语义最正、真相源不变），
> 旧链**不重算**，用**分段纪元（epoch）+ 段锚**把 21 处断链如实留在账上。

**复现脚本实测（6 进程 × 40 条 = 240 次 append，沙箱）**：

| 写者 | jsonl 行数 | 断链处数 | 不同 seq | 撕裂行 | sqlite 行数 | (a)(b)(c) |
|---|---:|---:|---:|---:|---:|---|
| **真源** `store.py` | 239~240 | **227~236** | 40 | 0~1 | **40** | 红 红 红 |
| **参考**（修法 A 原型） | 240 | **0** | 240 | 0 | **240** | **绿 绿 绿** |
| **缺陷**（拿掉跨进程锁） | 213~220 | 42~82 | 130~177 | 1~2 | 130~177 | 红 红 红 |

★ 真源那一行里 **sqlite 只有 40 行**（240 次写入只剩 40）：**200 条事件在索引里被覆盖没了**。

★ **复现手法说明（不是造假）**：脚本让 N 个**真子进程**各自构造一个写者（真源在

线上正是这个形态：每次 MCP/HTTP 调用起一个短命进程，

别的进程早把链尾推走了。栅栏只是把这个窗口**放大到必然命中**，不是造出来的病。

## 3. 根因：三条**互相独立**的缺陷（修的时候要一条条堵）

### 缺陷 1｜互斥只在进程内，链尾只在构造时读 ⇒ **seq 撞车 + 链分叉**

```
store.py:57   self._lock = threading.RLock()      # ← 只挡同进程的线程
store.py:61   self._head = self._load_head()       # ← 每个进程读一次，之后再也不读
store.py:154  with self._lock:                     # ← 进程内互斥
store.py:155      seq  = self._head[0] + 1         # ← 用的是**过期快照**
store.py:156      prev = self._head[1]
```

`threading.RLock` 对**另一个进程**完全无效 ⇒ 两个进程可以同时算出同一个 `seq`、
挂到同一个 `prev_hash` 上。实测现场形态（`timeline-20261019.jsonl` 第 334~341 行）：

```
334  2223  click                     prev=95cb5912
335  2224  shot                      prev=add6d819   ← 主写者
336  2225  windows                   prev=f0f4464b
337  2226  screen                    prev=6174c2fa
338  2224  action_allow_foreground   prev=add6d819   ← ★ 另一个进程：seq 又回到 2224
339  2225  scroll                    prev=8b2932a7
340  2227  shot                      prev=b9eb75ae   ← 主写者继续（它那边是连的）
```

★ 还有一个更隐蔽的坑：`_load_head()`（`store.py:110-128`）取的是
**max(seq) 那一行**的 hash，**不是文件顺序上的链尾**。
一旦链分过叉，这两者就不一样了 ⇒ 真源会**从错误的位置续链**。
（参考实现 `RefStore.read_tail()` 特意按**文件顺序的链尾**取，并在锁内重取。）

### 缺陷 2｜jsonl 追加**不是原子的** ⇒ **真相源自己丢事件**

`_append_jsonl()`（`store.py:134-142`）用 `open(path, "a")` 追加。
在 Windows 上，`O_APPEND` 的实现是「**先 seek 到 EOF，再写**」，
**不是**原子的 `FILE_APPEND_DATA` ⇒ 两个进程可以 seek 到**同一个** EOF，
后写的**覆盖**先写的字节 ⇒ 记录被**拼坏 / 撕坏**。

实测（`--writer=缺陷`，240 次写入）：

```
240 次 append → jsonl 只有 210~220 行，其中 1~3 行**不可解析**：
   坏行样例 1:  "}"                      ← 一条记录的头被另一条覆盖了，只剩尾巴
   坏行样例 2:  "{"actor":"repro",...    ← 两条记录被拼到了同一行
```

★ **这条比缺陷 1 更狠**：缺陷 1 只让**索引**少条，jsonl 还在；
缺陷 2 让**真相源本身**少条。它就是判据里 (a)「jsonl 行数 == 写入总数（今天会少）」的由来。
（真源跑的时候有时不触发、有时触发——**取决于时序**，所以判据 (a) 对真源是**竞态**的，
判据里对真源只断言「三条不可能同时成立」，不钉死哪一条红。）

### 缺陷 3｜`events.seq` 是 PRIMARY KEY + `INSERT OR REPLACE` ⇒ **索引覆盖丢条**

```sql
-- store.py:77   seq INTEGER PRIMARY KEY
-- store.py:173  INSERT OR REPLACE INTO events(seq, ...) VALUES(?, ...)
```

即使把缺陷 1、2 修好，只要还有任何两条记录 `seq` 相同，
**SQLite 就装不下它们**（`seq` 是主键）⇒ 索引**结构性地**少条。
⇒ 修法必须保证 **`seq` 全局唯一**，而不是「尽量不撞」。

★ 连带一条：`rebuild_index()`（`store.py:257`）是「从 jsonl 重建索引」的官方手段，
但它同样用 `INSERT OR REPLACE` ⇒ **重建修不好被撞 seq 的历史**（重建后还是 3396 行）。
这说明**旧链的修复不能靠重建索引**（见 §6）。

### 缺陷 4（次要，但会咬人）｜`clock.py` 的会话锚点是**跨进程**单调钟锚点

`clock.Clock.session_open()`（`clock.py:90`）给的是**跨进程可对账**的单调钟锚点
（`t_mono0` + `t_wall0`）。这条**用得上**：并发写下的事件排序，
除了 `seq`，还可以用 `(t_mono0 + t_wall0)` 的墙钟投影做**第二把尺子**，
用来判断「这 21 处断链到底是**谁**插进来的、插在什么时刻」。
（`t_mono` 是 `time.perf_counter()`，**每进程各算各的**，不可直接跨进程比；
但锚点把两边的墙钟对齐了。）

## 4. 修法对比（四种）

> 每种都按派单要求写清：**改动面 / 崩溃恢复语义 / 对「truth 是 jsonl 还是 sqlite」的影响 /
> 迁移路径 / 与现有 store.py 的兼容性**。

### 修法 A｜**跨进程文件锁**（★ 推荐）

**做法**：在 `store.py` 里加一把**跨进程**排他锁，把
「读链尾 → 算 seq/prev → 追加 jsonl → 写 SQLite」整段**临界区**包住。

**可执行原型**：`tests/_timeline并发_复现.py` 的 `RefStore`
（**只覆盖 `append` 一个方法**，其余记账逻辑全部继承真源 ⇒ 链格式与真源逐字同构）：

```python
class RefStore(tl_store.Store):
    def append(self, kind, **kw):
        with FileLock(self.lock_path):        # ← 跨进程（OS 级）排他锁
            self._head = self.read_tail()      # ← 锁内重读链尾（按文件顺序，不按 max(seq)）
            return super().append(kind, **kw)  # ← 记账逻辑全部走真源，一行没抄
```

**锁的选型**：用 **OS 级**锁（Windows `msvcrt.locking(LK_NBLCK)` / POSIX `fcntl.flock`），
**不要**用「`O_EXCL` 锁文件」——后者在进程被 kill 时会**留下死锁文件**（死等）。
OS 级锁随句柄关闭**自动释放**，进程崩了锁就没了。

| 项 | 结论 |
|---|---|
| **改动面** | 最小。`store.py` 加 1 个锁类 + `append`/`append_frame` 临界区约 20 行；**不改**记录格式、**不改** schema、**不改** 公开 API |
| **崩溃恢复语义** | 进程崩在临界区里 ⇒ 锁自动释放 ⇒ 下一个进程接着写。**最坏情况**：jsonl 已追加、SQLite 未写 ⇒ 索引少一条 ⇒ `rebuild_index()` 能补回（前提是 seq 不撞，锁保证了） |
| **truth 影响** | **truth 仍是 jsonl**。索引仍是**可重建**的派生品，与设计文档 §4 的定位**一字不改** |
| **迁移路径** | §6（与修法 B/C 同一套） |
| **兼容性** | 完全兼容。`Store(root)` 签名不变、`append()` 签名不变、`rebuild_index()` 不变、`verify()` 不变；**只加锁不加语义** ⇒ 旧数据不用重写 |
| **性能** | 临界区里含一次「读链尾」+ 一次 jsonl 追加 + 一次 SQLite 写。sqlite 本来就是串行写的 ⇒ 净增开销 ≈ 一次文件尾读。**链尾可以缓存**（见 §7） |
| **风险** | ① 锁粒度粗 ⇒ 所有写者排队（对 timeline 这个写入量完全够）；② 临界区里**必须**包含 jsonl 追加，否则缺陷 2 还在；③ **忘了把 `append_frame` 也纳入** ⇒ 事件链与帧链还会分叉 |

### 修法 B｜**单写者进程**（写者守护进程 / 本地 socket）

**做法**：所有写者把「要写的事件」交给**唯一一个**写者进程（daemon 或本地 socket 服务），
由它串行地追加。写者只管发请求。

| 项 | 结论 |
|---|---|
| **改动面** | **大**。要新增一个常驻进程 + 一套 IPC 协议 + 一套「写者掉线怎么办」的降级路径；`core.py` 里所有 `store.append` 调用点都要改成 RPC |
| **崩溃恢复语义** | 守护进程崩 ⇒ 写入通道断 ⇒ 必须有「排队缓冲 + 重试 + 降级（直写还是丢弃）」策略。**最难的部分在这里** |
| **truth 影响** | 仍是 jsonl；但多了一个「**缓冲中的事件还没落盘**」的中间态 ⇒ 真相源与「用户以为已经记下的事」之间出现**新的不一致窗口** |
| **迁移路径** | 同 §6 |
| **兼容性** | **不兼容**：写者 API 从「同步函数」变成「可能阻塞/可能失败的 RPC」⇒ 所有调用点的错误处理都要改 |
| **性能** | 最好（写者零竞争） |
| **风险** | ① **引入了常驻进程**——本仓明确「不许起常驻进程」；② 守护进程本身成了单点故障与新的「真相源之外的状态」；③ 交付/安装/开机自启链路全要动（`install.ps1`） |

### 修法 C｜**seq 分配器**（独立小进程只发号）

**做法**：起一个（或一个文件锁保护的）**号段分配器**，只负责发 `seq`；
写者拿到 `seq` 后自己写文件。

| 项 | 结论 |
|---|---|
| **改动面** | 中。需要一个「原子发号」机制（独立进程 + socket，或 SQLite 的 `AUTOINCREMENT` 行） |
| **崩溃恢复语义** | 号段分配器崩 ⇒ 发不出号 ⇒ 写入停摆（**可检测**：写者超时）。比修法 B 好，因为不需要数据缓冲 |
| **truth 影响** | 仍是 jsonl。但 ⚠ **`seq` 唯一 ≠ 链正确**：分配器只保证**号不撞**，**不保证 `prev_hash` 正确**——两个进程仍可能拿到 `seq=101/102`，却都把 `prev_hash` 写成 `seq=100` 的 hash ⇒ **链照样分叉** |
| **迁移路径** | 同 §6，但多一条：分配器要能从**现有 max(seq)=3396** 接着发号（现场还在涨，见 §6） |
| **兼容性** | 中等。`append()` 内部要改成「先要号，再写」 |
| **性能** | 好（发号极快） |
| **风险** | ⚠ **它只修缺陷 1、3，修不了缺陷 2**（两个写者仍可同时写 jsonl ⇒ 撕裂照旧）、也**修不了链分叉**（`prev_hash` 的正确性要靠写者自己保证 ⇒ 又回到「锁内重读链尾」）⇒ **单独用是不够的**，必须配一把写锁 |

### 修法 D｜**改成「SQLite 是真相源」**（对照列，不推荐）

| 项 | 结论 |
|---|---|
| **改动面** | 极大（整个真相源定位翻转） |
| **崩溃恢复语义** | SQLite 的 WAL 事务其实**比**裸文件追加**更**安全 |
| **truth 影响** | **truth 变成 SQLite** ⇒ 与本仓现有设计文档 §4「jsonl 是真相源、SQLite 只是可重建的索引」**正面冲突** ⇒ 详细设计、验收报告、判据都要重写 |
| **迁移路径** | 要把 3434 条 jsonl 灌进 SQLite，且**解决那 38 条重复 seq**（`seq` 得改成非主键或加 `rowid`）⇒ 哈希链的 `seq` 语义要重新定义 |
| **兼容性** | **不兼容**：`verify()`、`rebuild_index()`、所有对 jsonl 的直接读（`core.py`、面板、导出）全要改 |
| **为什么列它** | 因为它是**唯一**能同时解决缺陷 2、3 的路子（SQLite 事务天然原子）。但代价是把整个仓的真相源定位翻过来 ⇒ **本单不推荐**，除非用户决定重做真相源 |

### 对比汇总

| 维度 | A 跨进程文件锁 | B 单写者进程 | C seq 分配器 | D SQLite 为准 |
|---|---|---|---|---|
| 改动面 | **最小**（~20 行） | 大（守护+IPC+降级） | 中（发号机制） | 极大（真相源翻转） |
| 堵缺陷 1（撞 seq/分叉） | ✅ | ✅ | ⚠ 半个（号唯一≠链对） | ✅ |
| 堵缺陷 2（jsonl 撕裂） | ✅（临界区含追加） | ✅（单写者） | ❌ | ✅（事务） |
| 堵缺陷 3（索引覆盖） | ✅（seq 全局唯一） | ✅ | ✅ | ✅（改主键） |
| 崩溃恢复 | 锁自动释放，坏一次索引 | **最难**：缓冲 + 降级 | 分配器死 ⇒ 停写 | WAL 事务，最好 |
| truth 定位 | **不变（jsonl）** | 不变 | 不变 | **翻转（SQLite）** |
| 与现有 store.py 兼容 | **完全兼容** | 不兼容 | 中等 | 不兼容 |
| 常驻进程 | **无** | **有**（本仓不许） | 无（可退化为文件锁） | 无 |
| 性能 | 够用 | 最好 | 好 | 好 |
| **结论** | ★ **推荐** | 过度设计 | 单独不够 | 代价过大 |

★ **推荐 = A**，理由三条：
1. **改动面最小且完全兼容**——真源 `append()` 的签名、记录格式、schema、公开 API 一个都不动；
2. **一次锁同时堵住缺陷 1/2/3**——临界区把「读链尾 → 算号 → 追加 jsonl → 写索引」整段包住，
   链的正确性与文件的原子性**由同一把锁保证**；
3. **不引入常驻进程**——与本仓「不许起常驻进程」的边界一致。

★ **如果将来要上 B（单写者）**，A 的锁**仍然要留着**：
单写者解决的是「写者太多」，不解决「写者自己崩在临界区里」。
**A 是地基，B 是可选的优化**。

## 5. 修法 A 的最小补丁形状（**本单不提交真源**，这里只给形状给 本地 agent 单用）

```python
# src/agentctl/store.py （示意，未提交）
class _CrossProcessLock:
    """跨进程排他锁。Windows 用 msvcrt.locking，POSIX 用 fcntl.flock。
    ★ 进程崩 ⇒ 句柄关 ⇒ 锁自动释放（不留死锁文件）。"""
    ...

class Store:
    def __init__(self, root, *, fsync_every=1):
        ...
        self._lock = threading.RLock()          # 进程内（保留：同进程多线程）
        self._xlock = _CrossProcessLock(os.path.join(root, ".timeline-write.lock"))
        self._head = self._load_head()

    def append(self, kind, ...):
        with self._xlock:                        # ← 新增：跨进程临界区
            with self._lock:                    # 保留：进程内互斥
                self._head = self._read_tail()  # ← 新增：**锁内重读链尾**（按文件顺序）
                ...原逻辑一字不改...

    def append_frame(self, path, ...):
        ...同样包进 self._xlock...               # ← ★ 别漏：帧链与事件链共链
```

**三条必须一起做的点**（漏一条就白修）：

1. 临界区**必须包含 jsonl 追加**（否则缺陷 2 还在 ⇒ 真相源照样撕裂）；
2. **锁内必须重读链尾**（否则缺陷 1 还在 ⇒ seq 照样撞）；
3. **链尾要按文件顺序取**，不能取 `max(seq)` 那一行（否则链分过叉后会从错的位置续链）。

## 6. 旧链 21 处断链的迁移路径

> 派单明确要求：「旧链已有 21 处断链怎么办」。下面给**三条候选**与**一条推荐**。

### 6.0 先把事实钉住（这决定了迁移不能做什么）

* 断链**不是**「某条记录被篡改」——是**并发写**把两条记录挂到了同一个 `prev_hash` 上
  （§3 缺陷 1），以及极少数记录被**撕裂**（§3 缺陷 2）。
* 现场 `jsonl 行数 − sqlite 行数 == 重复 seq 条数`（3434 − 3396 = 38 = 38）⇒
  **jsonl 里那 38 条重复 seq 的记录本身是完好的**（能解析、hash 自洽），
  被丢的只是**索引**。
* 链断在 21 处，但**重复 seq 只有 38 条** ⇒ 断点数与重复数**不相等** ⇒
  断链**不全是**撞 seq 造成的，还有撕裂行造成的。**修复时不能只按撞 seq 去补。**

### 6.1 候选甲：**只往后写，承认旧链有断点**（不重算任何历史）

* 做法：从今往后用修法 A 写，**新记录接在当前链尾**（`max(seq)` 之后）。
  旧的 21 处断点**原样留着**，不修。
* 优点：**零风险、零改写**；旧记录的 hash 一个字节没动 ⇒ 「事后局部改动可检出」的语义**完全保住**。
* 缺点：`verify()` 会**永远**在第 1 处断点返回红 ⇒ 现场可观测性长期是红的。

### 6.2 候选乙：**重算整条链**（把 21 处断点焊死）

* 做法：按文件顺序重算每条的 `prev_hash`/`hash`，把 21 处断点**接成一条直链**。
* 致命问题：**这会抹掉「哪些记录是并发插进来的」这一信息**，而且
  **重算 = 把链的诚实边界降级**。`store.py:8-9` 自己写着：
  「本机链**只防『事后局部改』**，防不了『有磁盘权限者整体重算』」。
  ⇒ **一次官方重算，就把「整体重算」这件事变得不可检出** ⇒ 之后谁都能重算而查不出。
  ⇒ **不推荐**。（除非同时把旧链整体**带外锚点**化，代价见 §6.4。）

### 6.3 候选丙：**分段纪元（epoch）+ 段锚**（★ 推荐）

* 做法：
  1. **不重算**旧记录的任何 hash；把现有 3434 行整体定为 **epoch 0**。
  2. 在 epoch 0 的末尾写一条**段锚**（带外锚点 `anchors.jsonl` 已有这套机制，
     `store.py:335` 的 `write_anchor()`），记录 epoch 0 的
     `head_seq` / `head_hash` / `chain_ok`（诚实写 False）/ 统计。
  3. 从此往后开 **epoch 1**：新链从 epoch 1 自己的 genesis 开始，
     `prev_hash` 指向 **epoch 1 的 genesis**，并带上 `epoch=1` 字段。
  4. `verify()` 改为**按 epoch 分段验**：每段内部必须链通；
     段与段之间**只看段锚对不对得上**（epoch 0 的段锚 hash == epoch 1 的起点 hash）。
* 优点：
  - **旧记录一个字节没改** ⇒ 诚实边界保住；
  - 21 处断点**如实留在 epoch 0 里**（不修，但也不假装没有）；
  - `verify()` 能给出**有意义的绿**：epoch 1 全通 ⇒ 「从修好那天起没再坏过」；
  - 与「带外锚点」机制天然衔接（`clock.py` 的跨进程单调钟锚点可用来给 epoch 起点打时间戳）。
* 缺点：多一个 epoch 字段；`verify()` / 读侧要认 epoch（改动面比甲大，比乙小）。

### 6.4 若一定要「旧链也变绿」——只能靠**带外锚点**兜底

`store.py` 的 `anchors.jsonl` 机制（`write_anchor()`）就是为此准备的：
**在重算之前，先把「重算前的链头 hash + 统计」写到带外锚点**，
重算之后再写一条 ⇒ 事后能证明「重算发生在锚点之后」。
⇒ **唯一能安全做候选乙的方式**，但代价是：必须**先**有一批可信锚点
（现在 `anchors.jsonl` 有没有、覆盖多少时间跨度，**本单没查**，本地 agent 单要自己核）。

### 6.5 推荐结论

> **修法 A + 候选丙（分段纪元）**：
> 1. 先上修法 A，**止血**（从今往后不再撞）；
> 2. 再上候选丙，**分段**（把 21 处断点如实圈进 epoch 0，不重算）；
> 3. `rebuild_index()` **重跑一遍**，把索引补齐到 3434 行
>    ——⚠ 注意：现场有 38 条**重复 seq**，重建**补不齐**（`seq` 是主键）
>    ⇒ 重建前必须先**决定那 38 条重复 seq 怎么办**（见 6.6）。

### 6.6 那 38 条重复 seq 怎么办（迁移里最棘手的一块）

`seq` 是 PRIMARY KEY ⇒ SQLite **装不下**两条同 seq 的记录。
三条候选：

| 候选 | 做法 | 代价 |
|---|---|---|
| **甲** | **重编号**：把后写的重复 seq 改成新号（`max+1` 往后），**并重算它及其后所有记录的链** | 等于局部重算 ⇒ 诚实边界被局部破坏（但范围明确、有锚点可证） |
| **乙** | **保留 jsonl 原样**，SQLite 侧**放弃 `seq` 主键**，改用 `rowid` + 一列 `seq`（可重复），索引加 `(seq, hash)` 唯一约束 | **改了 schema** ⇒ `rebuild_index()` / 查询侧都要改；但 jsonl **一个字节不动** ⇒ 诚实边界**完整保住** |
| **丙** | 挑一条删掉 | ❌ **禁止**：删真相源记录就是篡改 |

★ **推荐乙**：把「重复 seq」这件事**如实反映到索引的 schema 里**（`seq` 不再是主键，
而是普通列 + 唯一约束 `UNIQUE(seq, hash)`）。
理由：重复 seq 本身就是「并发写的化石」——**它是证据，不是垃圾**。
真源 jsonl 是**只追加**的事实记录，**不许因为索引装不下就改历史**。
