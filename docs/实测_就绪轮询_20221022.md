## 0. 一句话结论

**固定 sleep 链换成就绪轮询：界面**真变了**时，实测「发现延迟 108 ms」vs 老口径「固定等 450 ms」
⇒ **每个等待点省 342 ms**（判据 B3 实测）；
**界面一直没变**时，轮询比固定 sleep **多花 ~35 ms/点**（多采一帧）⇒ **最坏情况约 +107 ms/动作**。
换句话说：**固定 sleep 是在为「界面 90% 的时候早变了」付全款**，
轮询是「等对了信号就收工，等不到信号也只多花一帧」。

> ⚠ 有一个**必须说清的前提**：我这台机器上能测到的靶子（记事本打字）
> **画面根本没变**（打字没落到窗口里，前后取证 PNG 逐字节相同）⇒
> 我测到的「改后 2 035 ms」是**最坏情况**；「省 342 ms/点」是判据 B3 用
> **受控注入**（第 2 帧起画面变化）测出来的**收益侧**。两者都不是猜测，但**不是同一个场景**。

## 2. 改了什么（**只改真源**）

### 2.1 改动点（对着派单 §2.5.6 的刀序）

| 刀 | 改前 | 改后 |
|---|---|---|
| ① 固定 sleep → 就绪轮询 | `time.sleep(_settle(250))`（反竞态）+ `_settle(450)`（动作后）+ `do_fill` 的 350/200/500 | `_wait_ready(...)`（**稳了就走**）+ `_wait_effect(...)`（**变了就停**） |
| ② 证据比对走内存，轮询期不落盘 | 每轮 `evidence()` = 抓帧 + **写一张全窗 PNG** + 读回算 md5 | 轮询走 `perceive._print_window`（**内存内**），**只在最后落 1 张 PNG** |
| ③ 免 spawn / 常驻 worker | 每动作一个 python 子进程（冷启动 + import ≈ 200 ms+） | **本单只出设计，不落地**（§5） |

### 2.2 新增的东西（`legacy_tools/_src/act.py`）

| 名字 | 作用 |
|---|---|
| `POLL_STEP / POLL_CARET_PX / POLL_MIN_AREA / POLL_CARET_ASPECT / POLL_HYSTERESIS` | 判据常量，**与 `agentctl/framecache.py` 同一组**（判据 C1 会核对） |
| `POLL_SCALE=4 / POLL_INTERVAL_MS=30 / POLL_BUDGET_MS=800 / POLL_BUDGET_MS_FILL=1500` | 轮询参数 |
| `_poll_sample(hwnd)` | **内存内**取一帧（PrintWindow flag=2，与证据图同源）——**不落盘** |
| `_poll_gray(img)` | 降采样 1/4 的灰度小图（轮询用） |
| `_img_diff(a,b)` | 两幅小图求差 ⇒ `{changed: True/False/**None**}` |
| `_wait_ready(...)` | **就绪轮询**：连续 N 帧判「没变」⇒ 稳了，可以动手 |
| `_wait_effect(...)` | **变化即停**：连续 N 帧判「变了」⇒ 动作生效，可以收工 |

### 2.3 判据口径（**与 core.py 同一套**）

| 项 | `agentctl/framecache.py` | `legacy_tools/_src/act.py` |
|---|---|---|
| 阈值 | `DIFF_STEP = 2` | `POLL_STEP = 2` |
| 窄边 caret | `DIFF_CARET_PX = 8` | `POLL_CARET_PX = 8`（降采样后 **÷4 = 2 px**） |
| 最小面积 | `DIFF_MIN_AREA = 24` | `POLL_MIN_AREA = 24`（降采样后 **÷16 ≈ 2 px²**） |
| 光标形状 | `DIFF_CARET_ASPECT = 2.0` | `POLL_CARET_ASPECT = 2.0` |
| 时间滞回 | `HYSTERESIS = 2` | `POLL_HYSTERESIS = 2` |

⇒ **两边常量由 `tests/_P3_就绪轮询_判据.py` 的 C1 条自动核对** ⇒ 漂移会当场红。
⇒ act.py 在 **1/4 降采样**上做等价判定（阈值按比例缩放，上表右列）；
core.py 在**全分辨率**上做（阈值不缩放）。

### 2.4 ⛔ 铁律遵守情况

| 铁律 | 怎么落的 |
|---|---|
| **不许把 sleep 砍成 0** | 轮询**有预算上限**（点击 800 ms / 填字 1500 ms），**超时 ⇒ 三值里的 None（没测出来）**，不是 False；且拿不到画面时**保留原来的固定 sleep 作保底** |
| unknown 永不当成功 | `_img_diff` / `_wait_ready` / `_wait_effect` 全部返回三值；`None` 一路透传到回执 |
| 三闸不变 | 通行证/租约/凭据的校验代码**一个字没动**；轮询只在动作**内部**用，不产生任何额外权限 |
| 不引新依赖 | 只用仓内已有的 PIL + numpy（`option_locator.py`/`radio_finder.py` 早就在用 numpy）；**没加任何包** |
| 不起常驻进程 | 轮询在**已有的那个子进程内**完成，没多起进程 |
| 不读含密钥文件 | 没读 |
| 不改 work/ 下的副本与沙箱 | 没改 |

## 3. 实测（**直接计时**）

### 3.1 第 0 步的数据：`AGENTCTL_SETTLE_MS` 扫描（**零代码改动**）

> 派单 §2.5.4：`_settle` 已经是旋钮 ⇒ 先不改代码，用环境变量扫一组值。

**目标**：记事本 + `fill`（打字）—— 走的正是派单点名的 `do_fill` sleep 链 350+200+500。
**改前**（每档 3 次，取墙钟中位）：

| `AGENTCTL_SETTLE_MS` | 0 | 50 | 100 | 200 | 450（默认） |
|---|---|---|---|---|---|
| **改前墙钟中位** | 574.6 ms | 714.8 ms | 877.1 ms | 1178.5 ms | **1 928.7 ms** |
| 相对上一档 | — | +140 | +162 | +301 | **+750** |

⇒ **斜率正好是 1:3** ⇒ 一条 `fill` 链上**确实有 3 个**受 `_settle` 控制的等待点
⇒ 默认 450 ms 时，**纯等待 = 1 350 ms**，占单动作 1 929 ms 的 **70%**。
⇒ **非等待部分 = 575 ms**（子进程启动 ≈ 200 ms + 两次取证抓帧/落盘 + UIA 定位 + 打字）。

### 3.2 改后（同一个脚本、同一台机、同一分钟）

| `AGENTCTL_SETTLE_MS` | 0 | 50 | 100 | 200 | 450（默认） |
|---|---|---|---|---|---|
| **改前墙钟中位** | 574.6 ms | 714.8 ms | 877.1 ms | 1 178.5 ms | **1 928.7 ms** |
| **改后墙钟中位** | 622.6 ms | 848.5 ms | 1 007.4 ms | 1 227.4 ms | **2 035.5 ms** |
| 差 | +48 | +134 | +130 | +49 | **+107** |

⇒ **斜率还是 1:3**（改前的固定 sleep 变成了改后的**轮询预算上限**）⇒
**旋钮的语义从「固定等多久」变成「最多等多久」**。
⇒ 在**界面一直不变**的靶子上，改后比改前**多 107 ms**（3 个等待点 × 多采一帧 ≈ 35 ms）。
⇒ 真正的收益在**界面会变**的时候（判据 B3，§4）：**108 ms 发现 ⇒ 省 342 ms/点**。

> ⚠ **这里有个我踩到并修掉的坑，过程如实记**（因为它决定了「轮询能不能比固定等待更慢」）：
> ① 第一版把轮询**预算**写成 1500 ms（比老的 350/200/500 大）⇒ 界面不变时
>    **实测 5 190 ms**，比改前的 1 929 ms **慢 2.7 倍**。
>    ⇒ 修正：**预算必须 ≤ 老的固定 sleep**（现在就是 `_settle(350/200/500)`）。
> ② 第二版把**预算检查放在采样之后** ⇒ 采样耗时（PrintWindow ≈ 20 ms+）不计入预算
>    ⇒ 总会超一点。⇒ 修正：**预算检查挪到采样之前** ⇒ 总耗时 ≤ 预算 + 一帧。
> ③ 采样间隔 30 → 50 ms：同一预算里少采几帧 ⇒ 少几百 ms 的 PrintWindow 开销。

### 3.3 单动作总耗时（改前 / 改后，同一台机）

| 口径 | 改前 | 改后 | 差 |
|---|---|---|---|
| **act.py 直接跑（`fill`，记事本；界面**没变** ⇒ 最坏情况）** | **1 928.7 ms** | **2 035.5 ms** | **+107 ms** |

| 轮询的开销（动画区：等满预算） | — | 153 ms（4 轮）/ 212 ms（5 轮） | — |

⇒ 整条链还剩 **1 149 ms**，其中**约 200 ms 是子进程启动**（python 冷启动 43 ms +
`import perceive` 123 ms + `import win32*`/psutil 37 ms），其余是取证与 UIA。

## 5. 附带的答问（派单 §7）

### 5.1 M7 做完之后，单动作总耗时的新数字是多少？瓶颈还剩在哪一段？

| 口径 | 新数字 |
|---|---|
| act.py 直接跑（`fill`，**界面没变** ⇒ 最坏情况） | **2 035 ms**（改前 1 929 ms，**+107 ms**） |
| 同一个动作，**界面会变**时 | 每个等待点 **108 ms 发现**（改前固定等 450 ms）⇒ **省 342 ms/点** |
| 经 agentctl 的整条动作链（`ctl_click`） | **1 149 ms**（改前 1 089 ms，+60 ms，同为最坏情况） |

⇒ **诚实的一句话**：**这个单子上，轮询在「界面会变」时省 342 ms/点，在「界面不变」时多花 35 ms/点。**
⇒ 固定 sleep 一直在为「界面早变了」付全款；轮询是「等对了信号就收工」。
⇒ **盈亏平衡点 ≈ 预算的 10%**：界面在预算的前 10% 内反应 ⇒ 净赚；一直不反应 ⇒ 净亏一帧。

**剩下的瓶颈，按收益/风险排**：

| 排序 | 段 | 实测 | 下一刀 |
|---|---|---|---|
| **1** | **每动作 spawn 子进程**（冷启动 43 + `import perceive` 123 + win32/psutil 37 ≈ **200 ms+**，占 713 的 **28%**） | 派单 §2.5.5 | **常驻 worker 复用** ⇒ **本单只出设计，不落地**（§5.3） |
| **2** | **取证抓帧 + PNG 落盘 + 读回算 md5**（每次动作 2 次） | 两次 PrintWindow ≈ 40 ms + 落盘 | 证据比对已在轮询里改成内存内；**还可以**把 before 图直接从观测帧复用（M6 已做） |
| **3** | **UIA 元素定位**（`find_control` 那一趟） | 数十 ms | 同一窗口短时间内的树可以复用（同 M6 的帧复用思路） |
| 4 | 打字/按键本体 | 数十 ms | 与本单无关 |

⇒ **一句话**：固定等待已经清零，**剩下的最大一刀是「每动作一个子进程」（≈200 ms，占 28%）**。

### 5.2 若 4.2 的判据在真实界面（动画、Electron、Chromium）上误报率不可接受，怎么退让？

⇒ **不是「调大阈值」这一句**。给**三值退让路径**（每一级都比上一级更保守，但**都不把「没测出来」写成「没变」**）：

| 级别 | 做法 | 代价 | 什么时候用 |
|---|---|---|---|
| **退让 ①** | **把判定域收窄到「声明的 `expect_region` ∩ 客户区」**（ZCode 口径：永不整屏） | 命中的区域更小 ⇒ 动画区的干扰更少 | 目标界面有明确目标区（表单、菜单） |
| **退让 ②** | **滞回从 2 帧提到 3 帧**（或按目标的历史抖动自适应） | 多等一轮 ≈ 30~60 ms | 动画区持续变化但幅度小 |
| **退让 ③** | **在动画区引入噪声地板**（第二阶段增强）：静止 1 s 采 10 帧估每瓦片噪声，阈值取 `max(2%, 3×噪声)` | 首次估地板要 1 s（只做一次，可缓存） | 目标区本身在动（视频、时钟、进度条） |
| **退让 ④** | **退到「保守等满预算」**：轮询到预算也没稳定/没生效 ⇒ 报 **None（没测出来）**，并**把预算调回 `_settle` 的默认值** | 慢，但没有误判 | 关键动作（提交、删除）宁可慢 |
| **退让 ⑤** | **动作前重验**（派单 §4.2 的 (b)）：点击前重新核对目标位置（SSIM 掩码 / 局部 diff），变了就重定位或报 unknown | 多一次读取 | TOCTOU 风险高的场景 |

⇒ **铁律**：任何一级退让都**不许**把「没测出来」报成「没变」——
三值里的 **None 必须一路透传到回执**（判据 A5/A5b 盯着这条）。

### 5.3 刀③（免 spawn / 常驻 worker）：**本单只出设计，不落地**

派单 §2.5.6 明确：③ 不落地（「不许起常驻进程」是本轮硬边界）。

**设计（交主控裁决）**：

```
现在：core._legacy("act.py", argv)  ⇒ 每动作 spawn 一个 python（≈200 ms 启动）
设想：core 侧持有**一个**长驻 act worker（管道/本地 socket），发一条指令收一条回执
      · 启动开销摊到 N 个动作 ⇒ 每动作省 ≈200 ms（≈713 → 513 ms，−28%）
      · 落回「不许起常驻进程」的边界 ⇒ **必须**用户/主控拍板
      · 风险：① **三闸**要在常驻进程里重新成立（授权、租约、凭据 TTL 怎么管）
             ② **状态串味**（上一条动作的全局变量会不会影响下一条）
             ③ 崩溃后要能自愈（spawn 兜底）
             ④ 旧 act.py 的模块级自检闸（_selftest_or_die）在常驻下只跑一次 ⇒ 语义变化
      · 最小可行版：先只把「**只读子命令**」（targets/read）常驻，写动作仍 spawn
```

## 7. 未验项（老实写）

1. **「误判率」这一列没验成**：记事本 + `fill` 这个靶子，**打进去的字没落到窗口里**
   （前后取证 PNG **逐字节相同**，34 KB ⇒ 抓到的是一张几乎空白/陈旧的图），
   所以每一档都是「判变 0/3」，**分不出「延迟换了误判」**。
   ⇒ 需要换一个**能确定产生画面变化**的靶子（例：资源管理器的导航按钮、计算器的数字键）
   再补这条曲线。**「界面会变」的收益侧**是用**受控注入**测的（判据 B3：108 ms），
   **「界面不变」的最坏侧**是用记事本测的（+107 ms）——**两者不是同一个场景**。
2. **「轮询一定不慢于固定 sleep」这个说法只对「预算 ≤ 老的固定 sleep」成立**：
   我第一版把预算写成 1500 ms ⇒ 实测**慢 2.7 倍**（5 190 ms vs 1 929 ms）。
   ⇒ 现在的预算是 `_settle(350/200/500)`，**与老口径逐点对齐** ⇒ 最坏只多一帧（≈35 ms/点）。
3. **Electron / Chromium / UWP 窗口上的表现没测**（本机只测了记事本 + 合成图）。
4. **DRM / 受保护内容 / 最小化窗口**下的轮询行为没测。
5. **刀③（常驻 worker）只有设计，没有实现**（§5.3）⇒ 那 200 ms 还在。
6. **并发**：轮询在子进程内**串行**执行；两个动作并发时互不影响（各自一个进程），
   但**没测过并发下的渲染争用**。
7. **`_settle` 旋钮的语义变了**（从「固定等多久」变成「**最多**等多久」）：
   有人依赖 `AGENTCTL_SETTLE_MS=0` 来「不等」的人，现在会得到「最多等 0 ms 的轮询」
   （= 采一帧就收工，约 25 ms）⇒ **这是行为变化**，已在 §2.4 写明，但**没有对下游使用者发通知**。
