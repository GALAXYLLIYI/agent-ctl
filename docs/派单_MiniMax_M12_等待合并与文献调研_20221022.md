## 1. 已知基线（**直接用，别重测**）

来源：`docs\实测_动作链分段_20221022.md`（M11 交付，主控已独立复核）。

| 段 | 实测 | 备注 |
|---|---|---|
| 端到端 `ctl_click` | **1,682~1,718ms** | 3 轮一致 |
| ② act 子进程（spawn+import 95~100ms、UIA 查找 43.8ms、注入 0.25ms、采样 40.96/47.68ms、其它） | **占最大头，3/3 轮一致** | 未归因 99.6~109.8ms 单列 |
| act 侧 `_wait_ready`（动作前就绪等待，预算 250ms） | **177.4ms**（就绪=True，2 轮） | M7 加的 |
| act 侧 `_wait_effect`（动作后生效等待） | **337.1ms**（画面会变）/ **840.7ms**（不变，9 轮） | M7 加的 |
| core 侧 `framecache.wait_change` | **321~343ms** | ★ **与 `_wait_effect` 等的是同一个窗口画面变化** |
| 每轮抓帧（PrintWindow） | 默认窗 **40.96ms** / 大窗 **47.68ms** | ★ **窗口尺寸相关**：小窗仅 13.6ms（占 21%），那 800ms 里约 640ms 是纯等待 |

### 两条假设的裁决（**这是已定事实，不是待讨论**）

- **假设 B 成立**：core 的 `wait_change` 与 act 的 `_wait_effect` 等的是**同一窗口画面变化**
  ⇒ 合并可省 **200~340ms/次**；前提是 act 侧要把「最后一帧/首次变化帧」回传 core，
  否则落盘 diff 没帧可用。
- **假设 A 被修正为「部分成立」**：抓帧开销**窗口尺寸相关**，不是普适瓶颈。
  ⇒ 「每轮重抓整窗」只在**大窗口**下值得动，小窗下动了也就省个位数 ms。

## 2. 阶段一要交付的东西

### 2.1 设计稿 `docs\设计_M12_等待合并_20221022.md`

必须回答（每条都要**指到文件+行号**，不许泛泛而谈）：

1. **链路全图**：`ctl_click` 从 core 到 act 的**完整调用链**（函数名 + 文件 + 行号），
   标出 core 侧 `wait_change` 与 act 侧 `_wait_effect` **各自在链上的确切位置**。
2. **进程边界**：core 与 act 是**父子进程**还是别的关系？两者之间**已有的数据通道**是什么
   （stdout 文本 / JSON / 临时文件 / 管道 / 共享内存）？
   ⇒ **合并方案必须复用已有通道，不许新造一条**。
3. **合并点在哪一层**：给出**至少两个**候选接口形状，各自写清：
