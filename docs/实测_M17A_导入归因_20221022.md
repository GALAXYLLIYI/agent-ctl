## 结论先行（先看这 5 条）

1. **动作子进程（act.py 真源，无参自检路径）的 import 总耗时 p50 = 83.5ms（n=20，p95=99.3ms）**，只占主控给的 1001.8ms 的 **8.3%**（p95 口径 9.9%）。import 不是这 1002ms 的主因。
2. **进程创建 + 解释器启动**（`python -c ""`，n=20）p50 = **31.7ms**，占 3.2%；若把父 CLI 与 act 两个进程都算上，约 63.4ms / 6.3%。
3. **其余 886.6ms（88.5%）** 是动作本身：截图 / UIA / 闸门读写 / JSON / 文件 IO。本线按红线没有跑真实点击，无法再细分，**未核到**逐项占比。
4. **可延迟候选 Top-3（按 importtime cumulative 实测，读路径口径）**：`tempfile` **12.9ms**、`secrets` **6.97ms**、`agentctl.digest`（实际拉入 `ctypes`）**5.51ms**，合计 **25.4ms**。但 `secrets/digest/subprocess` 三项都在 5–9ms 区间，与 importtime 轮间漂移同量级，**名次可能翻转，只有“合计约 25ms”这个量级可信**。
5. **对“真实写动作”而言，上述延迟几乎全是净省 0**：第一次用到时照付一次 import 代价。`tempfile` 只在“不计数”的只读/被拒/无参路径上真省 12.9ms；写动作在 `gate.require` 计数写回时立刻把 12.9ms 付回去。

## 一、任务 1：import 成本归因（实测）

### 1.1 五个入口总表

> 统计口径：`-X importtime` 的 **self 列求和** = 该次运行的 import 总耗时；每行先按 run 求和，再取 p50/p95。墙钟为 `subprocess` 外层 `perf_counter`。

|---|---:|---:|---:|

**为什么 CLI 入口选 `status`**：派单要求“一次只读动作”，红线又禁止跑 GUI 动作。`status` 是唯一不触发 UIA / 截图 / 鼠标键盘的只读动作，同时完整走 `core.dispatch` 的 import 链（`cli.py:29 → core.py:44-57`），因此适合做“入口 import 成本”的样本。真实 click 会在函数内额外拉 PIL / UIA，见 1.4 的上限推断；本线不跑。

**importtime 自身开销**：act 134.3 − 130.3 = **4.0ms**；CLI 224.1 − 218.4 = **5.7ms**。这是 `-X importtime` 钩子的墙钟成本，已包含在上表墙钟里；1.1 的 import self 是内部计时，不受这 4–6ms 影响。

**“只导包”到底导了什么？** `agentctl/__init__.py` **没有任何 import 语句**（只有 `__version__` / `__all__`）。18.9ms 与空壳 21.3ms 的差是 −2.4ms，**低于噪声门槛 ⇒ 不可判**。结论：`import agentctl` 的增量 ≈ 0，`python -m agentctl.cli` 不会因为包 `__init__` 多拉一串东西；CLI 的重头全在 `from agentctl import core`（cli.py:29）。

### 3.1 为什么 Top-3 是这三个，而不是 `argparse`/`win32gui`

- `argparse`（17.55ms）和 `win32gui`（7.45ms）的 cumulative 更大，但**每一次真实动作都要用**：argparse 在 `act.py` 的 main 入口；win32gui 在自检 `act.py:94` 就真导入、后面每个动作都要。延迟它们只是把成本从“启动”挪到“动作中”，**总时间不变**，还会改变失败语义。所以按“净省”排序，它们不进 Top-3。
- `tempfile` 之所以第一，是因为它**只在 `save_json` 用**；只读/无参/被拒路径根本不写回。写动作会在 `gate.py:439` 第一次写回时付回去——所以它是“**读路径 12.9ms、写路径 0**”的候选，不是“所有路径都省 12.9”。

### 3.2 延后后第一次用到它，会不会多付一次 import 代价？

**会，而且必须如实说：**

- Python 的模块缓存（`sys.modules`）只保证**同一个进程内第二次 import 免费**；延迟不是“消灭”成本，是“**把成本从启动挪到首次使用**”。
- 因此：
  - 只读/不触发该函数的路径：**真省**（本文的“净省”）。
  - 触发该函数的动作：**净省 0**，只是启动更快、动作中多一次 5–13ms 的抖动。
  - 对 1001.8ms 的动作 p50：如果动作会触发，**端到端不变**；如果不触发，省 5–13ms（<1.3%，端到端不可判）。

### 3.3 明确不建议的四类（派单红线）

- **不建议跳过 import / 动态 eval / `__import__` 字符串拼接**：破坏静态可查性，且异常从 `ImportError` 变成运行时 `NameError`。
- **不建议装新依赖 / 换第三方懒加载库**：本单红线，且收益 <13ms。
- **不建议起常驻进程/预加载服务**：把 83ms 摊到常驻进程，但引入生命周期、权限、闸门状态同步问题，远超本单收益。
- **不建议把 `argparse`/`win32gui`/`sqlite3` 当候选**：理由见 3.1。

“合并重复 import”只有一处值得记录：`hashlib` 在 core/gate/store/digest 各 import 一次，`subprocess` 在 core/clock 各一次。**模块缓存让重复 import 免费，合并它们省 0ms**；唯一有意义的是“两处 subprocess 都要延迟，否则只延一处等于没延”。

> 紧随其后：`subprocess` 8.85ms cumulative / **约 5.1ms 净省（推断）**；`glob` 4.21ms（实测）。这三项与 `secrets/digest` 在 5–9ms 区间，**名次可能因轮间漂移翻转**，只有“合计约 25ms”这个量级可信。
>
> **对 1001.8ms 的真实写动作**：Top-3 里只有 `tempfile` 在动作子进程路径上；且写动作在 `gate.py:439` 计数写回时会立刻付 12.9ms ⇒ **真实写动作的净省 ≈ 0**（上限 12.9ms，若该动作不计数/被拒）。`secrets`/`digest` 在父 CLI 路径，真实动作签发凭据/抓帧时同样会付回去。

### 4.3 一句话结论：1002ms 的构成

> **这 1001.8ms 里，“import 本身”占 83.5ms（8.3%；若含父 CLI 则 176.2ms/17.6%），“进程创建+解释器启动”占 31.7ms（3.2%；双进程 63.4ms/6.3%），“其余（策略加载/JSON/IO/截图/UIA/闸门）”占 886.6ms（88.5%）。import 不是这 1002ms 的主因；可延迟 import 在真实写动作上净省 ≈0，只在只读/无参路径上能省 5–13ms。**
