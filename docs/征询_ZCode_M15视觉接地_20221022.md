## 一、先把事实摆清楚（都是本机实测，不是推测）

| 事实 | 数值 / 证据 |
|---|---|
| OCR **逐词给 bbox** | `ocr.py:198-201` 取 `wd.bounding_rect` → `words[{t,x,y,w,h,conf}]` |
| 坐标口径 | **客户区相对、客户区物理像素**；`ocr.py` docstring 明写 |
| 实测样例 | 文 → x=31, y=114, w=32, h=31 ；件 → x=63, y=117, w=32, h=29 |
| **中文被逐字切分** | 「文件」= 两个框（x=31 与 x=63，首尾相接）⇒ **需要合并成词框** |
| 整客户区 OCR 耗时 | **1120 ms**（本机，2542 宽客户区）⇒ **不能进动作同步链** |
| 裁剪后 OCR 耗时 | **42~58 ms**（M6 实测，`docs\实测_响应速度三件套_20221022.md:260`） |
| M6 已经备好「变化区 bbox」 | 同上：只对**变化区**做 OCR（把 diff 的 bbox 喂给 OCR 的 `rect=` 参数）——本轮判据已具备 bbox，尚未接 OCR |
| ⚠️ **`rect=` 的口径有坑** | `ocr_window` docstring 说 rect 是「客户区**逻辑**坐标」；但 `grab_client` 两条路径返回的图尺寸口径不同（PrintWindow 路径=逻辑尺寸，ImageGrab 回退=物理矩形）。实测两路径 `words` 坐标差 ~5px ⇒ **喂 bbox 前必须先定死口径** |
| 契约已暴露 | `ctl_screen` 返回结构里本就写着 `ocr{…, words[{t,x,y,w,h,conf}], …}` |

## 二、M15 想做的一件事（三步，全是几何，**零新依赖**）

> **让「屏幕上这段文字」变成「一个能点的目标」，并和 UIA/DOM 的物体对上号。**

| 步 | 做什么 | 难点 |
|---|---|---|
| **① 字框合并** | 把逐字框合成词/短语框（文 + 件 → 文件） | 同行判定规则、间距阈值、字号一致性 |
| **② bbox ↔ 物体对齐** | OCR 框（客户区物理像素）↔ UIA 物体 rect / DOM 元素 rect | **两侧坐标口径是否真的同源**（UIA 的 rect 是不是也是客户区物理像素？） |

## 三、请你回答的四个问题（**先结论再理由**，标 [确定]/[推断]/[待核实]）

1. **① 字框合并的规则怎么定？**
   给一条可实现的规则（同行判据 + 间距阈值 + 是否要求字号一致）。
   中文逐字切分时，**相邻两字框首尾相接**（x=31, w=32 → 下一框 x=63，间隙 0）
   ⇒ 「间隙 ≤ 字宽的多少倍」是不是就够？**标点、空格、中英混排**怎么处理？
2. **② UIA 物体的 rect 到底是不是客户区物理像素？**
   这是**整条对齐链的地基**。若 UIA 给的是窗口坐标（不是客户区），就得先减掉客户区原点，
   而客户区原点每次都可能变（窗口移动）⇒ 还要带窗口代际。
   ⇒ 请给出**本机可核的证据**（哪个文件哪一行、口径是什么），别凭印象。
3. **③ `rect=` 的口径你怎么定？**
   两条抓图路径（PrintWindow / ImageGrab 回退）返回的图尺寸口径不同 ⇒ 同一个 rect 在两条路上含义不同。
   ⇒ 三个选项，你选哪个并说理由：
   (a) 统一成**物理像素**（改 `grab_client` 让两条路都返物理尺寸）；
   (b) 统一成**逻辑像素**；
   (c) 在返回值里**同时给出**两套坐标（`words` 带 `rect_physical` + `rect_logical`）。
4. **④ 有没有更省的做法？**
   例如：**先 UIA 找文字控件**（UIA 的 Name 属性常常就是屏幕上那段文字）⇒
   **UIA 命中时根本不需要 OCR**；OCR 只在 UIA 找不到时兜底。
   ⇒ 这个「UIA 优先、OCR 兜底」的路子，本机**已经有多少覆盖**？
   （M10 的纯图标覆盖度实测文档在 `docs\实测_纯图标可访问性覆盖度_20221022.md`，你可以引用它，但要给新数据。）
