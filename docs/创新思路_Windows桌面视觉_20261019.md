# 创新思路：基于 Windows 桌面的视觉（2026-10-19）

> 目的：不是复述论文，而是找**能落到 agent-ctl 上的新做法**。
> 判据：每条都要写「治我们哪个洞 / 成本 / 风险」，能马上做的排前面。

## 一、先把我们的洞列清楚（拿洞去找技术，不是拿技术找洞）

| 洞 | 现状 | 为什么疼 |
|---|---|---|
| **D1 纯图标没有文字** | OCR 搜不到、UIA 常常只有外壳 | 只能靠估坐标，点错率高 |
| **D2 抓一次帧 ~100ms** | 每动作都要前后各抓一次 | 一步动作 750ms，批量任务慢 |
| **D3 窗口被遮挡就只能拒** | 归属闸判「落点不归目标」就拒绝 | 不能"看被盖住的窗口内容" |
| **D4 轮询式感知** | `ctl_screen` 每次都重扫 | 变化没发生时也在花钱 |
| **D5 Electron/UWP 结构缺失** | UIA 只拿到外壳节点 | 只能退回像素 |
| **D6 回读靠截图** | 像素比对 + 日志 | 文本类回读本可更便宜 |

## 二、能马上做的（1 天内，收益立竿见影）

### ① 图标字体反查：**无模型识别图标**（治 D1）
```
Windows 自带图标大量来自 **Segoe Fluent Icons / Segoe MDL2 Assets**，码点公开
做法：把字体渲染成 bitmap 集 → 对屏幕上候选区域做模板匹配（归一化互相关）
成本：半天（渲染 + 匹配 + 少量阈值）
风险：非标准皮肤/第三方图标无效 ⇒ 只当"多一条证据"，不替代 OCR
依据：微软官方字体页 https://learn.microsoft.com/en-nz/windows/apps/design/iconography/segoe-fluent-icons-font
```
**为什么这是最值的一条**：它给「纯图标」一条**确定性、可解释**的识别路径，不需要 VLM、不需要 GPU。

### ② GPU 抓帧 + 增量 diff（治 D2）
```
Windows.Graphics.Capture（WGC，GPU 路径）替代 ImageGrab/BitBlt
配套：DWM 缩略图（DwmRegisterThumbnail 的缓存）可**不触发重绘**取窗口内容
收益：抓帧从 ~100ms 降到个位数 ms 量级（需实测）
风险：DRM/受保护内容黑屏；API 是 WinRT，需 winrt 绑定；权限提示
```
### ③ 帧复用 + 只 diff 变化区（治 D2/D4，零新依赖）
```
我们已经签发了 screen_version + TTL，但调用方基本不复用
改法：动作链里"同一帧内多步"，只在判词需要时抓 after 的**目标区域**（不是整窗）
```

## 三、中期（1~3 天，需要设计）

### ④ 事件驱动感知（治 D4，最大结构性提速）
```
UIA 事件：StructureChanged / PropertyChanged / FocusChanged
+ WinEventHook（前台切换、窗口创建/销毁）+ ETW
改法：常驻监听 → 只在"真的变了"时才重扫；平时零成本
风险：事件风暴（要节流）、跨进程 COM 回调的稳定性（我们踩过 COM 等待）
```
### ⑤ 锚点关系定位（无模型，治 D1/D5）
```
思路：用**已知文本**当锚（"保存"/"确定"），再用 UIA 关系（LabeledBy / Controller / 相邻 bbox）定位它旁边的图标按钮
收益：定位可解释（"就在『保存』右边 48px"），比纯坐标估更稳
```
### ⑥ TextPattern 回读（治 D6）
```
Win32/UWP 有 TextPattern 的控件，直接读文本 = 确定性回读，比截图便宜
我们已用 CDP 的 DOM 回读（网页），这条是**非网页应用**的对应物
```

## 四、长期（差异化，不是跟论文比准确率）

### ⑦ 遮挡证据链（治 D3）
```
把 DwmGetWindowAttribute(EXTENDED_FRAME_BOUNDS / CLOAKED) 与像素遮挡检测合并
⇒ 判词从"落点不归目标"升级为"被谁盖住、盖了多少、要不要等它"
```

### ⑧ 不可见网格（IDG）当对照基准
```
我们已有原型（192px 格子，静态 0.4 tok/帧）
用处：生成**合成任务**测定位精度，不依赖真实应用 ⇒ 可回归、可对标
```

### ⑨ 对标 ScreenSpot-Pro（外部可比数字）
```
ScreenSpot-Pro（CVPR/arXiv 2504.07981）是密集桌面场景的通行标尺
我们现在只有自建判据（25/26/27），**没有外部数字**
接一次基准 ⇒ 能说"我们在密集图标场景准确率 X%"，这是外部可比的第一句话
```
### ⑩ 本地小模型只在 must_vlm 时低频调用
```
Windows 本地 AI 栈（Foundry on Windows / Phi-Silica / ONNX+DirectML）
我们已有 must_vlm 开关 ⇒ 它天然是"低频兜底位"，不参与每步预算
```

## 五、我的排序（按"解决真洞 / 成本低"排）

| 顺序 | 做什么 | 治哪洞 | 成本 | 为什么排这儿 |
|---|---|---|---|---|
| **1** | 图标字体反查（Segoe 模板匹配） | D1 | 半天 | 唯一能给"纯图标"确定性识别的路，且不依赖模型 |
| **2** | 帧复用 + 只 diff 目标区域 | D2/D4 | 半天 | 零新依赖，直接省每步 100~200ms |
| **3** | WGC/DWM 抓帧实测对比 | D2/D3 | 1 天 | 若成立，抓帧数量级提升 + 能看被遮内容 |
| 4 | 事件驱动感知 | D4 | 2~3 天 | 结构最优，但 COM 事件稳定性有风险 |
| 5 | 锚点关系定位 | D1/D5 | 1 天 | 可解释性提升，与 1 互补 |
| 6 | ScreenSpot-Pro 对接 | 外部对标 | 1~2 天 | 拿到第一个外部数字 |

## 六、风险与不做什么
```
· 不做端到端 VLM 训练（40M 数据那类我们没条件，也不需要）
· 不承诺"准确率超过论文"——我们的卖点是**可核账**，不是刷榜
· 字体反查只对系统图标有效，遇到第三方皮肤会失效 ⇒ 必须带置信度、可退回 OCR
```
