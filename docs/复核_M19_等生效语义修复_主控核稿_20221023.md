## 一、★ 核心发现：**「8→5」这条通道根本不存在**（两条独立证据互证）

### 证据①（主控亲跑 · 合成判决测试）

`core._picture_verdict(r, df, ...)` 的 `df` 是 **core 自己的 diff**（`core.py:3305` `_act_diff_of(_before, _after, …)`），
它**不读** act 的 `生效`。主控 10:2x 直接调该函数（`src/agentctl/core.py`）：

```text
df.changed=True   => core code=0
df.changed=False  => core code=8
df.changed=None   => core code=5
effect 带 生效=None 时 core code=8 （期望 8）
```

⇒ **把 act 的三态塞进 effect payload，core 的判词纹丝不动。**

### 证据②（窗口A 独立静态复核 · `docs\复核_M19_影响面_windowA_20221023.md` §〇.3）

> `_emit_effect` 的 payload（act.py:1427-1440）只有 `rounds/first_change_ms/degraded/frame_ref/口径/origin/dpi_scale/来源/基线/判据版本` **十键**，
> **没有 `生效`、也没有预算裁决字段** ⇒ core 拿到 last 帧后用自己的尺子裁决。
> ⇒ 落地态实际行为：**末帧≠基线 ⇒ core 判 code=0（不是 5）**；**末帧==基线（闪烁收回）⇒ code=8（不是 5）**。

### 证据③（主控 grep 复核）

`rg -n "生效" src/agentctl/core.py` ⇒ **0 处代码引用**（命中的全是「未生效」「不再生效口径」这类中文注释）。

### ⇒ 合并结论

```
act.py:1353/1377 预算耗尽 ⇒ {"生效": False/None}   ← M19′ 改的就是这里
      │  ✗ 这条线**没有接到 core**：payload 不带 生效，core 不读 生效
      ↓
core.py:3305  core 用**自己的**尺子：before 帧 vs 最后一帧
      ├─ 末帧≠基线（看到过变化，只是没凑够 need=2）⇒ changed=True ⇒ **code=0 成功**
      └─ 末帧==基线（真没变 / 慢应用）        ⇒ changed=False ⇒ **code=8「确认没变」**
```

⇒ ★ **M19′ 的原始目标（「慢应用从 code=8 变 code=5，agent 才会重试」）在当前接线下没有落点。**

## 五、★ 唯一实质代价：13.84ms（二次判差）——已派修

主控实测（20 次平均，1632×1191 全尺寸帧）：`_img_diff(base_img, last)` = **13.84ms/次**。

⇒ M19′ 初版在预算耗尽时**又算了一次**判差 ⇒ 每次「画面没变」的动作多花 13.8ms，
且总耗时变成 450+13.8=**463.8ms**，破坏 `act.py` 自己写的「总耗时 ≤ 预算（永远不慢于改前的固定 sleep）」不变式。

**修法（零语义变化、零额外耗时）**：循环里已经算过 `d = _img_diff(base_img, cur)`，此刻 `last` 就是 `cur`，`d` 正是 `last` 的判差
⇒ 把它存下来（`last_d`）**复用**，两个出口只吃已算好的判差。

## 七、★★ 真正的下一刀（在 core 侧，不在 act 侧）——需要用户拍板

> ★ **为什么必须在 core 侧**：act 在预算耗尽那一刻**分不清**「真没变」与「慢应用」（两者最后一帧都与基线相同）
> ⇒ 想把慢应用从 code=8 救回来，**必须有人多看一眼** ⇒ 要么 core 多复核一会儿，要么 core 采信 act 的「没测出来」。

| 选项 | 做什么 | 得到什么 | 代价 | 主控倾向 |
|---|---|---|---|---|
| **甲 · core 复核（加长观测）** | act 报「预算耗尽·没看到变化」⇒ core 用自己的尺子**再看一会儿**（现成机制 `framecache.wait_change`）再判决 | 慢应用被救回来（只要它在加长的窗口内响应）＋ **「确认没变」语义保住** | **每次「没变化」动作多等约 300ms**（+20% 等待开销） | ★ 语义最干净，但与「提速」方向相反 ⇒ **要用户点头** |
| **乙 · core 采信三态（预算耗尽⇒code=5）** | act 把三态送到 core（`_emit_effect` 增发字段 → `_parse_effect` 透传 → code=8 分支消费） | 慢应用变 code=5 ⇒ agent 重试 ⇒ 自动化不再静默停住 | **零延迟**；代价：**「确认没变」基本消失**（预算耗尽都变 5）⇒ agent 对死按钮也会重试（双击风险上升、action 变多） | 也可做，但要用户认「牺牲确认没变的精度」 |
| 丙 · 砍预算（提速） | — | — | ❌ 已实测排除（响应 200–300ms 的应用整段 100% 检出→0%） | 不做 |

⇒ **主控建议**：**甲**（语义干净，代价是固定 +300ms），并**同时**修 W1/W2/W3（纯 act、3 行、零延迟、符合铁律）。
⇒ 但「+300ms」是用户可感知的延迟 ⇒ **这一条按规矩请用户拍板**（用户已授权「小事我自己定，大事拍板」）。

## 八、★ 方法论第六条（本轮新立，已建议写进手册）

> **改一个字段之前，先确认「谁读它、读到之后干什么」——没人读 ⇒ 改它等于没改（空刀）。**
>
> ★ 本轮代价：M19′ 改了 `生效` 的取值，而**全仓只有 3 个读者、全在 act 内部、且没有一个会把 None 变成「可重试」** ⇒ 端到端零效果，
> 却真真切切多花了 13.84ms/次。⇒ **「语义更诚实」不等于「行为变了」**；行为链必须**逐跳**核到 agent 拿到的那一个字节。
