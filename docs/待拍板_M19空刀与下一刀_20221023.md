## 一、一句话现状

**M19′ 这一刀落地了、代码正确、红线零违反，但它是「空刀」：agent 拿到的退出码一个字没变。**

原因（两条独立证据互证）：

```
act 改的是自己的三态 生效  ──✗──  这条线没有接到 core
                              （payload 不带 生效；core 全仓 0 处读 生效）
core 用**自己的**尺子判：before 帧 vs 最后一帧
   ├─ 末帧≠基线（看到过变化，只是没凑够两帧）⇒ code=0 成功   ← 本来就没事
   └─ 末帧==基线（真没变 / 慢应用）        ⇒ code=8「确认没变」 ← 慢应用卡在这
```

⇒ **真正要修的「慢应用」（点了之后 500ms 才响应 ⇒ 被判「确认没变」⇒ agent 不重试 ⇒ 自动化静默停住）没修好。**
⇒ 而且 M19′ 初版每次动作还**白花 13.84ms**（已派修，零成本化）。

## 二、为什么「慢应用」这件事**不能**在 act 侧修

预算耗尽那一刻，act 手里的证据只有「最后一帧」：

| 真实世界 | 最后一帧 vs 基线 | act 能分辨吗 |
|---|---|---|
| 按钮彻底没反应 | **相同** | ❌ |
| 应用慢，600ms 后才响应 | **相同**（450ms 时还没变） | ❌ |

⇒ act **分不清**这两件事 ⇒ 它说什么都是猜 ⇒ **必须有人多看一眼**（core）或**必须承认「没测出来」**（code=5）。

## 三、请你拍板：下一刀走哪条

### 甲 · core 复核（多看一眼）——★ 主控推荐

| 项 | 内容 |
|---|---|
| 做什么 | act 报「预算耗尽·没看到变化」⇒ core 用自己的尺子**再看一会儿**（现成机制 `framecache.wait_change`）再判决 |
| 得到什么 | 慢应用被救回来（只要它在加长的窗口内响应）＋ **「确认没变」这个语义完整保住**（真没变的界面仍然报 code=8） |
| **代价** | ⚠ **每次「画面没变」的动作多等约 300ms**（等待阶段 +20%）—— 这是**用户能感觉到的延迟** |
| 风险 | 低：只动 core 的判决顺序，不动契约、不动闸门、不动任何预算常量 |

### 乙 · core 采信三态（预算耗尽 ⇒ code=5「没测出来」）

| 项 | 内容 |
|---|---|
| 做什么 | act 把三态送到 core（`_emit_effect` 增发字段 → `_parse_effect` 透传 → code=8 分支消费）⇒ 预算耗尽一律判 code=5 |
| 得到什么 | 慢应用变 code=5 ⇒ **agent 会重试** ⇒ 自动化不再静默停住 |
| **代价** | ⚠ **零延迟**，但 **「确认没变」基本消失**（预算耗尽都变 5）⇒ agent 对「彻底没反应的按钮」也会重试（**双击/重复动作风险上升**、action 变多） |
| 风险 | 中：改的是 agent 可见的退出码语义 ⇒ 影响面比甲大 |

### 丙 · 砍预算（提速方向）

❌ **已实测排除**：450→200ms ⇒ 响应 200–300ms 的应用整段从「100% 检出」掉到「0%」，且全被误判成「确认没变」。

## 五、★ 顺带立的一条方法论（建议进手册）

> **改一个字段之前，先确认「谁读它、读到之后干什么」——没人读 ⇒ 改它等于没改（空刀）。**
>
> ★ 本轮 M19′ 改的是 act 自己的三态，而全仓只有 3 个读者、全在 act 内部、**没有一个**会把 None 变成「可重试」⇒ 端到端零效果，
> 却真真切切多花了 13.84ms/次。⇒ **「语义更诚实」≠「行为变了」**；行为链必须**逐跳**核到 agent 拿到的那一个字节。
