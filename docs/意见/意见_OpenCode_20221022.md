## Q1 「判定权留 core、act 只回传证据帧」这条形状认不认？

**结论：认，而且「两边都判、取 OR / 取 AND」都更差；但按现码，这条形状只兑现了 `ctl_type --focus` 一条路 —— `ctl_click` 的 `code` 现在仍由 act 的 md5 判，`degraded` 也被丢掉。所以要做的不是换形状，是删掉第二把尺子、把线接完。** [确定]

理由与证据：

1. **act 侧还有一把完整的尺子。** `do_click` 拍 `before`/`after` 两张整窗证据（`act.py:2599`、`2622`、`2765`），然后 `changed = (fp1 != fp0)`，`fp` 是文件 md5（`act.py:2542-2557`、`2756-2770`），最后 `return 0 if changed else 8`（`act.py:2806`）。core 的 `_map_rc` 把这个 rc 直接翻成 `code`（`core.py:2959`、`2340-2344`）。
2. **core 自己的判据确实在算，但默认不影响 `code`。** 覆盖 `code` 的那段要求 `args.get("_need_diff")`（`core.py:3066`），而 `_need_diff = frame_id or _need_diff`（`core.py:2899`）；普通 `ctl_click` 不带 `frame_id` ⇒ **不进覆盖分支**。`degraded ⇒ code=5` 也长在同一个分支里（`core.py:3030-3040`）⇒ **普通点击的退化根本落不到 code=5**。M12 §五第 2/3 条在 click 路是**没接上的**（`data.after.diff` 里有判词，`code` 里没有）。
3. **act 的基线还是「动作后」才抓的。** `_wait_effect(hwnd, _poll_base(hwnd), …)` 的三处调用（`act.py:2748`、`2762`、`2776`）都在注入**之后**；`_poll_base` 是**现抓一帧**（`act.py:1095-1100`）。⇒ 如果目标重绘快于一次 PrintWindow，基线里已经含了变化，**首变被吞掉，只能等满预算**；这也是「等两遍合并」之后剩下的那截假等待。同时 `first_change_ms` 的零点也在这个函数里（`act.py:1310`）⇒ **M13 要采的首变分布，零点和基线同时是偏的**。
4. **更稳的形状（建议）**：core 把 baseline **下发**给 act（帧路径 + `(w,h)` + `origin` + `dpi_scale` + 判据版本号），act 只做「对着这个 baseline 采样」，回传**首变帧 + 每轮时刻 + 轮次**；`rc` 只表示「输入送没送到」，**不再承载画面结论**。这样比较的两端都在 core 手里，act 退化成传感器 + 秒表 —— 比「act 回传一帧、core 再判」更严，因为现在 core 判的那一帧和 act 判的那一帧**用的不是同一个基线**（`core._before` vs act 注入后现抓的 `_poll_base`），严格说 core 只是"另测了一次"，不是"复核了 act 那次"。

> 一句话：**双判据取 OR 会把失败口径放松（任一把说变就算成功），取 AND 会把一次漏帧变成假失败；唯一正确解是删掉 act 那把，而不是再补一把。**

## Q2 下一刀该砍哪：视觉接地 / 预算形状 / 别的？

**结论：都不是第一刀。先砍「每轮固定成本 + 同一动作里的重复抓帧/落盘」（全在 act 侧，零口径改动，估 100~180ms/次）；视觉接地排第二（A 批已在做，别停，但只许在 bbox 上做）；「前密后疏退避」排最后 —— 因为循环是**抓帧受限**，不是 sleep 受限，退避改的是分母里最小的一项。** [确定/推断]

理由与实测：

1. **一轮到底多贵（这是关键账）。** 大窗每轮 = 抓帧 `40.96ms`（M11 直测；我实测整帧 diff `15.4~18.5ms` + `is_blank` `5.7ms` + sleep `50ms`）≈ **112ms/轮**；`HYSTERESIS=2` ⇒ 首变最早也要 **~224ms**，M11 直测「会变」`258.3~395.3ms` 正好对上。把 `poll_ms` 从 50 调到 15，只省 **35ms/轮**；而 no-change 时轮次上涨（`450/77≈6` 轮 vs `450/112≈4` 轮），**总 CPU 反而涨**。⇒ 退避曲线改不动大头。 [确定：算式 + 实测]
2. **每轮里有两笔纯浪费。** `_wait_effect` 每轮都做 `is_blank(cur)`（`act.py:1335-1340`，我实测 **5.7ms/次**），但退化只是"打标"，**每轮打一次和最后一帧打一次结论完全一样**；`_wait_ready` 每轮还跑 `_poll_gray(cur)`（`act.py:1283`，我实测 **6.3ms/次**）只为判断"图够不够大"，其实 `img.size` 就够。⇒ 两笔合计 **~12ms/轮**，是纯粹的税。 [确定：代码 + 实测]
3. **M13 守的预算常量不是生产用的那个。** `do_click` 三处都传 `budget_ms=int(_settle(450)*1000)`（`act.py:2749/2763/2777`），`POLL_BUDGET_MS=800` 只是函数默认参数；M11 的「837.1ms / 14 轮」是**直调默认 800** 测出来的（14×63.6≈890，450ms 装不下 14 轮）。⇒ 生产 click 的 no-change 上限约 **450ms + 一帧**，不是 800ms。拿 800 去定退避曲线会系统性偏一倍。 [推断，但算式闭合；建议一条打点确认]
4. **视觉接地：该做，但不是"砍成本"的刀。** 整客户区 OCR **1120ms**，裁剪后 **42~58ms** ⇒ 只有"只对 diff bbox / 命中区 OCR"才划算（一次裁剪 OCR 比一轮抓帧还便宜）。而且 A 批已落进工作树（`ocr.py:243 merge_word_boxes`、`ocr.py:461 coord_space`）⇒ **别回退，别加码到整屏**，B/C 批按原计划走即可，不必挤到"下一大刀"的位置。
5. **真正该先做的那一刀**：`_wait_ready` 的基线又抓一张（`act.py:2690` `_poll_base(hwnd)`），而 `before` 证据帧已经有了；动作后 act 又拍一张整窗 `after` 只为算 md5。**一次点击现在拍 5~7 张整窗、写 6~7 张 PNG**（下面 Q4 §1/§2/§3 有逐条数）。把"同一帧只抓一次、只编码一次"做掉，比任何曲线都直接。 [确定：代码路径；收益按实测单张折算]

## Q3 「看着该快、其实不快」的路，我还知道哪些？

**结论：还有 4 条；而且你们那条「换拷贝 API 没用」**不能外推**——换**抓帧 API** 确实没用（成本在目标应用渲染里），但换**交接/落盘格式**是真快：PNG 30ms → BMP 5.3ms → raw 1.9ms（同一张 2542×1400，本机实测）。** [确定：本机实测]

| 路 | 看起来 | 实测/机理 | 判断 |
|---|---|---|---|
| 换抓帧 API（BitBlt/Desktop Duplication） | 省拷贝就该快 | 你们已测：BitBlt 52.4ms vs PrintWindow 16.2ms | ✗ 已否，**结论只对抓帧成立** |
| **换交接格式**（PNG→BMP/raw） | 只是换个容器 | save：PNG **29.9** / BMP **5.3** / raw **1.9**；load：PNG 8.7 / BMP 9.7 / raw 2.5 | ✓ **真省 ~27ms/次**，且每动作 6~7 次 |
| 降采样预筛再精判 | 少算 4 倍像素 | 只省 diff 那 **16ms**；1/4 BOX 会把 8×8=64px² 平均掉，撞 `DIFF_MIN_AREA=24`（`framecache.py:466`）⇒ 要么漏报要么重算 | ✗ 不值（还会松失败口径） |
| 并发/多线程抓两帧 | 两路并行更快 | PrintWindow 的 `WM_PRINT` 要目标窗口 UI 线程处理 ⇒ 并发只是排队，还可能把"无响应"变成超时；PIL 解码在 GIL 下也不并行 | ✗ |
| 缓存 UIA 控件/句柄，省 43.8ms 查找 | 少一次树遍历 | `act.py:2692` 的二次 `find_control` 正是防"读到与点到之间矩形变了"；缓存必须配 rect 复核，省不到一半还引入 stale 绑定 | ✗（省的钱不够赔风险） |
| 用事件驱动替代轮询 | 不用轮询就零成本 | 已否；补一句：它只配当"提前收轮"的提示，且钩子要常驻进程 | ✗ 已否 |
| JPEG 存证据 | 编码和 BMP 一样快 | 编码 5.3ms ✓，但解码 **10.0ms** + 有损 ⇒ diff 会误报（阈值 2/255） | ✗ 证据图不该有损 |

> 反过来说：**凡是"减少一次整窗抓帧/一次 PNG 编码"的路，基本都真省；凡是"换一个更快的拷贝/判据算法"的路，基本都不省。** 因为账本里的大头是**次数 × 固定开销**，不是单次算法复杂度。

## Q4 有没有漏掉的刀？（围绕「最小代价、只在 GUI 层面」）

**结论：有 6 条，其中前 3 条是"删重复"，不是"加机制"，最符合最小代价；第 6 条是唯一一条"把已有数据变成能力"的刀，但它排最后。** [确定/推断]

1. **每次点击白拍一张 before 证据。** `act.py:2599` 无条件 `before = evidence(hwnd,"before")`，随后正常路径（非 post、非 dry）在 `2622` **又拍一次覆盖它**。⇒ 一次整窗抓帧 + 一次 PNG 编码 + 一张多余 PNG，**小窗 ~43ms / 大窗 ~78ms**，纯浪费。 [确定：代码；耗时按 M11 抓帧 12.5/47.7 + 我实测 PNG 30ms 折算]
2. **act 的 md5 判据整条可以删。** 它带来：`after` 整窗抓帧 + PNG（43~78ms）、两次 md5 读盘、以及 Q1 说的第二把尺子。core 已经把 `_before`/首变帧/`_df` 都算好了，**删掉 act 的判词不影响任何既有失败口径**（反而把 click 路补上）。审计图留一张 after 即可（core 的 `work\_actions\<fid>\` 里已有）。需要保留的只有：`retry>0` 时 act 用 `_eff["生效"]` 决定要不要重点（同一把尺子，不进退出码）。 [确定/推断]
3. **落盘 PNG 被算进了「未归因」。** `_act_diff_store` 非复用路径固定写 `before.png`+`after.png`（`core.py:2761-2769`），加 `crop.png`；act 侧再写 2~3 张（含 `first.png`，`act.py:1384`）。合计 **6~7 张 PNG/次 ≈ 180~210ms 编码**（我实测 29.9ms/张，**这是下界**：合成图比真实截图好压）。这正好落在 M5 的"未归因 99.6~109.8ms"量级上。⇒ **M5 拆账时把 `PNG 编码` 单列打点**，别再叫"未归因"；改法：内部交接走 raw/BMP，证据只留 `crop.png` + `after.png`，其余懒生成。 [推断：数字可一条打点证实]
4. **`_wait_ready` 的基线可以复用。** `act.py:2690` 又 `_poll_base(hwnd)` 抓一张，而 `before`/core 的 `_before` 已经在内存里 ⇒ 省 12.5~47.7ms + **至少 1 轮（~63.6ms）**。 [推断]
5. **`effect` 里两个字段被扔掉。** core 只消费 `degraded` 和 `frame_ref`（`core.py:2961`、`3035`、`2698`），`rounds` / `first_change_ms` 解析完就丢。⇒ agent 分不清"对方一直没反应"和"反应了但超预算"，两者都只看到 `code=8`。这两个量已经在回传里，**接进 `data.after` 是零成本**。 [确定]
6. **帧的口径没随帧回传。** `effect` 只有 `frame_ref` + 4 个标量，没有 `(w,h,origin,dpi,scale)`；core 把可能来自"复用观测帧"的 `_before` 与 act 的客户区帧**逐像素**比，origin/size 差一点就整窗报变（M15 裁决已实测两条抓图路径差 ~5px）。⇒ 建议随帧回传这 5 个字段，core 不一致就**回落 `wait_change`（fail-closed）**，不要"现取 origin"补救。 [推断，有 M15 的 5px 实测做背景]
7. **（能力向，排最后）`code=8` 之后缺"为什么没变"的一跳。** diff 的 `bbox` + `crop.png` 都已在手，边际成本接近 0（crop 180×60 PNG 仅 **0.3ms**；裁剪 OCR **42~58ms**）⇒ 可做"没变 ⇒ 对 bbox 做一次局部 OCR/放大，回执里给候选解释（点到的是按钮还是空白/是否弹了小框）"。这是**把已有数据变成下一步动作**，不是新机制。 [推断]

## 附：本机实测原始数字（供复核）

合成帧 2542×1400 RGB（10.7MB 内存），Python + PIL，5 次取最小/中位：

| 操作 | min / 中位 (ms) |
|---|---|
| `framecache.diff_images`（有变化） | **17.7 / 18.5** |
| `framecache.diff_images`（无变化） | **15.4 / 15.8** |
| `framecache.is_blank` | **5.7 / 5.7** |
| `convert("L")` | 2.9 / 3.0 |
| `convert("L") + resize 1/4 BOX` | **6.2 / 6.3** |
| `ImageChops.difference + L + point` | 12.6 / 14.0 |
| PNG save / open+load | **29.9 / 30.0** ｜ 8.7 / 8.8 |
| BMP save / open+load | **5.3 / 6.2** ｜ 9.7 / 10.5 |
| raw write / read（10.68MB） | **1.9 / 2.0** ｜ 2.5 / 2.6 |
| JPEG(q85) save / open+load | 5.3 / 5.6 ｜ 10.0 / 10.1 |
| 180×60 crop → PNG save | 0.3 / 0.4 |

⚠ 两点如实说明：
- 合成图是大片纯色，**PNG 是下界**；真实窗口截图更大更花，编码只会更贵，不会更便宜。
- 上面所有"按单张折算"的收益都是**推断**，落地前用一条打点（把 `Image.save`、`perceive.shot`、`diff_images` 各包一个计时器）就能证实/证伪，不需要改判据。

## 一句话总账

**形状认，但"判定权在 core"现在只接了一半（click 的 `code` 还是 act 的 md5，退化也不落 code=5）；下一刀不是视觉接地也不是退避曲线，而是"同一帧只抓一次、只编码一次 + 删掉 act 的第二把尺子"—— 这是唯一一刀同时砍时间、砍磁盘、砍判据分裂，且不改任何失败口径。**
