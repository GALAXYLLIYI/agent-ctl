## 二、K2 缓存的裁决：**有条件立项，降级到第 3 位**

**采纳 窗口A 的正解形状**（不造第三套）：复用 **eid 旁表**（core.py:147）那一套，
把 **ctl_tree / ctl_find**（`_uia_gate` 现走全 walk）接进去。
**采纳 窗口B 的四条禁令**：缓存**永不签 capture、永不产坐标**；失效键 = hwnd + 代际 + 秒级 TTL + 焦点，**遮挡不进键**（遮挡不改树内容，进键必常 miss）；**禁出「页面上没有它」这种否定结论**；**volatile 元素不入缓存**。
**采纳两票共同的前置条件**：**先埋命中计数器**，命中率不到阈值就不建缓存。
**收益口径纠正**：K2 命中一次省 **51ms**（ctl_tree 口径），不是 191ms。

⇒ **排序：确定性成本先砍，概率性收益后砍。**

| 序 | 刀 | 省 | 性质 | 谁提的 |
|---|---|---|---|---|
| **1** | **双 spawn（verify_expect 动作验两次 动作.py）** | **≈200ms** | 确定性 | 窗口A Q5① |
| **2** | **动作后 UIA 重扫按需化** | **≈191ms** | 确定性（eid 命中时每次都付） | 窗口B Q5① |
| 3 | K2 树缓存 | 命中率×**51ms** | 概率性，**先埋点** | 窗口A 正解 + 窗口B 四禁 |
| 4 | spawn+import 懒加载 | ≤95ms | 确定性上限 | 窗口B Q5② |
| 5 | window_state 双跑 | <20ms | 确定性 | 窗口B Q5⑤ |

**已在 M12 阶段三里、不重复派的**：删重复抓帧（K1）、基线复用（Q5④）、`is_blank`/`_poll_gray` 两笔纯税（Q3）、
PNG→raw/BMP 交接（K1）。

## 三、K7（一次观测多动作）的裁决：**本轮不立项，max_uses = 1 不变**

两票都**没有说它违法**（窗口A：[确定]不违铁律；窗口B：形状可留）⇒
**不拿它去撞铁律**，这是事实澄清。真正的理由是**收益落错了地方**：

1. **省的是「模型往返」，不是 agentctl 的本机 ms** ——
   用户的诉求是「加快 **agentctl 控制电脑**的响应速度」，而本机延迟账单里**没有「模型往返」这一项**
   （端到端 1,496~1,622ms 全部是本机时间）⇒ K7 对本轮目标**贡献 ≈ 0**；
2. 要做，就得给 capture 加 `max_uses` ⇒ **放宽「一次性消费」这道 TOCTOU 防线**，
   而 TOCTOU 防线正是 arXiv:2604.18860 的主题（观测→动作间隙均值 6.51s）；
3. **M14（PUSV-L1，动作前再验一次）还没落地** ⇒ 先补安全地基，再谈放宽。

⇒ 决定：**max_uses 本轮 = 1 不变**（这是「不是大事我自己定」的范围，但会写进最终汇报）。
K7 挂账，等 M14 落地后重新评估。

## 四、Q4 验收口径的裁决：**p50 ≤900ms + 两个守门指标**

- **为什么不是 800**：窗口A 的 550~750 下限里含 K4（budget 折半，**只对声明了 verify_expect 的动作生效**，不是普适收益）
  与 K2（**命中率未知**，按 51ms 算）两条软腿；
- **为什么不是 1000**：窗口B 的算式里「−100（spawn）」被算进收益，但**懒加载能不能拿回 100ms 未实测**
  （=上限，不是实测）；且 ≤1000 与当前基线 1,496 的差距不足以体现本轮三单的合力；
- **900 是折中且有区分度**：M12 三落地后基线预计 ≈1,270~1,350
  （1,496 −140（删重复抓帧+PNG）−90（两笔纯税）），
  再减 200（双 spawn）+191（UIA 重扫）+ import 优化 ⇒ **≈820~900**。

**守门指标（两条，防「加速靠松判据」）**：
1. **code=8 率与 unknown 率不得高于基线**（窗口A 提出，采纳）——降级一律写 unknown，**不许**写成「没变」；
2. **同时报 p95**（窗口A 提出，采纳）——no-change 场景会把 p95 拖长，p50 好看不算数。

**不许靠砍「等生效」达标**：p50 ≤500 直接判负（窗口A 同）。

## 四之二、★ 测量方法学的裁决（主控 13:02~13:08 实踩出来的）

做「加速」这一单绕不开的一件事：**要量 n≥20 次的 p50/p95**，而
**连续做「点了但画面没变」的点击必然拉下急停**（急停一拉，连感知都停，全机 agent 全部瘫痪）。
主控为此实测踩了两轮：

| 轮次 | 现象 | 根因 |
|---|---|---|
| 13:02 | 探针第 6 轮被拉闸 | `fail_streak=6`：code=8「确认没变」**计入**失败 |
| 13:05 | 只抬 fail_streak 后，第 6 轮**又被**拉闸 | `same_target_streak=5`：同一 actor 连续对**同一坐标**动作 |

⇒ 裁决（写进 M16 派单，当验收方法的一部分）：
1. **测量进程走自己的护栏口径**：用官方环境变量 `AGENTCTL_ACTION_GUARD_POLICY`
   （action_guard.py:81）指向一份**测量专用策略文件**；该文件里
   **`fail_streak` 与 `same_target_streak` 两个都要抬**（只抬一个会被另一个再拉一次）；
2. **生产口径文件 `src\agentctl\action_guard_policy.json` 一个字节都不许改**
   （MD5 `73F5F0DD2C1B7729032EAB3707D934FD`）—— 改了就毁掉护栏本身；
3. **每次测量用独立 actor 名**（带时间戳）：判据与测量器共用 `M11分段测量`
   ⇒ **连击计数跨 run 累加**（这正是 13:02 误判的帮凶）；
4. **主控的独立基线（已跑完，n=20）**：**p50=1348.6ms｜p95=1405.2ms｜mean=1355.4**
   ⇒ M16 的 **p50 ≤ 900ms** 等于**再砍 ≥450ms**。

★ **主控自认的错**：第一版探针忘了豁免护栏，**13:02 把全机急停拉了**，
连 MiniMax Code 的判据都被挡。⇒ 记在案，**不是执行者的问题**。
