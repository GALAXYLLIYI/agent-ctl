## Q1｜M13-a 事件驱动在本机覆盖什么？

**结论：[确定] Win32/UIA 事件是「可访问性语义事件」，只覆盖「有对象且发了通知」的变化；三类里只有「原生表单值变」有可靠事件，网页文本要靠 CDP，Canvas 零事件——且按项目自己裁定过的纪律，事件只当唤醒提示、判变仍以帧差为真相。**

理由与清单。**覆盖**：① 表单值变——原生 EDIT 的 `EVENT_OBJECT_VALUECHANGE`（EN_CHANGE→MSAA→WinEvent，标准路径）；UIA `AutomationPropertyChangedEvent`（ValuePattern/NameProperty）；② 网页文本变——唯一确定覆盖的通道是 **CDP 注入 MutationObserver**（DOM 层 100% 有回调），UIA 侧 `TextTextChanged`/NameChange 要 Chromium 开无障碍才发；③ 焦点/前台变化——`EVENT_SYSTEM_FOREGROUND`（项目早已裁定只留这一个钩子位）。**不覆盖清单**：Canvas/WebGL 重绘（DOM 层无事件，进页面里 readPixels 抽验也只是把轮询搬进页面）；未开无障碍的 Electron（事件与树同塌——ChatGPT 3 节点/QQ 13 节点是实锤）；不发通知的第三方框架（Qt 自绘控件常静默）；动画/视频/时钟区（事件源不停，反要限频）；DWM 合成动画。**架构约束**：钩子必须挂常驻侧（core/MCP 进程）——act 子进程活 1~2 秒，hook 注册+COM marshall 固定成本摊不掉 [推断]；正确形状是「事件到达 ⇒ 提前收轮询/折半 budget」，不是「事件=结论」，miss 掉就挂死的口子用 budget 兜底。

## Q2｜M13-b 区域抓帧省不省？

**结论：[推断] 大概率「照样整窗渲染、只省拷贝」——PrintWindow 的语义是向目标窗口发 WM_PRINT 让它把整个客户区渲染进你给的 HDC，渲染发生在目标进程、目标决定画多少，DC 尺寸只决定接收多少；按 L3 结论（成本在目标自己的渲染里）外推，小 DC 只省 GDI 拷贝段。**

理由：raw PrintWindow 8~16ms 里渲染段与拷贝段的比例不知道，所以别立项、先用一条探针定生死——同一窗口同负载各 12 次取中位：整尺寸 DC vs 1/4 尺寸 DC，都带 `PW_RENDERFULLCONTENT`。**判据：省 <20% ⇒ 判负不立项；省 ≥50% 才立项**（若 Chromium 对 WM_PRINTCLIENT 做了裁剪优化则有救，Chromium 是否优化 [待核实：以探针为准]）。顺带一句：比「区域抓」更便宜的「少抓」是**轮询调度**（见 Q4）——它不依赖任何应用行为，数据条件（first_change_ms 分布）M5 一导出就有。

## Q3｜M14 PUSV 怎么落地？

**结论：[确定] 先纠一个偏：PUSV 原文是「动作前」的 TOCTOU 安全再验证（L1=点击目标 masked SSIM、L2a=全屏 diff、L2b=X11 快照，<0.1s 开销、180 次对抗试验 100% 拦截 0 误报），**不是**为省动作后等待设计的——主控「动作后不必长等」是引申；本机正确落法 = 把 L1 本地化进 `_bind_capture`（现有 verify_image 全窗哈希升级为「落点区域 masked MAD」），通过者才给动作后 budget 折半，且仅限有 verify_expect 谓词的动作。**

理由：本机三件套各司其职、不用新造——`expect_uid`/uid_state 是**跨调用对象身份**（太重，不是 PUSV 的用途）；`expect_region` 是动作**后**的判定区声明（救不了动作前）；真正的 PUSV-L1 对应物是 `_bind_capture` 里现成的 verify_image——现在是全窗 SHA-256 全等（太脆，一像素变就拒），升级成「落点周围 64×64 的 masked MAD」后既拦 TOCTOU 又不误伤远处无关变化。paper 自己承认纯视觉防不住隐形 DOM 注入 ⇒ 网页目标的补位是 R1/CDP 侧核对（与 M15 Q4 的 R1 接线并单）。判据直接搬论文指标本地化：注入「观测后改落点再点」拦截率 100%、静止桌面 50 动作 0 误报、开销 ≤100ms（本机预期 20~40ms）。

```
# core._bind_capture 升级（PUSV-L1 本地化，动作前）
rec = framecache.STORE.get(cap_id, hwnd)               # TTL 内的观测帧
r   = 64                                               # 落点邻域半径
new = grab_client(hwnd, rect=client_rect_around(xy, r))# 小 DC，只抓 128×128
old = crop_client(rec.img, client_rect_around(xy, r))
if mad_gray(new, old) > MAD_THRESH:
    return GateDenied(code=12, "TOCTOU：落点区域已非观测帧，重新观测再点")
# 动作后：仅当 verify_expect 存在 ⇒ _wait_effect budget 折半；无谓词照旧等满
eff_budget = base_budget // 2 if args.get("verify_expect") else base_budget
```

## Q4｜有没有第四个刀？

**结论：[推断] 第四刀不在「抓」也不在「等」，在「预算的形状」——①固定 poll_ms 改成前密后疏退避 + 首变早停；②no-change 动作的整段等待是「证明没变」的必要成本，只能靠 Q3 的谓词折半和区域化收窄，没有免费的刀。**

理由：337~841ms 的构成是「变了 ⇒ 首变后早停」+「没变 ⇒ 等满 budget」。前者用退避调度压：首变集中在注入后前 300ms（first_change_ms 分布 M5 一导就有 [待核实：数据未导]），前 200ms 密轮（poll=15ms，raw 抓帧 8~16ms 两轮）之后指数退避到 50~100ms——抓帧次数直接砍半且首变不漏；同时核一件小事：`_wait_effect` 的 HYSTERESIS 满足后是否真的立即 return（act.py:1280 起，若等满 budget 才出就是白等，一行判据能红）。后者的小刀：`_poll_sample` 21~49ms 里 PIL 链占 13~33ms（raw 8~16ms 之外的差值），先 1/8 降采样粗筛「没变」就跳过全链精比对——省的是处理段。退避曲线参数别拍脑袋，等 M5 把未归因 99.6~109.8ms 和首变分布拆出来再定 [推断]。除这些外，20~50ms 级的组合拳还有（notices/W5 身份取值每动作一次），但没有第三个 ≥100ms 的现成刀。
