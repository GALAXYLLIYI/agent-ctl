## 〇之二、★★ 19:30 实测修正（**主控推翻自己上面的第一条结论**）

M16R 的交错重测（轮次 1，**每段 n=20**，code=8 率 100%，四段全有效）给出了**直接打点**的分段中位数，和我原先的账本对不上：

| 段 | 我原先的账单 | **实测（from_capture，改前）** |
|---|---|---|
| ① 前置 | 小 | **13.1ms** |
| ② 子进程 spawn+import+act | ≈1100ms | **1001.8ms** |
| ③ 动作后回读（等生效） | 450ms（当固定成本） | **10.2ms** |
| ④ 落盘 PNG+diff | ≈255~275ms | **11.8ms** |
| 未归因 | — | **364.0ms** |
| 端到端 p50 | 1449ms | **1405.6ms** |

**⇒ 我错在两处**：

1. **「450ms 等生效预算」几乎不花钱**（实测 ~10ms）—— 那是**上限**，不是常态成本（画面没变时指纹一比就退出了）。⇒ 我上一版说的「**唯一能改变物理地板的是第 5 条（事件驱动等待）**」**作废**。
2. **④ PNG 落盘已经不是 275ms**（实测 ~11.8ms）—— M12 阶段三把内部交接帧 PNG 改 BMP 之后，这一刀**收益归零**。⇒ 「热路径去 PNG」**降级**（除非将来证据落盘量级回升）。

**真正压着 p50 的是 ② 冷启动（约 1000ms，占 ~70%）＋ 364ms 未归因。** ⇒ 优先级重排见 §五之二。

**M16 本身的速度收益：不可判。** 轮次 1 四段对比：from_capture 1405.6 → **1407.2**（+1.6ms）；eid 1531.1 → **1521.0**（−10.1ms）—— 都**小于本机噪声门槛 ±145ms（≈10%）**，⇒ **写「不可判」，不许吹**。M16 的实际价值在**判词真实度与冗余消除**（E 刀那类），不在毫秒。

## 〇、一句话结论

**在动任何优化之前，必须先把关键路径解剖开**：现有分段账单里 **②1100ms + ③450ms + ④275ms ≈ 1825ms > 实测 p50 1449ms** ⇒ 三段在关键路径上**有重叠**（或②本身已含等待）。**不先拆重叠就优化，等于优化不在关键路径上的部分。**

## 一、★ 先决问题：关键路径到底长什么样（**这是 M17 的全部内容**）

### 1.1 现有账本的自相矛盾

| 段 | 账单耗时 | 来源 |
|---|---|---|
| ② 动作子进程（spawn + import） | ≈1100ms | 主控 M11 分段打点 |
| ③ core wait_change（等生效预算） | 450ms | 固定预算 |
| ④ 落盘 PNG + 像素 diff | ≈255~275ms | 主控 M11 分段打点 |
| **合计** | **≈1825ms** | — |
| **实测端到端 p50** | **1449ms / 1424ms** | M12 阶段三 |

⇒ 差 **−376ms** ⇒ **至少有一段不在关键路径上**（最可能是：③ 的等待与④ 的落盘**部分并行**，或② 的 import 与 spawn 重叠计时）。

### 1.2 解剖要产出什么（缺一不可）

1. **单次动作的绝对时间线**（不是分段总和）：从 `ctl_click` 入口到返回，打 6 个时间点：① 参数解析完 ② 子进程**真正开始执行** ③ 注入完成 ④ 等生效开始 ⑤ 等生效结束 ⑥ 证据落盘完。
2. **`python -X importtime` 归因**：act.py / agentctl.cli 的 import 成本**按模块排序**，找出最贵的那几个（推断候选：numpy/cv2/PIL、pywin32、策略 JSON 加载、Defender 首次扫盘）。**这是推断，必须实测。**
3. **③ 与 ④ 是否重叠**的证据（同线程时间戳对比）。

## 二、七条候选（OpenCode 调研结论，主控已核出处）

| # | 改动 | 净省(推断) | 风险 | 动契约/闸门 | 主控判定 |
|---|---|---|---|---|---|
| 1 | **热路径去 PNG**（原始 BGRA 留内存，证据改「帧序号＋单调钟＋全帧哈希＋无损裁剪」异步写） | 200~240ms | 低 | 否 | **可做**（但要保证「判定用的帧 == 存证的那块 buffer」） |
| 2 | **入口拆薄 + 延迟 import**（`python -m` 会走 runpy 并全量导入包 `__init__`；重模块延后到真用时） | 200~500ms | 低 | 否 | **M17 第二步**，先按 1.2 归因再定改哪几行 |
| 3 | **预热一次性 worker 池**（服务启动时 spawn 若干已导入进程，每进程只接一单、做完即退） | 900~1050ms | 中 | 否（须重证单写者） | **可做，但有前提**：每请求**重新校验租约**＋**审计同步落盘后才 ACK**；跨请求复用授权结论＝降级，不许 |
| 4 | **UIA 批量化**（CacheRequest 一次取全 + `FindFirstBuildCache` + 按窗口收窄根 + StructureChanged 事件刷新 + `IUIAutomation2.ConnectionTimeout`） | ≈150ms | 低 | 否 | **可做**（191ms→~30ms 有官方依据） |
| 5 | **事件驱动等待 + 静默判定**（SetWinEventHook / UIA 事件 / DXGI `AcquireNextFrame` 为主，8~16ms 指纹轮询兜底，「连续两帧相同」判静默，450ms 保留为**硬上限**，超时落 unknown） | 350~420ms | 中 | **是**（三值语义细化） | **需要用户拍板**（改的是「等多久」的语义） |
| 6 | **DXGI Desktop Duplication + dirty rect** | ≈60ms | 中 | 否 | 可做，但收益小、坑多（全屏独占/安全桌面会 ACCESS_LOST） |
| 7 | 视觉 ROI（模板匹配 1~5ms → Windows.Media.Ocr 30~80ms/裁剪 → 图标检测器 40~120ms） | 0（提命中率） | 中 | 否 | 视觉走 ROI，**不在热路径跑 VLM** |

### 2.1 「唯一能改变物理地板」的是第 5 条

地板 ≈930ms 里 **450ms 是「预算冒充物理量」**；PNG 那 ~270ms 压到 20ms 之后，地板仍由 450ms 封顶 ⇒ **其余优化只动 p50，不动地板**。

## 三、视觉那条路的排序（纯 CPU，本机无 GPU）

1. **UIA/a11y**（不是视觉，但最优先：~30ms、精确到 uid）
2. **ROI 模板匹配**（TM_CCOEFF_NORMED，1~5ms；对主题/DPI 敏感 ⇒ 模板按 app build+DPI+主题版本化）
3. **ROI OCR**（`Windows.Media.Ocr` 内置，零依赖，30~80ms/裁剪；先 det 出候选框、只对候选框 rec；2560×1600 原图别直接 OCR）
4. **图标/可点框检测器**（OmniParser icon detector 之类，int8 CPU 40~120ms，**只给可点框不给语义**；语义交给 OCR/a11y）
5. 特征点（ORB/AKAZE+RANSAC，10~50ms；平整 UI 上退化，只适合同窗滚动/缩放后配准）
6. 量化 grounding 模型（Florence-2-base 0.23B int8 / GroundingDINO-T，CPU 单图 **0.5~3s**）⇒ **不进热路径**，只做异步慢路径 + 按屏幕哈希缓存
7. 外部 API（数据出机 + 300~2000ms）⇒ **热路径否决**，最多离线评测

**不值得做**：SAM/SAM2 分割 UI、每步全屏 VLM 描述、自训 grounding、无 ROI 剪枝的多尺度金字塔。
⚠ **150% 缩放下必须 PerMonitorV2 并统一物理/逻辑换算** —— 「接地错」有一大类其实是**换算错**（本机 M16 期间已踩过一次：unaware 进程 `GetCursorPos` 给逻辑坐标，钩子给物理像素，差 1.5 倍）。

## 四、★ 不要做什么（会踩铁律/三闸，逐条给了原因）

- 跨动作复用授权/租约 ⇒ 三档授权退化成一次性会话授权。
- 多 worker 并发同一桌面 ⇒ 破坏租约单写者。
- 把「超时/无变化」记为成功 ⇒ 违反「**unknown 永不当成功**」。
- 砍回读验证换速度 ⇒ 动作不可复核。
- 审计异步批量写 ⇒ 崩溃即丢证据。
- `PostMessage`/UIA Invoke 直调控件绕过输入栈 ⇒ 绕过闸门、无法归因（M16 的 E 刀正是把这条路废掉了）。
- 为提速关 Defender / 关 DPI 感知 / 关 UIA ⇒ 计时变准、判定变错。
- 只存哈希或缩略图 ⇒ 人无法复核；**证据必须是被判定的原帧**。
- 把常驻 worker 提权或做成服务 ⇒ 扩大授权边界。

## 五之二、★★ 优先级重排（**以实测为准，覆盖 §二 的排序**）

| 新序 | 刀 | 依据（实测） | 预期净省 |
|---|---|---|---|
| **1** | **② 薄入口 + 延迟 import**（`python -m` 走 runpy + 全量导包；重模块延后到真用时） | ② = **1001.8ms**，占 p50 的 ~70% | 200~500ms（须先按 M17 的 `importtime` 归因点名） |
| **2** | **预热一次性 worker 池**（每请求重校验租约、审计同步落盘后才 ACK） | 同上，剩下的冷启动 | 900~1050ms |
| **3** | **解剖那 364ms 未归因** | 实测未归因中位数 364ms（from_capture） | 未知，先查 |
| **4** | 事件驱动等待 + 静默判定 | ③ 实测只花 10ms ⇒ **只对「真变了」那条路有价值** | 低（常态路径） |
| **5** | 热路径去 PNG | ④ 实测只花 11.8ms ⇒ **收益已归零** | ≈0 |

**给用户的那句结论也跟着改**：先前我建议「450ms 预算不碰、留给用户拍板」—— 现在看，**那条预算在常态路径上根本不花**（实测 ~10ms），**真正的瓶颈是每次动作都冷启一个 Python 子进程**。⇒ 「要不要动 450ms」这个议题**降级**（只在「真等变化」的路上才是成本）；**新的议题是：动作要不要常驻化**（worker 池）—— 那一刀要重证「租约单写者」，但它**不改铁律、不改契约、不改三值判定**。

## 五、裁决与派单顺序

1. **M17（下一刀）＝关键路径解剖**：`python -X importtime` 归因 ＋ 6 点绝对时间线 ＋ ③/④ 重叠证据。**本刀不改产品代码**（只出测量与归因），产出「下一刀该改哪几行」的施工单。
2. **M18 ＝薄入口**（按 M17 归因结果，只改被点名的那几行 import 路径）。**「热路径去 PNG」从本单删掉**（实测收益归零）。
3. **M19 ＝预热一次性 worker 池**（须先重证「单写者」不变式：每请求校验租约、审计同步落盘后才 ACK）。
4. **M20 ＝事件驱动等待**（**待用户拍板**：动的是「等多久」与三值语义细化；450ms 保留为硬上限，超时永远落 unknown）。
5. **UIA 批量化**与**视觉 ROI** 各自独立成刀。
