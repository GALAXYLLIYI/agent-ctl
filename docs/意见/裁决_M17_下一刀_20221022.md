## 〇、一句话结论

**「瓶颈在哪」这个问题已经从猜变成了有证据，但答案连着翻了三次**：①不是 450ms 等生效预算（实测只花 10ms）②不是子进程冷启动（import 83.5ms + spawn 31.7ms，占 1001.8ms 的 11.5%）③**是 act 进程内部那 886.6ms（88.5%）**——但它内部**又分两层**：

- **core 侧**（动作前后）：eid 复核走整棵 UIA 树（**129.9ms**，B 实测）+ 抓帧（**19.4ms** 热路径口径）+ **★ 计划外的「dispatch 事后段 ≈347ms」**（B 实测：wall 501ms vs 服务端 elapsed 154/190ms，两工具一致）——**这 347ms 至今未拆开，是当前最大的黑箱**。
- **act 子进程侧**：C2 的 Top-12 嫌疑（S1 置前 0.9s／S2 证据 PNG／S3 numpy 每进程 ~98ms／S4 基线 BMP 解码两次／S5 click 固定 130ms／S6 过闸读写／S12 硬 sleep）——**其中 S1 已被历史日志否掉**（见 §二）。

⇒ **下一刀 = 「动作面瘦身三刀」**，全部落在**不碰判据、不碰闸门、不碰契约**的位置上；**C1（六点打点）是这三刀各自的靶子**，等它把 886ms 与 347ms 拆开，再定每刀最终省多少。

## 二、★ 主控自己挖的一条：**S1（置前 0.9s）不是常态**

C2 的 S1 列的是「置前后固定等 0.9s」（`act.py:1684 FOREGROUND_SWITCH_TIMEOUT = 0.9`／`1710 time.sleep(...)`）——**单笔 900ms，很吓人**。
主控读源码发现它**有早退**：`ensure_foreground`（`act.py:1717-1719`）先判「目标已在前台 ⇒ 直接 return 0」，只有**不在前台**才进 `_try_foreground` 睡那 0.9s。

⇒ 再查 **live `act.log`（今天 4912 条带时间戳的日志、3108 条动作行）**：

| 事件 | 次数 | 占动作行 |
|---|---|---|
| 「↑ 动作前自动置前成功」 | **31** | 1.0% |
| 置前失败（rc=5「现前台仍是…」） | **53** | 1.7% |
| **合计走到置前路径** | **84** | **2.7%** |

⇒ **那 0.9 秒只在 2.7% 的动作里触发**（且其中一半是失败即被拒）⇒ **它不是那 886ms 的来源**。
⇒ 但它**仍是体感最差的尖峰**（一旦触发就是白等 0.9 秒）——**属于「改「等多久」」类改动 ⇒ 需要用户拍板**（见 §五 待拍板项）。

## 三、★ B 线抓到但还没拆开的黑箱：**事后段 ≈347ms**

B 的实测：`ctl_tree` 端到端 **501.4ms**（p95 561.7）vs 服务端 elapsed **154ms**；`ctl_screen` 端到端 **510.2ms** vs 服务端 **190ms**。**两工具一致 ⇒ 差额 ≈347ms 落在「dispatch 的事后段」**（core 收尾：拿回 rc → 落盘 → 写事件 → 审计）。

C2 给出的**最可能嫌疑（带行号）**：

- **S9** `core.py:3006 _im.save(...)`（写 1~3 张 PNG）＋ `core.py:3018 os.listdir(_base)`
- **S10** `store.py:350-356` 每条事件**全量重读** jsonl ＋ `store.py:396-397` fsync
- **s4** `store.py:229-233 / 446` **每条事件新建 sqlite 连接** ＋ `PRAGMA journal_mode=WAL` **每次重设**（journal_mode 本身是持久设置 ⇒ 每次重设是多余往返）
- **S2** `act.py:2751 / 2909` 每次动作两张整窗证据 PNG（`act.py:2730` 注释自承「一张多余 PNG」）

⚠ **主控已核**：`store.py:346-360` 那段全量重读是**启动时的 `_load_head`**（一次性），**不是每条事件**；但 `timeline.db-wal` 今天已 **4.84MB**、`timeline-20261022.jsonl` **6.02MB**、`timeline.db` **8.73MB** ⇒ 每条事件仍要写 sqlite＋WAL＋fsync，**这块必须由 C1 打点定量**。

## 四、★ 「下一刀」施工单（M18 · 动作面瘦身三刀）

> 三刀全部**不碰**：contract/tools.json、gate.py、action_guard_policy.json、三值判定、闸门授权口径、450ms 等待预算。
> 每刀都要**自带判据**：证明「判词没变」+「红线没破」+「省了多少（交错测量 n≥20，p50/p95，10% 噪声门槛）」。

### 刀 1 · core 侧 eid 复核：从「全树 walk」改成「按 eid 精确定位」

| 项 | 内容 |
|---|---|
| 落点 | `core.py:3598` `nodes, trunc = uia_tree.walk(hwnd, roles=roles, ...)`（带 eid 的动作，**注入前先扫一遍全树**） |
| 依据 | B 实测：`uia_tree.tree()` **129.9ms**（纯遍历 64.2 + 属性/模式读 ~66）；`FindFirst(TrueCond, Descendants)` **3.04ms**；`FindAll` 36.7ms；`ElementFromHandle` 1.09ms；**`FindAllBuildCache` 91.3ms ＝负优化（比 FindAll 慢 2.5×）⇒ 第一刀不是 CacheRequest** |
| 改法方向 | 用 `ElementFromHandle` + 按 eid/控件特征**精确定位**替代全树 walk；**语义必须等价**（「eid 指向的元素还在不在」这一结论不许变弱） |
| 预计省 | **~100~125ms**（带 eid 的动作）；待 C1 定量 |
| 风险 | ★ **判词风险**：全树 walk 能顺带发现「同名多个元素」，精确定位可能漏 ⇒ 判据必须覆盖「同名多元素」「元素已消失」「元素已换代」三种情形；**不许把「查不到」写成「没变」** |
| 红线 | 判据先红后绿；行尾 LF；三处 act.py 全等（若动 act 则三处都动） |

### 刀 2 · act 侧：`_wait_effect` 路径上的 **numpy 每进程 ~98ms**

| 项 | 内容 |
|---|---|
| 落点 | `framecache.py:442 import numpy as np`（在函数内 ⇒ **每个 act 进程首次 diff 时付一次**）｜C2 标注 A 线测得 numpy **+98.4ms**（`A:197`）｜`act.py:1274` `_fc.diff_images(a, b, ...)` |
| 改法方向 | 两条路二选一：①**换更轻的 diff 实现**（纯 Python/PIL 逐行比较，避免 numpy）；②**把 numpy 的 import 成本变成一次性**（不可能——每进程独立），⇒ 实质只有 ① 或「只在真需要 diff 的路径才 import」（现状已如此，但每进程仍要付） |
| 预计省 | **~98ms**（每个带 diff 的动作）｜待 C1 定量 |
| 风险 | ★ **判词风险**：diff 结果必须逐位一致（含小方块/光标规则，M6-① 两级算法）⇒ 判据必须含「8×8 方块仍判 changed=true 且 bbox 正确」（B 已实测过一次，搬进判据） |

### 刀 3 · core 侧事后段：timeline 落盘的**纯浪费**先砍

| 项 | 内容 |
|---|---|
| 落点 | `store.py:229-233 / 446`（每条事件**新建 sqlite 连接** ＋ **每次重设 `PRAGMA journal_mode=WAL`**）｜`store.py:396-397`（fsync 频率）｜`core.py:3006/3018`（写 1~3 张 PNG ＋ `os.listdir`）｜`act.py:2751/2909`（两张整窗证据 PNG ＋ 注释自承有一张多余） |
| 改法方向 | **只砍「纯浪费」**（连接复用、journal_mode 只设一次、去掉那张多余 PNG、去掉多余的 listdir）；**⛔ 不许砍 fsync/审计完整性**（铁律：证据丢了就是事故；OpenCode 建议里「审计异步批量写」被明确列为禁项） |
| 预计省 | **待 C1 定量**（B 说事后段共 347ms）——**这一刀是三刀里最可能拿到大头的，但必须先拆** |
| 风险 | 审计完整性、证据可复核性 ⇒ 判据必须覆盖「事件一条不少」「哈希链不断」「临时目录不泄漏」 |

### 刀 4（**待用户拍板**）· 置前 0.9s 尖峰 ⇒ 改短轮询

`act.py:1684/1710`：固定睡 0.9 秒。**改法**：改成「`SetForegroundWindow` 后按 10~20ms 短轮询，前台一变就返回；超时上限仍保留」。**取舍**：①变快了 ②但**可能把「其实会成功的置前」判成失败**（rc=5 拒绝）⇒ 慢应用/抢焦点的场景下**拒绝率可能上升**。⇒ **这属于「改「等多久」」，必须用户拍板**，且判据必须覆盖「置前失败率不得上升」。

## 五、明确**不做**的（省时间但会坏判据/安全性）

砍回读验证换速度｜超时/无变化记成功｜缓存后不核验或「查不到就当没有」｜跨动作复用授权/租约｜并发 worker 同桌面｜关 DPI 感知/关 UIA/关 Defender 换速度｜只存哈希不存原帧｜提权/做成服务/动态 eval/装新依赖。

## 六、验收线（写死，不许事后放宽）

- 端到端 p50（n≥20，**交错**测量）报 p50 + p95；**差值 <10% 噪声门槛（±145ms）一律写「不可判」**。
- 守门两条：code=8 率与 unknown 率**不得高于基线**；红线：contract / gate / policy 零改动，三处 act.py 全等，行尾全 LF。
- 每刀必须有「**判词没变**」的判据（先红后绿），不许只看毫秒。

## 七、★ 用户从需求侧验不了的那一项

用户看到的是「我点一下它多久动」。⇒ 每个毫秒数必须由主控**亲跑同一把尺子**复核，并附**背景负载声明**（本机 MiniMax Code 一直在跑用户自己的桌宠任务，~150~200% CPU）。

## 八、这一轮的方法论收获（三条，建议进手册）

1. **「X 是瓶颈」必须有「X 内部再拆一层」的证据**——本轮我犯过两次（450ms 预算、子进程冷启动），都被第三方实测推翻。
2. **并行/串行要按「测量是否互相污染」分，不按「人/工具」分**：本单**静态并行、时序串行**，用「测量窗口令牌」把串行化变成机制而不是靠自觉。
3. **历史日志是免费的证据**：C2 列出的 S1（0.9s 置前）看着最大，**主控查 live `act.log` 4912 行**就否掉了（2.7%）——**先翻盘上已有数据，再设计实验**。
