## 二、★ 主控自己挖的一条：**S1（置前 0.9s）不是常态**

C2 的 S1 列的是「置前后固定等 0.9s」（`act.py:1684 FOREGROUND_SWITCH_TIMEOUT = 0.9`／`1710 time.sleep(...)`）——**单笔 900ms，很吓人**。
主控读源码发现它**有早退**：`ensure_foreground`（`act.py:1717-1719`）先判「目标已在前台 ⇒ 直接 return 0」，只有**不在前台**才进 `_try_foreground` 睡那 0.9s。

⇒ 再查 **live `act.log`（今天 4912 条带时间戳的日志、3108 条动作行）**：

| 事件 | 次数 | 占动作行 |
|---|---|---|
| 「↑ 动作前自动置前成功」 | **31** | 1.0% |
| 置前失败（rc=5「现前台仍是…」） | **53** | 1.7% |
| **合计走到置前路径** | **84** | **2.7%** |

⇒ **那 0.9 秒只在 2.7% 的动作里触发**（且其中一半是失败即被拒）⇒ **它不是那 886ms 的来源**。
⇒ 但它**仍是体感最差的尖峰**（一旦触发就是白等 0.9 秒）——**属于「改「等多久」」类改动 ⇒ 需要用户拍板**（见 §五 待拍板项）。
