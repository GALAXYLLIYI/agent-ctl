## 一、OpenCode 这份意见的质量

它不是泛泛而谈：**实读产品代码 + 本机实测（合成帧 2542×1400，取 5 次最小/中位）**，
给出可复核的原始数字表（`diff_images` 17.7/18.5ms、`is_blank` 5.7ms、PNG save **29.9ms**、BMP 5.3ms、raw 1.9ms…）。
⇒ **采信，并据此修订方向。**

## 二、主控逐条核实的结果（**三条全部成立**）

### ① 「判定权留 core」在普通 click 路上**没接上** ✔ 成立

`core.py:2899`

```python
_need_diff = bool(args.get("_need_diff") or args.get("frame_id"))
```

`core.py:3030` 的「退化 ⇒ code=5」与 `core.py:3066` 的「`_df.changed` ⇒ code=8」
**都长在 `if _need_diff:` 里面** ⇒ **普通 `ctl_click`（不带 `frame_id`）根本不进这两个分支**。

⇒ **后果**：普通 click 的 `code` 仍由 **act 的 rc** 决定（`act.py:2806` `return 0 if (dry or changed is True) else 8`），
而 act 的 `changed = (fp1 != fp0)` 是**文件 md5 比对**（`act.py:2766-2770`）⇒ **第二把尺子仍在裁决**；
且 **`degraded` 被丢掉**（不会落 code=5）。

★ **这也是我自己的验证盲点**：判据的 ⑧「退化 ⇒ code=5」走的是测量器
`tests\_M11_分段测量.py:198` 的 `ctl_click`，而它**传了 `frame_id: sv`** ⇒ `_need_diff=True`
⇒ **判据测的是「带 frame_id 的路」，不是普通 agent 真正调用的那条路**。
⇒ 这条要**改成在普通 click 路上验**，并在 M12 阶段三里补齐实现。

### ② act 的**基线是注入之后才抓的** ✔ 成立

`act.py:2748` / `2762` / `2776` 三处都是：

```python
_eff = _wait_effect(hwnd, _poll_base(hwnd), budget_ms=int(_settle(450) * 1000))
```

`_poll_base(hwnd)` 是**实参** ⇒ 在该行求值 ⇒ **在注入之后**。

⇒ **若目标重绘快于一次 PrintWindow，基线里已经含了变化 ⇒ 首变被吞 ⇒ 只能等满预算**。
⇒ 这正是 M12 合并之后**剩下的那截假等待**（337~841ms 的一部分）的机理。
⇒ 且 `first_change_ms` 的零点（`act.py:1310`）**与基线同时是偏的** ⇒ M13 要采的「首变分布」会失真。

### ③ 「生产预算不是 800ms」 ✔ 成立

`act.py:2749/2763/2777` 都传 `budget_ms=int(_settle(450) * 1000)`；
`POLL_BUDGET_MS = 800` 只是 `_wait_effect` 的**函数默认参数**（`act.py:1300`）。

⇒ **生产 click 的 no-change 上限 ≈ 450ms + 一帧**，不是 800ms。
⇒ M11 的「837.1ms / 14 轮」是**直调默认 800** 测出来的 ⇒ **拿 800 去定退避曲线会系统性偏一倍**。

## 三、裁决

| 事项 | 裁决 |
|---|---|
| M12 阶段二的状态 | **部分兑现**（合并本身成功：wait_change 321~343ms → 14~31ms、端到端 −142~195ms、双实现已消、退化检测已接）⇒ **但「判定权归 core」在普通 click 路上未兑现** ⇒ **补 M12 阶段三** |
| 判据的 ⑧ | **必须改成在普通 click 路（无 `frame_id`）上验** —— 否则它测不到真缺口 |
| 更稳的形状 | ★ **采纳 OpenCode 的建议**：core 把 **baseline（帧 + `w/h/origin/dpi_scale` + 判据版本号）下发**给 act，act 只做「对着这个 baseline 采样」并回传**首变帧 + 每轮时刻 + 轮次**；**act 的 rc 只表示「输入送没送到」，不再承载画面结论** |
| 帧口径 | ★ 随帧回传 `(w,h,origin,dpi_scale)`；core 侧不一致 ⇒ **回落 `wait_change`（fail-closed）**，**不许**「现取 origin」补救 |
| `effect` 里被扔掉的两个量 | ★ `rounds` / `first_change_ms` 零成本接进 `data.after` ⇒ agent 能分清「对方一直没反应」与「反应了但超预算」（现在都只看到 `code=8`） |

## 四、★ **修订 M13 的方向**（OpenCode 的 Q2 推翻了主控的裁决）

主控原裁决：「第四刀 = 预算的形状（退避调度）」。**OpenCode 用算式 + 实测把这个排序推翻了**：

> 大窗每轮 ≈ 抓帧 40.96 + diff 15.4~18.5 + is_blank 5.7 + sleep 50 ≈ **112ms/轮**；
> `HYSTERESIS=2` ⇒ 首变最早 ~224ms（M11 直测 258~395ms 正好对上）。
> **把 `poll_ms` 从 50 调到 15，只省 35ms/轮**；而 no-change 时轮次上涨（450/77≈6 轮 vs 450/112≈4 轮）
> ⇒ **总 CPU 反而涨**。⇒ **退避曲线改不动大头。**

⇒ ★ **修订**：

| 序 | 刀 | 裁决 |
|---|---|---|
| **1** | **删重复**（同一帧只抓一次、只编码一次） | ★ **升为第一刀**。OpenCode 数出：**一次点击拍 5~7 张整窗、写 6~7 张 PNG**。具体：①`act.py:2599` 无条件拍 before、`2622` 又拍一次覆盖它 ②act 的 `after` 整窗只为了算 md5 ③core 落盘 `before/after/crop` + act 侧 `first.png` ⇒ **6~7 张 PNG/次 ≈ 180~210ms 编码**（这正好是 M5「未归因 99.6~109.8ms」的量级）④`_wait_ready` 又 `_poll_base` 抓一张（`act.py:2690`），而 before 已在内存里 |
| **2** | **交接/落盘格式**：PNG → **raw / BMP** | ★ **真省 ~27ms/次**（save: PNG **29.9ms** / BMP **5.3ms** / raw **1.9ms**）。⇒ ⚠ **主控原结论要限域**：「换拷贝 API 没用」**只对抓帧成立**；换**交接格式**是另一回事 |
| **3** | 每轮的两笔纯税 | `is_blank` 每轮 **5.7ms**（退化只是打标 ⇒ 最后一帧打一次就够）、`_poll_gray` 每轮 **6.3ms**（只为判「图够不够大」⇒ `img.size` 就够）⇒ **~12ms/轮** |
| **4** | 视觉接地（M15） | **维持原计划**：B/C 批按派单走，**不许**加码到整屏 OCR（整客户区 1120ms） |
| **5** | 退避调度 | **降级到最后**：它改的是分母里最小的一项，且**首变分布的零点目前是偏的**（见 §二②）⇒ 要先修基线时机，再谈曲线 |
| 6 | 「为什么没变」的一跳（能力向） | 排最后：diff bbox + crop.png 已在手，局部 OCR 42~58ms ⇒ 边际成本接近 0，但属于「把已有数据变成能力」，不是本轮的提速 |

### 明确**不做**的（OpenCode 的 Q3 逐条核过）

| 路 | 判定 | 理由 |
|---|---|---|
| 降采样预筛再精判 | ✗ | 1/4 BOX 会把 8×8=64px² 平均掉 ⇒ 撞 `DIFF_MIN_AREA=24` ⇒ 要么漏报要么重算；**还会松失败口径** |
| 并发/多线程抓两帧 | ✗ | `WM_PRINT` 要目标窗口 UI 线程处理 ⇒ 并发只是排队，还可能把「无响应」变成超时 |
| 缓存 UIA 控件/句柄 | ✗ | `act.py:2692` 的二次 `find_control` 正是防「读到与点到之间矩形变了」⇒ 缓存必须配 rect 复核，省不到一半还引入 stale 绑定 |
| JPEG 存证据 | ✗ | 解码 10.0ms 且**有损** ⇒ diff 会误报（阈值 2/255）⇒ 证据图不该有损 |
| 事件驱动替代轮询 | ✗ | 维持原判：只配当「提前收轮」的提示，钩子要常驻进程 |

## 五、给用户的一句话（**不粉饰**）
