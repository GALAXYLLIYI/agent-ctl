# 耗时归因（profiling）· 口径与接法 · 2026-10-25

> **一句话**：通宵记录 §七 那条「800–1300ms 延迟带」自认**无归属**；本模块给它一把**分阶段**的尺子 ——
> 时间按阶段分桶记下来，并**诚实标注样本够不够**下结论。（本单只交尺子，**不接线**。）

## 一 · 口径（哪些阶段、何时开始计）

* **计时源** `time.perf_counter()`（单调钟，不受校时影响，**不依赖 `clock.py`**）；**内部单位 = 整数纳秒**（不浮点累加，长跑不漂），对外换算**毫秒**。
* **谁在计 / 何时算起**：`with profiling.span("阶段名"):` 包住一段（**进入时起、退出时止**，**异常路径也记账**〔`finally`〕⇒ 抛异常的样本不丢）；外部已知耗时用 `profiling.record("阶段名", ms)`。
* **嵌套**：`span` 可套 `span` ⇒ **外层含内层**；「总耗时」看外层桶，「子阶段」看内层桶。
* **分位数** = **nearest-rank**（第 `ceil(p/100*n)` 小，1-based）⇒ 手算可核对：n=100 ⇒ p50 第 50 小、p95 第 95 小。
* **`total_ms`** = 所有样本耗时之和 ⇒ 嵌套**重复计** ⇒ 是「被计时的总量」，**不是**链路墙钟时间。
* **线程**：写入/读取同一把 `threading.Lock` ⇒ 并发写不丢计数（判据 A4：8 线程 1000 条）。

## 二 · 样本门槛（别拿噪声当结论）

* **n < 20 ⇒ 渲染时逐行打「⚠ 样本不足（<20），不足以归因」**＋末尾汇总提醒（n 小时 p95 可能就等于 max）。
* ⇒ 引用前至少攒 **20 个样本**（最好 100+）；**连 n 一起写**（`render` 已带 n）。
* ⇒ p95 仍**不是**「那一段慢了」的证据：**先看 max 与分布**，再谈归因。

## 三 · 怎么贴着 dispatch 用（只写怎么接，不接线）

1. **阶段名**用 `<入口>.<子段>`：`dispatch.total` / `dispatch.ownership` / `dispatch.shot` / `dispatch.click` /
   `act.legacy` / `act.legacy.wait` / `core.picture_verdict` / `core.extend_observe` / `ocr.recognize`。
2. **最外层**包总桶（现有 dispatch 逻辑一行不改）：`with profiling.span("dispatch.total"): ...`
3. **边界处**加子桶：`legacy_tools/act.py` 是**子进程** ⇒ 父进程只能看到「黑盒总时长」，
   **子进程内部的细分只能由子进程自己上报**（否则父进程无从得知）。
4. 外部已知耗时（Windows API / OCR 引擎自报）用 `profiling.record(阶段名, ms)` 补进来。
5. 收尾 `print(profiling.render())` ⇒ 中文表＋样本数＋不足归因警告；长跑分段用 `profiling.reset()`（**生产路径不要调**）。

## 四 · 本模块守的红线

不 import core / gate（不碰闸门/契约、无循环依赖）｜不写盘（只在内存，进程退出即散）｜只用标准库｜**不接 dispatch**。
判据静态核这两条红线（`tests\_P3_耗时归因_判据.py` A6，tokenize 剥注释后只判真代码行）。
