### 于是今天的真实痛点是这条（不是「勾选」问题）

> **你手上有一张 B+C 的证。现在 agent 只要 A（只读感知）。你点了授权 ⇒ 新证里只剩 A，
> 你原来的 B、C 被这次「小请求」抹掉了。**
> 下次 agent 想点东西，又得重新弹一次窗；反过来，你刚才明明还有 B+C 的权限，却因为批准了一个更小的请求而丢了。

## 二、一个具体场景，三种走法

**前提**：你有一张 30 分钟内有效的 **B+C** 证（能点击、能打字）。现在 agent 请求 **A**（只读感知）。

### ① 今天（现状）

- 弹窗上写：「本次授权范围：A」
- 你点**授权** ⇒ 新证 = **A**（B、C **没了**），`acts` 归零，`expires` 刷新
- 你点**拒绝** ⇒ 旧证 **B+C 原封不动**（不写盘）

### ② 方案 A（窗口A 最小改法：「默认 = 现有 ∪ 本次要的」）

- 弹窗上写：「本次授权范围：**A、B、C**」（= 现有的 B、C ＋ 这次要的 A）
- 你点授权 ⇒ 新证 = **A、B、C** ⇒ **你以前批过的范围留着**，加上这次要的
- 你点拒绝 ⇒ 旧证 B+C 原封不动（不变）
- **一个概念**：`scopes` 就是这张证的范围。**改动面**：`_initial_scope_states` 多接一个「现有证的范围」作输入；`merge_pass` 那行**不用动**（弹窗算出来的并集就是批准集）。
- **代价**：这张证**比这次请求宽**（请求 A 却拿到含 B 的证）—— 等于「你以前批过的权限，在以后的小请求里免重批」。
  而且**今天弹窗里没有勾选框** ⇒ 你**没法在弹窗里把 B 去掉**（这引出 §五）。

### ③ 方案 B（两概念：`ceiling` 天花板 / `grant` 实授）

- 证里记**两个值**：
  - **ceiling（天花板）** = 这次**最多**能批到哪 = 现有 ∪ 本次要的 = A、B、C ——「你最多可以给我这些」
  - **grant（实授）** = 这次**真给了**什么 = 本次请求要的（= A）——「我现在就给你这些」
- 弹窗上写：「可批范围（ceiling）：A、B、C　／　本次授予（grant）：A」
- 你点授权 ⇒ 证里 **grant=A、ceiling=A,B,C** ⇒ **agent 实际只能用 A**（判定按 grant 判，不按 ceiling 判）
- **两个概念**。**改动面**：签发侧（弹窗落盘两个字段）**＋ 校验侧**（`gate.check` / `parse_scopes` 要读 grant）⇒ **两边都动**；
  而且**老证没有 ceiling 字段** ⇒ 得定「老证的 ceiling 算什么」的兼容口径。
- **好处**：① 语义准（能批 ≠ 已授）；② 为「预勾选 / 免重批」留了**正规位置**（ceiling 就是给未来留的额度上限）；
  ③ 审计能说清「你批过最多什么 / 这次真给了什么」。

## 三、对比表

| 维度 | 方案 A（并集，一个概念） | 方案 B（ceiling + grant，两个概念） |
|---|---|---|
| 证里装什么 | 现有 ∪ 本次要的 | grant=本次要的；ceiling=现有 ∪ 本次要的（**只作上限记录**） |
| agent 实际能用哪些 | 证里的**全部**（A、B、C） | **只有 grant**（A） |
| 弹窗上写什么 | 一行：「本次授权范围：A、B、C」 | 两行：「可批 ceiling：A、B、C ／ 本次 grant：A」 |
| 改签发侧 | 改 1 处（多接一个输入） | 改（多落一个字段） |
| 改**校验侧** | **不改** | **要改**（判定读 grant） |
| 老证兼容 | 天然兼容（老证没并集概念） | **要定口径**（老证的 ceiling 算什么） |
| 能不能支撑「小请求免重批」 | 能（但代价是证变宽） | 能（且证不变宽） |
| 审计能说清 | 「这张证有哪些范围」 | 「你最多批过什么 / 这次真给了什么」 |
| 主要风险 | 证比请求宽 ⇒ 一次小批准**长期挂着**更大的权限 | 概念多 ⇒ 校验侧与老证两处都要小心；**但语义更准** |
| 改动量 | 小（1 处） | 中（签发 + 校验 + 兼容） |

## 四、方案 B 的 `ceiling` 今天**有没有人用**？

**没有。** 现在的校验侧只读 `scopes`，`ceiling` 若落盘将是一个**没人读、没人判、没人限**的字段。

⇒ 所以选 B 的真实意义只有一个：**你近期要「小请求免重批」这个能力。**
- 要 ⇒ 直接做 B（ceiling 从第一天起就有消费者）。
- 不要 ⇒ 现在做 B 是**提前抽象**（先上一个没人用的概念），而 A 已经能解决今天的痛点（小请求抹掉大范围）。

## 五、★ 隐藏的第三个决定（独立于 A/B）

派单判据要求「**取消勾选 ⇒ 证不含那个范围（fail-closed）**」。
但今天**没有勾选框** ⇒ 用户要缩小范围，手里**只剩「拒绝」这一个动作**（拒绝 = 整张证不换）。

所以还要你定一件事：**要不要给用户「缩小范围」的手段？** 三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| ① 不给（维持现状口径） | 批准 = 全盘接受这次算出的范围；想缩小就拒绝 | 用户想「只要 A、别给我 B」时**做不到** ⇒ 判据里那条「取消勾选」得改写成「拒绝 ⇒ 不换证」 |
| ② 把勾选框加回来 | 弹窗里加 A/B/C/D 四个勾 | **违背 2026-10-18「第三轮 C」的决定**（那次你明确要弹窗回到改前、不加可见控件） |
| ③ 弹窗里给一行**可编辑的范围串** | 例如显示「A,B,C」并允许改成「A」 | 不加勾选框，但**加了可见控件**（同样是第三轮 C 不想有的）——不过是**一个输入框**，比四个勾轻 |
