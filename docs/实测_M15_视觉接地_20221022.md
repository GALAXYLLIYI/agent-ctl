## 0. 一句话

**A 批（口径统一 + 字框合并）已交付并自测绿**；过程中实测揪出**一个 A 批自己没发现的洞**：
`ocr.py` 的客户区尺寸**无条件乘 `dpi_scale`**，在**服务进程**（= PER_MONITOR_AWARE）

## 2. ★ 实测揪出的洞：客户区尺寸在感知进程里**双乘 1.5**

### 2.1 现象

同一个记事本窗口、同一时刻，**只因进程 DPI 感知级别不同**，`GetClientRect` 读出两套数：

```
Q1 进程 DPI 感知级别： DPI_UNAWARE(0)          ← 判据脚本进程
   GetClientRect 客户区尺寸 = (1695, 1013)        ← 逻辑（虚拟化）像素
   ClientToScreen 原点 = (6, 0)

（导入 uia_tree / 跑过 _dpi_awareness() 之后）
   GetClientRect 客户区尺寸 = (2543, 1520)       ← 物理像素
   ClientToScreen 原点 = (9, 0)
```

`2543 / 1695 = 1.5` = 本机 150% 缩放。**改前** `client_rect_screen` 无条件 `width = raw × k`：

| 进程 | 改前报出的客户区 | 真值（物理） | 判定 |
|---|---|---|---|
| DPI-unaware（判据脚本） | 1695×1.5 = **2542×1520** | 2543×1520 | 尺寸对（巧合），**原点错**（(6,0) 是虚拟化坐标） |
| **PER_MONITOR_AWARE（服务进程）** | 2543×1.5 = **3814×2280** | 2543×1520 | ★ **尺寸双乘 1.5** |

服务进程为什么会是 aware：`legacy_tools/coord.py` **导入即** `SetProcessDpiAwareness(2)`，
而 `core._win_rect` 会 import 它 ⇒ 服务一旦用过 `ctl_screen`/`ctl_tree` 就已是感知进程。
（另：`uia_tree._lib()` 里的 `_dpi_awareness()` 同理。）

### 2.2 这个洞的实际后果

1. **A 批初版**把 `grab_client` 的位图改成按 `box["width"]` 建 ⇒ 在服务进程里位图变成 **3814×2280**，
   窗口内容只占左上 2543×1520、**右侧/下方 1/3 是空白**（实测：PrintWindow 不会把窗口缩放铺满，
   它按 1:1 画，多出来的部分是空的）。
2. **ImageGrab 退路**按 `(left, top, left+3814, top+2280)` 抓 ⇒ 抓回来的是**比客户区大 1.5 倍**的一块屏幕，
   里面混着别的窗口 ⇒ 两条路径的词框根本不在同一套坐标上（这正是派单说的「两路差 ~5px」的成因，
   实际量级是 1.5 倍）。
3. `core._screen_ocr` 的 usable 判定拿 `客户区.width/height` 当边界 ⇒ 边界虚高 1.5 倍，判定被放松。

### 2.3 修正后（实测）

```
client_rect_screen = {'ok': True, 'left': 9, 'top': 0, 'width': 2543, 'height': 1520,
                      'logical_width': 1695, 'logical_height': 1013,
                      'dpi_aware': 2, '口径可靠': True}
ocr_window 客户区 = {'left': 9, 'top': 0, 'width': 2543, 'height': 1520,
                    'dpi_aware': 2, '口径可靠': True, '画面稳定': True,
                    'origin_口径': '屏幕物理像素（与 UIA BoundingRectangle 同一套）'}
```

**与 `uia_tree`（另一套实现）交叉核对**（判据 A④，绿）：
`ocr 客户区 = 2543x1520@(9,0)` ＝ `uia_tree 客户区 = 2543x1520@(9,0)` ⇒ **尺寸一致、原点一致**。

### 2.4 词框数值：三种口径下**没变**（这点要说清楚）

| 版本 | 进程 | 位图尺寸 | words 换算 | 「文」的框 |
|---|---|---|---|---|
| 改前 | unaware | 1695（逻辑） | ÷f **×k** | x=21 |
| 改前 | **aware** | 2543（物理，1:1） | ÷f **×k** | x=21×1.5=**31.5** ★ |
| A 批初版 | aware | 3814（1:1 内容+空白） | ÷f | x=21 ✓ |
| **A 批修正版** | aware | 2543（物理，1:1） | ÷f | x=21 ✓ |

⇒ **A 批初版起，词框数值就已经是客户区物理像素了**（这一点 A 批没做错）；
本轮修正改的是**客户区尺寸**（3814→2543）、**ImageGrab 退路的 bbox**、以及**原点的物理性**。


### 3.4 判据口径的两处改动（要说清楚，别让人以为「判据放水」）

1. **A② 从「比图尺寸」升级为「比同一区域的词框坐标」**。
   老口径只比尺寸 ⇒ 「PrintWindow 返 1695×1013 vs ImageGrab 返 2542×1520」这种**差 1.5 倍**的洞会被放过。
   新口径要求**同一个词的框坐标差 ≤ 1px**（实测 **0 px**）。
2. **A② 只在「屏幕上确实可见」的区域上量**。
   本机 Windows 前台锁很硬：`SetForegroundWindow` 被系统直接拒（`pywintypes.error`），
   `SetWindowPos(HWND_TOPMOST)` 也压不住用户的 OpenCode 窗口 ⇒ 整块客户区被别的窗口遮住。
   两条路径的坐标偏移是**常数**（都在客户区相对系里），所以判据**自动找一块可见子区域**
   （试 16 块候选，命中 (0,0,700,150)，两图平均差 1.7/255）来量同一个偏移。
   找不到可见区域 ⇒ 报**验不了**（环境受阻），**不报红**——环境红和产品红必须分得开。

## 4. 真机实测（自己的记事本，不碰用户正在用的窗口）

```
hwnd = 141010（本次新开的空记事本）
客户区（物理）= 2543×1520 @ 屏幕 (9,0)   dpi_aware=2（PER_MONITOR_AWARE）
逐字框（前 5）= 文 x=21 y=76 w=21 h=20 ｜ 件 x=42 y=78 w=21 h=20 ｜ 无 x=86 y=32 w=18 h=16 …
词框（前 3）  = 文 x=21 y=76 w=21 h=21 ｜ 行 x=35 y=1488 ｜ 件 x=42 y=78 w=21 h=20
```

⚠ **与主控实测的数值不同**：主控给的是「文 x=31, w=32」，本单是「文 x=21, w=21」。
**原因**：这是**两个不同的窗口**（本次是新开的空记事本，字号/字体/布局都不同），
且主控那次是**改前**的代码在 unaware 进程里跑出来的。
⇒ **本单不宣称「数值与主控逐字相同」**；跨窗口逐字比对没有意义。
能证的是：**改前/改后/A 批修正版在同一个窗口上的 words 数值一致**（§2.4）。
