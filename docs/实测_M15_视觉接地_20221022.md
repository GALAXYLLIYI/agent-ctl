### 2.4 判据口径的两处改动（要说清楚，别让人以为「判据放水」）

1. **A② 从「比图尺寸」升级为「比同一区域的词框坐标」**。
   老口径只比尺寸 ⇒ 「PrintWindow 返 1695×1013 vs ImageGrab 返 2542×1520」这种
   **差 1.5 倍**的洞会被放过。新口径要求**同一个词的框坐标差 ≤ 1px**（实测 **0 px**）。
2. **A② 只在「屏幕上确实可见」的区域上量**。
   本机 Windows 前台锁很硬：`SetForegroundWindow` 被系统直接拒（`pywintypes.error`），
   `SetWindowPos(HWND_TOPMOST)` 也压不住用户的 窗口B 窗口 ⇒ 整块客户区被别的窗口遮住。
   两条路径的坐标偏移是**常数**（都在客户区相对系里），所以判据**自动找一块可见子区域**
   来量同一个偏移。⚠ **选块必须「可见且有字」**：空白区域两条路径当然一致（mad≈0），
   拿它去比「词的坐标」是**比不出东西**的（实测踩到：挑到一块空白 ⇒ 两条路径都 0 词 ⇒ 白跑一趟）。
   ⇒ 现在选块条件是「两图平均差 ≤ 12 **且** 这块 OCR 得有词」。
   找不到这样的块 ⇒ 报**验不了**（环境受阻），**不报红** —— 环境红和产品红必须分得开。
3. ★ **C⑤ 改成走生产真链**（主控 2026-10-22 复核意见立的教训：M12 判据 ⑧ 就是因为
   借了测量器的 `frame_id` 才没测出「普通 click 路走不到 core 判定」的缺口
   ⇒ **判据不许只在函数层打桩**）。
   改前：C⑤ 调的是 `core._screen_build()`（**函数层**）+ `_eid_recheck` 算点击点（**没真点**）。
   改后：`core.dispatch("ctl_screen", …)` → `objects[]` 里的带 eid 词元素 →

## 3. ★ 洞 ①：客户区尺寸在感知进程里**双乘 1.5**

### 3.1 现象

同一个记事本窗口、同一时刻，**只因进程 DPI 感知级别不同**，`GetClientRect` 读出两套数：

```
Q1 进程 DPI 感知级别： DPI_UNAWARE(0)          ← 判据脚本进程
   GetClientRect 客户区尺寸 = (1695, 1013)        ← 逻辑（虚拟化）像素
   ClientToScreen 原点 = (6, 0)

（导入 uia_tree / 跑过 _dpi_awareness() 之后）
   GetClientRect 客户区尺寸 = (2543, 1520)       ← 物理像素
   ClientToScreen 原点 = (9, 0)
```

`2543 / 1695 = 1.5` = 本机 150% 缩放。**改前** `client_rect_screen` 无条件 `width = raw × k`：

| 进程 | 改前报出的客户区 | 真值（物理） | 判定 |
|---|---|---|---|
| DPI-unaware（判据脚本） | 1695×1.5 = **2542×1520** | 2543×1520 | 尺寸对（巧合），**原点错**（(6,0) 是虚拟化坐标） |
| **PER_MONITOR_AWARE（服务进程）** | 2543×1.5 = **3814×2280** | 2543×1520 | ★ **尺寸双乘 1.5** |

服务进程为什么是 aware：`legacy_tools/coord.py` **导入即** `SetProcessDpiAwareness(2)`，
而 `core._win_rect` 会 import 它 ⇒ 服务一旦用过 `ctl_screen`/`ctl_tree` 就已是感知进程
（`uia_tree._lib()` 里的 `_dpi_awareness()` 同理）。

### 3.2 这个洞的实际后果

1. **A 批初版**把 `grab_client` 的位图改成按 `box["width"]` 建 ⇒ 在服务进程里位图变成 **3814×2280**，
   窗口内容只占左上 2543×1520、**右侧/下方 1/3 是空白**（实测：PrintWindow 不会把窗口缩放铺满，
   它按 1:1 画，多出来的部分是空的）。
2. **ImageGrab 退路**按 `(left, top, left+3814, top+2280)` 抓 ⇒ 抓回来的是**比客户区大 1.5 倍**的一块屏幕，
   里面混着别的窗口 ⇒ 两条路径的词框根本不在同一套坐标上（这正是派单说的「两路差 ~5px」的成因，
   实际量级是 1.5 倍）。
3. `core._screen_ocr` 的 usable 判定拿 `客户区.width/height` 当边界 ⇒ 边界虚高 1.5 倍，判定被放松。

### 3.3 修正后（实测）

```
client_rect_screen = {'ok': True, 'left': 9, 'top': 0, 'width': 2543, 'height': 1520,
                      'logical_width': 1695, 'logical_height': 1013,
                      'dpi_aware': 2, '口径可靠': True}
ocr_window 客户区 = {'left': 9, 'top': 0, 'width': 2543, 'height': 1520,
                    'dpi_aware': 2, '口径可靠': True, '画面稳定': True,
                    'origin_口径': '屏幕物理像素（与 UIA BoundingRectangle 同一套）'}
```

**与 `uia_tree`（另一套实现）交叉核对**（判据 A④，绿）：
`ocr 客户区 = 2543x1520@(9,0)` ＝ `uia_tree 客户区 = 2543x1520@(9,0)` ⇒ **尺寸一致、原点一致**。

| 版本 | 进程 | 位图尺寸 | words 换算 | 「文」的框 |

## 4. A 批：字框合并

### 4.1 窗口A 规则（主控已采纳，一条没改）

同行（垂直中心差 ≤ 0.5×min(h)）+ 紧邻（水平 gap ≤ 0.5×min(h)）+ 同号（|Δh| ≤ 25%），
按 x 排序贪心；标点并入左词；空格断词；**尺度基准用 h 不用 w**；
词框 = 成员框并集；`conf` = min(成员 conf)；`t` = 成员文本依次拼接。

### 4.2 ★ 洞 ②：窗口A 伪代码的「单一开放组」在多行画面上会漏合

窗口A 的伪代码是「按 x 排序 + 新词只跟**最后一个**输出比」。
本机真机实测：记事本状态栏有个「行」字 `x=34`，恰好**夹在**「文」(x=21) 与「件」(x=42) 中间
⇒ 按 x 排序后「件」跟「行」比（不同行）⇒ **「文」「件」合不成「文件」**。

⇒ 改成**多个开放组**（每组 = 一行里的一个词）：新词跟**所有**组比，
命中「同行 + 紧邻 + 同号」的那个（取 gap 最小的），合不上就**另起一组**。
★ **三条判据一条没改**，只改了「跟谁比」。

判据 A①d 把这条钉住（合成一组里的两个 case，注入时红）。

### 4.3 合并效果（真机）

修之前：B④b「词 24 个，命中 UIA 3 个」；修之后：「词 **18** 个，命中 UIA **8** 个」
（合并把逐字框收成词，词框更接近 UIA 物体的矩形 ⇒ 命中更多更准）。

```
OCR 词框(客户区物理) + 帧绑定 origin(屏幕物理) ⇒ 屏幕物理矩形
        ↓ IoU ≥ 0.6
UIA 物体 rect(uia_tree.py:249「屏幕物理像素」)
```

- **origin 必须与那帧绑定**：`ocr_window` 抓图**前后各取一次几何**，一致才认（`画面稳定=True`）；
  窗口在抓图期间动过 ⇒ `画面稳定=False` ⇒ `_screen_ocr` **不给 origin** ⇒ 调用方拿不到就自然不会去对齐
  （fail-closed，不蒙混）。**全程没有"现取 origin"**。
- **origin 只在「口径可靠」时给**（进程 DPI 感知级别 = 2）。

### 5.2 C 批：词元素（带 eid、可点）

R3 命中后，那个词有**两条路**：

| 情况 | 处置 | eid | 复核方式 |
|---|---|---|---|
| 词**对上**了某个 UIA 物体（IoU≥0.6） | **不造新对象**，给那个 UIA 物体挂 `ocr` 标注（同一个地方两个对象会把 agent 带沟里） | UIA 原来的 `e<n>` | `_eid_recheck`（重走元素树） |
| 词**没对上**（UIA 瞎了：Canvas/Electron） | **造一个带 eid 的词元素**（role=`OcrWordControl`，进 `objects[]`） | `w<n>` | `_ocr_word_recheck`（**重跑 OCR** 找同一个词） |

- **命中不了就一个都不造**（没跑 / 没命中 / 退化 / 口径不可靠 / 画面不稳）⇒ 不编对象。
- 词元素**不进** `cands` ⇒ `screen_version` 仍只描述 UIA 结构
  （把 OCR 结果塞进版本号，版本会随 OCR 抖动漂移 ⇒ `since` 差分全是噪声）；
  但它**进** `objects[]`、**进**旁表（`--eid w0` 取得到）、**不进**树指纹。
- **窗口代际第二道闸**：词元素带 `window_gen`，点的时候回传它 ⇒ 窗口清单动过了就 code=12 拒（零像素）。

### 5.3 ★ 洞 ③（我自己写的代码，被判据抓出来）

`_ocr_align_words` 原本写成「`objs` 为空就返回空」⇒ **UIA 瞎了的时候（`objs` 为空）
一个词元素都造不出来** —— 恰恰是 R3 存在的理由那条路。判据 C⑤b 抓出来，已修
（「`objs` 为空时照样返回每一行，IoU=0、命中UIA=False」）。

### 5.4 副作用控制

- 词元素的 `source_confidence` 用 `SCREEN_SOURCE_CONF["ocr"]`（bbox 0.55 / text 0.55 / existence 0.40），
  **不另造一套分档**。
- 词元素的 `role` 不是 UIA 的 ControlType ⇒ **不会**混进 R2 的「可交互数」口径。
- `omitted.total` 把词元素算进去（`total ≥ returned` 这条不变式仍成立），
  `omitted.breakdown.ocr词元素` 单列计数。
