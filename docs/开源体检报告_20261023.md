### 1.2 GPL-3.0 vs AGPL-3.0：本项目的具体后果对比

本项目的形态特征决定了选型（这是事实，不是推测）：

- 本地 CLI：`src/agentctl_main.py`
- 本地常驻服务：`src/agentctl/server.py`（`server_version = "AgentCtl/0.1"`）
- **可被远程调用的 HTTP 服务**：`src/agentctl/mcp_http.py`（`AgentCtlMCP/0.1`）、`src/agentctl/mcp.py`（`PROTOCOL_VERSION = "2025-06-18"`，stdio 型 MCP）
- 插件形态：`dsh-viewer-plugin` 侧的 `tools/act.py` 是真正执行动作的那一份（`docs/交接_M19P与下一刀_20221023.md:38`）
- 证据链与时间线：`work/timeline/*.jsonl`、`src/agentctl/store.py`

**法律要点**：GPL-3.0 的触发条件是「分发（distribution）」——你把作品交给别人即触发；**单纯在服务器上运行并通过网络提供服务，不构成分发**。AGPL-3.0 第 13 条补上了这一段：**只要用户通过网络与你的修改版交互，即视为向你提供了该修改版的分发**，必须以 AGPL 公开对应源码。

| 场景 | GPL-3.0 | AGPL-3.0 | 对本项目意味着什么 |
|---|---|---|---|
| 自己用 / 公司内部用（不外传） | 自由 | 自由 | 无差异 |
| 内部发行版（企业 fork 后只在自己公司内部分发副本给员工） | 允许（不传播即不触发；即使传播也只要求给接收者提供源码） | 允许 | 无差异 |
| 分发二进制 / 源码给外部用户 | 触发：必须附 GPL-3.0 原文 + 源码 + 变更说明 | 触发：同上 | 两边都要做，第三章 P0 的第三方许可工作一样要做 |
| **闭源 SaaS**：把本项目改造成托管服务，收订阅费但不开源 | **允许**（未分发） | **不允许**（第 13 条触发） | ⭐ 这是选型的分水岭：你的形态里「本地服务 + MCP over HTTP + 可远程调用」已经站在 SaaS 门口。走 SaaS 收费路线 ⇒ GPL-3.0 会让你**收不到源码约束** |
| 被闭源产品**链接/打包**进商业产品 | 不允许（GPL 的传染性要求整体以 GPL 发布） | 不允许（更严） | 若 `dsh-viewer-plugin` 插件会被闭源桌面软件加载 ⇒ 两条路都要求对方开源 |
| 闭源硬件厂商**预装**（整机销售，随附源码） | 允许 | 允许（随附源码即可） | 无差异 |
| 商业授权 / 双许可 | 允许（版权人保留权利，可另行授权） | 允许 | 无差异（见 1.5） |
| 社区接受度与采用阻力 | 最高 | 中等偏低（部分企业法务对 AGPL 有戒心） | 若目标是「让更多人用起来」，GPL-3.0 阻力小 |
| 换协议成本 | — | — | **极低**：只动 `LICENSE` + `README.md:46` + 新增第三方声明；无源码版权头要改（见 1.3） |

### 1.4 软著（计算机软件著作权登记）：材料、周期、费用、以及它与开源许可的关系

> 以下为**中国版权保护中心实务口径**的通用说明；**当日官方价目与窗口期未核到**（我没联网核官方价目表），费用区间只给市场常见量级，落地前请以官方/代理机构书面报价为准。

**实际材料清单**

1. **软件著作权登记申请表**（在线填写：中国版权保护中心官网）：软件全称、简称、版本号、开发完成日期、首次发表日期、著作权人信息、硬件/运行环境、编程语言与代码量、**软件功能与技术特点**（这是关键，要写实质内容）。
2. **源程序鉴别材料**：**前 30 页 + 后 30 页**（不足 60 页则全部提交）；每页不少于 50 行；页眉标注软件名称、版本号、页码；页尾标注著作权人。
3. **文档鉴别材料**：《软件说明书》或《用户手册》——同样前 30 页 + 后 30 页。**直接用本仓的 `README.md` + `docs/AGENT接口.md` 改造是性价比最高的做法**（已存在、已脱敏、成本最低）。
4. **主体证明**：个人 = 身份证复印件；企业/其他 = 营业执照副本（加盖公章）。
5. 可能还需要：**代理委托书**（委托代理提交时）、**权利归属证明**（合作开发/委托开发/职务开发需附合同或协议）、**身份证明文件**（线上提交需按系统要求上传）。

**周期与费用（量级，务必现场核价）**

- 周期：官方受理后的审查时限通常按 **60 个工作日**理解；加上补正与寄送，实务常见 **2~3 个月**；加急通道另计。
- 费用：**自愿登记，无强制**。官费本身不高，市场代理报价常见在 **¥800 ~ ¥3000 / 件**区间（个人开发者、小软件），企业件、复杂件、加急件更高。⚠️ 未核到当日官方价目。

**它与开源许可的关系（本节最关键，四句话）**

1. **著作权自作品完成之日起自动产生**（《著作权法》第 2 条），登记**不是**权利产生的前提，只是**权属证据**（在诉讼中有初步证明与举证责任减轻的意义）。
2. **开源 ≠ 放弃著作权**：开源是「著作权人**授予他人**一份许可」；著作权**仍然完整属于你**。你依然可以起诉侵权，也可以另行做商业授权（双许可，见 1.5）。
3. **登记证书上的著作权人仍然是你**：登记与公开开源**不冲突、不互斥**，两者可以并存；登记证书不会因为代码公开而失效。
4. **唯一要注意的公开性**：登记时提交给版权中心的源程序是**保密材料**（不公开），但**登记信息本身在版权保护中心网站可公开查询** ⇒ 登记 = 公开宣告「这个软件存在、著作权人是谁、版本号是什么、首次发表日期是什么」。**不泄露技术细节，但会泄露「你有一个叫 agent-ctl 的软件」**。因此：① 登记名称要与公开仓名一致；② 版本号要与 `__version__` 对齐（这正是 P0 里要先做 `pyproject.toml` 的原因）；③ 若连「存在性」都不想在登记前暴露，就等公开后再办。

### 1.5 双许可（商业授权 + 开源）：可行性与代价

- **可行**：GPL-3.0 与 AGPL-3.0 都**不要求**版权人放弃自己的权利。你可以对公众发 GPL/AGPL，同时对愿意付费的客户提供**商业闭源许可**（豁免 copyleft 义务）。经典模式是「双许可（dual license）」。
- **代价（要提前想清楚）**：
  1. **削弱 copyleft 的保障**：一旦你发出可商用的闭源许可，社区会要求「凭什么他们能闭源、我不能」；商业许可的定价与透明度会成为持续议题。
  2. **需要明确的授权文本**（商业许可协议 + 单独的「商标许可」条款，商标与著作权分开授权是业界惯例）。
  3. **需要权属与贡献者条款**：双许可要求「你有权授予商业许可」，因此要有 CLA（Contributor License Agreement）或明确的著作权转让/授权条款，把外部贡献也纳入同一授权口径。**本仓目前只有 2 位作者（见 1.3），成本不高，但现在就把 CLA 立起来最省事。**
  4. **商业上要有东西可卖**：本项目的价值主张是「可审计的桌面动作闸门」。企业愿意付费的通常是 **审计合规、SLA、私有化部署、签名发行、闭源集成**，而不是「代码本身」。⇒ 双许可能不能卖钱，取决于你能不能提供**支持/合规/集成**服务。
- **如果目标只是「别让 SaaS 白嫖」**：那不必上双许可，**AGPL-3.0 本身就是这个效果**（第 13 条），成本为零。**双许可只在「我要从闭源集成里收钱」时才有必要。**

### 4.3 安全漏洞报告渠道：两套方案

> 原则：**报告内容要能到维护者手里，但不能进公开 index**；**公开仓里不要出现明文邮箱**（会被爬、被垃圾邮件轰炸、被钓鱼利用）。

**方案 A（推荐首选）：平台自带的私有漏洞报告（Private Vulnerability Reporting）**

- GitHub：仓库 `Settings → Security → Security advisories → Private vulnerability reporting` 开启后，公开仓页会出现「Report a vulnerability」按钮，报告不进公开 issue，系统自动给维护者发邮件。
- Gitee：Gitee 提供**私密 issue / 安全 issue** 能力；⚠️ **未核到**当前界面具体位置与是否支持匿名提交，发布前需在 Gitee 后台确认。
- **优点**：零维护成本；**邮箱完全不出现在仓库里**（隐私 + 防垃圾邮件）；平台可加 PGP 签名与加密附件；报告与 issue 分离，读者看不到「有人在报漏洞」。
- **配套**：`SECURITY.md` 只写「请通过平台的私有漏洞报告入口提交，不要开公开 issue」，**不放任何邮箱**。

**方案 B：专用邮箱（当平台不支持私有报告，或你想留一个备用通道）**

- 用一个**专用别名**（自有域名下的 `security@…`），只转发给 1~2 个人，**不用个人邮箱**。
- **公开仓里不写明文**。可选做法（按推荐度降级）：
  1. 只写「请通过平台私有报告入口」+ 把邮箱写在**仓库 Wiki**（Wiki 可不公开 / 可随时改，比代码仓难被批量爬）；
  2. 把邮箱写成**图片**（`docs/images/security-contact.png`）—— 挡掉简单爬虫，但不挡 OCR，成本低、够用；
  3. 把邮箱**拆成两半**并注明拼接规则 —— 效果一般，**不推荐**（仍会被人工拼出来）。
- 配套 `SECURITY.md`：报告内容模板（版本 / 复现步骤 / 影响 / PoC）、响应时限自定、什么不算漏洞、致谢政策。
- **两者都建议**：公开 issue 里提供一句「如果你觉得不适合公开讨论，请走私有渠道」，把人引到正确的地方。

### 5.2 平台取舍、Python 矩阵、依赖安装、缓存与耗时

**平台取舍**

| 维度 | GitHub Actions | Gitee Go |
|---|---|---|
| Windows runner | `runs-on: windows-latest` 官方提供，含 Python、桌面会话 | ⚠️ **未核到**（Windows 镜像可用性、配额、是否兼容 GitHub Actions 语法，均需在 Gitee 侧确认） |
| 生态（setup-python / cache / artifact） | 完整 | 有限 |
| 私有漏洞报告 | 原生（4.3 方案 A） | ⚠️ **未核到**是否有等价能力 |
| 与本仓现状的契合 | ⚠️ `tools/pack_dist.py:332` 明写「仓库在 **Gitee**，不是 GitHub；`gh` 用不上」；`install.ps1:64` 明写「长期宿主已定为 **Gitee**（2026-10-12 用户拍板）」 | ✅ 与现状一致 |

> **关键现实约束**：CI 只能跑**本仓**的 workflow ⇒ **CI 宿主 = 代码托管宿主**。若坚持 Gitee 唯一宿主，则只能用 Gitee Go；若想用 GitHub Actions，必须在 GitHub 上有镜像仓（带来「两个公开源」的同步成本）。**这正是第七章要用户拍板的第 4 项。**

**Python 版本矩阵**

- 下限来自 `install.ps1:72` `$MinPy = [Version]'3.10'`；`install.ps1:98` 优先找 `py -3.12` → `-3` → `-3.11`。
- 实测报告用的是 **Python 3.12.7 64-bit**（`docs/实测_M17A_导入归因_20221022.md:25`）。
- **建议矩阵**：`3.10` / `3.11` / `3.12`（3.13 待 numpy / pillow / pywin32 轮子可得性再定）。
- `install.ps1:98` 的查找顺序说明：3.12 是首选，3.11 兜底。

**依赖安装（含 vendor 内置包要不要 pip 装）**

- `requirements.txt` 14 条里，**5 条 `winrt-Windows.*` 已在 `vendor/` 内置**（3.2.1）；`windows-capture` 也在 vendor 内（2.0.1）但**不在 requirements.txt 里**。
- ⇒ **CI 建议：只 pip 装 9 个常规依赖（pywin32 / uiautomation / comtypes / pillow / mss / numpy / psutil / websocket-client / zstandard），winrt 与 windows-capture 直接用 `vendor/`**（照抄 `src/agentctl/clock.py:153-154` 的 `sys.path.insert` 做法）。好处：CI 不依赖 PyPI 上 winrt 轮子的可得性与架构匹配；坏处：vendor 里的 winrt 是 **cp312 时代的预编译轮子**，在 3.10/3.11 上可能不匹配 ⇒ **要么 CI 矩阵只跑 3.12，要么在 vendor 里放多版本轮子**（`vendor/` 现在的结构是按包名平铺，没有 ABI 目录，没有 `__init__.py` 之外的版本标识）。
- **可复现性**：`requirements.txt:3-7` 明确「版本一律用下限，不锁上限」的立场（理由是「要在别人家的机器上跑」）。这个立场对**终端用户**是对的；但 **CI 需要可复现** ⇒ 建议另建 `requirements-ci.txt`（钉死精确版本 + `--require-hashes`），**两套并存**：用户装 `requirements.txt`，CI 装 `requirements-ci.txt`。
- `windows-capture` 的 Rust 扩展（`vendor/windows_capture/__init__.py`）是预编译 wheel ⇒ CI 换 Python 版本时可能缺对应 wheel。

**缓存与耗时预估**

```yaml
      - run: python -X utf8 tests/_元判据_判据接线.py
  inject:                  # job2 —— 注入自证：rc=0 表示「可注入的判据全红」
    runs-on: windows-latest
    timeout-minutes: 20
    steps: [ checkout, setup-python, pip install -r requirements-ci.txt, run: python -X utf8 tests/run_all.py --inject ]
  fastlane:               # job3 —— 快车道（需 windows runner 真桌面）
    runs-on: windows-latest
    timeout-minutes: 30
    steps: [ checkout, setup-python(+cache:pip), pip install -r requirements-ci.txt, run: python -X utf8 tests/run_all.py ]
  package:                # job4 —— 打包 + 独立核验 + 校验和
    runs-on: windows-latest
    timeout-minutes: 20
    steps: [ checkout, setup-python, python -X utf8 tools/pack_dist.py --out dist/agentctl.zip,
             python -X utf8 tools/verify_dist.py dist/agentctl.zip,
             上传 artifact + SHA256 ]
```

**要点说明**

- **触发条件**：`push` 到 `main` + 所有 `pull_request` + 手动；建议加 `paths` 过滤（`src/**`、`tests/**`、`tools/**`、`requirements*.txt`、`vendor/**`、`LICENSE`、`README.md`）。
- **步骤顺序原则**：**静态层最先、且不装依赖**（这样红得快、反馈快，也不被 PyPI 波动影响）。
- **必跑命令**：静态层 7 条 + `run_all.py --inject`。快车道是否进 CI 取决于 5.1 的第 1 个前置决策。
- **超时**：job 级 `timeout-minutes`（静态 5~10 / 注入 20 / 快车道 30 / 打包 20）。**单条判据也要有超时保护**（`run_all.py` 逐条 subprocess 时应带 timeout，否则一条挂死拖垮整个 job）。
- **失败即红**：任何非零退出码 = 失败；**不设 `continue-on-error`**（唯一例外：明确登记的「已知预期失败点」，如 `smoke_clean_clone.py:16-22` 的 E1）。注入自证类命令的**期望值是「非零」**，要用 shell 判一下「rc==1 才算过」，不要直接当红。
- **矩阵**：`fail-fast: false`，`python-version: ['3.10','3.11','3.12']`；但注意 5.2 的 vendor ABI 问题 ⇒ 若 vendor 只支持某个版本，先只在那个版本跑全量，其余版本跑静态层。
- **凭据**：CI 不需要任何凭据（只要不开签名 job）。签名 job 另开，用托管签名服务或 secret，**不把 PFX 放仓库**。
- **缓存**：`setup-python` 的 `cache: 'pip'`；`vendor/` 不需缓存（已入库）。
- **制品**：`dist/agentctl.zip` + `.sha256` 传 artifact（供发版复用）。

### 6.2 Windows 代码签名（code signing）方案对比

| 方案 | 年费量级 | 门槛 | 拿证难度 | SmartScreen 表现 |
|---|---|---|---|---|
| **OV**（组织验证）代码签名证书 | 约 **$200~500 / 年**（公开市场价区间，⚠️ **当日官方价未核到**） | 需**组织实体**（公司/事务所）；**个人名义在多数 CA 拿不到**代码签名证书 | 中（需提交组织证明文件） | 签名后**仍可能**弹「未知发布者」；需靠下载量积累信誉 |
| **EV**（扩展验证） | 约 **$300~700 / 年**（⚠️ **当日官方价未核到**） | 组织实体 + 更严核验（面对面/第三方核查视 CA 而定） | 高 | 传统上**自带即时 SmartScreen 信誉**；⚠️ **微软 2020 年后调整过 EV 即时信誉政策，当前细则未核到**，不能当作确定结论 |
| **Azure Trusted Signing**（微软） | **按签名次数计费的订阅制**（公开价档位 ⚠️ **未核到**），通常显著低于传统 CA 年费 | 需 Azure 账号 + 完成**身份验证**（个人/企业）+ **公开信任**智能验证流程 | 中 | 由**微软自己的 CA** 签发，签名产物通常**立即获得 SmartScreen 信誉**；受 Azure 生态、地域与数量限制 |
| **SignPath**（开源项目免费） | **开源项目免费**（需申请审核；商业用途收费） | 必须是**公开**开源项目 + 通过审核（LICENSE 齐备、构建可复现） | 中（填申请表单，说明项目与分发方式） | 用 DigiCert OV 证书，**不给** SmartScreen 即时白名单，仍靠信誉累积 |
| **不签名（源码态发布）** | **0** | 无 | — | 本项目**当前设计就是这样**：`install.ps1:11-14` 明写「本方案落地的全是 .py 源码 + 一个 pythonw.exe（解释器自带的），**没有任何新可执行文件被写进系统目录 —— 所以整套东西不需要签名**」 |

> **这张表最重要的一行是最后一行。** 你当前的产品形态（源码 + `pip install` + 桌面快捷方式指向 `pythonw.exe`）**在设计上就不需要代码签名** ⇒ **签名不是 P0**。只有当你要发布 **EXE**（`build/AgentCtl.spec` / `AgentCtlPanel.spec` 的 PyInstaller onedir，或 Inno Setup 安装包）时，签名才变成刚需（否则 SmartScreen 拦、杀毒误报）。
>
> 决策建议（供拍板）：**先按「不签名、源码态发布」把第一版公开出去**，把签名预算留到「确实要出 EXE」那一刻。届时优先评估 **Azure Trusted Signing**（按次付费、无年费、私钥不出 HSM）或 **SignPath**（若届时仓库已公开且审核通过）。

### 6.3 `signtool` 命令模板

> Windows 官方代码签名工具（Windows SDK / Windows Kits 里的 `signtool.exe`）。

```powershell
# ── 1) 对压缩包签名（Authenticode 支持对 zip 签名）
#    /fd = 文件摘要算法；/td = 时间戳摘要算法；两者都要 SHA256
#    /tr = RFC3161 时间戳服务器（★时间戳必须加：证书到期后签名仍然有效）
#    /t  = 旧式 Authenticode 时间戳（与 /tr 可同时给）
& "$env:ProgramFiles(x86)\Windows Kits\10\bin\10.0.xxxxx.0\x64\signtool.exe" sign `
    /fd SHA256 `
    /td SHA256 `
    /tr http://timestamp.digicert.com `
    /t  http://timestamp.digicert.com `
    /f  "$env:AGENTCTL_PFX_PATH" `
    /p  "$env:AGENTCTL_PFX_PASSWORD" `
    "$env:AGENTCTL_OUT\agentctl.zip"

# ── 2) 验签（发布前自检）
& signtool.exe verify /pa /v "$env:AGENTCTL_OUT\agentctl.zip"

# ── 3) EXE（若将来做 EXE 发布）
& signtool.exe sign /fd SHA256 /td SHA256 /tr http://timestamp.digicert.com `
    /f "$env:AGENTCTL_PFX_PATH" /p "$env:AGENTCTL_PFX_PASSWORD" `
    "$env:AGENTCTL_OUT\AgentCtl.exe"
```

**安全纪律（每一条都会出事）**

- **时间戳必须加**（`/tr` + `/td SHA256`）：没有时间戳，证书到期即签名失效，所有已安装的用户会突然看到「签名无效」告警。
- **私钥不进仓、不进 CI 明文**：PFX 只走 CI secret；在 CI 里用 base64 secret 把它解到 runner 临时目录，签完立刻**删掉该临时文件**；**建议加 pre-commit 钩子挡 `*.pfx` / `*.pem` / `*.p12`**（本仓 `.gitignore:146-151` 已挡 `.env` / `secrets/` / `*_key.json` / `*_key.txt`，⚠️ **但没有 `*.pfx` / `*.pem`** ⇒ 做签名前必须补）。
- **口令不要进命令行历史**：`/p` 会出现在进程列表里。更好的做法：用 **CSP/KSP**（`/kc` / `/sha1`）让私钥留在密钥容器里，或用托管签名服务（见下）。
- **优先用托管签名服务**：Azure Trusted Signing / SignPath 的 API 签名方式 ⇒ **私钥永不离开 HSM（硬件安全模块）**，CI 里也没有私钥可泄露。这是当前行业默认做法。
- 签名 job 与构建 job **分开**，只在打标签时触发，且需要 `environment` 保护 + 人工审批。
### 6.4 该签哪些产物，以及**签名解决不了什么**

| 产物 | 现状 | 该不该签 | 理由 |
|---|---|---|---|
| 发布压缩包（`dist` 目录下那个 zip） | 由 `pack_dist.py` 产出 | **走 EXE 路线建议签；纯源码路线可不签** | Authenticode 可签压缩包，验签时显示发布者与有效期；能降低「下载被篡改」疑虑。⚠️ 但用户默认不会验签 ⇒ 收益主要在**分发渠道**（企业 IT 白名单） |
| `install.ps1` / `uninstall.ps1` | 仓内脚本 | 可签（Authenticode 支持 `.ps1`） | ⚠️ **SmartScreen 不看 `.ps1`**，签名对用户的提示价值有限；主要价值是「防篡改可感知」与部分企业策略 |
| Python wheel | **当前不存在**（无 `pyproject.toml` / `setup.py`） | **签不了** | wheel 格式**没有签名机制**，只有 `RECORD` 哈希（防篡改、不证明来源）。能签的是**上传到 PyPI 时用的 API token**（或用 Trusted Publishing 免 token） |
| `AgentCtl.exe` / `AgentCtlPanel.exe` | `build/*.spec` tracked，但 `dist/` 里**当前没有 exe** | **做 EXE 就必须签** | 否则 SmartScreen 拦 + 杀毒误报；这是唯一「签了立刻有用」的产物 |
| Inno Setup 安装包 | `build/installer.iss` **未 tracked**、产品名与版本过时 | 同上 | 若发布 ⇒ 必须签 + 先对齐版本 |

**签名解决不了什么（避免把签名当银弹）**

1. **不解决杀毒软件误报**：启发式引擎（行为特征）不看签名；签名只解决「发布者身份可信」这一维。
2. **SmartScreen 信誉需要累积**：新证书 / 新文件哈希（每次重新打包哈希都变 ⇒ **要考虑「时间戳 + 固定容器」策略，或干脆不签**）第一次被下载时仍可能弹窗。
3. **签名 ≠ 隐私声明**：签名证明「这包来自作者」，**不证明**「它不采集你的屏幕」。隐私边界只能靠 `docs/开源声明_隐私与安全边界.md` 明写。
4. **签名 ≠ 许可证声明**：用户仍可自由阅读 `LICENSE`。
5. **不解决供应链安全**：依赖被投毒、构建被篡改 —— 那要靠 lockfile（`requirements-ci.txt` + `--require-hashes`）、SBOM（Software Bill of Materials，软件物料清单）、构建可复现性，与签名是不同的问题。
