## 1. 本单四件事（按「确定性成本优先」排序）

### A. ★ 消掉「双 spawn」——**声明 verify_expect 的动作会 spawn 两次验 动作.py**（≈200ms）

- 位置：core.py `_cl_run` 一带（ZCode 实读给出的行号约 2434，**你以现码为准**）。
- 事实：M11 实测 spawn + 全 import = **95~100ms**；有 verify_expect 的动作要验两次 ⇒ **多付 ≈200ms**。
- 改法：**复用 act 已经拍的前后帧**，不要为「验」再起一个进程。
  ⛔ **不许**用「常驻一个 worker」来解（撞「不起常驻进程」红线）；**只许**少 spawn 一次。
- 判据：**现仓即红的那个判据**（大意：「有 verify_expect 的动作比没有的慢 ≥150ms」）——
  本单做完它必须**变绿**。你可以在原判据上改，**别新建**。

### B. ★ 动作后 UIA 重扫「按需化」——**eid 命中时每次 click 都要付 191ms**

- 事实（主控已核到 HEAD 版行号，你以现码为准）：
  - core.py :4030 `if r.get("ok") and args.get("_eid_hit"):` ⇒ :4040 调 `_click_after_state`
  - `_click_after_state` 内部 :3457 调 `_screen_build`（**整屏重建**）⇒ **191ms**
  - 触发条件 = **ok 且 eid 命中**（**不是**所有 click）
- 改法：整屏重建**只在真需要整屏变化清单时**做；否则改成**对被点对象的定向查询**。
- ⚠ **口径零松（铁律）**：
  1. **不许改 contract/tools.json** ⇒ `after` 字段**必须还在**；
  2. 降级时 `uid_state` 写 **unknown** + 明确写「未做动作后回读」——
     **绝对不许**把「没查」写成「没变」（OK）⇒ 那是撒谎，unknown 永不当成功；
  3. 声明了 `expect_uid` 时，三档判词**不许变弱**（该判得出还得判得出）。
- 判据（**行为级**）：断言「省了 ≥150ms」**且**「声明 expect_uid 时三档判词与改前一致」。

### C. K2 树缓存：**本单只埋点，不建缓存**

- 形状（ZCode 正解）：复用 **eid 旁表**那一套，把 `ctl_tree / ctl_find`（现走全 walk）接进去。
  **不许造第三套缓存**。
- **本单只做埋点**：给这两条路加**命中计数器**（窗口级计数即可），跑 **≥30 次**典型调用序列
  （连读、读→找→点、找→点→找），报告**命中率**。
- 判据：命中率 **< 50% ⇒ 本单就此结案**（只留埋点，不建缓存），**≥ 50% ⇒ 另开一单再谈**。
  ⇒ **本单不许直接建缓存。**
- ⚠ 收益口径纠正（主控核过）：ctl_tree 全树扫描是 **51ms**（阶段总结:36），
  **不是 191ms**（191ms 是 `_screen_build` 的）⇒ 命中一次省 51ms，别按 191 算。
- ⚠ 四条禁令（即使将来建缓存也照抄）：**永不签 capture、永不产坐标**；
  失效键 = hwnd + 代际 + 秒级 TTL + 焦点，**遮挡不进键**；
  **禁出「页面上没有它」这种否定结论**；**volatile 元素不入缓存**。

### D. 两条小的（顺手做，零风险）

   ⛔ 不许改语义、不许引依赖、不许起常驻。
2. **window_state 双跑去重**（core.py 一处 + uia_tree.py 一处，**<20ms**）。

### E. ★★ 修 `ctl_keys` 的「判词不实」缺陷（**主控实测三次复现**）

**事实**（2026-10-22 12:36~12:37，主控清桌面时撞上）：

| 发了什么 | core 返回 | 实际发生 |
|---|---|---|
| ctl_keys `Delete` | `{ok:False, code:5, warning:"坐标/前台/窗口稳定性拒绝"}` | **键照送**（文件确实被删了） |

- 连续 **三次** 复现（两个目录 + 一个文件）。
- ⚠ 契约文案明写「本次**一个键都没发**」⇒ **判词与事实不符**。
- 这是**「报告不实」级缺陷**：比慢更危险 —— 调用方看到 code=5 会以为「没动」，
  实际**已经动了**；反之看到 ok=True 也可能什么都没动。
- 主控判词：**precheck 拒绝 ⇒ 必须真的不投递**；post-check 的「画面没变」
  应当**与「没发出去」区分开**（现在两者都落 code=5，调用方分不出来）。

**本单要做的**：
1. 定位：act 的 precheck 拒绝后**仍继续投递**的那条路径（**你以现码为准，别照抄我的行号**）。
2. 修：**拒绝就不投递**（或把「已投递但画面没变」单独给一个可区分的 code/字段，**不许改现有 code 的数值语义**）。
3. 判据：**先红后绿** —— 现仓里能造出「判拒但实际投递」的用例吗？造不出就**先造**：
   - 用例1：把窗口搞到不满足稳定性条件，发 `Delete` ⇒ 断言 **目标文件没被删** 且返回拒绝；
   - 用例2：正常发 `Delete` ⇒ 断言返回语义与实际投递**一致**。
4. ⚠ **不许**为了让用例变绿去放宽稳定性判定（那是拿安全换通过）。
