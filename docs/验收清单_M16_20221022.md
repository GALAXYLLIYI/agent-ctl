## 五、★ 用户从需求侧验不了的那一项（派单 §4 要求明确列出）

1. **K2 命中率的因果判断**（5.7% vs 98.6% ⇒ 命中率由写动作密度决定）—— 只有数字能说清，需求侧只能看见「点了之后界面变了没」。
2. **p50 633ms 差额的落点**（act 的等生效/抓帧/判差）—— 逐段账单是打点测出来的。
3. **「记事本会话恢复把 N 个历史 tab 变成 N 个窗口」这条根因** —— 用户看到的是「几十个记事本」；需求侧的复现办法：**开一次记事本，看是不是凭空多出几个 `*MM` 窗口**；治本后的验收：**只出 1 个「无标题 - Notepad」**。
4. **「靶场窗口用完即关」** —— 这条用户**能**从需求侧验：跑一次判据，桌面记事本数量必须回到跑之前的值（实测 0 → 0）。★ **收口轮的实测：靶场记事本残留：跑前 0 → 跑后 0**（进程 0→0、可见窗口 0→0；11 段逐段断言全过）。
5. **「前台被隐形系统服务窗钉死 ⇒ 谁都抢不到前台」** —— 现象是判据报「环境受阻：置前失败」；本单修掉了自伤（不再杀前台窗），但**系统级那个**我方无权解除（UIPI），需要用户**在屏幕上点一下**（本次即由用户点一下恢复）。
6. **K2 埋点写进了产品代码** —— 用户看不到「埋点」；只体现为 `core._k2_probe_report()` 的数字与**零性能开销**。
