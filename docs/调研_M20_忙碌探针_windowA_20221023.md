## 〇、结论先行

1. ★ **不能替代甲案。决定性档「慢但活着（异步味）」实测 5/5 漏检**：靶标点击后 405ms 才重绘、消息循环全程泵消息，滞后窗内探针 5 个采样**全部回答「不忙（0.077~0.637ms）」**——与「真没变」**完全同判**。WM_NULL 只能测「**不泵消息（卡死/阻塞）**」，测不出「**泵着消息但画面还没更新**」；而后者正是 M19′ 要抓的场景——现代应用（Chromium/Electron/WinUI/Qt Quick + DWM 合成）的 UI 线程与渲染**本来就是解耦的**，「慢但活着」不是边缘情况，是这些应用**处理点击的常态**。派单第 4 条的担心被实测坐实。
2. **唯一能救的子集是「同步阻塞型」**（点击处理器把消息循环堵住 300~600ms）：实测 450ms 阻塞窗内 3/3 采样报「忙（49~64ms）」。**但命中取决于采样时机**——act 的判定发生在预算耗尽（M18R 实测「画面不变」p50 **482ms**），对 300~450ms 的处理器通常**已出窗**；同一靶标仅因 watch 晚启动 1.6s，就 8/8 全部漏检（§三·表4）。
3. **这个信号两个方向都没有判别力**（全部实测）：
   - **不忙 ⇏ 真没变**：慢而活（异步）档漏检；**模态框**窗口与空闲**完全同判**（主窗 0.058~0.833ms 不忙——模态循环照常泵消息，主窗被禁用这件事对 WM_NULL 不可见）；
   - **忙 ⇏ 慢应用生效**：正常干活的泵忙窗口 30% 采样判「不忙」、70% 判「忙」，且「忙」只说明它在算自己的，与「刚才那个点击有没有生效」**无逻辑关联**（后台线程大计算、动画、视频都推高「忙」）。
4. **成本确实近乎零**（这点主控猜对了）：空闲档 **n=20 均值 0.0745ms / 中位 0.0391 / 最大 0.3846**（n=200 均值 0.0339ms）≈ `_img_diff` 一次判差 13.84ms 的 **1/200 ~ 1/460**。但「忙」路径每次 **55.5ms**（n=6 均值，50ms 超时 + 开销）——**便宜的是「不忙」那一侧，而「不忙」恰好是 laden 全部漏检场景的那一侧**。
5. **实测出两个此前没人写下来的坑**（已修进探针）：
   - ★ **5 秒假死线**：目标跨过系统 `IsHungAppWindow`（≈5 秒不泵）后，`SMTO_ABORTIFHUNG` 会**立即打断**并返回 0，此时 `GetLastError()==0` 而**不是 1460** ⇒ 「0 且 1460 才算忙」的口径会把真卡死**漏判成「错误」**；必须拿 `IsHungAppWindow` 交叉归「忙」。假死相探测成本反而降到 **0.0022ms**（n=8）。
   - ★ **WaitForInputIdle 在本环境整体不可用**：`OpenProcess` 的 **SYNCHRONIZE** 权限对打包应用（Win11 新版记事本，WindowsApps）**以及同会话普通 python.exe 一律被拒（err=5）**，沙箱开/关无差别；QUERY 类权限却开得开。WaitForInputIdle 必须在进程句柄上「等」⇒ 没同步权就没法等 ⇒ **对照信号只剩 WM_NULL 一条**。UIA 文档自己也说「调用方不应依赖此方法精确判断窗口何时空闲」。
6. **建议**：**甲案照做，探针不接线。** 若将来非要复用，唯一站得住的用法是「code=8 判定前的**单侧否证**」：先花 ~0.05ms 探一下，**报「忙」⇒ 改判可重试（相当于省掉甲案的 300ms）；报「不忙」⇒ 什么都不断定，照走甲案加长观测**。但它九成时候回答「不忙」（全部漏检场景都在这一侧），省不出几个 300ms，且接线要动 core 的判决顺序（本单红线禁区）。另有一条诊断价值：`--watch` 能把「卡死/假死/泵忙/空闲」可视化，可当排障工具留档。

## 四、离线论证：「忙」这个信号的六个坑

1. **异步 UI 是常态，不是例外（最致命）**。Chromium/Electron 把点击处理、布局、绘制摊在多线程/多进程 + 合成器上；WinUI/Qt Quick 渲染在独立线程。「点击 → UI 线程照常泵消息 → 画面 300~600ms 后才更新」是这些应用处理点击的**正常路径** ⇒ M19′ 要抓的目标场景恰好系统性落在探针盲区（④a 实测 5/5 漏检）。**WM_NULL 测的是「输入队列的服务状态」，不是「画面是否已更新」——这两件事在现代应用里没有必然联系。**
2. **模态框**。模态期间主窗口被 `EnableWindow(FALSE)` 禁用，但线程转入模态循环**照常泵消息** ⇒ 主窗判「不忙」；而模态框挂着的窗口画面本来也不会变 ⇒ 「不忙」推不出「点击已生效」也推不出「确认没变」。实测与空闲完全同判（0.058~0.833ms）。拖拽循环、菜单循环同理。
3. **后台定时器/动画/视频**。窗口自己每几十毫秒自刷（时钟、进度条、动画）⇒ UI 线程持续有消息要处理；②a 实测忙:不忙 ≈ 7:3 且**逐采样抖动** ⇒ 二值「忙」输出不稳定；反之渲染线程/GPU 忙而 UI 线程闲（更常见）⇒ 判「不忙」但画面照样卡。**「忙」与「刚才那次点击是否生效」在两个方向上都没有因果。**
4. **假死的定义错位**。系统 `IsHungAppWindow` ≈ 5 秒；本方案用 50ms ⇒ 探到的「忙」混入大量「正常干活」的窗口（②a），而真卡死跨过 5 秒线后 `SMTO_ABORTIFHUNG` 打断使 `GetLastError()==0 ≠ 1460` ⇒ 「0 且 1460」口径**漏判真卡死**（实测表3）。阈值与系统口径差 100 倍，两边都要打补丁。
5. **快但没重绘 / 渲染管线延迟**。点击处理 5ms 就返回（泵消息正常），但重绘被 DWM 合成、脏区合并、掉帧排队延迟数百毫秒 ⇒ 探针「不忙」+ 画面没变 ⇒ 照样误判 code=8。与 ④a 同属一个盲区的不同深度。
6. **采样时机不可控（时序悖论）**。探针最有价值的时刻是「点击处理器阻塞中」，但它被调用的时刻是「act 预算耗尽、末帧==基线之后」（M18R 实测 p50 482ms）。对 300~450ms 的同步处理器，判定时刻通常**已出窗**（表4 第一场 8/8 漏检）；要命中就得把探针往前挪——往前挪就变成「每次点击后立刻探」，那等于把预算检查提前，跟甲案要解决的「等多久」是同一个旋钮，没有省出任何东西。

## 五、对甲案的建议

- **甲案（core 用 `framecache.wait_change` 自己再看 ~300ms）照做**，本信号不进入判决链。理由浓缩成一句：**它对「慢但活着（异步）」5/5 漏检、对「模态」完全同判、对「同步阻塞」只在凑巧的采样时机下有效——三个漏检场景覆盖了 M19′ 目标场景的大头，而它唯一便宜的路径（0.07ms 的「不忙」）恰恰不能证明任何事。**
- 若用户将来想复用：**只作「忙 ⇒ 单侧改判可重试」的否证**（不忙 ⇒ 照走甲案），并接受三条工程前提：① 用修正后的判定（err==0 需 `IsHungAppWindow` 归「忙」）；② 承认每「忙」一次花 55ms；③ 接线动 core 判决序 ⇒ 需要主控单独立项授权，本单未动。
- 探针脚本本身建议留档：`--watch` 模式能实时可视化「空闲/泵忙/阻塞/假死」四态迁移，可当 agent-ctl 排障工具（例：判断某窗口卡死是 5 秒假死还是 50ms 级阻塞）。

## 八、本单边界（诚实交代）

- 「三档校准」的②用的是 **tkinter 大计算**，没有起浏览器页面：浏览器是多进程/多线程架构，WM_NULL 打到的是浏览器 UI 进程线程——它**本来就**不太阻塞，这本身就是坑 1/坑 5 的一部分（§四.1、§四.5），用靶标窗口把「泵忙」单变量隔离出来更干净；但「真实浏览器点击后 400ms 才重绘」这条未在真浏览器上重演（属阶段二范畴，未核到）。
- **WaitForInputIdle 对照数据缺失**：本环境 SYNCHRONIZE 一律被拒（含同用户普通进程、沙箱外），WII 的「忙=258」行为**在本机没有实测数字**，其不可靠性只有 UIA 文档背书（§〇.5）——若主控环境权限不同，可用同一探针直接补测（代码已就绪，含 LIMITED 回退与显式失败报告）。
- 探测成本数字在**本机当前负载**下取得（采样时 MiniMax Code 桌宠任务在跑，与 M18R 口径相同的「非干净环境」）；成本结论是数量级判断（0.07ms vs 13.84ms），不受此影响。
