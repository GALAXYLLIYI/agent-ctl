## 〇、结论先行

**一句话：不能替代；最多只能当「单侧否证」的辅助，而它在决定性档上 100% 漏检 ⇒ 对甲案没有增量价值，建议不接线。**

| 问 | 答 | 依据 |
|---|---|---|
| 能**替代**甲案那 300ms 加长观测吗？ | **不能** | ★决定性档「慢但活着」（触发后 300ms 才重绘、但消息循环全程泵消息）：**滞后窗内 60/60 个样本全部判「不忙」，判「忙」0 个（0.0%）**；与「真没变」**完全同判**，信息量为零。 |
| 能**辅助**（只做单侧否证）吗？ | **技术上能，工程上没价值** | ① 它只对「**UI 线程被阻塞**」敏感（同步阻塞档命中 94.3%），对「**泵着消息但画面没更新**」全盲；② 它是**瞬时无滞回**的，真忙的应用单次采样也有 **1/3（66/199）** 概率答「不忙」⇒ 「不忙 ⇒ 真没变」这个推理**不成立**；③ 忙路径**不零成本**：单次 **53.77ms**（比 `_img_diff` 的 11.08ms 还贵 **4.85 倍**）。 |
| 那它到底测的是啥？ | **「UI 线程有没有在泵消息」**（不泵 ⇒ 卡死/阻塞），**不是**「画面更新了没有」。二者是**两类问题**。 | 见 §五。 |
| 甲案怎么办？ | **照原样保留**（core 判「确认没变」之前用自己的尺子再看 ≤300ms）。探针**不接线**。 | 见 §六。 |

> **不迎合「零成本」的诚实点**：探针在**空闲窗口**上确实是零成本（0.0187ms/次，≈ `_img_diff` 的 1/593）；
> 但「零成本」**只对空闲路径成立**，**忙路径单次 53.77ms**，而且它**在最需要它的那一档上给不出信息**。

## 一、探针 API 与判定阈值

### 1.1 主信号：WM_NULL 空消息探测

```
SendMessageTimeoutW(hwnd, WM_NULL=0x0000, 0, 0, SMTO_ABORTIFHUNG=0x0002, timeout_ms=50, &ret)
```

`WM_NULL` 是空消息：不改窗口内容、不触发点击、不改变焦点，且在 UIPI 允许列表内（可跨完整性级别发）。

| # | 返回 | `GetLastError()` | 判定（机读码） | 人读 | 含义 |
|---|---|---|---|---|---|
| 1 | `ret != 0` | 0 | `NOT_BUSY` | 不忙 | 50ms 内**泵到了**这条空消息 ⇒ UI 线程活着 |
| 2 | `ret == 0` | **1460**（`ERROR_TIMEOUT`） | `BUSY_TIMEOUT` | 忙（阻塞） | 50ms 内**没泵**消息 ⇒ 阻塞中，**尚未到系统假死线** |
| 3 | `ret == 0` | **0** | `BUSY_HUNG` | 忙（假死） | ★**`SMTO_ABORTIFHUNG` 打断了**（跨过 ≈5s 假死线）⇒ 必须用 `IsHungAppWindow` 交叉确认 |
| 4 | `ret == 0` | 其它（如 **1400** 无效句柄） | `ERROR` | 错误 | 句柄失效/窗口已关等 |

★ **第 3 档（`err==0`）不许并进「不忙」** —— 那正是被 `ABORTIFHUNG` 打断的**真卡死**。本实现把它单列为 `BUSY_HUNG`（仍属「忙」），并用 `IsHungAppWindow` 交叉确认。**§四 有实测复现。**

### 1.2 对照信号：WaitForInputIdle（进程级）

| 返回 | 判定 | 说明 |
|---|---|---|
| `0` | `IDLE` 空闲 | 已空闲等待输入 |
| `258`（`WAIT_TIMEOUT`） | `TIMEOUT` 忙 | 50ms 内未空闲 |
| `0xFFFFFFFF`（`WAIT_FAILED`） | `FAILED` 失败 | 记 `GetLastError`；**本环境恒为「拿不到可等句柄」**（§四·坑2） |

★ 本环境该信号**整体不可用**（`OpenProcess` 的 `SYNCHRONIZE` 一律 err=5），因此**全部实测里 WII 恒为 `FAILED`、耗时 0.0000ms**；**不许**把 `FAILED` 静默当作「空闲」。

### 1.3 辅助：`IsHungAppWindow`

系统级「假死」定义（≈5 秒不泵消息），**只作归因参考**，不是 50ms 口径。

### 1.4 探针用法（本单交付版）

```powershell
python -X utf8 M20_忙碌探针.py --list                       # 只读枚举可见顶层窗口
python -X utf8 M20_忙碌探针.py --hwnd 123456                # 单次探测（人读）
python -X utf8 M20_忙碌探针.py --hwnd 123456 --json         # 单次探测（JSON）
python -X utf8 M20_忙碌探针.py --hwnd 123456 --watch --seconds 13 --interval 100
python -X utf8 M20_忙碌探针.py --hwnd 123456 --watch --json  # 连续采样（JSON，含绝对壁钟）
python -X utf8 M20_忙碌探针.py --hwnd 123456 --bench --n 20  # 成本基准
python -X utf8 M20_忙碌探针.py --find M20T4A                 # 按标题子串定位（自造靶标用）
```

* `--watch` 输出**可视化时间线**：每字符一个样本（`.` 不忙 / `B` 忙(阻塞) / `H` 忙(假死) / `E` 错误）+ 判定分布。
* `--json` 输出机读结果，watch 样本带 `abs_ms`（绝对壁钟）⇒ 可与靶标事件日志**逐毫秒对时**。

## 四、两个已知坑的复现证据

> ⇒ **若按「`err==1460` 才算忙」的口径实现，这 17 个样本会被判成「不忙」或「错误」**，
> **真卡死被漏判**，而且漏判得**极其便宜（0.03ms）** —— 越快越危险。
> ⇒ 本探针把 `err==0` 单列为 `BUSY_HUNG`（**仍归「忙」**），并用 `IsHungAppWindow` 交叉确认（实测恒 `True`）。

**顺带发现（本单新记）**：`err==1400`（`ERROR_INVALID_WINDOW_HANDLE`）= **窗口已不存在**。
实测 t2 靶标自毁那一刻起，连续 89 个样本全部 1400（`ret=0, err=1400`）⇒ 判定档里必须留这一档，
否则会把「窗口没了」误报成「忙」。

### 坑 2 ★：`OpenProcess` 的 `SYNCHRONIZE` 一律被拒（err=5）⇒ **已复现**

| 目标 | 类型 | `OpenProcess(QUERY_INFORMATION|SYNCHRONIZE)` | `OpenProcess(QUERY_LIMITED_INFORMATION|SYNCHRONIZE)` | `OpenProcess(QUERY_LIMITED only)` | `WaitForInputIdle` |
|---|---|---|---|---|---|
| 自造靶标 `M20T1`（pid 32792） | **同会话普通进程**（python.exe） | **FAIL err=5** | **FAIL err=5** | **OK** | **不可用（FAILED）** |
| 我自己开的记事本（pid 29516） | **WindowsApps 打包应用** | **FAIL err=5** | **FAIL err=5** | **OK** | **不可用（FAILED）** |

探针诊断串（原样）：

```
OpenProcess(QUERY_INFORMATION|SYNCHRONIZE)=FAIL err=5;
OpenProcess(QUERY_LIMITED_INFORMATION|SYNCHRONIZE)=FAIL err=5;
OpenProcess(QUERY_LIMITED only)=OK ⇒ 拦路虎就是 SYNCHRONIZE
```

⇒ **拦路虎是 `SYNCHRONIZE` 本身**（去掉它就能开），不是「整个进程打不开」。
⇒ **本环境 `WaitForInputIdle` 整体不可用**：所有实测里它恒为 `FAILED`、耗时 **0.0000ms**。
⇒ **绝不许把 `FAILED` 静默当成「空闲」** —— 那会直接伪造出「不忙」的结论。

## 五、★ 决定性结论：能不能替代/辅助那 300ms 等候？

### 5.1 先把两类问题分开

| | **探针测的** | **甲案 300ms 测的** |
|---|---|---|
| 物理量 | UI 线程**有没有在泵消息** | 画面**有没有更新**（像素级判差） |
| 抓到的是 | **卡死 / 阻塞**（线程不动） | **滞后**（画面没跟上） |
| 手段 | `WM_NULL` 往返（消息级，50ms 窗） | `framecache.wait_change`（像素级，300ms 预算） |

**这两类是不同的现象，不能互相替代。**

### 5.2 逐问回答

**问：能不能替代那 300ms？**
**不能。** 决定性档 ④a（触发后 300ms 才重绘、线程全程泵消息）里，**滞后窗内 60/60 样本全判「不忙」**，
与「真没变」**完全同判** ⇒ 拿它当甲案的判据，等于**永远答「真没变」** ⇒ 它**不能**替代 300ms 的像素级观测，
只会在慢应用上**给出恰好要避免的错误答案**（code=8「确认没变」）。

**问：能不能辅助？**
**只能当「单侧否证」，且工程上没价值。** 理由五条：

1. **盲区正好是目标场景**：④a 命中率 **0.0%**（0/60）；能命中的 ④b（同步阻塞）**不是**甲案要救的那一档。
2. **「不忙 ⇒ 真没变」不成立**：探针是**瞬时、无滞回**的单次采样。真忙的应用（②档）单次采样
   **有 33.2%（66/199）** 概率答「不忙」⇒ 「空闲 ⇒ 画面没变」是**不成立的推理**。
   ★ 这条同时否掉了「**用它提前结束那 300ms**」这种最诱人的用法：一旦提前结束，②/④a 都会给出**错误**的 code=8。
3. **「忙 ⇒ 还没生效」只是启发式**：忙说明线程在阻塞，通常意味着「活还没干完」，
   但**画面可能已经先变了**（应用先更新画面、后做长任务）⇒ 单侧也不是铁律。
4. **忙路径不零成本**：单次 53.77ms（≈ `_img_diff` 的 4.85 倍）。若做成「轮询到不忙为止」的闸门，
   烧掉的等待**和它想省掉的 300ms 同一量级** ⇒ 省不下什么。
5. **看不见「等用户操作」**：③档模态框**与空闲完全同判**（主窗 50/50 + 20/20、对话框 30/30 全「不忙」）。
   而「弹了框在等用户点」恰恰是生产上最常见的「慢/没生效」形态 —— **等待期间**像素也不再变，
   ⇒ **探针与像素级观测都看不见这一段**（框**刚弹出**那一刻像素是变的，但那是「弹了个框」，
   不是「动作生效了」，那是像素路的**另一种**风险，不在「忙碌探针能不能补」这个问题范围内）。
   ⇒ 这类只能靠别的信号（如 UIA 树/模态状态/焦点），**不是这条探针能补的洞**。

### 5.3 一句话（贴给主控）

> **不能替代、也不值得辅助**：这条探针测的是「**线程有没有在泵消息**」，甲案 300ms 测的是「**画面有没有更新**」；
> 在决定性档「慢但活着」上它 **60/60 全答「不忙」**（信息量为零），在忙应用上又有 **1/3 概率误答「不忙」**，
> 且忙路径单次 **53.77ms**（比判差还贵）⇒ **不接线**，甲案照原样。

## 六、它对甲案意味着什么

1. **甲案（core 判「确认没变」之前用自己的尺子再看 ≤300ms）保持不变，本单不改任何产品代码。**
2. **不建议把探针接进 core 判决序**：它在最需要的那一档给不出信息，却要在忙路径上付 50ms/次，
   还会给判决链引入一条新的失败模式（`err=1400` 窗口已关 / `err=0` 假死档写错就漏判真卡死）。
3. **如果将来一定要用，唯一说得通的位置是「单侧否证」**：仅当 `BUSY_TIMEOUT`/`BUSY_HUNG` 时，
   把「确认没变」降级成「没测出来（code=5，让 agent 重试）」；**`NOT_BUSY` 必须原样放行**，
   **绝不许**用它提前结束 300ms 观测（否则 ④a 场景会稳定给出错误答案）。
   代价：那 50ms/次忙路径成本 + 判决序改动，**相对收益很小** ⇒ 本单建议**不做**。
4. **本单留下三样可直接复用的东西**：探针（只读、可直接跑）、四档靶标（可一键复现四档 + 两个坑）、
   对照成本脚本（可一键复算 `_img_diff` 与探针的同口径成本）。

## 九、未核到（明确不编）

1. **真机慢应用（真实业务软件）上的效果未核到**：④a 只用自造 tk 靶标复现；**没有**在用户的 Edge/QQ/记事本上做「触发后 200~500ms 才更新」的实验（红线不许碰用户窗口）。
2. **UIPI 跨完整性级别未核到**：实测全部是**同权限**进程；「低权限进程探高权限窗口会怎样」未测（推理上 `WM_NULL` 在 UIPI 允许列表内，但**未实测**）。
3. **`IsHungAppWindow` 的精确阈值未逐毫秒定位**：只观测到在「连续约 5.2s 没泵」后翻转；「≈5s」是文档口径，本单未做阈值标定。
4. **`WaitForInputIdle` 在**有** `SYNCHRONIZE` 权限时到底返回什么未核到**：本环境一律 err=5，**根本进不到那一步** ⇒ 本单只能下结论「**在本环境不可用**」，不能下「普遍不可用」的结论。
5. **主控那个 13.84ms 未逐位复现**（未拿到那两帧原图）；本单同口径自测 **11.0ms**，量级一致。
6. **甲案 300ms 在真实慢应用上的端到端效果**：不在本单范围（甲案由另一单落地）。
7. **多显示器 / DPI 缩放对 `WM_NULL` 的影响未实测**（消息级 API 与像素无关是推理，非实测）。
