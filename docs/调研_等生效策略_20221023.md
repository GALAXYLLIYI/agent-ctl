## 〇、结论先行（给用户拍板用）

1. **「等生效」的真相是：它在等「画面变了」，而且把「预算内没看到变化」直接说成「确认没变」。**
   这是本次调研最关键的一条：`_wait_effect` 返回 `False` 的字面含义是「**预算内没观察到变化**」，
   而 core 用**自己的尺子**（before 帧 vs 最后一帧，`core.py:3305`）判定后给出 **code=8「确认没变」**（`core.py:2896`）
   ⇒ ★ **犯错的不是 core，是 act 在 `act.py:1353` 丢了信息**（把「没机会比」也写成了 `False`）。
   ⇒ **缩短预算的真正代价，不是「慢一点」，而是把「没测出来」压成「确认没变」** ——
   agent 拿到 code=8 不会重试，拿到 code=5（没测出来）才会重新观测。
2. ★★★ **【实测，2026-10-23 01:45–01:52】名义预算比有效预算少一整轮，而且边界带抖动。**
   一轮真实成本 **86.2ms**（抓帧 24 ＋ diff 12.2 ＋ 间隔 50）；450ms 只够 **5.2 轮**；
   响应恰好落在边界轮时，**第 5 轮只有 70% 能检出**（14/20），**第 6 轮起 100% 归零**（n=20/格）。
   ⇒ **名义 450ms ≠ 有效 450ms** ⇒ 这个差在**每个动作类型上重复发生**（各有各的边界轮）。
3. ★★★ **【实测】边界轮失败的根因已被直接证据钉死：不是「没看见」，是「看见了但 need=2 凑不够帧」。**
   用返回值 `首变图` 判别：**第 6 轮起变化时 17/20 都「看见过变化」却 0/20 判生效**；
   第 7 轮起才是 100%「连看都没看见」。
   ⇒ ⇒ **这直接框定了修法的收益上限**：**「边界轮看见即认」最多救回 +1 轮（≈+86ms）**，
   **救不回「连看都没看见」那部分** ⇒ **缩采样间隔不是可选项，是补洞项**。
4. **不建议直接砍固定预算（450→200ms）**：① 慢应用会被判成「确认没变」而不是「没测出来」（语义倒退）；
   ② **实测**轮次 6 → 3 ⇒ 安全区从「可靠 4 轮 ＋ 1 灰带」压到「可靠 2 轮」
   ⇒ **响应 200–300ms 这一整段从 100% 检出掉进 100% 误判**；③ 它是**全局旋钮**（`AGENTCTL_SETTLE_MS`）⇒
   改一次，**全部动作类型**的时序都变 ⇒ M16/M17 的所有基线一次性作废。
5. **建议顺位**：**先语义修复 → 再修边界轮 → 再调采样间隔/轮次 → 最后才谈分档**。
   语义修复（「预算用完 ⇒ 没测出来（可重试）」）**不提速、但让「提速」变安全**
   （缩短预算的代价从「误判失败」降级为「多花一次重试」），且**不碰契约/闸门/预算值 ⇒ 可独立上线、可独立回滚**。
6. **分档预算的元数据几乎零成本，但接线不是零成本**：契约里**已经有** `expect_within_sec`（`contract/tools.json:651`）
   ⇒ **全仓没有任何代码读它** ⇒ 它是一枚**已经批准、但没接线的旋钮**；
   ⚠ **但契约 description 明写「非 0 时本版不另造等待机制」** ⇒ 接线要**改 description ＋ 升 schema_version**（踩冻结线）。
   ⇒ 且**分档权必须收在服务端**（不能让 agent 自选，否则等于给 agent 一枚「把等待调长」的旋钮）。
7. **社区的标准答案不是「等短一点」，而是「在动作前一刻复核」**（TOCTOU 论文 arXiv:2604.18860，本仓 `act.py:1097` 已引用）：
   其 PUSV 防御（动作派发前立刻复核 UI 状态）据论文报告**180 次对抗试验 100% 拦截、零误报、开销 <0.1 s**
   ⇒ 比 450 ms 小一个数量级。⇒ **「等生效」这条路的天花板，可能不在「等多久」，而在「等之前」。**
   ⚠ **这三个数字本单未独立复核**（无联网核原文）⇒ **只作方向参考，不作拍板依据**。
   ⇒ ★ 补充：本仓 M7 已有一版就绪轮询（`act.py:1095-1099`）⇒ 它是「已有思路换位置」，不是从零新造。

### 1.2 轮询是怎么走的（逐行）

```
deadline = t0 + budget_ms/1000                      # 1349：预算是**墙钟上限**，不是轮数
while True:
    rounds += 1
    if now >= deadline:  return 生效=False          # 1353：预算检查在**采样之前**
    cur = grab(hwnd)                                 # 1358：抓一帧（≈24ms 实测中位）
    if cur is None or too_small(cur): return 生效=None   # 1359-1363：**图拿不到 ⇒ 没测出来**
    last = cur
    d = _img_diff(base_img, cur)                     # 1365：转发给 framecache.diff_images
    if d["changed"] is True: streak += 1              # 1366-1369（并记 首变图）
    else:                    streak = 0             # 1370-1371
    if streak >= need(2):    return 生效=True        # 1372-1376：**连续 2 帧判变 ⇒ 生效**
    if now >= deadline:      return 生效=False      # 1377-1381：预算用完 ⇒ 没看到变化
    sleep(POLL_INTERVAL_MS/1000)                    # 1382：50ms
```

**⇒ 450ms 预算怎么分配**：450ms 内最多采样 **9 轮**（450/50）；但每轮还要花一次抓帧（≈24ms）⇒
**实际只跑得下 ~6~7 轮**（实测：不变场景 p50 **491.0ms**，n=20，见 §二）。
**⇒ 「等多久」这个旋钮同时决定了两件事**：能等多久（覆盖多慢的应用）**和** 能采样多少轮（漏检概率）。

### 1.3 「画面变了」是怎么被认出来的

1. `cur = grab(hwnd)`：抓**客户区**一帧（core 下发基线 ⇒ 口径必须是 client，`_POLL_SCOPE`）。
2. `d = _img_diff(base_img, cur)` → `framecache.diff_images`（阈值 `DIFF_STEP=2`、
   光标规则 `caret_px=8 + aspect≥2.0`、最小面积 `min_area_px=24`）。
3. `changed is True` ⇒ `streak += 1`；否则 `streak = 0`。
4. `streak >= 2` ⇒ **生效=True**。

⇒ **「变了」= 连续 2 轮都判变**。这与 Playwright 的 actionability「Stable = 包围盒**连续两个 animation frame** 不变」
是**同一个思路**（§五 ①）：用「连续两次」压掉闪烁/动画的假阳性。

### 1.4 ★「没测出来」(None) 与「确认没变」(False) 在这条路上怎么区分 —— **以及落差在哪**

| 出口 | act 返回 | 触发条件 | core 的判词 | 出处 |
|---|---|---|---|---|
| 图拿不到 | **None** | `cur is None`（抓帧失败）或 `_too_small(cur)` | **code=5 没测出来** | `core.py:2902-2906` |
| 退化画面 | (True/False 都可能) | `_is_degraded(last)` | **code=5 退化** | `core.py:2887-2892` |
| 预算用完 | **False** | 跑满 deadline 仍 `streak < 2` | **code=8「确认没变」** | `core.py:2896-2901` |
| 连续 2 帧判变 | **True** | `streak >= 2` | 成功 code=0 | `core.py:2894-2895` |

> ★★ **主控核稿补正（本节已按 `docs\复核_调研_等生效策略_主控核稿_20221023.md` §1.3 改写）**：
> 上表第 3 行的箭头 **「act 返回 False ⇒ core 判 code=8」严格说不成立** ——
> **core 的判词不读 act 的 `生效` 字段**，它用自己的尺子（`core.py:3305` → `_act_diff_of(_before, _after, …)`，
> 即 **before 帧 vs after 帧**）。真实链路是：
>
> ```
> act.py:1353  预算耗尽 ⇒ 返回 {"生效": False}   ← 这里把「没机会看到」和「看到了没变」混成同一个值
>    ↓ act 不再轮询，把最后一帧交回
> core.py:3305 core 用自己的尺子：before 帧 vs 最后一帧
>    ↓ 最后一帧与 before 无差异
> core.py:2896 changed is False ⇒ code=8「确认没变」
> core.py:2902 changed is None  ⇒ code=5「没测出来」   ← 只有这一条才可重试
> ```
>
> ⇒ ★ **犯错的不是 core，是 act 在 1353 丢了信息**（把「没机会比」也写成了 False）；
> ⇒ **但结论照样成立**：最后一帧与 before 无差异 ⇒ core 给出**比事实更强的结论**
> —— 事实是「我没测出来」，判词是「确认没变」。
> ⇒ **这也违反 `core.py:2881` 自己写的铁律**（「『没测出来』与『没变』必须分开」）。

★ **语义落差（本单核心发现）**：
- act 侧 `False` 的字面含义是「**预算内没观察到变化**」；
- core 侧把它判成「**确认没变**」，文案是「动作前后画面逐像素比对没变（阈值 2/255）」。
⇒ **当预算不够长时，一句「我等了 450ms 没看见」被翻译成了「我确认它没变」。**
⇒ 这直接决定了「缩短预算」的代价形状：
**不是「慢一点」，而是「把『没测出来』说成『确认没变』」** —— 前者会让 agent **重新观测再试**，
后者会让 agent **认输**（code=8 的处方是「换个定位招/换目标」，不是「再等一会儿」）。

★ **契约侧的实证**（`docs\AGENT接口.md`）：

| 码 | 契约给 agent 的处方 | 出处 |
|---|---|---|
| **code=8** | 「**核验；别当成功**」；「现在『点了没反应』**由你判断**（换定位招：xy → eid → name → OCR → CDP；**或换目标**），确要重试就显式传 `retry=N`」 | `AGENT接口.md:213`、`:431-432` |
| **code=5** | 「**重新观测**」 | `AGENT接口.md:705`（S5 补两种情形时写的原处方） |
| **code=12** | 「**重新观测**，绝不硬点」 | `AGENT接口.md:214`、`:699` |

⇒ ★ **两条处方完全不同**：code=5/12 叫 agent **重新观测**（还能再来一次），
code=8 叫 agent **换定位招/换目标**（**不是「再等一会儿」**）。
⇒ 所以「预算不够 ⇒ 判成 code=8」的真实代价是：**agent 不会重试这个动作，而是去怀疑自己的定位** ——
它可能改用 OCR/CDP 换一条路重做同一个意图，**在慢应用上反而更慢、更容易点错**。
⇒ **这是「改等多久」类改动必须先解决的前置问题**：不解决它，任何缩短预算都是在拿「误判失败」换「省几百毫秒」。

## 三、候选改法（三个，各写代价）

### 候选 a · 固定预算改短（450 → 200ms）

**怎么改**：**零代码** —— 设环境变量 `AGENTCTL_SETTLE_MS=200`（`act.py:1087` 已在读它）。
⇒ ★ **这是现成的旋钮，可以先零成本试一把**。

**代价（按实测/推导排序）**：
1. ★ **语义倒退（最贵）**：预算用完 ⇒ act 返回 False ⇒ core 判 **code=8「确认没变」**
   ⇒ 慢应用被说成「确认没变」，agent 不会重试（§一.4）。**这条与「省了多少 ms」无关，是独立的红线。**
2. ★ **漏检（本单实测，把「~9 → ~4」改成实测值）**：`_wait_effect` 实际跑的轮次
   —— **450ms ⇒ 返回轮次恒为 6**（5 个完整轮 ＋ 第 6 轮在顶部预算检查处被拦，n=20 无一例外）；
   **200ms ⇒ 返回轮次 = 3**（n=5）；**300ms ⇒ 返回轮次 = 4**。
   ⇒ **轮次从 6 砍到 3（腰斩）** ⇒ 采样更稀 ⇒ 变化若恰好发生在两轮之间、或只持续 1 轮，会被漏掉。
   ⇒ ★ **更关键的是它砍掉的是「最贵的那几轮」**：450ms 的第 5 轮是 **70% 概率灰带**（§二.3），
   第 6 轮起 **100% 归零** ⇒ **砍到 200ms 等于把安全区从「可靠 4 轮 ＋ 1 灰带」压到「可靠 2 轮」**
   ⇒ ★ **这正是 §二.2 曲线里「200ms 一栏从 100% 直接掉到 0%」的机制解释**。
3. ★ **它不是「把 450 砍到 200」，而是「把 6 档全压成 200」** ——
   `_settle(default_ms)` 优先读环境变量、**忽略各调用点自己的默认值** ⇒
   `AGENTCTL_SETTLE_MS=200` 会把 **打字路（500ms）、fill 路（200ms）、重试路（350ms）…** 一并改掉
   ⇒ ★ **打字路最吃亏**：它本来要等「内容真的变了」（500ms），砍到 200ms 后**打了一半字就判「没变」**的风险最高。
   ⇒ ⇒ 「有的动作快有的慢」的不一致**已经存在**（6 档写死），环境变量会把它们**压成同一档**，反而更不一致。
4. **历史基线作废**：M16/M17 的全部端到端基线（p50 1405ms 等）**一次性失效** ⇒ 下一轮对比要从零重取。
5. **收益上限**：画面不变时端到端省 ≤250ms（450→200）；**画面会变时省 ≈0**（早停，本来就不等满）
   ⇒ ⇒ **收益只在「点了没反应」这条路上存在**，而那条路恰恰是「白等」最没价值的路。

### 候选 b · 早停策略改细

| 变体 | 怎么改 | 能省 | 代价 |
|---|---|---|---|
| **b1** `need` 2→1 | `act.py:2816` 显式传 `need=1`（或改默认） | 检测延迟减半（早 ~50ms） | ★ **「刚变又变回去」会被误判成生效**（闪烁/动画/加载态）⇒ code=0 假阳性上升；这与 `need=2` 的设计初衷（压假阳性）**直接冲突** ⇒ 必须配判据 |
| **b2** 采样间隔 50→16~30ms | `act.py:1113` `POLL_INTERVAL_MS` | 同预算下轮次 ×2 ⇒ 检测最多早 ~34ms | 每轮多一次 PrintWindow（≈24ms）⇒ **抓帧次数翻倍**（CPU/IO 上升）；`act.py:1113` 的注释明说「实测 50 更省 CPU，同一预算里少采几帧 ⇒ 少几百 ms 的 PrintWindow 开销」⇒ **这与本仓已有的实测结论相反方向**，改前要重新量 |
| **b3** 事件驱动 / 动作前复核 | 见 §五 ④⑤：UIA `WaitForInputIdle`、TOCTOU 的 PUSV（动作派发前复核） | **不是省等待，而是省「等」本身** | 需要新机制（新依赖/新 API），风险最高；但**开销 <0.1s**，比 450ms 小一个数量级 |

★ **b 的真正价值不在那几十毫秒**，而在于把「等生效」从「固定预算 + 连续 2 帧」升级为「**有上限的早退**」。

### 候选 c · 分档预算（按动作类型/声明给不同预算）

**现成的元数据（全部已在契约里）**：

> ⚠ **★ 措辞更正（本节原写「不需要改契约」不准确，已按主控核稿 §二 改）**：
> `expect_within_sec` 的**元数据确实已在契约里**（省掉的是**设计成本**，不是**契约改动成本**）；
> **但契约 `tools.json:654` 的 description 明写「非 0 时本版不另造等待机制」**
> ⇒ 也就是说**契约当前明文声明这个字段「本版不实现」**
> ⇒ ★ **要把它接线成真正的分档预算，不是「不改契约」，而是「要改 description ＋ 升 schema_version」**
> （`contract/tools.json:5` 明写「改动必须升 schema_version」）⇒ **踩了契约冻结线**。
> ⇒ 正解二选一：**① 升 schema_version 并改描述；② 另起一个服务端字段。**
>
> ★ **前提澄清**：分档**早就存在** —— `_wait_effect` 的 6 个调用点各有各的预算
> （`act.py:2536`=350ms、`2548`=200ms·fill、`2555`=500ms·打字、`2804`/`2817`/`2829`=450ms）。
> ⇒ 候选 c 要做的**不是「引入分档」，而是「把写死的档换成按动作类型/声明决定的档」**
> —— 机制已经在，缺的是**谁来定档**与**定档依据**。

| 参数 | 契约出处 | 可用来分档吗 |
|---|---|---|
| `expect_within_sec` | `contract/tools.json:651-654` | ★★ **「预期多久之内见效」；全仓**没有任何代码读它**（只有契约 + 测试基线里出现）⇒ **一枚已批准但没接线的旋钮** |
| `expect_region` | `contract/tools.json:648-649` | 声明了「预期会变的那一块」⇒ **这个动作本来就该有画面变化** ⇒ 适合**短**预算（早退即命中） |

**谁决定分档？** ★ **不能让 agent 自己选** —— 那等于给 agent 一枚「把等待调长」的旋钮（把 450ms 拖到 5s，端到端直接失控）。

## 四、★ 风险判据设计（最重要的一节）

> 目标：**用数字证明「拒绝率没上升」**，而不是靠肉眼。本节给出可执行的判据设计，
> **基线数字直接取 §二.2 的检测率曲线**（可复用，不必重取）。

### 4.1 造「慢应用」靶场（不改产品代码）

| 靶场 | 造法 | 用途 |
|---|---|---|
| **慢反应靶场** | `work` 下起一个临时小窗（tkinter/Tk）：点按钮 ⇒ `after(T, 改画面)`，T ∈ {50,100,…,600}ms | 测「响应慢的应用」被误判成「确认没变」的比例 |
| **变-回靶场** | 按钮 ⇒ 改画面 50ms ⇒ 再改回去 | 专门打 `need=2` 的假阳性（若采纳 b1） |
| **抖动靶场** | 每 80ms 换一次颜色 | 打「连续 2 帧」判据的鲁棒性 |
| **真应用** | 记事本 / 资源管理器 / 浏览器 | 交叉验证，不作主靶场（不可控） |

★ 靶场**只放 `work` 下、跑完即关**（铁律 13）；**桌面零产物**。

### 4.2 统计口径：「本来能成功、现在被判失败」

- 定义：**误判率(B, T) = 1 − 检测率(B, T)**（§二.2 的曲线直接给出；T = 应用响应延迟，B = 预算）。
- 在真应用上的等价口径：**code=0 率下降** ＝ **code=8 率上升**。
- ★ **必须同时盯 code=5（没测出来）率**：
  **code=5 率下降 ⇒ 说明有「没测出来」被压成了「确认没变」⇒ 语义倒退 ⇒ 红线**。

### 4.3 数字判据（建议直接写进验收清单）

| # | 判据 | 阈值（建议） | 理由 |
|---|---|---|---|
| J1 | 慢应用检出率不下降：对 T ∈ {50,100,…,400ms} 的靶场动作，改前改后**配对**比 | code=0 率下降 **≤ 1 个百分点** | 「本来能成功」不许变「本来会失败」 |
| J2 | 「不会变」的动作不被误报成功 | code=0 率上升 **≤ 1 个百分点** | 防 b1 把闪烁当成功 |
| J3 | ★ **code=5（没测出来）率不下降** | 下降 **= 0**（不许有任何下降） | 语义倒退红线（§一.4） |
| J4 | code=8 率不上升（在同一批「本来不会变」的动作上） | 上升 **≤ 1 个百分点** | 直接对应派单说的「拒绝率」 |
| J5 | 端到端收益必须超过噪声门槛 | **> 145ms**（本机轮间漂移 ≈10%） | 小于门槛一律写「不可判」（M16/M17 纪律） |
| J6 | (ok, code) **完整分布**逐格比对 | 任何一格的出现/消失都要**逐条解释** | 防「用 code=5 换 code=8」这种对调 |
| J7 | 三值语义不倒：False 只能来自「确认没变」，None 只能来自「没测出来」 | 判据直接断言 | §一.4 的落差是根因 |

### 4.4 基线怎么取

1. **先取后改**：本调研的 §二.2 曲线就是**改前基线**（n=20/档，存档 `M18R_等生效曲线.json`）。
2. **交错测量**：改前/改后**交替**跑（每组 n≥20）⇒ 机器漂移在配对间抵消（本机漂移 ≈145ms ⇒ 不交错就不可判）。
3. **同一批靶场动作**：同一窗口、同一坐标序列、同一响应延迟档 ⇒ 只变预算这一个变量。
4. **判据先红后绿**：注入一个「阈值放宽」或「need 改成 1」的缺陷 ⇒ 判据必须 **exit=1**
   （沿用 M18-b/c/d 三单的既有做法）。

## 五、社区怎么解决「等界面变化」（文献与做法）

### ① Playwright 的 actionability —— **「连续两次」不是我们的发明，是行业标准**
- 来源：<https://playwright.dev/python/docs/actionability>、<https://playwright.io/playwright/nodejs/actions>
- 做法：动作前自动跑一串 **actionability 检查**（Visible / **Stable** / Receives Events / Enabled / Editable），
  **全部通过才动手**；断言也会自动重试直到成立或超时。
- ★ 关键两条可直接引用：
  - **Stable ＝ 包围盒连续两个 animation frame 不变** ⇒ 与我们的 `need=2`（连续 2 帧判变）**同思路**。
  - **超时 ⇒ 抛 TimeoutError（一次明确的失败）**，而不是「假定元素没出现/没变」
    ⇒ **Playwright 把「等不到」与「没发生」分开**；**我们把「预算内没看到变化」说成了「确认没变」** —— 这正是 §一.4 的落差。
- 另：`force: true` 可跳过检查，但官方明确「不推荐」⇒ **放宽检查不是解法**。

### ② Selenium 的 WebDriverWait / FluentWait —— **「超时」与「轮询频率」是两个旋钮**
- 来源：<https://helpmetest.com/blog/explicit-wait-in-selenium>、<https://www.guru99.com/implicit-explicit-waits-selenium.html>、<https://makeseleniumeasy.com/webdriverwait-expected-conditions-selenium>
- 做法：`WebDriverWait(driver, timeout, poll_frequency)`；**默认 poll = 500ms**；`FluentWait` 可自定义轮询间隔与忽略的异常。
- ★ 两条可直接引用：
  - 「**慢元素要加 timeout，不要改 poll 频率**」⇒ 对我们：**提速优先调轮询频率/轮数，而不是砍总预算**（与候选 b2 同向）。
  - `Thread.sleep` 是明确的反模式（「总是等满，不管元素是否早就出现」）⇒ **我们已经在 M7 把固定 sleep 换成轮询**（方向正确）。
- ★ WebDriver 源码自己的警告（被多处引用）：「**加大隐式等待会拖慢测试运行**，尤其在 XPath 这类慢定位上」⇒
  **不要用「全局加长等待」当解决方案** ⇒ 对应我们：不要把 `AGENTCTL_SETTLE_MS` 整体调大。

### ③ Puppeteer 的 `waitForFunction` —— **「短轮询 + 早退 + 超时」的标准范式**
- 来源：<https://pptr.cn/api/puppeteer.framewaitforfunctionoptions/>
- 做法：`polling` 可选 **`'raf'`（默认，在每个 requestAnimationFrame 回调里跑谓词）/ `'mutation'`（每次 DOM 变更）/ 毫秒数**；
  **`timeout` 默认 30000ms、传 0 可禁用、可 `Page.setDefaultTimeout()` 全局改**；`signal` 可取消。
- ★ 对我们的映射：我们现在的「轮询」是**固定 50ms 固定间隔**；Puppeteer 的等价物是
  「**更密的轮询（raf/mutation）+ 谓词一成立就早退 + 一个上限**」⇒ **正是候选 b2/b3 的形状**。
  ⚠ 代价也一样：轮询越密，采样成本越高（我们每轮 ≈24ms PrintWindow）⇒ 有一个甜点，不是越密越好。

### ④ Windows UIA 的 `WaitForInputIdle` —— **Windows 自家的「等窗口准备好」**
- 来源：<https://learn.microsoft.com/zh-tw/dotnet/api/system.windows.automation.windowpattern.waitforinputidle>、
  <https://learn.microsoft.com/zh-tw/dotnet/api/system.diagnostics.process.waitforinputidle>
- 做法：`WaitForInputIdle(int milliseconds)` = 「**阻塞指定时间或直到相关进程进入 idle 状态，以先完成者为准**」，
  返回 `true`=已 idle / `false`=暂停发生（等价于「等超时了」）。
- ★ 两条警示（对我们直接有用）：
  - UIA 官方备注：「**调用方不应依赖此方法精确判断窗口何时空闲**」（实现依赖应用框架，窗口可交互后仍可能返回一段时间）
    ⇒ **idle 判定本身不可靠，不能单独当「生效」判据**。
  - `Process.WaitForInputIdle` 备注：「**可能使应用程序停止响应**」（若程序总是立即退出消息循环）。
- ⇒ **可借鉴的是它的「二值结果 + 上限」形状**（我们已有），**不是**它本身。

### ⑤ ★ TOCTOU 论文（arXiv:2604.18860）—— **本仓 `act.py:1097` 已经引用它**
- 来源：<https://arxiv.gg/abs/2604.18860>（*Temporal UI State Inconsistency in Desktop GUI Agents*）
- 事实：截图-点击式的 GUI agent 存在**观测→动作间隙**（真实 OSWorld 工作负载上**平均 6.51 秒**）⇒ 构成 TOCTOU 窗口；
  论文的防御 **PUSV（Pre-execution UI State Verification）**＝**在每次动作派发前立刻复核 UI 状态**
  （点击处掩膜 SSIM ＋ 全屏截图 diff ＋ 窗口快照 diff，三层）⇒
  **180 次对抗试验 100% 拦截、零误报、开销 < 0.1 s**。
- ⚠ **★ 证据强度声明（必读）**：上面这三个数字（180 次 / 100% 拦截 / <0.1s）**本单未独立复核**
  （本轮无联网核原文）⇒ **按「引用他人报告」对待，不作为拍板的量化依据**，只作**方向参考**。
  ⇒ 主控核稿 §三 同结论：「**不作为拍板依据**」。
- ★ **对我们的直接含义（两条）**：
  1. 本仓 `act.py:1097-1099` 用它论证「**不许把等待砍成 0**」——**这条依然成立**
     （观测到动作之间的间隙是真实的安全问题）。
  2. 但论文给出的**第三条路**是：**不是把「等」砍短，而是把「等」换成「动作前一刻复核」**，开销 **<0.1s**。
     ⇒ **「等生效」这条路的优化空间，可能主要不在「等多久」，而在「等之前就少等」。**

### ★ 我的明确推荐（供用户拍板）

**推荐（按顺位）：① 语义修复 → ② 修边界轮（a′）→ ③ 调轮次/间隔（b2）→ ④ 分档（c，服务端定档）。
★★「砍总预算」降为基本可排除。**

**理由链**：
1. **先修语义**（把「预算用完 ⇒ 确认没变」改成「预算用完 ⇒ 没测出来/可重试」）——
   **这一步不提速，但让后面任何提速都不再拿「误判失败」换钱**。
   而且它是**纯语义修复**，不碰预算值 ⇒ **可独立上线、可独立回滚**。
2. **再修边界轮**（a′）—— §二.3 的直接证据：**边界轮失败 =「看见了但 need=2 凑不够帧」**（第 6 轮 17/20 看见过却 0/20 生效）
   ⇒ **改判定**就能把这一格救回来，**不动任何时间、不砍任何预算** ⇒ 收益 ≈ **+1 轮（+86ms 覆盖范围）**。
   ⇒ 风险已知且可测：**削弱 `need=2` 的抗假阳性保护** ⇒ 必须配「闪烁（变一帧又变回去）仍不判成功」的判据。
3. **提速走轮次/间隔**（b2），**不砍总预算** —— 与 Selenium 的经验（「慢元素要加 timeout，不要改 poll 频率」）
   **方向相反但目标相同**：我们要的是**同样预算下更高的命中率**，不是**更短的等待**。
   ⇒ ★ §二.3 结论 3 还给了它一个**独立职责**：它是唯一能补「**连看都没看见**」那部分的手段
   （A′/C 都救不了那部分）⇒ **B 不是可选项，是补洞项**。
4. **★ 拍板前还缺一张表（主控核稿 §5.2.2 的要求，本单认同）**：
   §二.2 的曲线量的是**修复前**的行为（脚本直接调盘上的 `act._wait_effect`，`act.py:1353` 现在返回 `False`）。
   ⇒ ★ **M19 语义修复落地后，必须用同一个脚本、同一套参数再跑一次**（`M18R_测等生效曲线.py --n 20`），
   得到**修复后对照表** ⇒ 那一栏应从「**误判为确认没变率**」变成「**没测出来率（可重试）**」
   ⇒ ★ **只交修复前这一张表，不足以拍板**（它只说明「现在有多糟」，不说明「修了之后能砍多少」）。
5. **如果用户要的是用户感知的响应速度**，那 §五⑤ 的方向（**动作派发前复核**，开销 <0.1s）比「等生效」这条路更有潜力 ——
   但它是**新机制**，不是改预算，建议单独立项。
   ⇒ ★ 补充：本仓 M7 已有一版就绪轮询（`act.py:1095-1099`）⇒ 它是「已有思路换位置」，不是从零新造。
